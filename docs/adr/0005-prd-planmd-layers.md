# ADR 0005 · PRD 与 plan.md 分层关系

- **状态**:已接受(ACCEPTED)
- **日期**:2026-09-16
- **决策者**:4 人团队
- **关联模块**:文档体系重构,跨所有模块
- **关联文档**:`docs/prd/PRD.md`(新建)、`plan.md`(已存在,职责收窄)、`docs/api/`、`docs/agents/designs/Mx-xxx.md`

---

## 背景

仓库目前已积累大量工程视角文档,但缺顶层产品视角文档:

| 已有文档 | 视角 | 覆盖度 |
|---|---|---|
| `plan.md` | 工程拆分 + 验收标准 | 14 模块全覆盖 |
| `docs/api/`(9 份) | 接口契约 | 全模块 |
| `docs/agents/designs/Mx-xxx.md`(7 份) | 关键模块设计评审 | M4/M5/M6/M7/M8/M9/M10 |
| `docs/adr/0001-0004` | 架构决策 | 4 个决策点 |
| `docs/db/` | ER 图 / 数据字典 / EXPLAIN / 种子说明 | M1 |
| **缺**:**PRD** | **产品视角**(愿景/用户/旅程/价值/NFR/风险) | — |

课程设计评分场景下需要一份"产品文档"给老师/团队对齐用,但**直接复用 plan.md 不合适**——plan.md 是工程师视角,讲"怎么拆模块 / 接口长什么样 / 验收怎么过";老师评审或新成员入职时想看的是"为什么做 / 给谁用 / 价值在哪 / 做成什么样"。

可选两条路:

**方案 A:让 plan.md 一肩挑两职**——在 plan.md 顶部加"产品视角"章节,既有工程拆分又有产品叙事。代价是 plan.md 变得极长(已经 600+ 行),产品视角和工程视角混在一起,读者路径不清。

**方案 B:PRD 在上,plan.md 在下,分层清晰**——新建 `docs/prd/PRD.md` 只讲产品语言,plan.md 保留工程语言;两者通过引用互链。

---

## 决策

**采用方案 B**:PRD 与 plan.md 分层。

```
docs/prd/PRD.md            ← 产品视角(本文档上篇 / 中篇)
   │
   │  正文每处功能/模块节点散跳链 ↓
   │
plan.md                    ← 工程视角(具体职责 / 验收 / 范围调整)
docs/api/0X-xxx.md         ← 接口契约
docs/agents/designs/Mx.md  ← 关键模块设计评审
docs/adr/0001-0004         ← 架构决策
docs/db/                   ← 数据视角
```

### 责任划分

| 文档 | 职责 | 不写 |
|---|---|---|
| PRD | 愿景、用户画像、旅程、价值、NFR、风险、成功度量、范围**两段式** | 怎么拆模块、接口签名、状态机代码实现 |
| plan.md | 模块拆分、具体职责、验收标准、依赖拓扑、阶段范围调整 | 用户画像、旅程、NFR、风险 |
| docs/api/ | 接口契约、错误码、字段说明 | 业务背景、用户故事 |
| designs/Mx | 关键模块的数据流 + 状态机 + 验收清单(已落地代码) | 产品视角 |

---

## 后果

### 收益

- (+) **读者路径分流**——老师评审读 PRD,新成员入职读 PRD,开发实施读 plan.md + docs/api,4 人团队不必"读两份重叠文档"
- (+) **PRD 长度可控**(5-15 页 / 3000-8000 字),产品视角不被工程细节淹没
- (+) **产品视角独立演化**——产品侧调整(如新增"老人视频问诊"概念)不会冲击 plan.md 的工程稳定性
- (+) **明确的反向约束**——"PRD 改了,plan.md 和设计评审要跟上",形成"产品 → 工程"的文档影响路径

### 代价

- (-) **双向引用需要维护**——PRD 中每个模块节点都有 `plan.md §Mx` + `docs/api/0X` + `designs/Mx` 的引用链;模块拆分变化时这些链接会失效
- (-) **团队需要理解边界**——4 人需要记住"PRD 是产品语言 / plan.md 是工程语言",避免在 PRD 里堆实现细节或在 plan.md 里写用户画像
- (-) **首次创作时需要克制**——写 PRD 时容易把 plan.md 内容"复制翻译"一遍,实际应该让 PRD 链接到 plan.md

### 缓解措施

- PRD 正文采用**散跳链**(而非只在附录索引),读者读 PRD 时随手能跳到 plan.md 细节;反向亦然
- 每个 PRD 版本修订时,在 PR 描述里**显式检查**:所引用的 plan.md / docs/api / designs 章节是否同步需要更新
- ADR-0006 定义版本锁节奏,避免频繁改 PRD 造成引用漂移
