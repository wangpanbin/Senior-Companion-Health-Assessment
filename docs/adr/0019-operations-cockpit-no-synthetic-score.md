# ADR-0019 · V3.5 平台运营驾驶舱：不给合成分，异常必须复用而不是另建

> **状态**：已接受 · 2026-10-21
> **相关**：[V3.5-operations-cockpit-spec.md](../spec/V3.5-operations-cockpit-spec.md) · [V3.5-tickets.md](../spec/V3.5-tickets.md) · [ADR-0010](0010-order-state-transition-single-entry.md) · [V3.x-roadmap-spec.md](../spec/V3.x-roadmap-spec.md) §4.5
> **影响范围**：`controller/admin/OperationsController` · `service/OperationsService(+Impl)` · `mapper/OperationsMapper` · `GET /api/admin/operations/{overview,exceptions,trend,health}` · `frontend/src/views/admin/operations.vue`

---

## 一、背景

V3.5 要给管理员一个「运营驾驶舱」：概览、异常中心、趋势、平台健康度四个端点。

这四个端点的共同风险不是做不出来，而是**做出一堆看起来专业、但没人能解释的数**。
一个管理后台最容易长成的样子是：上面一个大大的「平台健康指数 96 分」，
底下六个看不懂的小卡片 —— 每个卡片单看都没错，凑在一起没人敢下结论。

总纲决策 5.2 提前把这条红线写死了：

> 平台健康度**由客观指标构成**；**禁止**「AI 平台健康指数 96」这类无法解释的数，
> 除非存在明确计算公式。

同时 V3.1 已经建好了履约风险中心（`/api/admin/fulfillment/summary`），
而 V3.5 的异常中心要展示「需人工介入」「超匹配预警」——
**同一件事如果被算两遍，就必然漂移。** V3.2 在用药三桶上已经吃过这个亏（ADR-0014）。

---

## 二、决策 1：健康度是**六个并列的客观指标**，不是合成分

### 决策

`GET /api/admin/operations/health` 返回六个**并列**指标：

| 指标 | 口径 |
|---|---|
| 履约率 | `(COMPLETED + REVIEWED) / (COMPLETED + REVIEWED + CANCELLED)` |
| 接单速度（分钟） | 平均接单时间，整数 |
| 完成率（按时） | 按时完成单数 / 已完成单数 |
| 投诉率 | 投诉订单数 / 区间订单数 |
| 平均评分 | 两位小数字符串 |
| 活跃陪诊员数 | 区间内有接单的陪诊员 |

**不给合成分**：不返回「健康指数」「综合评分」这类需要权重的数。

### 理由

合成分要成立，必须同时回答两件事：**权重从哪来**、**这个分怎么解释**。

而运营看到「健康指数 72」时，第一个问题永远是「72 是好还是坏、比上周高了还是低了」——
答不上来的数，**要么没人看，要么被随便解读成「平台出问题了」**。

六个并列指标各有各的口径、都在指标字典里登记过、各自都能对上业务事实 ——
运营要做的判断（「履约率掉了，但完成率没掉」）反而更准。

> 六个指标**不给权重、不排序、不打星**。要合成一个数的那天，
> 先去指标字典里把合成公式登记成一条指标 —— 那样它至少可被校验。

## 三、决策 2：异常中心**聚合** V3.1 风险中心，不另建一套判定

### 决策

异常中心的前两项（需人工介入订单 / 超匹配预警时间订单）
**直接取** `AdminService#fulfillmentSummary()` 的判定结果，
**不另写一套风险判定**。

该同源关系由 `OperationsExceptionParityTest` 锁死：两边必须逐项相等。

### 理由

V3.1 的风险判定已经是一套完整的状态机 + 事件流 + 阈值配置
（`nianglin.fulfillment.*`）。驾驶舱再写一遍「什么叫需人工介入」，
就会出现两个答案：

- 阈值配置改了，只改了一处 → 两边不一致；
- 判定逻辑本来就复杂（风险只对 `PENDING` 有意义、一轮扫描只写一条事件），
  重写一遍必然漏掉某条边界。

**两套判定必然漂移** —— 这正是 V3.2 用药三桶踩过的坑。
所以这里用**测试**而不是注释来保证一致：写一个 parity 测试，
让「两边不等」变成一条会变红的断言。

## 四、决策 3：「履约率」与「完成率（按时）」是两个不同的指标

### 决策

| 指标 | 公式 | 含义 |
|---|---|---|
| `operations.fulfillment_rate` | `(COMPLETED + REVIEWED) / (COMPLETED + REVIEWED + CANCELLED)` | 区间内订单**最终履约**的比例 |
| `operations.completion_rate` | 按时完成单数 / 已完成单数，其中「按时」= `finish_time ≤ visit_time + 履约时长窗口`（默认 240 分钟，配置化） | 已完成订单里**没超时**的比例 |

两者在指标字典里**各占一条**、公式不同、界面上分别标注「履约率」与「完成率（按时）」。

### 理由

迭代计划 §42 / §45 同时列了「履约率」与「完成率」。
如果两者都按「完成 ÷（完成 + 取消）」算，那就是**同一个数字挂了两个名字** ——
决策 6.2 禁止「同一指标不同口径」，反过来也禁止「两个名字一个数」。

「按时完成」的判据依赖 `visit_time + 窗口`，而履约率只看终态 ——
**它们回答的是两个问题**：订单最后有没有办成（履约），办的时候有没有超时（按时）。

> 该差异由 `MetricDictionaryTest` 的「两指标公式必须不同」断言锁死。

## 五、决策 4：异常卡片的 `linkUrl` 必须是**真实存在的前端路由**

### 决策

每类异常带一个 `linkUrl`，**直接指向真实存在的前端路由**
（`/admin/fulfillment`、`/admin/complaint`、`/admin/order` …），
前端**直接用后端下发的值跳转，不自己拼**。

E2E 逐个点开验证落地页可达。

### 理由

「看到了但处理不了」是这一版最典型的**假绿**：
后台列出 6 条需人工介入的订单，运营点进去是 404 —— 功能在，但没闭环。

前端自己拼路由的问题更隐蔽：后端改路径时前端不会报错，
链接静默失效，而且只在**运营真的需要处理的时候**才暴露。

所以 `linkUrl` 是**后端下发的数据**，不是前端的约定 ——
一处定义、两处使用（渲染 + 跳转），漂移无从发生。

## 六、决策 5：四类异常**恒定全部返回**，数量为 0 也返回

### 决策

异常中心**固定返回四类**异常（需人工介入 / 超匹配预警 / 投诉率异常陪诊员 / 用药漏服异常），
某一类数量为 0 时**仍然返回该条**（`count = 0`），不省略。

### 理由

省略零值的条目，卡片就会**随数据消失** ——
运营会以为「这项今天没问题」，而真相是「这项没有数据」。

**「0」和「没有」是两件事**：前者是事实，后者是缺失。
把两者渲染成同一个界面状态，运营就会把缺失读成安全。

## 七、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 给健康度合成一个「平台健康指数」 | 权重无来源、结果无法解释；决策 5.2 明令禁止 |
| 用 AI 给平台打分 | 不可解释、不可复现，且与合规红线「不做诊断」的边界只隔一层纸 |
| 异常中心自己写一套风险判定 | 两套判定必然漂移（ADR-0014 的教训）；改为直接复用 + parity 测试 |
| 履约率与完成率用同一个公式 | 同一个数字挂两个名字，决策 6.2 的另一种形态 |
| 前端自己拼 `linkUrl` | 后端改路径时静默失效；且「链接指向 404」是典型假绿 |
| 数量为 0 的异常不返回 | 卡片随数据消失，运营把「没有」读成「没问题」 |
| 趋势在前端切分后端返回的区间 | 违反 G8；且前端的「今天」边界与后端不一致 |

## 八、后果

### 正面

- 驾驶舱上的每个数字都能在指标字典里查到公式，且可被机器校验
- 异常中心与履约风险中心**永远一致**（parity 测试保证）
- 「链接可达」成为一条可自动验证的性质，而不是一次人工抽查
- 零值条目恒定返回，运营不会把「没数据」读成「没问题」

### 负面 / 代价

- 驾驶舱**不是一个可以一眼看完的「总分」** ——
  运营需要自己看六个指标，这比一个 96 分费脑力
- 异常中心必须依赖 V3.1 的风险服务，**耦合**换来了口径一致
- `linkUrl` 由后端下发，前端新增管理页时**必须同步在后端登记**，
  否则卡片会指向一个不存在的路由（E2E 逐个点开正是为了守住这条）

### 待观察

- 驾驶舱的六个指标**没有合成**，运营会不会自己脑补一个综合分？
  如果这种诉求出现，应当**先在指标字典里登记合成公式**，
  而不是在前端或后端随手乘一个权重
- 异常中心目前只覆盖四类异常。**新类别的异常该不该进这里**，
  判据是「它有没有一个可复用的判定来源」——
  没有判定来源就另建一套判定，等于主动制造漂移
