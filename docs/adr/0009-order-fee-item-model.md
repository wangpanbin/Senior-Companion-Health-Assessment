## 背景

`plan.md` §M4 具体职责第 6 条写的是：

> 线下记账：订单完成时生成费用明细（**代垫/服务费**），不做在线支付。

一期范围控制（`plan.md` §一 硬性约束 3）砍掉了在线支付，改为「**线上记账 + 线下结算**」。

但代码现状是：`companion_order` 只有两个标量字段——

| 字段 | 位置 | 语义 |
|---|---|---|
| `fee` | `CompanionOrder.java:105` | 预估费用，下单时由 `OrderServiceImpl#resolveFee` 计算或用户传入 |
| `actual_fee` | `CompanionOrder.java:111` | 实际费用，陪诊员完成订单时经 `OrderCompleteDTO.fee` 申报 |

**没有任何明细表 / 明细实体 / 明细接口。** 全库 `grep -rn "FeeDetail\|fee_item\|feeItem"` 无命中。

### 问题：两类费用的结算对象不同，混在一个标量里无法对账

「代垫」与「服务费」不是同一笔钱：

| 类型 | 性质 | 结算对象 | 举例 |
|---|---|---|---|
| **代垫** | 陪诊员先垫付的**第三方支出** | 家属 → 还给陪诊员 | 挂号费、检查费、药费、住院押金 |
| **服务费** | 陪诊员提供服务的**劳动报酬** | 陪诊员 ← 平台结算或家属直付 | 陪诊服务费、误工补贴 |

线下结算的最小前提是能区分这两类：家属要知道自己欠陪诊员多少**垫款**、平台要结算多少**服务费**。当前只有 `fee` / `actual_fee` 两个总额，`companion/income.vue`（陪诊员记账收入页）只能给出一个无法拆分的数字，对账口径缺失。

---

## 决策

**建立 `order_fee_item` 明细表，`fee` / `actual_fee` 降级为明细求和的冗余汇总，不再作为唯一真源。**

### 表结构要点

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK AUTO | |
| `order_id` | BIGINT | 关联 `companion_order.id` |
| `item_type` | VARCHAR(16) | `ADVANCE`（代垫）/ `SERVICE`（服务费） |
| `item_name` | VARCHAR(64) | 项目名，如「心内科挂号费」「陪诊服务费」 |
| `amount` | DECIMAL(10,2) | 金额 |
| `occurred_at` | DATETIME | 费用发生时间 |
| 审计字段 | | `create_time` / `update_time` / `deleted` |

### 口径约定

- **正向口径**：真源是明细。`fee` / `actual_fee` 由明细 `SUM(amount)` 得出，读取时若与明细不一致以明细为准。
- **写入路径**：订单完成（`OrderServiceImpl#complete`）时随状态变更一并写入明细，与订单状态变更**同事务**。
- **兜底**：允许明细为空且仅 `actual_fee` 有值（历史订单兼容），此时明细页显式提示「该订单无明细记录」，**不静默伪造明细**。
- **合规**：费用明细不含医疗诊断信息，只记录支出项目与金额，遵守 `plan.md` §一「不做诊断、不开药方」。

---

## 选项

### A. 维持两个标量字段（现状）

- **优点**：零改动，最简单。
- **缺点**：`plan.md` §M4-6 明文要求「费用明细」，当前实现不满足验收项；代垫与服务费无法分账，线下结算没有对账口径。

### B. 单标量字段 + 一段自由文本备注

- **优点**：改动量比 C 小。
- **缺点**：自由文本不可统计、不可校验、无法用于 `plan.md` §M10 的统计导出与漏斗对账；下一个人还得再解析一遍文本。**这是把结构化问题降级成字符串问题。**

### C. 建 `order_fee_item` 明细表，标量降级为汇总缓存 ← **本次选**

- **优点**：满足 `plan.md` §M4-6；代垫 / 服务费可分账、可统计、可导出；明细是 M10 统计与 M9 纠纷仲裁的事实来源。
- **缺点**：新增一张表 + entity + mapper + 明细接口 + 两个前端展示位；`fee` / `actual_fee` 变成派生字段，存在与明细短暂不一致的风险（已用"以明细为准"的口径约束）。

---

## 后果

### 正面

- `plan.md` §M4-6 验收项从「未满足」变为「满足」，T4.1 的费用明细页面有了数据基础。
- 线下结算有了最小对账单元：家属看代垫、平台看服务费。
- M10 统计导出可以直接按 `item_type` 分组出报表，不必解析文本。

### 负面

- **Flyway 不可回退**：`V1`~`V3` 已执行，`validate-on-migrate: true` 会校验 checksum。新表只能走 `V4__*.sql` 增量，不能改既有脚本。
- 派生字段需要一致性保障：明细写入与标量更新必须在同一事务内，且要有单测覆盖「明细求和 == actual_fee」。
- 历史种子数据（`V2`/`V3`）的订单没有明细，需接受兜底提示文案，或补一版 `V5` 脚本为历史订单生成合理明细（**须显式决策，不静默补**）。
