# ADR-0018 · V3.3 陪诊员工作台：口径必须自带区间，字段名必须自带口径

> **状态**：已接受 · 2026-10-21
> **相关**：[V3.3-companion-workbench-spec.md](../spec/V3.3-companion-workbench-spec.md) · [V3.3-tickets.md](../spec/V3.3-tickets.md) · [ADR-0009](0009-order-fee-item-model.md) · [ADR-0014](0014-medication-bucket-single-source.md) · [V3.x-roadmap-spec.md](../spec/V3.x-roadmap-spec.md) §4.3
> **影响范围**：`service/CompanionStatisticsService` · `mapper/CompanionStatisticsMapper` · `dto/DateRangeQuery`（与 M10 共用） · `GET /api/statistics/companion/me{,/trend,/profile,/income}` · `frontend/src/views/companion/**`

---

## 一、背景

V3.3 要给陪诊员一个「工作台」：概览、趋势、画像、收入四个端点。

开工复核（`V3.3-tickets.md` §〇）发现三件事，每一件都指向同一个结论 ——
**这一版真正要解决的不是「加四个页面」，而是「把散在三个地方的统计口径收到一处」**：

1. 旧 `companion/income.vue` 仍在用 `reduce()` 拉全量订单**在前端自算**「累计 / 已结算 / 未结算」——
   违反总纲 G8，且口径与后端无处可比；
2. 既有费用模型里**根本没有「平台服务费」**（只有 `fee` 合同服务费 / `actualFee` 结算金额
   + 费用项两型，ADR-0009），而预写 spec 按「订单金额 / 平台服务费 / 实际收入三分」写的；
3. `companion_profile.order_count` 这个字段**运行期无人维护**（只在建档时置 0）——
   累计完成单数若读它，会**永远返回 0**，而且不报错。

第 3 条最危险：它不抛异常、不报错，页面只是「永远是 0」。

---

## 二、决策 1：统计一律由后端完成，前端零自行计算

### 决策

四个工作台端点的**全部**聚合与口径计算放在后端；
前端只消费端点结果并展示，**不得**用 `reduce()` / `filter()` / `groupBy()`
对订单明细自行汇总（总纲 G8）。

既有 `companion/income.vue` 的前端自算必须收敛掉。

### 理由

前端自算有三个绕不开的问题：

1. **口径无法被机器校验**。后端的口径能登记进指标字典、能被 `MetricDictionaryTest` 双向核对；
   前端的一段 `reduce()` 只是一段 JS，**没有任何机制会在它漂移时报警**；
2. **区间上限装不下「累计」**。统计区间上限 366 天，「累计」在区间语义里根本无法表达；
3. **同一指标出现两个数**。家属端（后端算）与陪诊员端（前端算）一旦口径有差，
   运营看到的就是「两边对不上」，而谁也说不清哪边对。

> 这不是新规矩。M10 统计模块早就这么定，G8 把它上升为全局决策 ——
> 前端**只做展示，不做经营口径**。

---

## 三、决策 2：金额只做五项，不引入「平台服务费」

### 决策

工作台的金额一律沿用**现有费用模型**（ADR-0009），只做五项：
**订单金额 / 实际收入 / 待结算 / 已结算 / 费用构成**。
**不引入「平台服务费」这个字段**。

### 理由

预写 spec 的「三分」里有一项在现有模型里**根本不存在**。
新增一个金额字段意味着：

- 要定它从哪来（从 `fee` 里拆？按比例抽？）；
- 要让它与 `actualFee` / 费用项三者的关系被理解、被测试、被对账；
- 而这一版的真实需求是「让陪诊员看清自己赚了多少、结了多少」，
  **不需要**一个平台侧的抽成口径。

「不新增金额字段」优先于「三分」这个说法本身 ——
**没有可信来源的字段，加进去就等于加了一个永远对不上的数。**

---

## 四、决策 3：概览（区间口径）与画像（累计口径）用**不同字段名**

### 决策

**字段名自带口径**：

| 出口 | 口径 | 字段 |
|---|---|---|
| 概览 `/me` | 统计区间内 | `completedOrderCount` / `serviceDurationMinutes` / `completionRate` / `periodIncome` |
| 画像 `/me/profile` | 历史累计 | `totalCompletedOrderCount` / `totalServiceDurationMinutes` / `totalCompletionRate` / `totalServedElderCount` / `punctualityRate` |

两条在指标字典里各占一个 key，统计范围分别写明「统计区间内」/「历史累计」。

### 理由

概览回答「这一个月做得怎么样」，画像回答「我到底什么水平」。
两者都有「完成率」「服务时长」—— 如果都叫 `completionRate`，
**接口契约本身就埋了口径分裂**：前端拿到的 `completionRate` 是区间还是累计，
只有写接口的人知道，用接口的人只能猜。

而且这不只是命名洁癖：指标字典的**双向校验**（字典 ↔ VO 逐条核对）
按字段名绑定。共用一个名字时，字典里那条指标到底绑到哪个出口，
机器根本分不出来 —— 校验会变成「看起来对」。

---

## 五、决策 4：「本月」改为「统计区间」

### 决策

所有 V3.3 指标走共享区间 `dto/DateRangeQuery`（闭区间、默认最近 30 天、上限 366 天），
指标名与界面文案统一用「区间」，**不出现「本月」**。

### 理由

「本月」是一个**固定日历月**，与**可传参的统计区间**不是一回事。
默认区间是「最近 30 天」，手动传参可以是任意闭区间 ——
于是同一个字段名在两种情况下指两个口径，正是决策 6.2 要禁掉的那类漂移。

---

## 六、决策 5：累计完成单数从 `companion_order` 现算，不读冗余字段

### 决策

`totalCompletedOrderCount`（累计完成单数）与 `totalServedElderCount`（累计服务老人数）
**从 `companion_order` 现算**，不读 `companion_profile.order_count`。

### 理由

`companion_profile.order_count` **运行期无人维护** —— 只在建档时置 0，
此后接单 / 完成都不会刷新它。读它会**永远返回 0**。

冗余字段省一次聚合，代价是「谁负责刷新它」这件事没有答案 ——
没人刷新，而**没人发现的恒 0 比报错更糟**。
既然这个字段在项目里没有维护者，就不该读它。

> 这条与 V3.2 的用药三桶漂移（ADR-0014）是同一类问题的两面：
> **一个数有两份来源时，必须指定唯一真源**；指定不了，就不要有第二份。

---

## 七、决策 6：陪诊员端的区间过滤用 `visit_time`，与家属端同源

### 决策

陪诊员端工作台与家属端 `elder.visit.order_count` 用**同一个时间字段**（`visit_time`）过滤。

### 理由

两端数的是**同一批「已完成订单」**。若陪诊员端按 `create_time`、
家属端按 `visit_time`，同一个指标在两个端点上就是两个数 ——
决策 6.2（同一指标只有一个口径）当场破掉。

> 预写 tickets 原写的是 `DATE_FORMAT(create_time,'%Y-%m-%d')`，
> 开工复核后改用 `visit_time`（偏差 D-3.3-4）。

## 八、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留 `income.vue` 的前端 `reduce()` 自算 | 违反 G8；口径无法被机器校验；同一指标出现两个数 |
| 新增「平台服务费」金额字段 | 现有模型里没有这个口径；新增即新增一个永远对不上的数 |
| 概览与画像共用 `completionRate` 字段名 | 接口契约层面埋口径分裂；指标字典的字段绑定无法机器区分 |
| 用「本月」作为默认区间 | 固定日历月 ≠ 可传参区间；同一字段名两种口径 |
| 读 `companion_profile.order_count` 取累计完成单数 | 运行期无人维护 → 永远返回 0，且不报错 |
| 陪诊员端按 `create_time`、家属端按 `visit_time` | 同一指标两个口径（决策 6.2） |
| 把「擅长服务」做成运营手工配置 | 决策 3.3 要求来源于真实业务数据；配置会与实际服务历史脱节 |

## 九、后果

### 正面

- 陪诊员端的每一个数字都能在指标字典里查到口径，且能被人读面核对
- 概览与画像的口径差异写在**字段名**里，前端不需要读文档就不会搞混
- 「累计」类指标全部现算，不再依赖无人维护的冗余字段
- 前端自算被清掉，经营口径的改动只需动后端一处

### 负面 / 代价

- 旧收入页的「累计收入」文案必须改成「**区间收入**」——
  这是**产品语义的变化**，不只是改个词：旧文案对应的是「拉全量」，新文案对应的是「统计区间」
- 累计类指标每次都现算，数据量上来后需要索引与缓存（当前规模未触及）
- 区间口径与累计口径并存，同一页面出现两套数，需要靠字段名与文案引导用户

### 待观察

- `companion_profile.order_count` 这个字段**仍然存在**且仍然不刷新。
  本版只是**不再读它**；将来若有人清理 schema，应记得它是一个死字段而不是「慢字段」
- 陪诊员端与家属端共用 `visit_time` 口径后，跨端对账的前提是
  「同一批已完成订单」在两端都成立 —— 订单状态机的任何改动都会影响这一点
