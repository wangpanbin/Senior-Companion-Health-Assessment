# ADR-0016 · V3.4 智能调度：为什么必须先做结构化改造，以及为什么每条推荐都必须可解释

> **状态**：已接受 · 2026-10-20
> **相关**：[V3.4-matching-spec.md](../spec/V3.4-matching-spec.md) · [V3.4-tickets.md](../spec/V3.4-tickets.md) · [ADR-0013](0013-hall-single-recommend-order.md) · [ADR-0014](0014-medication-bucket-single-source.md) · [V3.x-roadmap-spec.md](../spec/V3.x-roadmap-spec.md) §4.4
> **影响范围**：`backend/sql/V7__matching_structured.sql` · `service/support/matching/**` · `service/MatchingService` · `OrderServiceImpl#hall` · `GET /api/order/{id}/recommend-companions`

---

## 一、背景

迭代计划 §37 要求的匹配模型有五个维度：区域 / 时间 / 距离 / 服务能力 / 评分。
2026-10-20 开工核实，**其中三个没有数据基础**：

| 维度 | 当时的数据形态 | 能不能算 |
|---|---|---|
| 服务能力 | `companion_order.department` 有真实数据 | ✅ 能算 |
| 评分 | `companion_profile.score` | ✅ 能算 |
| 区域 | 陪诊员 `service_area VARCHAR(100)` 是**自由文本**；订单侧**没有**区域字段 | ⚠️ 只能做包含式匹配 |
| 时间 | 陪诊员 `available_time VARCHAR(100)` 是**自由文本** | ⚠️ 只能做包含式匹配 |
| 距离 | 订单有 `longitude` / `latitude`，**陪诊员档案没有坐标** | ❌ 完全算不了 |

ADR-0013 原文即写着「一期无坐标、无真实结算」。
所以「距离 20%」这个权重在开工当天**没有任何数据支撑**。

---

## 二、决策 1：先做结构化改造（expand–contract），再建规则引擎

### 决策

在规则引擎之前，先做一次**可回退的结构化改造**：

- `companion_profile` 增 `longitude` / `latitude` / `service_region_code`（**全部可空**）
- `companion_order` 增 `service_region_code`（可空）
- 新表 `companion_available_slot`（陪诊员可服务时段）
- backfill：自由文本 → 区域码（**映射不上的留空**）
- 读路径：**优先结构化列；缺失时回退自由文本包含式匹配**
- **一期不删旧列**

### 理由

**规则引擎是「怎么算」，结构化改造是「有什么可算」。**
顺序反了的话，引擎只能建在流沙上 —— 权重配得再漂亮，算出来的分也是空的。

expand–contract 而不是直接改造的理由：
1. **可回退**：区域码 backfill 是**加列**，不是改列；出错了把列一删就回到原样。
2. **不打断存量**：新列可空，老数据一行不改就能继续跑；
   读路径的回退分支保证「老陪诊员照样能被匹配到」。
3. **不删旧列是纪律，不是省事**：`service_area` / `available_time` 里还有历史语义
   （比如「周一至周五 08:00-18:00」不只是一个时段，还有排班习惯），
   删列是不可逆动作，而它还没到该删的时候。

### 区域码的两级结构

区域码格式 `<CITY>_<DISTRICT>`（全大写拼音），**城市前缀（`_` 之前）就是「区」这一层**：

```
区域码相等                                → 1.0
同市不同区（HAIKOU_MEILAN vs HAIKOU_XIUYING）→ 0.5
跨市（HAIKOU_x vs SANYA_y）                → 0
```

为什么要有两级：种子的服务区域有 8 个区县、分属 4 个市。
只有一级的话，「海口市美兰区」和「海口市秀英区」只能算「不同」，
但它们其实是**同一个市场的供给** —— 把它们判成 0.5 才对。

映射表放在 `backend/sql/tools/region_code_mapping.json`，
由 `gen_region_codes.py` 生成 backfill SQL，并用 `--check` 模式**机械核对**
迁移文件里手写的 CASE 与生成器逐字一致 ——
「手写的迁移」与「可复现的生成器」之间必须有一道自动校验，否则两边迟早漂移。

### 为什么可服务时段用表而不是 JSON 列

时段要参与**筛选**（订单就诊时间落在哪个时段里），必须可索引、可 JOIN。
JSON 列做不到「按星期 + 时刻范围」的高效筛选，而这恰恰是时间匹配维度要用的条件。

### 为什么还要保留自由文本回退

存量陪诊员的 `available_time` 是「周一至周五 08:00-18:00」这样的自由文本，
结构化表对新数据才有内容。如果只读结构化表，**所有存量陪诊员的时间维度都是 0**，
匹配引擎等于少了一条腿。

所以 `LegacySlotParser` 把常见写法解析成时段（**只认几种明确形态，解析不出来就返回空**，
宁可让这一维记 0 并标注，也不猜）。这是**回退路径**，不是主路径。

## 三、决策 2：五维加权在 Java 侧算，不写进 SQL 的 ORDER BY

### 决策

大厅的 `RECOMMEND` 排序改为：**候选集 → 五维打分（Java 侧）→ 排序 → 内存分页**。
规则是**无 Spring 上下文的纯函数**，权重来自 `nianglin.matching.*.weight`。

### 理由

三件事写进 SQL 会出错：

1. **距离要 Haversine**，MySQL 没有内置函数；
2. **服务能力**要按「我在这个科室做过多少单」归一化，需要子查询；
3. 最要紧的是「**陪诊员无坐标 → 距离记 0 且不推断**」需要一条**分支** ——
   而 SQL 里写 `CASE` 会让「没数据」与「坐标相同（距离 0）」落进同一个值。

第 3 条是硬伤：如果把 `NULL` 坐标当成 `(0,0)` 算，会得到「离几内亚湾 2000 公里」的结果，
然后在排序里把真正合适的人挤下去。**这是「看起来能跑、实际在害人」的错误**，
必须由「分支 + 标注」来防住，而分支在 Java 侧写起来最自然。

### 纯函数的意义

规则只吃快照、只吐结果，不碰数据库、不碰时钟、不碰配置中心。
这样「每个阈值的边界」都能被**毫秒级地反复测试** ——
而这正是匹配引擎最需要被锁住的东西。

权重之和必须等于 1，且在**启动期**校验：错误的权重不会报错，
只会让排序悄悄变得不合理 —— 那是最难定位的一类故障，
所以让它在启动的十秒内就失败。

## 四、决策 3：每条推荐都必须可解释

### 决策

匹配结果不只给一个分数，还要给：
- **各维度得分**（区域 / 时间 / 距离 / 服务能力 / 评分）
- **命中理由**（`reasons`）：「同服务区域」「服务过该科室 12 单」
- **降级说明**（`notes`）：「未填写坐标，距离维度记 0」

### 理由

如果只返回一个 `double`，那就回到了**黑盒推荐**：
家属看到「匹配度 86」不知道凭什么，陪诊员看到「凭什么是我」也不知道，
运营调权重时更无从判断哪一维在起作用。

**理由与降级说明必须分开**：
把降级写进理由会让人误以为「距离不匹配」，而真相是「距离没法算」。
这两件事混在一起，运营会拿一个不存在的结论去调权重。

> **不允许出现一个没有理由的分数** —— 这条由单测锁死。

---

## 五、决策 4：推荐 ≠ 派单

### 决策

`GET /api/order/{id}/recommend-companions` **只做推荐**，不产生任何订单状态变更。
接单权始终在陪诊员手里（roadmap 决策 4.4）。

界面上必须明确标注「推荐仅供参考，最终由陪诊员本人确认接单」，
**不得出现「已指派」「已分配」「自动派单」**之类暗示自动派单的文案 ——
那是产品边界的改变，不是文案问题。

---

## 六、决策 5：`INCOME` 排序仍不开放

「收益优先」需要**真实结算金额口径**，而现有费用模型里没有这一条
（只有 `fee` 合同服务费、`actualFee` 结算金额与费用项两型，ADR-0009）。
所以 `sortBy=INCOME` 继续返回 400，但错误消息改成一句人话：
「收益优先需要真实结算金额口径，本版未开放」——
而不是笼统的「后续版本开放」，因为它不是「还没做」，是「没有可信的数据」。

## 七、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 直接在 SQL 的 `ORDER BY` 里写五维加权表达式 | 「无坐标 → 记 0」需要分支，SQL 的 CASE 分不出「没数据」与「距离为零」；且 Haversine 无内置函数 |
| 保持大厅的 DB 分页，排序只按能算的维度做近似 | 那就不是「五维推荐序」，而是一个缩水版；而且需求方会拿它当五维用 |
| 把 `service_area` / `available_time` 直接改成结构化列并清空旧值 | 不可逆；且历史语义（旧文本里的排班习惯）会丢 |
| 用 JSON 列存可服务时段 | 时段要参与筛选，必须可索引可 JOIN |
| 无坐标时按 (0,0) 算距离 | 会把「没填资料」翻译成「离得很远」，在排序里挤掉真正合适的人 |
| 推荐结果直接派单 | 违反决策 4.4（接单权在陪诊员） |
| 给健康度之类的复合指标一个总分 | 本版不做；V3.5 决策 5.2 同理 |

## 八、后果

### 正面

- 匹配引擎有了**真实的数据基础**，而不是建在自由文本上的近似
- 每条推荐都能说出「为什么是他」，运营调权重有依据
- 规则是纯函数，边界可被毫秒级测试
- 权重配置化，运营能针对供给不足的时段调策略（不改代码、不发版）

### 负面 / 代价

- 引入一次数据库迁移（V7）
- 大厅从 DB 分页改为**候选集 + 内存分页**：
  - `total` / `page` / `size` / `pages` / `records` 结构与语义**零变更**（`total` 仍是满足筛选条件的待接单订单数）
  - 但候选集要整批加载 → 引入 `nianglin.matching.hall-candidate-limit`（默认 500），
    超限时**记 warn 日志**（不静默截断）
- `LegacySlotParser` 只能解析几种明确写法；写得很随意的排班文本仍会落到「时间维度记 0 + 标注」

### 待观察

- 陪诊员坐标目前**全是空**（结构化列刚加）→ 距离维度现在对所有候选人都是 0。
  这是**如实反映「现在没有距离数据」**，不是缺陷；
  等陪诊员开始填坐标，排序自动生效，不需要改代码。
  `sortBy=DISTANCE` 在此期间退化为「并列 → 回落就诊时间」，这一点已在 spec 里写明。

## 九、后续影响（V3.7 智能助手）

V3.7 的家属智能助手**不改动**本 ADR 确立的匹配引擎：

- **排序仍由本 ADR 的规则引擎唯一负责**（`MatchingServiceImpl` + `service/support/matching/**`）。助手**不得**重排候选、**不得**修改任何维度分或总分、**不得**补充 `CompanionMatchVO` 之外的事实。
- 助手只做**叙述**：把 `reasons`（命中理由）/ `mismatches`（算了没命中）/ `notes`（数据缺失没法算）**三段分别**讲成人话，**不合并、不美化**。
- 本 ADR 的核心结论「不允许出现一个没有理由的分数」在 V3.7 继续成立：助手叙述里的理由必须来自这三段；`notes` 写「未填写坐标，距离维度记 0」时**必须**表达为「距离维度无法计算」，**不得**说成「距离近」「离得近」「就在附近」。
- 「推荐 ≠ 派单」（决策 4）同样延续：助手输出**不得**出现「已指派」「已分配」「自动派单」。

助手侧的边界、护栏与降级口径见 [ADR-0020](0020-assistant-boundary-and-recommendation-guardrail.md)。
