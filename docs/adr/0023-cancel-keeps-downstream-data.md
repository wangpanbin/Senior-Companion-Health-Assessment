# ADR-0023 · 订单取消保留全部下游数据

| 项 | 内容 |
|---|---|
| 状态 | 已接受（Accepted） |
| 日期 | 2026-11-28 |
| 决策人 | 银龄伴诊团队 |
| 相关工单 | `docs/spec/closure-2026-11/P2-5-cancel-downstream.md` |

---

## 背景

订单进入 `CANCELLED` 后，与它关联的五类下游数据在系统里**全部保留**：

| 表 | 内容 |
|---|---|
| `order_checkin` | 6 节点打卡记录 |
| `companion_track` | 打卡点与抽稀位置点 |
| `chat_message` | 家属 ↔ 陪诊员聊天（ADR-0011） |
| `sys_file` | 各类附件（证件、投诉证据、聊天图片/视频） |
| `internal_message` | 站内信 |

但全仓**没有任何一处写明这是刻意的**：

- `V1__init_schema.sql` 里一条 `FOREIGN KEY` 都没有，看起来像「没设计级联」；
- `OrderServiceImpl#cancel` 与 `OrderTransitionServiceImpl#forceTerminal` 都没有注释解释；
- 接口文档也没有向用户说明「取消后聊天仍可查看」。

结果是每个新成员（或评审人）都会问一次「取消后这些数据为什么不删」，然后得到一个口头回答。这个问题的重复出现，本身就是文档缺口。

## 决策

**订单进入 `CANCELLED` 后，上述五类下游数据一律保留，不做删除、不做级联、不做伪匿名。**

具体地：

1. 取消路径（家属自助取消、管理员强制取消、超时自动取消）**都不删除任何下游数据**；
2. 数据库**不引入** `FOREIGN KEY ... ON DELETE CASCADE`；
3. 代码里在取消写入之后补注释指向本 ADR；
4. 接口文档明确说明「取消后仍可查看打卡、轨迹、聊天、附件、站内信」。

## 理由

1. **纠纷取证**：取消常常是纠纷的结果或起点。删掉过程数据等于让管理员在没有证据的情况下仲裁（`AdminServiceImpl#arbitrate` 依赖完整过程）。
2. **劳动凭证**：陪诊员可能已经到院、已经打卡。取消不代表他没干活，删掉打卡等于消灭他的凭证。
3. **交涉场景**：ADR-0011 明确「`CANCELLED` 后仍可互发消息」——这是刻意设计，不是漏洞。
4. **平台不做在线支付**：不存在「退款后应销毁交易记录」这类合规要求。数据保留不带来资金类风险。
5. **删除的代价不可逆**：误删一次就永久失去；保留的代价只是存储。

## 后果

### 正面

- 所有纠纷处置都有完整证据链；
- 陪诊员的劳动凭证不会因家属取消而消失；
- 数据口径简单：任何时刻查订单的下游数据，得到的就是全部发生过的事。

### 负面 / 代价

- **数据只增不减**，存储随订单量线性增长（当前量级下可接受）；
- 「取消」在用户认知里常等于「作废」，需要文档与 UI 文案显式说明数据仍在；
- 若将来需要清理，必须走**归档**（搬冷存储）而不是删除，需要独立的数据生命周期策略。

### 不受本决策覆盖的对象

| 对象 | 说明 |
|---|---|
| Redis 中的临时键（锁、限流、幂等、验证码） | 按 TTL 自然过期，与订单生命周期无关 |
| 幂等键与草稿判重键（P2-4 / `medicationDraftFromOrder`） | TTL 过期即消失，不承载业务事实 |
| 逻辑删除标记 `deleted = 1` | 与本 ADR 无关；`@TableLogic` 的语义是「对用户不可见」，不是「物理删除」 |

### 对未来的约束

若将来确实需要「真删」（例如合规要求的数据主体删除请求），**必须**：

1. 新增本 ADR 的替代 ADR，明确覆盖范围与例外；
2. 删除动作必须走独立的审计路径（不能混在取消逻辑里）；
3. 保留「已删除」的可查痕迹（删除时间、操作人、依据）。
