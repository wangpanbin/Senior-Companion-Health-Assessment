# ADR-0017 · V3.6 数据闭环：口径登记必须是「机器校验」而不是「人读的表」

> **状态**：已接受 · 2026-10-20
> **相关**：[V3.6-data-loop-spec.md](../spec/V3.6-data-loop-spec.md) · [V3.6-tickets.md](../spec/V3.6-tickets.md) · [metric-dictionary.md](../spec/metric-dictionary.md) · [ADR-0014](0014-medication-bucket-single-source.md) · [V3.x-roadmap-spec.md](../spec/V3.x-roadmap-spec.md) §4.6
> **影响范围**：`backend/src/main/resources/metrics/endpoints.yml` · `util/MetricEndpointRegistry` · `util/MetricDictionary` · `service/support/metrics/**` · `GET /api/admin/operations/gap` · `GET /api/admin/operations/effect`

---

## 一、背景

V3.2 建立指标字典时，它解决的是「**指标**有没有登记」：
字典里写的字段必须真的存在，VO 里的每个字段必须真的登记过。
这套双向校验（`MetricDictionaryTest` 三层：字典→VO / VO→字典 / 可达性）已经能挡住
「代码加了指标但没人登记」和「字典登记了但代码没实现」。

但它**挡不住**第三种情况：

> **某个端点返回了一堆数字，而这些数字的口径没人登记过。**

V3.2 – V3.5 期间一直是靠「人记得在写 VO 时顺手登记」维持的。
这在四个人并行开发、每个版本新增 10~20 条指标的情况下，
必然出现「某个 VO 的字段被声明成了 `structural`（结构字段）就绕过了登记」的情况 ——
而结构字段这个逃生舱口，本意是给「不是指标」的字段用的。

---

## 二、决策 1：建立「端点 ↔ 指标」的机器面

### 决策

新增 `backend/src/main/resources/metrics/endpoints.yml`：

```yaml
endpoints:
  - endpoint: "GET /api/statistics/companion/me"
    metrics:
      - companion.workbench.completed_order_count
      - companion.workbench.service_duration
      ...
```

并由 `MetricEndpointContractTest` 做**三条双向校验**：

1. **yml 里声明的端点必须真实存在**
   —— 反射扫描所有 `@RestController`，收集方法上的 `@GetMapping` / `@PostMapping` /
   `@PutMapping` / `@DeleteMapping`，拼上类级 `@RequestMapping` 前缀，
   规范化成 `"GET /api/xxx"`。
   yml 里出现一个代码里没有的端点 → **变红**。
2. **yml 里声明的指标必须在指标字典里** → 变红。
3. **指标字典里每条指标声明的端点，必须在 yml 里出现** → 变红
   （防「指标登记了，但没人知道它属于哪个端点」）。

### 理由

**「口径登记」必须从「靠人记得写」升级成「机器逼你写」。**

前两条是**声明式**的：yml 是人写的，但它被机器核对，所以写错就会红。
第三条把「端点」也纳入同一张网 ——
从此「一个端点返回了什么指标」这件事是**可查询的**，而不是散落在各人的脑子里。

这直接服务决策 6.1（「每个核心统计指标必须明确：指标名称 / 统计范围 / 统计时间 /
数据来源 / 计算公式」）与决策 6.2（「同一指标在不同角色端只能有一个口径」）：
当「端点 → 指标」的映射是机器可查的，
「这个指标在三个端点各出现一次」这种漂移就能被看见。

### 为什么用 yml 而不是 Java 注解

注解要写在 Controller 方法上，**而 Controller 里的每个方法已经有很多注解了**
（`@Operation` / `@PreAuthorize` / `@GetMapping` …），
再加一个 `@Metrics({...})` 会让「这个接口返回哪些指标」这件事散落在几十个类里。

yml 是**一张表** —— 想看全局时打开一个文件即可，
而这正是「口径收敛」这件事需要的形态。

## 三、决策 2：同一个指标只能有一个计算器

### 决策

新增 `service/support/metrics/MetricCalculator` 接口与 `MetricCalculatorRegistry`：

```java
public interface MetricCalculator {
    String metricKey();          // 必须已在指标字典登记
    String calculate(DateRange range);
}
```

**注册表里同一个 key 只能有一个实现。**
效果对比端点（`/api/admin/operations/effect`）只接受**已注册**的指标 key，
未注册的返回 `400` —— 不许「猜一个算法算出来」。

### 理由

决策 6.2 要求「同一指标在不同角色端只能有一个口径」。
这条要求光靠**文档**约束不住 —— 文档不会在改动时报警。

而「一个 key 一个计算器」把它变成**结构约束**：
家属端要算完成率 → 调注册表；陪诊员端要算完成率 → 调注册表；
管理员端要算完成率 → 还是调注册表。
**物理上只有一份实现**，也就不存在「两份实现漂移」的可能。

这正是 V3.2 在用药三桶上吃过的亏的根治办法：
当时 M10 的漏服统计与服药日历口径不一致，
靠 ADR-0014 把判定收敛到 `MedicationBucket` / `MedicationBucketSql` 两个唯一真源才解决。
V3.6 把同一个思路推广到**所有**指标上。

## 四、决策 3：缺口分析的供给数按「可服务时段」分桶，并如实披露数据质量

### 决策

`GET /api/admin/operations/gap` 的 `availableCompanions`
= **该时段确实可服务**的陪诊员数（按其可服务时段分桶），
而不是「当前 AVAILABLE 的陪诊员总数」。

另设 `companionsWithoutSlots` 字段，说明有多少陪诊员
**没有可解析的可服务时段**、因而不参与供给统计。

### 理由

预写 spec §2.1 的字面写法（按工作状态统计）会让每个桶的供给数都是同一个值 ——
那是一个**没有信息量**的指标。

按可服务时段分桶才是「哪个时段没人接单」真正需要的数：
一个只上早班的陪诊员，不该被算成下午的供给。

而 `companionsWithoutSlots` 是**对数据质量的如实披露**：
供给数算得偏低时，管理员需要知道这是「真的没人」还是「没人登记时段」。
把这些 0 混进分母却不说明，就是**用一个不存在的结论去调运营策略**。

### 桶的粒度固定为「周内第几天 × 小时」

与查询区间的长度无关。这正是迭代计划 §47 那个闭环的数据基础：

```
订单无人接 → 统计发现 14:00–16:00 陪诊员数量不足
          → 管理员调整排班
          → 下一周期重新统计 → 履约率提升
```

只有桶的粒度与区间长度无关，「这一周和上一周的同一时段」才可比。

## 五、决策 4：干预效果对比的两侧必须走同一个计算器

### 决策

`GET /api/admin/operations/effect?metric=&from=&to=&compareFrom=&compareTo=`
的两期数值由**同一个 `MetricCalculator`** 算两遍得到，
不写第二份公式。

`compareFrom` / `compareTo` 不传时，自动取「与后一期等长、紧邻其前」的区间。

### 理由

「干预让下一次服务变好了吗」这个问题，只有在**两侧同口径**时才有意义。
用两个各写一遍的公式对比，比出来的差值可能全是公式差异。

而「等长、紧邻其前」这个缺省推导是刻意的：
两期**长度不等**时，比的是「一段 7 天 vs 一段 30 天」，那是量纲错误。

## 六、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 在 Controller 方法上加 `@Metrics({...})` 注解 | Controller 注解已经很多；「全局看有哪些端点返回哪些指标」需要翻几十个类 |
| 只在文档里维护「端点 → 指标」表 | 文档不会在改动时报警 —— 这正是 V3.2 建立指标字典的原因 |
| 效果对比时「两期各写一个公式」 | 比出来的是公式差异，不是干预效果 |
| 缺口分析按「当前可接单陪诊员总数」分桶 | 每个桶供给数相同，指标没有信息量 |
| 把没登记时段的陪诊员按「全天可用」计入供给 | 那是替运营猜了一个他没承诺过的范围 |
| 未注册指标在效果对比里「按最接近的指标算」 | 猜出来的对比没有意义，应该直接 400 |

## 七、后果

### 正面

- 「端点 → 指标」的映射变成**可查询、可校验**的机器面
- 同一个指标**物理上只有一份计算实现**，口径不可能漂移
- 供给缺口分析能真正回答「哪个时段没人接单」
- 干预效果对比能真正回答「这次干预有没有用」

### 负面 / 代价

- 引入一份新的机器面文件（`endpoints.yml`），要维护
- 效果对比只支持**已注册**的指标 —— 不是所有指标都能按区间算
- 缺口分析依赖陪诊员**登记了**可服务时段；存量数据大量依赖自由文本解析，
  解析不出来的那部分会以 `companionsWithoutSlots` 的形式被**暴露**，而不是被悄悄算成 0

### 待观察

- 「端点 ↔ 指标」机器面目前只覆盖**统计类端点**。
  业务 CRUD 端点（如创建订单）返回的字段不是统计指标，不进这张表 ——
  边界是「这个字段是不是一个**有口径的统计量**」。
