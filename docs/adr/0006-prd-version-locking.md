# ADR 0006 · PRD 版本锁对齐竞讲节点

- **状态**:已接受(ACCEPTED)
- **日期**:2026-09-16
- **决策者**:4 人团队
- **关联模块**:文档维护流程,跨所有模块
- **关联文档**:`docs/prd/PRD.md`、`plan.md`、ADR-0005

---

## 背景

PRD(`docs/prd/PRD.md`)作为课程评审和团队对齐的"顶层文档",需要回答:什么时候修订、改动幅度多大、什么版本可以对外发?

可选两条路:

**方案 A:持续同步(像 plan.md 一样)**——PRD 每周随代码演进更新,跟代码保持"零漂移"。代价是 PRD 没有"签收时刻",老师评审时拿不到"某个时间点的可交付物";且每次微调都触发评审,文档评审成本被稀释。

**方案 B:版本锁(对齐 3 个竞讲节点)**——v1.0 在 M0-M2 完成时冻结;v1.1 在 W7 竞讲后修订;v1.2 在 W12;v2.0 在 W17。中间过程 PRD 不动,新需求/调整记录到 issue 或 plan.md。

---

## 决策

**采用方案 B**:PRD 版本锁对齐竞讲节点。

### 版本节奏

| 版本 | 触发时刻 | 评审方式 | 对应课程阶段 |
|---|---|---|---|
| v1.0 | M0-M2 完成时(项目骨架就位) | 团队 4 人 PR 评审 | 起点,锁版本冻结 |
| v1.1 | W7 竞讲后 | 团队 4 人 PR 评审 + 老师反馈 | 迭代二交付物后 |
| v1.2 | W12 竞讲后 | 团队 4 人 PR 评审 + 老师反馈 | 迭代三交付物后 |
| v2.0 | W17 终交付 | 团队 4 人 PR 评审 + 老师最终评审 | 课程终交付 |

### 修订原则

- **每个版本修订走 PR**——标题 `docs(prd): bump vX.Y → vX.Z + <关键变更>`;描述里显式列"已同步更新的配套文档"
- **配套文档同步约束**——PRD 改了,所引用的 `plan.md §Mx` / `docs/api/0X` / `designs/Mx` 必须在同一 PR 里同步或显式说明"故意不跟"
- **增量变更,不要重写**——v1.0 → v1.1 只增改"这一阶段新增/调整"的章节,其他章节保留旧版本内容;避免每次大改变成"重写 PRD"
- **v2.0 才允许结构调整**——v1.x 内只允许"内容修订",章节顺序 / 体量占比等结构性变更留到 v2.0

---

## 后果

### 收益

- (+) **3 个竞讲节点都有可签收的 PRD 版本**——老师评审"v1.1 提交"时,拿到的是锁版本而非"上周又改了"的滚动文档
- (+) **版本之间不混改**——评审范围清晰,易于回回和回退
- (+) **结构性变更少**——v1.x 内不做结构调整,意味着文档结构本身经过验证,后续读者路径稳定
- (+) **评审成本可控**——每个版本只评审"上一版以来的变更",而非从头看

### 代价

- (-) **修订频率低,中间期 PRD 与代码可能漂移**——例如 v1.1 锁版本后,M5 的实现做了局部调整但 PRD 没更新;缓解 = 每个 PR 描述里显式检查"PRD 是否需要联动更新"
- (-) **团队需记住 4 个发布时刻**——v1.0 / v1.1 / v1.2 / v2.0,容易遗忘;缓解 = 项目看板 / `docs/agents/issue-tracker.md` 中显式标注
- (-) **v1.x 内增量修订可能让文档"长出冗余"**——例如 M6 范围从 A 调整为 A+B,文档里既有 v1.0 写 A 的段落又有 v1.1 加的 B 段落,读到 v1.1 的人会困惑;缓解 = 修订时优先"覆盖",非"追加"

### 缓解措施

- **配套文档同步检查清单**(每次 PRD PR 必填):
  1. 所引用的 `plan.md §Mx` 是否需要更新?
  2. 所引用的 `docs/api/0X` 接口签名是否仍一致?
  3. 所引用的 `docs/agents/designs/Mx` 设计评审是否仍准确?
  4. 所引用的 `docs/adr/0001-0004` 是否仍成立?
  5. 是否需要在 `README.md` 文档索引中追加新章节引用?
- **竞讲前 1 周提醒**——用 issue 或 cron 在 W7/W12/W17 前 1 周提醒"PRD 待修订评审"
- **历史版本不删**——v1.0 / v1.1 / v1.2 等历史版本可归档到 `docs/prd/archive/`,方便回顾
