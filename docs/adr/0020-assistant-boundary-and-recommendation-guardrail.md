# ADR-0020 · V3.7 家属智能助手：边界对齐「谨慎使用」档、推荐由规则引擎负责、合规词表单一真源

> **相关**：[V3.7-assistant-spec.md](../spec/V3.7-assistant-spec.md) · [V3.7-tickets.md](../spec/V3.7-tickets.md) · [ADR-0016](0016-matching-structured-and-explainable.md) · [ADR-0011](0011-order-chat.md) · 仓库 `plans/迭代计划.md` §40 / §60 / §61.3

## 一、背景

家属在下单前后反复问两类问题：**「给我找个靠谱的陪诊员」**与**「这个流程怎么走、这钱怎么算」**。今天这两件事都没有答案：

| 家属的处境 | 平台今天的形态 |
|---|---|
| 想找陪诊员 | 订单进大厅后，家属只能在订单详情页看 V3.4 的「系统正在为你匹配」卡片。那是规则引擎的五维分，**但它是给「看」的，不是给「问」的**——家属不会知道自己该问什么，也不知道匹配结果该怎么理解 |
| 问平台规则 | 平台规则散落在 `docs/api/*.md` 与 `plan.md` 里，**没有任何问答入口**。费用口径（工作日 128 / 夜间周末 158）、取消规则、投诉入口全靠人肉翻文档 |

需求是加一个「家属端智能助手」，用 **Python + LangChain + FastAPI** 实现。

但这件事有三处不能拍脑袋：

1. **仓库对 AI 能力有明确分级**（`plans/迭代计划.md` §60），本能力落在哪一档决定了要不要护栏；
2. **V3.4 已把「推荐必须可解释」写成硬约束**（ADR-0016），引入 LLM 会不会破坏它；
3. **合规词表只有一份，在 Java 里**（`ComplianceCheckUtil`），而它的 javadoc 明写「不要另起一份词表」。

---

## 二、决策 1：边界对齐「谨慎使用」档，不碰禁止档

### 决策

本助手的 AI 能力**全部落在 `plans/迭代计划.md` §60 的「谨慎使用」档**：

| 档位 | §60 原文 | 本助手的关系 |
|---|---|---|
| 允许 | 运营数据分析 / 用户反馈总结 / 投诉文本归纳 / 服务质量分析 / 管理员辅助决策 | 「解答平台常用问题」是**平台服务规则的转述**，不引入任何外部知识，落在允许侧 |
| **谨慎使用** | **订单智能推荐 / 陪诊员匹配 / 异常检测** | **「向家属推荐陪诊员」正落此档** → 必须配护栏 |
| 禁止 | 疾病诊断 / 疾病预测 / 治疗建议 / 药物推荐 / 药物剂量调整 / 医疗风险诊断 | **一律不碰**。医疗类提问**固定拒答**并引导线下就医 |

并且遵守 §61.3「AI 医疗诊断 明确禁止：症状诊断 / 疾病预测 / 处方推荐 / 药物推荐 / 治疗方案」。

### 理由

「谨慎使用」不是禁止，但它**要求付出代价**——这个代价就是本 ADR 决策 2 与决策 3 的护栏。跳过这一步直接设计，最容易做出的越界形态是「LLM 直接给陪诊员排序并顺带说两句病情相关的建议」：前者违反 ADR-0016，后者踩 §61.3。

### 顺带的版本约束

`docs/spec/V3.x-roadmap-spec.md` §6 与 `docs/spec/V3.4-matching-spec.md` **两处明写**「V3.4 第一阶段不引入 AI 模型」。

所以本能力**不能塞进 V3.4**，必须新开 **V3.7 智能助手** + 新模块 **M14** + 新 ADR（本文件）。这不是形式主义：如果不新开版本，后来者会以为「V3.4 不引入 AI」这条约束已经被某个补丁解除了。

## 三、决策 2：推荐由 Java 规则引擎负责，LLM 只做叙述

### 决策

**陪诊员的排序永远由 V3.4 的 Java 规则引擎负责**（`MatchingServiceImpl` + `service/support/matching/**`）。本助手：

- **不得**重排候选；
- **不得**修改任何维度分或总分；
- **不得**补充 `CompanionMatchVO` 之外的事实；
- **只能**按 `reasons`（命中理由）/ `mismatches`（算了没命中）/ `notes`（数据缺失没法算）**三段分别转述**。

助手的输入是 Java 门面**预装好的上下文**，其中 `candidates` 直接来自现成的 `GET /api/order/{id}/recommend-companions`（`OrderRecommendVO`）——**零改造、零重算**。

### 理由

ADR-0016 的核心结论是「**不允许出现一个没有理由的分数**」，且明确区分了「没命中」与「没法算」：

> 「把降级写进理由会让人误以为『距离不匹配』，而真相是『距离没法算』。这两件事混在一起，运营会拿一个不存在的结论去调权重。」

这段话对 LLM 同样成立，而且**LLM 的出错概率远高于人**。陪诊员坐标目前**全是空**（ADR-0016「待观察」段），所以距离维度对所有候选人恒为 0，`notes` 里会出现「未填写坐标，距离维度记 0」。

LLM 极容易把它美化成「离得比较近」——**那正是把「距离没法算」说成「距离不匹配」的同款错误**，而且这次会直接误导一个正在决定给哪位老人找陪诊员的人。

所以护栏是三层，且**第三层写进了单测**：

| 层 | 位置 | 行为 |
|---|---|---|
| 1 输入 | `ai-service/app/guard.py` `scan_input` | 医疗意图 → 直接返回固定拒答模板，**不经 LLM**；辱骂 / 违规引流 → `10003` |
| 2 Prompt | `ai-service/app/prompts.py` | system prompt 写死：只基于给定事实回答、不得引入外部医学知识、不得给出剂量 / 诊断 / 疗效判断、**必须原样转述 `notes`** |
| 3 输出 | `ai-service/app/guard.py` `scan_output` | 命中 17 词禁用表 → **整段替换为拒答模板**；命中「已指派 / 已分配 / 自动派单」→ 同样拦下 |

输出侧沿用 `ComplianceCheckUtil` 的既有决策：**命中即拒，不打码后放行**（打码会把「建议服用阿司匹林」变成「建议**阿司匹林」，读者仍能猜出原意）。

「已指派 / 已分配 / 自动派单」三个词沿用 ADR-0016 决策 4.4 —— **推荐 ≠ 派单**，接单权始终在陪诊员手里。这三个词前端 `matching.test.js` 已经断言过，助手输出同样不得出现。

## 四、决策 3：合规词表单一真源，Java 与 Python 读同一份

### 决策

把 `ComplianceCheckUtil.MEDICAL_ADVICE_WORDS` 的 17 个词从 Java 硬编码，改为**读 classpath 资源**：

```
backend/src/main/resources/compliance/medical-advice-words.txt
```

- **Java**：`ComplianceCheckUtil` 静态初始化读该资源，**签名与行为完全不变**，17 词一字不改；
- **Python**：`ai-service/app/paths.py` 解析该文件的**可配置路径**（默认 `../backend/src/main/resources/compliance/medical-advice-words.txt`，相对 `ai-service/`），生产部署时把**同一份文件**挂给两个服务。

> **同批抽出的还有两份**（收口评审时补上，纪律相同）：
> `compliance/sensitive-words.txt`（辱骂 / 违规引流词，Java `SensitiveWordUtil` + Python `guard.py` 共读）
> 与 `compliance/refusal-template.txt`（固定拒答模板，Java `ComplianceCheckUtil#refusalTemplate()` + Python `guard.REFUSAL_TEMPLATE` 共读）。
> 拒答模板也共享，是因为**它本身不得含任何禁用词** —— 两侧各写一份，早晚有一侧把自己拦下。

### 理由

`ComplianceCheckUtil` 的 javadoc 已经把这条教训写下来了：

> 「M7 的评价内容校验可直接复用本类，**不要另起一份词表** —— 两份词表一定会有一份先过期。」

本助手是新引入的第二个消费方。如果 Python 侧自己抄一份 17 词，那不是「暂时重复」，而是**当场违反项目已经写明的纪律**——而且失效方式极其隐蔽：词表过期后，Java 侧拦住的东西 Python 侧放行，两边行为分叉，且没有任何报错。

备选方案「Python 独立一份 + parity 脚本比对」被否决：那仍然是**两份词表 + 一道校验**，校验本身也会漂移（这正是 `ADR-0017` 记录的口径漂移模式）。真正的单一真源是**结构上不可能漂移**。

### 空词表 fail-fast

两侧都遵守「配置错要在启动十秒内暴露」这条纪律（`MatchingProperties#validate` 是样板）：

- Java：读不到 classpath 资源 → **启动失败**；
- Python：文件不存在 / 词数 < 10 / 缺少「建议服用」与「剂量」→ **启动失败**。

理由：**词表读空 = 护栏静默失效 = 最危险的一类故障**。它不会报错，只会让所有医疗回答放行，而且看起来一切正常。

## 五、决策 4：确定性路由器 + 降级路径与主路径同构

### 决策

助手内部**不使用自主 Agent**（`AgentExecutor` / `create_react`）。决策链是**代码里写死的**：

```
输入护栏 → 意图分类（规则，不用 LLM）→ FAQ 检索 → 事实装配 → LLM 叙述 → 输出护栏
```

意图分类与 FAQ 检索**都不依赖 LLM**，因此：

- 未配置 `LLM_BASE_URL` 时，整条链路照跑，只是最后的「叙述」退化为**直接返回 FAQ 条目原文**（`degraded = true`）；
- 断网、LLM 超时、LLM 报错，三种情况走**同一条**降级路径。

### 理由

这与 ADR-0016 决策 2 是同一条纪律的延伸：**规则是无 Spring 上下文的纯函数**——因为「每个阈值的边界都能被毫秒级地反复测试」，而这正是推荐引擎最需要被锁住的东西。

助手的领域极窄（FAQ + 2 类工具数据），自主 Agent 的「多轮自主决策」带来的不确定性，换来的是一个**无法写单测**的行为面。而在 §60「谨慎使用」档里，**可审计性比灵活性重要**。

降级路径与主路径同构（而不是「主路径 + 一个补丁」）还有一层好处：**没有 LLM 也能完整演示**，评审现场不依赖外网、key 与配额。

## 六、决策 5：助手只填草稿，永不自动建单

### 决策

助手从对话里抽取就诊信息后，**只回填前端 `orderDraft` store**，由用户点击「去确认下单」进入既有的下单三步流程提交。

助手**不调用** `POST /api/order`，**不产生任何订单记录**。

### 理由

两个后果：

1. **零垃圾订单**。若助手为了出推荐而先建单，那些 PENDING 订单会出现在**陪诊员大厅**里 —— 机器人意图的单会挤占真实供给，污染陪诊员的工作台。
2. **推荐天然是订单锚定的**。`MatchTarget` 的七个字段（`orderId / regionCode / address / visitTime / longitude / latitude / department`）**全部来自订单**。没有订单就没有科室、没有就诊时间、没有坐标、没有区域码 —— 五维里塌陷四维，排序必然失真。

所以「无订单推荐」不是「实现难度更高」，而是**推荐质量上根本不成立**。这一点在开工时被明确否决（备选方案：新增「无订单推荐」后端端点）。

## 七、决策 6：Python 服务无状态、无鉴权、无数据库连接

### 决策

`ai-service` 是**纯计算 HTTP 服务**：

- **不查库**、**不调 Java**、**不持有任何令牌**；
- 工具数据由 Java 门面**预装**在 payload 里；
- 对话历史由**前端 `sessionStorage`** 保存，随请求带上，后端**不落库**、**不新增表**。

### 理由

- **避免令牌二次流转**：门面把用户令牌透传给 Python，就多了一个令牌可能出现在日志 / 异常栈 / 第三方 SDK 请求里的位置。隐私最小化是本仓库的红线之一，没必要为此开一个口子。
- **Python 侧不需要知道 Java 的地址**，所以它是**可独立部署、可独立单测**的：Python 的单测**不需要起 Java**，Java 的单测**不需要起 Python**。
- **不新增表** → 不动 Flyway 迁移、不动数据字典、不动数据库文档。本仓库的「数据库迁移已冻结」约束（`docs/prd/功能拓展规划.md` §2.1）因此不受影响。

代价：Python 拿不到「实时」数据，只能用门面在这一次请求里装好的快照。对本助手够用——**陪诊员推荐本来就是一次快照**（`MatchingMapper` 每次推荐都现查，但那是 Java 侧的事）。

## 八、被否决的方案

| 方案 | 否决理由 |
|---|---|
| LLM 直接给陪诊员排序 / 改分 | 违反 ADR-0016「不允许出现没有理由的分数」；且 §60 把「陪诊员匹配」列为谨慎使用档，正是因为排序需要可解释 |
| Python 侧另抄一份合规词表 | `ComplianceCheckUtil` javadoc 已明写「两份词表一定会有一份先过期」；失效方式是**静默分叉** |
| 用 LangChain Agent 让 LLM 自主选工具 | 在「谨慎使用」档里引入无法写单测的行为面；决策链必须可审计 |
| Python 回调 Java 做工具调用（真 tool calling） | 令牌需在 Python 侧二次流转；每次问答多一轮网络往返；Python 与 Java 互相耦合，单测要起两个进程 |
| 新增「无订单推荐」后端端点 | `MatchTarget` 七字段全来自订单，无订单时五维塌陷四维，推荐质量不成立 |
| 助手对话直接建单再出推荐 | PENDING 订单会污染陪诊员大厅；等于用机器人意图的单换真实供给 |
| 用向量库（FAISS / Chroma）+ embedding 做 RAG | 领域只有 25–30 条 FAQ，语义检索的收益远小于依赖成本（embedding 模型下载、CI 变慢、评审机器装不上）；关键词 + 2-gram 检索可解释、可单测、零依赖 |
| 每次回答都回调 Java 做合规校验 | 每答一次多一次网络往返；合规词表应当是**共享文件**，不是共享接口 |
| 用 YAML 存 FAQ | 需要追加 `PyYAML` 依赖；JSON 是 Python 标准库直接读的，零依赖。**若将来改 YAML，需先报批依赖** |
| SSE 流式输出 | 收益（少等几秒）不抵复杂度（新增 SSE 通道 + 改前端渲染 + 改 Java 转发）；且 `request.js` 支持按请求覆写 timeout，60s 足够 |

## 九、后果

### 正面

- AI 能力边界**有据可依**（对齐 §60 三档），且新开版本 + 新 ADR，不与 V3.4 的「第一阶段不引入 AI 模型」冲突；
- 助手输出**可溯源**到具体 FAQ 条目或具体后端端点；
- 合规词表**结构上不可能漂移**，且两侧都在启动期 fail-fast；
- 无 LLM / 断网 / 模型报错时**功能完整可用**（降级为 FAQ 原文直出）；
- 推荐结果**完全继承** ADR-0016 的可解释性（`reasons` / `mismatches` / `notes` 三段分别转述），并被单测锁死「不得把『距离没法算』说成『距离近』」；
- 零新增表、零数据库迁移、零令牌在 Python 侧流转。

### 负面 / 代价

- 引入**第二个技术栈**（Python 3.12 + FastAPI + LangChain）与**第二个构建链路**（pytest + venv）。这是本项目最重的一次技术栈扩张，**必须同步更新 `AGENTS.md` §0 技术栈表**，把授权写进项目宪法 —— 否则后来的 agent 会把这项当成违规实现；
- CI 多一个 job（LangChain 依赖树不小，用 `setup-python` 的 pip 缓存缓解）；
- Java 门面成为助手的**单点**：Python 挂了 → 门面兜底 FAQ 原文 → 再兜底才 `10002`；
- FAQ 的时效性靠**人工维护** + 锚点校验脚本，不靠模型。

### 待观察

- FAQ 覆盖是否贴合真实家属提问分布 —— 当前按仓库 docs 推导，未经真实用户验证；
- LLM 叙述质量是否稳定 —— 核心断言不依赖 LLM，LLM 只影响「说法好不好听」，不影响「答案对不对」；
- 限流阈值（每用户每分钟 10 次）是否合适 —— 当前是拍板值，无真实流量数据支撑。
