# 0013. 订单大厅只实现一种推荐序，不做多维排序选择器

## 背景

大厅（`GET /api/order/hall`）是陪诊员「谁先看到谁抢」的入口。
排序键直接决定一个陪诊员**先看到哪一单**，因此它不是一个 UI 细节，而是派单策略。

`docs/prd/功能拓展规划.md` 曾列过四个候选维度：距离优先 / 时间匹配 / 收益优先 / 推荐序。
V3.1 的取舍是：**只实现「推荐序」，其余三个留到 V3.4**。

---

## 决策

大厅**只实现一种排序（推荐序）**，接口形态：

- 路径不变，新增可选参数 `sortBy`；
- `sortBy` 走**白名单**，V3.1 只放行 `RECOMMEND`（大小写不敏感，前后空格忽略）；
- 缺省值取配置项 `nianglin.fulfillment.hall-default-sort`，**配置值同样过白名单**；
- **非法值一律返回 `400`，不静默回落推荐序**；
- 前端不做排序选择器，也不传 `sortBy` —— 只有一个排序项时没有选择器。

推荐序是三级稳定排序：

```
visit_time ASC → 服务区域 / 可服务时段包含式匹配优先 → id ASC
```

---

## 理由

### 为什么只做一种

**一个陪诊员在大厅里做的决定是「接不接这一单」，排序替他决定的是「先看到哪一单」。
在没有可靠距离数据的前提下，四个排序维度给出的其实是四种同样不可信的顺序。**

- **距离优先**：一期明确不做地图导航（合规红线-3）。没有坐标，只能靠陪诊员档案里的
  `serviceArea` 自由文本与医院名做包含式匹配 —— 这是**弱信号**，
  把它做成主排序键，会让「文本里恰好写了这个区」的陪诊员排在真正更近的人前面。
- **时间匹配**：按 `availableTime` 自由文本匹配就诊时段。同样是弱信号，
  且与 `visit_time` 高度共线（早的单本来就在前面），单独排序收益极低。
- **收益优先**：本项目一期**不做在线支付**（合规红线-3），`fee` 只是记账字段。
  按一个「不代表真实到账」的数字排序，等于让陪诊员按错误的前提决定接不接单。

三种维度都「可以排序，但排出来的顺序没有可信依据」。
多做一个选择器，得到的不是更好的派单，而是**四种同样不准的视角**，
以及陪诊员在四者之间反复切换的成本。

### 为什么非法值不静默降级

静默降级（传了不认识的值就退回推荐序）看起来更宽容，实际更糟：
陪诊员会以为自己拿到的是「按距离排」的结果，实际是推荐序，
**拿错误的前提决定接不接单，比直接报错更糟**。
所以非法值一律 `400`，并在消息里说明该维度将在后续版本开放。

配置值同样过白名单：「配置写错」和「参数写错」的后果完全一样 —— 都是拿不到实现的排序键。
若配置绕过校验，一个写错的配置会让所有大厅请求静默失效。

### 为什么排序键白名单放在 Service 而不是 DTO 注解

`@Pattern` 一旦写死在 DTO 上，将来加维度要同时改两处（DTO 正则 + Service 映射），
而映射表是唯一真相。白名单做成 Service 层的一个 `Map<String, String>`，
请求参数与配置项共用同一份判定 —— 一处放行，两处都放行。

---

## 后果

### 收益

- (+) 大厅的排序行为**可解释**：一句话说清「先看早的，再看匹配的，再按 ID 稳定」，
  不存在「为什么这单排这么靠前」的争议；
- (+) 排序键与实现分离：V3.4 加距离维度时，只在白名单里加一项 + 加一条排序分支，
  **不改路径、不改参数名**，前端不需要为新版本做兼容；
- (+) `400` 而不是静默降级，让「拿不到想要的排序」这件事在测试期就暴露，而不是上线后靠反馈。

### 代价

- (-) 陪诊员无法按自己的偏好排序 —— 缓解 = 推荐序已经吸收了「早的单优先」与「区域匹配优先」两条最常用的偏好；
- (-) 三个维度要等到 V3.4 才开放 —— 缓解 = 接口形态已定，后续是纯增量，不影响已上线的调用方。
