---

## 背景

V3.2 要把「订单 / 陪诊执行 / 用药 / 消息」四类事按时间排成一条**老人健康时间线**，
外加一张跨域的**健康概览**。

一个直觉的做法是：建一张 `health_record` 表，把这些事件都归一化写进去，
时间线直接查它。

但这条路有三个问题：

1. **写入面爆炸**。订单状态流转（`OrderTransitionService`）、打卡（`ExecutionService`）、
   用药确认（`MedicationService`）、消息发送（`MessageService`）四处都要写。
   任何一处漏写，时间线就少一条 —— 而「少了」是<b>静默</b>的，看不出来。
2. **与既有真相表重复**。订单状态已经在 `companion_order` + `order_status_log` 里，
   打卡在 `order_checkin`，用药在 `medication_task`。再建一张表等于把同一事实存两遍，
   两遍迟早对不上。
3. **写路径有风险**。往订单流转里插一次额外写入，等于动到 V3.1 刚刚收口的履约逻辑 ——
   而 ADR-0010 刚刚把「状态流转只有一个入口」这件事立成铁律。

---

## 决策

### 1. 零迁移：健康时间线由既有表实时聚合

时间线的四类事件全部来自既有表，**在 Service 层聚合**：

| 事件 | 来源 |
|---|---|
| 订单状态 | `companion_order` 的五个时间戳 + `order_review` |
| 陪诊打卡 | `order_checkin` |
| 用药确认 | `medication_task` |
| 站内信提醒 | `internal_message` |

**不建 `health_record` 表，不加任何字段**（本版 Flyway 零迁移）。

### 2. 聚合入口唯一：`elder_id`

`order_checkin` 与 `internal_message` **都没有老人 ID**，
所以聚合统一以「先取该老人的订单 ID 集合，再让子表用 `IN (...)` 过滤」的方式取数。

**禁止**为每类事件各写一条 JOIN —— 那会让 `companion_order` 被重复扫 N 次。

### 3. 取数有上限，且不静默丢数据

每类事件上限 200 条，超出按时间倒序截断；
订单取数上限 200 单。超出时响应里给出截断标记，而不是假装完整。

### 4. 写路径只读

本版**零写操作**：不改订单状态机、不改用药规则、不新建任何表。
唯一的副作用是「读」。

---

## 将来出现新事实时怎么办

只有出现**无法由既有数据表达的新健康业务事实**时，才考虑持久化
（roadmap 决策 2.1）。届时按 expand–contract 走：

1. **expand**：加可空列 / 新表，既有读写路径零改动；
2. **backfill**：回填历史数据；
3. **contract**：读路径切到新结构，旧结构保留一段过渡期。

> V3.4 的结构化改造（陪诊员坐标 / 区域码 / 可服务时段）就是这套范式，
> 见 `docs/spec/V3.4-matching-spec.md`。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 建 `health_record` 宽表 | 写路径要动四处；与既有真相表重复；漏写是静默的；且要动刚收口的履约逻辑 |
| 建 `elder_timeline_event` 窄表 | 同上，且新增的宽窄之争毫无收益 |
| 允许前端自行拼时间线 | 违反决策 G8「前端统计零自行计算」；且家属端 / 老人端会各拼各的 |
| 为每类事件各写一条 JOIN | `companion_order` 被重复扫 N 次；且口径分散在 SQL 里，改一处漏一处 |

---

## 影响

| 项 | 影响 |
|---|---|
| 数据库 | **零迁移** —— V3.2 不动 Flyway，V6 仍是最新版本 |
| 写路径 | 零改动 —— 订单状态机、用药规则、消息系统都不碰 |
| 性能 | 每次请求若干次带索引的只读查询（`idx_elder_id` / `idx_elder_date_status` / `idx_biz`）；靠取数上限兜住 |
| 缓存 | **不加** —— ADR-0003 已否决统计缓存；家属端「读多写少」确实是它的反例，但推翻已接受的 ADR 必须走新 ADR，不能默默加（见 spec §风险 R-1） |

## 验证

| 判据 | 怎么验 |
|---|---|
| 确实没建表 | `mvn verify` 后 `information_schema` 里无新表；V6 仍是最新迁移版本 |
| 确实没动写路径 | 订单状态机、用药确认、消息发送的既有单测**零修改**全绿 |
| 聚合口径对 | `ElderHealthReadMapperTest`（真库）与 `ElderHealthServiceTest`（真值）双侧锁住 |
| 性能不退化 | 每次请求的子查询全部命中索引（`idx_elder_id` / `idx_elder_date_status` / `idx_biz`） |
