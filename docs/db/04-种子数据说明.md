## 二、边界场景覆盖（答辩演示用）

种子数据刻意制造了下列边界，方便演示系统的健壮性：

| 场景 | 数据表现 | 演示价值 |
|---|---|---|
| 未绑定家属的老人档案 | `elder_profile` 431 / 432：`bind_status='UNBOUND'`，`user_id`、`phone` 均为空 | 家属「认领老人」流程 |
| 已解绑的绑定关系 | V3：`family_elder_relation` id 531 `status='UNBOUND'`，有 `unbind_time` | 解绑后历史订单仍可追溯 |
| 订单被取消（三种成因） | V3：1061 待接单时取消 / 1062 接单后取消 / 1063 管理员强制终止（`arbitrate_flag=1`） | 订单终态 + 管理员纠纷处理 |
| 一星差评 | V3：`order_review` id 30031，`score=1` | 差评 → 投诉 → 违规累计链路 |
| 资质被驳回 | `companion_audit_record` 3 条 `REJECTED`，带驳回原因 | 陪诊员重新提交申请 |
| 健康证过期 | `companion_profile` 2 人 `health_cert_expire < CURDATE()` | 系统自动置为不可接单 |
| 账号已被封禁 | `sys_user` id 230（`elder030`）`status='DISABLED'` | 登录被拦截 + 失败日志落库 |
| 拒单后不再显示 | `order_reject_log` 36 条，订单本身仍为 PENDING | 「拒单不改变订单状态」 |
| 异常打卡 | `order_checkin` 13 条 `is_abnormal=1`，`distance` 远超阈值 | 定位校验与异常告警 |
| 跨零点服药 | `medication_plan` 6 条 `time_points` 含 `00:30` | 跨日任务生成 |
| 长期用药 | `medication_plan` 18 条 `end_date IS NULL` | 无终止日期的计划 |
| 漏服与补记 | `medication_task` 120 条 MISSED，其中 55 条 `was_missed=1` | 漏服提醒与漏服率统计 |

| 匿名评价 | `order_review` 6 条 `is_anonymous=1` | 对外不暴露家属姓名 |
| 超长文本 | 病史 433/500 字、订单备注 268/500 字、用药计划备注 184/200 字、投诉正文 440/1000 字 | 长文本渲染与字段上限 |

## 四、冗余聚合字段的一致性

`companion_profile` 的 `score` / `review_count` / `order_count` / `accept_count`
是**有意冗余**的聚合值（避免列表页实时聚合）。V3 新增订单与评价后已同步更新：

| 陪诊员 | 变化 | 原因 |
|---|---|---|
| 311 徐文斌 | `accept_count` +1 | 订单 1062 被接单（虽后取消，接单数仍计入） |
| 312 孙玉兰 | `accept_count` +1 | 订单 1063 被接单 |
| 313 马晓东 | `accept_count` / `order_count` / `review_count` 各 +1，`score` 4.09 → 4.04 | 订单 1064 完成并收到 1 星评价，按加权平均重算 |

> `score` 的重算按 `(旧均分 × 旧评价数 + 新增评分) / (旧评价数 + 1)`；
> 注意 MySQL 的 `UPDATE` 中后置赋值会读到已更新的值，故脚本里 `score` 写在 `review_count` 之前。

### 为什么 `review_count` 与 `order_review` 的行数对不上

`companion_profile` 的 `review_count` / `order_count` / `accept_count` 表示
该陪诊员的**平台累计值**（含种子数据窗口之前的更早历史），
而 `order_review` 只落了最近 **31 条**评价样本。两者不相等是**有意为之**：

- 若严格按 `order_review` 重算，每个陪诊员只剩 1–2 条评价，
  评分会退化成「1.0 / 3.0 / 5.0」几个离散值，**失去区分度**，
  榜单、评分排序、优质陪诊员筛选这些页面就没法演示；
- 真实系统里累计值本就由**异步任务**随订单完成逐步累加，
  而不是每次从明细表现聚合（这正是该字段冗余存在的原因）。

> 因此 M10 做数据统计时，口径要明确：**陪诊员维度的累计指标读 `companion_profile`，
> 评价明细与舆情分析读 `order_review`**，不要把两者混用。

## 五、敏感数据处理

| 字段 | 处理方式 | 说明 |
|---|---|---|
| `sys_user.password` | BCrypt 哈希 | `$2a$10$` 前缀，不可逆；禁止明文/可逆加密 |
| `elder_profile.id_card` | AES-256-GCM 密文 | 密钥由 `ID_CARD_AES_KEY` 环境变量注入，密钥经 SHA-256 派生 |
| `companion_profile.id_card` | AES-256-GCM 密文 | 同上 |
| `companion_audit_record.id_card` | AES-256-GCM 密文 | 同上 |
| `*.phone` | 明文入库，**接口返回脱敏** | Service 层统一 `138****8888` 处理后返回 VO |
| `*.address` | 明文入库，门牌号打码后返回 | 同上 |

> 加密工具：`backend/src/main/java/org/company/nianglin/util/AesUtil.java`。
> 密钥未配置时使用开发默认值，**生产环境必须通过环境变量覆盖**。
