## 三、四版各自的「难的那一件事」

### V3.3 · 把统计口径从前端搬回后端

`companion/income.vue` 原本循环分页拉全量订单、用 `reduce()` 自算「累计收入 / 已结算 / 未结算」——
这既违反决策 G8（「前端统计零自行计算」），也让「累计」这个语义无法用统计区间表达。

处置：KPI 改吃 `/api/statistics/companion/me/income`，文案「累计收入」→「区间收入」，
页面明示区间；**账单明细列表保留**（那是账单不是统计指标）。
前端单测里加了**静态扫描**（`reduce(` / `.filter(` / `groupBy`），并配 3 条**扫描器自证用例**
防止扫描本身变成恒过的空转。

**顺带修掉一个存量数据缺陷**：`companion_profile.order_count` **运行期无人维护**
（只在建档时置 0），预写 spec 要求「累计完成单数」读它 —— 那会永远返回 0。
改为从 `companion_order` 现算。

### V3.4 · 「距离 20%」今天没有任何数据基础

开工核实：陪诊员的 `service_area` / `available_time` 是**自由文本**、订单侧**无区域字段**、
陪诊员档案**无坐标**。ADR-0013 原文即写着「一期无坐标」。

所以先做**结构化改造**（V7 迁移，expand–contract），再建规则引擎：
- 区域码 `<CITY>_<DISTRICT>` 两级（码相等 1.0 / 同市不同区 0.5 / 跨市 0）
- 可服务时段用**表**不用 JSON 列（时段要参与筛选，必须可索引可 JOIN）
- 自由文本时段用 `LegacySlotParser` **回退解析**（存量陪诊员才有时间维度）
- 映射表由 `gen_region_codes.py` 生成，`--check` **机械核对**迁移里手写的 CASE

五维加权放在 **Java 侧**而不是 SQL 的 `ORDER BY`：Haversine MySQL 没有内置函数、
服务能力要归一化子查询，而「**无坐标 → 记 0 且不推断**」需要一条**分支** ——
SQL 的 CASE 分不出「没数据」与「距离为零」。

> ⚠️ 详见 [ADR-0016](../adr/0016-matching-structured-and-explainable.md)

### V3.5 · 「看到了但处理不了」是最典型的假绿

异常中心**不另建风险判定**，而是直接复用 `AdminService#fulfillmentSummary()` ——
两套判定必然漂移（这正是 V3.2 在用药三桶上踩过的坑）。
同源关系由 `OperationsExceptionParityTest` 锁死。

四张异常卡片的 `linkUrl` 逐个核对过前端路由表，E2E **逐个点开**验证落地页可达。

平台健康度是**六个客观指标**，**不给合成分** ——
禁止「AI 平台健康指数 96」这类无法解释的数。

### V3.6 · 口径登记必须从「人读的表」升级成「机器校验」

V3.2 的指标字典能挡住「代码加了指标没登记」，但挡不住
「**某个端点返回了一堆数字，而这些数字的口径没人登记过**」。

处置：`metrics/endpoints.yml` 声明「哪个端点返回了哪些指标」，
`MetricEndpointContractTest` 做**三条双向校验**（端点必须真实存在 / 指标必须在字典里 /
字典里的端点必须在 yml 里出现）。
配合 `MetricCalculatorRegistry`（「一个 key 只能有一个实现」），把决策 6.2
从**文档约束**变成**结构约束**。

> ⚠️ 详见 [ADR-0017](../adr/0017-metric-endpoint-machine-contract.md)

## 四、跨版本沉淀的机制（这才是这四版最大的产出）

| 机制 | 落点 | 解决的问题 |
|---|---|---|
| **指标字典**（机器面 + 人读面） | `metrics/metric-dictionary.yml` + `docs/spec/metric-dictionary.md` | 「同一指标在不同角色端只有一个口径」 |
| **人读面 ↔ 机器面一致性校验** | `tools/check_metric_dict_parity.py` | 人读面写了 20 条、机器面只有 15 条的漂移（本版实测抓出过一次） |
| **端点↔指标机器面** | `metrics/endpoints.yml` + `MetricEndpointContractTest` | 「某个端点返回的口径没人登记过」 |
| **指标计算器注册表** | `MetricCalculatorRegistry` | 同一指标跨端各写一遍公式 |
| **共享统计区间** | `common/DateRange` + `dto/DateRangeQuery` | 默认 30 天 / 上限 366 天 / 闭区间，各端口径一致 |
| **区域码映射生成器 + 校验** | `backend/sql/tools/gen_region_codes.py` | 手写迁移与可复现生成器之间的漂移 |
| **静态扫描 + 扫描器自证** | `frontend/src/__tests__/matching.test.js` 等 | 「前端零自算」的断言本身不能是恒过的空转 |

## 六、留下的「诚实的已知限制」

| 项 | 说明 |
|---|---|
| 距离维度目前恒为 0 | 陪诊员坐标是 V3.4 新增的列，存量全空。如实反映「现在没有距离数据」，坐标一填即自动生效 |
| `DISTANCE` 排序当前无区分度 | 同上 —— 全部并列后回落到就诊时间升序 |
| `INCOME` 排序仍不做 | 缺真实结算金额口径（决策 D8），错误消息已改成一句人话 |
| 大厅候选集整批加载 | 上限 500，超限记 warn 日志**不静默截断** |
| 存量排班文本解析有限 | `LegacySlotParser` 只认几种明确写法；写得很随意的仍落到「时间维度记 0 + 标注」 |
| 异常中心只做**发现与跳转** | 不做自动决策（决策 5.2 / 5.4） |
