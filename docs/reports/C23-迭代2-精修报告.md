# 「银龄伴诊」——老年人就医陪诊与用药协同管理平台

## 摘要

「银龄伴诊」是一款面向老年群体的就医陪诊与用药协同管理平台，用四个角色（老人、家属、陪诊员、平台管理员）把"陪老人看一次病"这件线下的事拆成可追踪的状态机与可核对的凭证。课程按 17 周排布，交付节点四个：第 4 周分组定题；第 7 周交迭代 1——「系统原型/初稿」，打通"家属下单—陪诊员接单—履约打卡—评价"的最小可用主链（Git v3.0–v3.6）；第 13 周交迭代 2——「精修」，在不推倒 MVP 的前提下把系统做成一条可验收、可审计、可展示的完整产品；第 17 周才是「演示/复盘/终稿」。本报告正是第 13 周的迭代 2 交付稿。迭代 2 覆盖 Git 标签 v3.6 到 v6.0，共 178 次提交、539 个文件变更（新增 56308 行、删除 3240 行），补齐四条线：合规闭环（注销与数据导出、评价公信力裁定）、业务闭环（漏服提醒三级触达、检查准备提醒、就诊小结转用药草稿、结算核对）、智能能力（独立的 Python 助手服务与"检索不到就不乱答"的兜底）、工程完整度（1582 个后端单测、269 个前端单测、196 个助手单测、23 个 Playwright 端到端用例文件共 272 例，另有跨进程 e2e 断言）。团队用一条"需求先写成可执行判据"的工作线，让"做完了"变成"跑一遍就能证明做完了"。

关键词：适老化设计；陪诊服务；用药协同；闭环验收；AI 辅助开发

## 1．团队分工

本项目为 4 人团队、17 周三次迭代交付的课程设计（第 4 周分组定题、第 7 周交 MVP、第 13 周交精修稿、第 17 周演示复盘交终稿）。分工不按"前端/后端"简单二分，而是按**交付责任**划分：每个人对一个可演示、可验收的业务闭环负责，跨端协作在接口文档上对齐而不是在口头约定上对齐。

| 成员 | 主责 | 迭代 2 的增量交付 |
|---|---|---|
| 组长【组长姓名】 | 系统架构、订单与履约域、AI 助手服务、迭代统筹与评审 | 状态机单入口重构、履约风险中心、助手服务独立进程与守卫、21 条 ADR 的维护 |
| 组员 1【组员姓名/学号】 | 前端与适老化交互、桌面/移动双形态适配 | 四个角色工作台、老人模式、订单沟通、评价巡查页、UI 走查与三项定案 |
| 组员 2【组员姓名/学号】 | 用药与健康域、结算与运营域、数据库与迁移 | 漏服三级提醒、检查准备须知、体征记录、结算核对、运营参数可调化 |
| 组员 3【组员姓名/学号】 | 测试与质量、文档体系、演示与答辩材料 | 测试欠账清零、跨进程 e2e、CI 静态门禁、文档同步矩阵 |

协作规则是"三条硬约定 + 一条软约定"：每晚 22:00 群内三句话站会（做了什么/卡在哪/明天做什么）；分支模型固定为 `main`（保护）← `feature/*`，禁止在主干上直接写代码；接口先行，先改 `docs/api/*.md` 再写代码再写前端；软约定是"文档由改动触发"，谁改了接口谁补文档，收尾时按 `docs/agents/doc-sync.md` 的联动矩阵逐条核对。

每周五做一次 30 分钟的合并评审：本周所有 `feature/*` 分支合并到 develop 之前，由非作者本人走查一遍，重点看三件事——有没有硬编码状态字符串、有没有绕过脱敏、有没有新增依赖。这条制度的实际作用是"把规范从纸面拉到评审桌上"：每个人都会犯错，但四个人不会同时在同一处犯错。第 13 周交付时统计，合并评审拦下的问题中，约六成是"违反规范但功能正常"的隐性风险，这类问题恰恰是最难靠测试发现的。

## 2．策划的过程

### 2.1 调研得到的三个事实

课程开始的两周，团队做了一轮小样本调研：访谈 6 位 60 岁以上老人（其中 4 位独居或空巢）、5 位 30–45 岁的子女、2 位医院周边陪诊从业者，并在社区医院门口做了半天的观察。调研没有得出"老人需要一个大而全的健康 App"这种结论，反而收敛到三个很具体的事实：

1. **老人不缺信息，缺"被代办"**。受访老人大多记不清药名与吃法，也分不清科室方位；但他们共同的诉求是"最好啥也不用动"。这说明产品的主入口不能是老人，而应该是家属与陪诊员——老人端只承担"看"和"确认"。
2. **家属的痛点不是"不知道结果"，而是"过程不可见"**。子女最焦虑的时刻是就诊当天：挂上号没有、人到了没有、医生说了什么。他们要的是过程节点，而不是一张事后总结。
3. **陪诊行业的痛点是没有凭证**。两位从业者都提到接单靠微信群、结算靠转账、纠纷靠"讲道理"。没有状态记录、没有评价、没有可申诉的仲裁，就没有办法把这门生意正规化。

### 2.2 为什么决定做这件事

三个事实指向同一个缺口：**老年人就医这条链上，缺的不是"服务"，而是"能被记录和核对的过程"**。这正是软件工程能提供价值的地方——把线下的口头承诺变成有时间戳的状态流转、有凭证的费用明细、有规则的评价与仲裁。因此项目定位被压成一句话：让不会用手机的老人，也能有人陪着把病看好。

同时团队明确了一条边界：**不做诊断、不开药方、不碰在线支付**。这不是能力不足的妥协，而是产品能落地的前提——一旦越界成"医疗建议"或"资金通道"，合规成本会直接压死一个课程项目。

### 2.3 怎么做、难点在哪

整体做法是"四角色 × 一条状态机"：订单从"待接单"到"已评价"共 10 个状态，每一次流转都写时间线；家属看到的是过程，陪诊员看到的是任务，管理员看到的是风险。

三个真正的难点：

- **难点一：老人不会用，但老人必须参与**。解法是"老人账号默认只读"——所有写操作由家属代做，服务端强校验（老人令牌调用任何写接口直接 403），老人端只保留"看健康记录、看用药计划、看消息"三件事，字号 ≥18px、可点区域 ≥48px、核心流程 ≤3 次点击。
- **难点二：不能做支付，但钱必须说清楚**。解法是"线上记账 + 线下结算"：费用按明细录入（挂号/检查/药费/车费分组），平台只核对、不代收，结算由管理员核定并留审计日志。
- **难点三：不能做地图导航，但位置必须可信**。解法是"文字地址 + 签到坐标"：下单填结构化地址，履约时打卡记录经纬度，不做路径规划。

### 2.4 别人怎么尝试、我们怎么绕开

调研中看到两类现成做法：一类是"大平台陪诊频道"，功能齐全但流程重、抽成高，个体陪诊员用不起；另一类是"微信群接单"，零成本但没有凭证。团队的选择是取两者中间：**用一套轻量状态机 + 数据契约把微信群的行为规范化**，不追求平台规模，先把"一次陪诊的完整证据链"做扎实。

同一思路也解释了后续两个决策：一期不做 IM，用站内信；二期放开聊天时也只放开"按订单的双向沟通"，不做自由加好友——因为群聊的价值是"围绕这一单说话"，而不是社交。

### 2.5 风险与预案：先想清楚"哪里会崩"

策划阶段团队列了一张风险表，每条都配了触发信号与预案。事后回看，这张表是本项目少走弯路的直接原因：

| 风险 | 触发信号 | 预案（实际采用） |
|---|---|---|
| 范围失控（功能越加越多） | 每周新增需求超过 5 条 | 需求先进"待评估池"，只有能写出一条可执行判据的才进入本轮迭代 |
| 合规越界（文案被理解成医嘱） | 评审或自测发现剂量建议、病因推断一类的表述 | 建立违禁词扫描 + 文件级白名单，把"防漏"变成 CI 门禁 |
| 数据被测试写脏 | e2e 跑完种子数据出现新行 | 夹具自建自清 + 按最大 ID 水位比对 + 白名单行逐列一致 |
| 联调互相等待 | 前端等接口、后端等页面 | 接口先行：先定 `docs/api/*.md` 与错误码，前端用 Mock 先跑通 |
| 演示当天环境起不来 | 端口被占、Redis 未启动 | 一键起停脚本 + 身份闸门 10 项，先验身份再演示 |

## 3．需求分析的过程

### 3.1 从访谈记录到 PRD

需求分析的产出不是一份"功能清单"，而是一份**可以被反复对照的产品宪法**。团队的做法是：访谈记录 → 角色画像 → 产品原则（横切约束）→ 功能需求 → 验收标准，逐层收窄。

其中"产品原则"这一章被单独命名为**产品宪法**，因为它承担一个特殊职责：后面所有功能描述遇到边界时都回到这里判定，不再重复声明。它写死了三件事：适老化底线（字号、触控区、对比度、点击次数）、三条合规红线（不做诊断、隐私最小化、一期不做支付/导航/自由 IM）、老人账号默认只读。这个设计的收益在迭代 2 体现得非常明显：新增的每一个功能（漏服提醒、检查准备、智能助手）都不需要重新讨论"能不能给出一句剂量建议"，因为答案在宪法里。

需要说明的是这轮调研的局限：样本是便利抽样（熟人介绍 + 社区门口偶遇），不是概率抽样；访谈以半结构化问题为主，没有做量表；观察只有一个半天。因此团队只把三条结论当作"设计假设"而不是"市场结论"，并在后续每个迭代用可用性走查去验证假设是否成立，而不是把访谈原话当需求直接排期。

### 3.2 PRD 锁版本，而不是持续漂移

4 人团队最容易出的事故是"文档永远比代码旧"。团队用 ADR-0006 定了一条规则：PRD 只在三个竞讲节点锁版本（W7 / W13 / W17），版本号一旦锁定就冻结，后续变更走"新增章节 + 变更记录"，不回头改已锁版本。迭代 1 期间依次产出 V3.1 履约保障中心、V3.2 老人健康协同中心、V3.3 陪诊员工作台、V3.4 智能调度、V3.5 运营驾驶舱、V3.6 数据闭环六份增量 PRD；迭代 2 期间产出 V3.7 家属智能助手、V4.0 闭环与工程完整度、V5.0 运营与结算三版增量 PRD，以及 PRD-E4 评价公信力，产品版本与 Git 标签的对应关系是 v4.0↔V3.7、v5.0↔V4.0、v6.0↔V5.0。

### 3.3 信息架构：角色与形态正交

信息架构没有按"页面树"画，而按**角色 × 形态**两个维度切分（ADR-0007 / ADR-0008）：四个角色（老人/家属/陪诊员/管理员）各有自己的主页与业务页；两种形态（移动 / 桌面）由同一个路由表按宽度切换——移动端是主角，桌面端只对"必须在大屏上完成"的页面（后台管理、工作台）做适配，而"订单执行"这类依赖拍照与实时定位的页面**刻意不做桌面适配**，在桌面上直接提示"请在手机上使用"。这条"形态与角色正交"的规则后来省掉了大量重复开发：一个页面只写一次，两种形态各取所需。

### 3.4 交互原型与统一认知

原型阶段团队只做了三件事：画出四条主链的页面流（下单、履约、用药、后台审核）、标注每个页面的"空态/错误态/无权限态"、把老人端的所有文案改成短句。第三件事后来被证明最有价值——它逼着团队在写代码前就想清楚"这句话老人能不能读懂"，而这一步在迭代 2 直接沉淀成 `docs/agents/interaction-checklist.md` 里的陷阱清单（多入口口径收敛、单向操作不给反向选项、Boolean 筛选的"不限"怎么传等）。

### 3.5 用户故事写成验收断言

本项目的需求分析有一个刻意的做法：**用户故事的最后一行必须是可执行判据**。以"E4 评价公信力闭环"为例，PRD §13.3 把"家属信任评价"这个模糊目标写成五条断言：

1. 陪诊员回复评价后，家属端 3 秒内收到站内信；
2. 管理员裁定"无效"后，接口返回的平均分与手工 SQL 逐字一致；
3. 裁定后公开列表减一，家属订单详情带"已裁定无效"标注；
4. 陪诊员 A 用 B 的评价 ID 回复，业务码必须是 3004；
5. 全站扫描违禁表述为空。

这五条后来直接变成了 `tools/e2e/e2e_review_appeal.py` 的五段判据（第 5 条因词表本体含违禁词，改为"限定扫描面 + 文件级白名单"，口径差异在 PRD 里同步补注）。需求能被机器验证，是迭代 2 与迭代 1 最大的方法论差别。

### 3.6 权限与访问矩阵：把"谁能做什么"写成表

需求分析里最容易被糊过去的是权限。团队的做法是先画一张访问矩阵，再写接口：行是接口（139 个），列是角色（ELDER / FAMILY / COMPANION / ADMIN）+ 匿名，格子里填"允许 / 拒绝 / 只读"。矩阵定稿后，后端由 `SecurityConfig` 与注解共同实现，前端由路由 `meta.roles` 实现，测试则由一个专门的 spec 逐格验证。三处同源，才不会有"前端藏了按钮但接口没拦"的漏洞。

矩阵里有两类特殊情况被单独记录：一是"老人账号写操作一律 403"（连家属代操作也不行，必须换令牌）；二是"订单详情返回全名"的唯一豁免——它由 `OrderService#requireInvolved` 把守，非相关方一律返回业务码 3004，也就是"能打开详情的只有该看到的人"。

### 3.7 非功能需求

课程项目容易只写功能需求，本项目把非功能需求也写成了数字：

| 维度 | 指标 | 落地方式 |
|---|---|---|
| 适老化 | 基线字号 ≥18px、可点区域 ≥48px、对比度 ≥4.5:1 | 设计令牌 + 老人模式样式覆盖 |
| 可用性 | 核心流程 ≤3 次点击 | 老人端只保留三条链路：看健康、看用药、看消息 |
| 性能 | 列表接口 P95 < 300ms（课程量级） | 索引设计 + Redis 缓存热点统计 |
| 安全 | 密码 BCrypt、令牌 7 天有效、验证码一次性消费 | Spring Security + Redis 验证码 + 令牌黑名单 |
| 可观测 | 每次管理动作留审计日志 | `admin_oper_log` 统一写入 |

## 4．设计的过程

### 4.1 技术选型

| 层次 | 选型 | 理由 | 放弃的方案 |
|---|---|---|---|
| 前端 | Vue 3.5 + Vite 6 + Element Plus 2.9 + Pinia + Vue Router 4 + Axios + Sass | 组件库成熟、中文文档完整，适老化定制（字号/触控）成本低 | React（团队上手成本高）、原生小程序（无法一套代码覆盖移动+桌面） |
| 后端 | Spring Boot 3.3.5 + JDK 21 + MyBatis-Plus 3.5.7 + Spring Security + JJWT 0.12.6 | 事务与权限是核心诉求；MyBatis-Plus 的 `@TableLogic`/`@Version` 直接覆盖软删与乐观锁 | 微服务拆分（4 人 17 周，运维成本大于收益） |
| 数据 | MySQL 8.0 + Redis + Flyway | 关系模型契合订单状态机；Redis 承担验证码、限流、分布式锁与缓存；Flyway 保证"迁移历史与实物一致" | 手工建库（会造成"脚本说有、库里有/没有"两套真相） |
| 文档 | Knife4j + EasyExcel | 接口文档随代码生成；导出报表零依赖 | 手写 Word 接口文档 |
| 助手 | Python 3.12 + FastAPI + LangChain（独立进程，仅监听 127.0.0.1） | 助手是"第二个技术栈"，与 Java 进程解耦：模型/依赖出问题不影响主链 | 把 LLM 调用塞进 Java（依赖不可控、故障会拖垮主服务） |

### 4.2 架构：模块化单体的理由

系统分三层：前端（四角色两形态，一套路由）→ 后端（模块化单体，按域分包：auth / user / order / execution / medication / review / message / admin / statistics / chat / assistant）→ 数据层（MySQL + Redis）。助手服务是旁路进程，后端只通过 HTTP 调用它，且**调用失败会自动回落本地 FAQ**。

不做微服务是显式决策：订单、执行、用药三个域共享同一套事务边界（"就诊小结转用药草稿"必须在一个事务里），拆成服务后就要引入分布式事务或补偿，收益远小于成本。模块化单体 + 包边界约束（controller 不写业务、entity 不当 VO 返回）已经能满足 4 人协作。

### 4.3 三个关键设计决策

项目在迭代 2 期间沉淀了 21 条 ADR。挑三条最有代表性的说明设计过程：

**决策一：订单状态流转单入口（ADR-0010）**。所有状态变更必须经过 `OrderStatus.canTransitTo(...)` 判定，并在同一事务内写 `order_status_log`。收益是"能不能从服务中直接跳到已完成"这种问题只需要回答一次；代价是新增状态必须同步改枚举与测试，所以团队把 `OrderStatusTest` 当成"状态机的第二份文档"。

**决策二：履约风险不塞进订单状态（ADR-0012）**。项目早期曾想把"超时未接单"做成订单状态，评审时否决了：风险是**派生指标**，随时会消失，而订单状态是**业务事实**，不能被时间维度污染。最终做法是独立的"履约风险中心"，按等待时长实时计算正常/等待较长/风险较高/需人工介入四档，管理员在后台处理，订单状态保持不变。

**决策三：助手边界与推荐守卫（ADR-0020）**。助手只答"平台服务规则"（费用怎么算、怎么取消、检查前要注意什么），不答诊疗问题；回答必须带来源锚点，检索不到就明说"没查到"，不生成推测内容。检查准备须知这类"可能被理解成医嘱"的内容**完全不由模型生成**，而是走 `sys_dict` 静态字典 + FAQ 锚点门禁（`tools/check_faq_anchors.py` 校验每条 FAQ 的 anchor 指向真实文档段落）。

### 4.4 数据设计

数据库共 29 张表，按域分组：用户与资质（user / elder_profile / companion_profile）、订单与履约（orders / order_status_log / order_fee_item / service_checkin）、用药（medication_plan / medication_task / medication_log）、评价与纠纷（order_review / complaint）、消息与沟通（message / chat_message）、运营（sys_dict / admin_oper_log / sys_login_log）。

三条数据层约定贯穿全程：所有业务表带 `deleted` 软删与 `create_time`；状态类字段一律用字符串枚举而不是魔法数字；迁移脚本只允许前进（新增 `V*.sql`），已执行的脚本不改——"迁移冻结"这条约定在迭代 2 救过一次：某次需要给订单表加区域码，正确做法是新加一版迁移做 backfill，而不是回头改 V1。

### 4.5 前端设计：设计令牌与"一套代码两副面孔"

前端没有为老人端单独写一套页面，而是用**编译期令牌 + 运行期类名**做形态切换：`variables.scss` 里定义字号、间距、圆角、中性色（`--nl-*` 变量），老人模式通过 `<html class="elderly-mode">` 一次性覆盖字号与触控尺寸。收益是组件本身不需要知道"现在是给谁看的"，只需遵守令牌。

桌面形态的取舍同样是显式的：`NlDesktopShell` 只在宽度达到阈值时接管布局，并且只对"必须在大屏完成"的页面开放宽档；聊天室这种三栏页面单独申请更宽的档位。所有"仅移动端"的页面（订单执行、个人中心、协议页）在桌面上统一渲染为"请在手机上使用"的提示卡片。这条规则避免了"为了桌面端再写一套执行页"的浪费，也让产品的移动优先定位不被桌面端悄悄稀释。

### 4.6 安全设计：默认拒绝

安全上没有堆功能，只做四件事并把它们做实：其一，认证走 JWT + 验证码，令牌进 Redis 黑名单才可登出，验证码一次性消费、5 分钟过期；其二，授权走"路径规则 + 注解"双层，`/api/admin/**` 在配置层强制 `hasRole(ADMIN)`，业务层再用 `requireInvolved` 校验"是不是这一单的相关方"；其三，隐私走"先脱敏再拼接"，日志层禁止打印身份证号与完整手机号；其四，越权统一返回**业务码 3004 而不是 HTTP 500**，让调用方能区分"没权限"与"系统坏了"。

一个反面例子说明了"默认拒绝"的价值：早期有一个查询接口为了省事把 `orderId` 直接拼进 SQL 的 `where` 条件，评审时被拦下，改为参数绑定 + 归属校验。这类问题单测很难发现，只能靠代码评审与规范条款拦住，所以它被写进了 Do/Don't 底线。


## 5．开发的过程

### 5.1 AI 开发环境与工具分工

团队的开发方式是"人定规则、AI 写实现、门禁做裁判"。工具层分三块：

- **编码工具**：Claude Code / Cursor 等支持仓库上下文与多文件编辑的助手，承担"按规范补全模块、补测试、补文档"；
- **规范层**：仓库根目录的 `AGENTS.md` 被当作**机读版项目宪法**——技术栈不可改、包名固定、三条红线、目录归属、Do/Don't 底线、验收清单。AI 每次开工先读它，避免"自由发挥"；
- **裁判层**：CI 与本地同一套门禁（后端 `mvn verify`、前端 `lint:check` + `vitest` + `build`、助手 `pytest`、密钥体检、指标字典双面一致性、错误码双向一致）。

这三个层次的关系可以概括为：**规范给 AI 划边界，门禁替人做验收**。人只负责两类判断——语义是否等价、体验是否可接受。

团队的口径是：AI 负责"生成候选"，人负责"确认判据"。写代码前的最后一步永远是把任务的完成条件写成人能复述的一句话（例如"这个接口在越权时必须返回 3004"），AI 产出后先对着这句话验一遍，再进门禁。这个习惯看起来低效，实际减少了大量返工——返工最常见的原因不是 AI 写错，而是人没想清楚。

关于使用比例，团队没有做精确统计，但从代码评审的观察看：模板化程度高的部分（DTO/VO/Mapper/测试骨架、文档同步）AI 产出占比最高；涉及业务语义的部分（状态机边界、脱敏策略、指标口径）几乎都要人改一遍才可用。这个分布本身就是结论：**AI 缩短的是"从想法到第一版"的距离，不缩短"从第一版到可交付"的距离**。


### 5.2 prompt 交互的真实过程（四个案例）

报告里最容易写成"我们用了 AI，效率很高"这种空话，所以这里给四个真实案例，每个都写清"初始 prompt → 产出问题 → 修正 → 定案"。

**案例一：状态流转不能随手改字符串**

初始 prompt 是"给订单加一个'催单'动作"。AI 的第一版直接在 Service 里写 `order.setStatus("PENDING")` 并更新。问题很明显：绕过了状态机，等于给后面所有流转开了后门。修正 prompt 改成："任何状态变更必须调用 `OrderStatus.canTransitTo`，并在同一事务写 `order_status_log`；同时补一个能证明非法流转被拒的测试"。定案后，"催单"被重新定义为**不改变订单状态**的独立动作（写催促次数 + 推送），状态机反而更干净。

由此沉淀出一条规范：**AI 产出里出现硬编码状态字符串，一律打回**。这条后来进了 Do/Don't 底线。

**案例二：脱敏必须先于拼接**

初始 prompt 是"列表里手机号打码"。AI 的实现是先把姓名、手机号拼成一句"张德海 138****8888"，再对整串做隐藏。问题在于拼接后的字符串里字段边界丢失，二次隐藏会切错位置。修正 prompt 明确写"先调 `MaskUtil` 再拼字符串，禁止先拼后脱敏，禁止用工具类的通用 hide 代替业务脱敏"。这个修正还引出一个更深的讨论：订单详情页到底要不要显示全名？最终形成了项目里唯一一个有书面豁免的例外——**列表脱敏、详情全显**，并且要求三处一起改（VO 的 `ofDetail` 注释、Controller 的接口契约描述、规范里的豁免说明），避免后来者把它当成 bug"修"掉。

**案例三：三态筛选不能退化成两态**

初始 prompt 是"评价巡查页加一个有效性筛选"。AI 给的是 Boolean（true/false），漏掉了"不限"。这类缺陷不会报错，但会让管理员永远看不到"全部"。修正后统一了口径：`isValid` 三态（不传=全部 / true=有效 / false=已裁定无效），并把这条写进 `interaction-checklist.md` 的新陷阱条目——"Boolean 筛选的'不限'怎么传"。定案的判断依据不是"AI 写错了"，而是"这个错误会重复发生，所以要沉淀成规则"。

**案例四：助手不要说它不确定的话**

初始 prompt 是"让助手回答检查前要注意什么"。AI 的第一版让模型直接生成"空腹 8 小时、前一天清淡饮食"这类内容。这在产品宪法上是不允许的：禁食时长属于医疗准备要求，模型生成等于医疗建议。修正后把这条能力拆成两半：**内容侧**走 `sys_dict` 静态字典（逐条带来源与免责声明），**对话侧**只做检索与转述，检索不到就说"没查到，请以就诊医院要求为准"。定案结果是 ADR-0020，并配套了一个门禁脚本校验 FAQ 锚点是否指向真实文档。

### 5.3 判断"什么交给 AI、什么必须人拍板"

团队沿用了仓库里 `docs/agents/daily-ai-workflow.md` 的三条判据：**规则有真源、结果可机器验证、动作可逆**——三条同时成立才整段交给 AI。落到实际：

- 可以交：补测试、按接口文档补实现、文档影响面对账、门禁红点定位、按清单做 UI 走查；
- 人来定：文案与交互手感、某个失败是否可接受为"已知"、任何对外可见或不可逆的动作（提交、推送、发布、删数据）。

这条判据直接决定了工作流的形状：AI 负责"把活干到一键可执行"，人负责"按下那个按钮"。

### 5.5 迭代 2 期间因 prompt 调整而改的决策

有两个例子说明"改 prompt 其实是改设计"：

其一，要求 AI"给每个新接口补 Knife4j 注解"时发现注解里写的权限描述与 `SecurityConfig` 不一致。追下去发现是接口文档与代码两套口径在漂移，于是加了一条静态门禁：错误码必须在 `ResultCode` 与接口文档双向一致。这不是 AI 的问题，而是"让 AI 批量改文档"把原本隐藏的不一致放大了——**放大问题是 AI 的副作用，修掉问题是人的责任**。

其二，要求 AI"把重复的评分口径抽成一处"时，它顺手把"未评价订单的评分兜底"也合并了，导致指标的"有效评价均分"与"累计评分"混算。修正 prompt 明确了两个口径的边界（一个只算 `is_valid=1`，一个算历史累计），并要求在指标字典里各写一行。结论：**涉及指标的合并，必须先在指标字典里确认口径，再让 AI 动代码**。

### 5.6 迭代 2 的工程基建轮

功能之外，迭代 2 花了两周做"看不见的活"，这部分最容易被课程报告略过，但它决定了后面九项能力能不能安全落地。

第一是**门禁统一**。此前本地与 CI 的检查集合不一致，本地绿、CI 红的情况反复出现。这一轮把两边的命令对齐成同一套，并把静态检查从 workflow 里搬进独立脚本、统一到一个入口（`tools/ai_flow/gate_check.py`，避免"抄两份必然漂移"）：

- `--only secrets`：密钥体检五条（明文口令、真实手机号、身份证、私钥、`.env` 入库）；
- `--only error-codes`：`ResultCode` 与接口文档的错误码双向一致；
- `--only metric-dict`：指标字典"人读面 ↔ 机器面"一致性；
- `--only faq`：FAQ 锚点指向真实文档段落，且不含违禁表述；
- `--only page-codes`：`routes.js` 的 `meta.code` 与设计文档页面表双向一致；
- `--only md`：文档围栏成对、引用路径存在。

坏字符扫描单独成一个脚本（`tools/scan_bad_chars.py`），命中即失败。本地一键全跑是 `tools\verify_all.ps1`，第一步就是同一份 `gate_check.py`。

第二是**文档唯一真源**。此前同一个版本号在 CHANGELOG 与 Git 标签之间有 off-by-one，导致"v4.0 到底是 V3.7 还是 V4.0"这种问题反复被问。这一轮建立了映射表并写进规范：Git 标签是代码快照锚点，CHANGELOG 是产品版本口径，引用数字时必须注明是哪一种。同时做了一次文档路径对账，清掉 10 处悬空引用，并把校验从"抽样"改成"全量"。

第三是**AI 工作流工具化**。把高频重复劳动收敛成四个环节（文档同步、门禁定位、提交准备、项目切换），每个环节都写清"何时触发、产出什么、判据是什么"，并配套脚本。这件事的意义在报告里值得单独写一句：**它把"用 AI"从个人技巧变成了团队可复用的流程**。


## 6．测试的过程

### 6.1 为什么这套测试能验证团队的设计

迭代 1 的测试是"围着功能转"：每个接口有单测，每个页面有冒烟。迭代 2 改成"围着验收标准转"，测试金字塔的四层各有明确职责：

| 层 | 规模 | 职责 |
|---|---|---|
| 后端单测（JUnit 5） | 1582 例 | 状态机、权限矩阵、脱敏、事务回滚、并发（乐观锁）——不启容器的纯逻辑与切片测试为主 |
| 前端单测（Vitest） | 27 文件 / 269 例 | 组件行为与交互陷阱（空态、重复提交、三态筛选、单向操作） |
| 端到端（Playwright） | 23 文件 / 272 例 | 四角色真实登录、真实接口，覆盖移动/桌面双形态与访问矩阵 |
| 跨进程 e2e（Python） | 5 条断言 + 身份闸门 10 项 | 真 HTTP + 真 MySQL + 真 Redis：推送时延、评分一致性、越权业务码 |

一个具体例子说明"为什么这些功能能验证设想"：PRD 说"家属信任评价"。如果只写一条 `ReviewServiceTest`，测的是"回复能存进数据库"，与"家属能不能及时看到"毫无关系。跨进程 e2e 的做法是：真实下单 → 真实接单 → 真实完成 → 真实评价 → 陪诊员回复 → **家属令牌轮询站内信**，判据是"命中 bizId=该订单的那条且耗时 ≤3 秒"，实测 0.04 秒。这条断言才真正证明了产品设想。

### 6.2 测试欠账清零：一次"不面向用户"的迭代

迭代 2 的第一件事不是加功能，而是补测试欠账（V4.0 的 P0-3）。原因是团队在一次重构中发现两个"假绿"：一个定时任务的测试用了 Mock 的锁，所以并发重复发送的问题永远测不出来；一个前端页面的测试只断言了"没有报错"，所以按钮点了没反应也算通过。欠账清单被写进 `docs/agents/BUG_LIST.md`，逐条给了"根因—修法—回归判据"。这件事的直接收益是随后 9 项新能力（注销、导出、提醒、贯通、结算、体征、参数、找回密码、站外提醒）的改造没有出现一次"改完不知道坏了没有"。

补欠账排在第一位，是团队对"顺序"的一次判断：测试短板不补，新能力每加一个都会在旧债上叠新债，最后连"哪里坏了"都定位不到；补完之后再加功能，每个功能都自带一条可回归的判据，返工成本反而更低。代价是这两周从功能视角看是"零产出"，这也是课程项目里最容易被动摇的决策——评审时唯一能拿出来的证据只有测试数量与"假绿"清单，看不到新页面。团队愿意承担这个代价，是因为验收那天要回答的问题不是"做了多少功能"，而是"凭什么说它能用"。

这条经验后来固化成一句工作约定：**新能力上线前，先补它将要复用的那一层测试**。例如站外提醒复用消息推送通道，就先给通道补"重复投递只落一条"的断言，再写提醒任务本身。

### 6.3 为什么系统是可行、完整的

三个证据：

1. **基线对账**：种子数据入库后校验"成对性"——例如 `REVIEWED` 订单数与 `order_review` 行数必须相等（当前 31 == 31），e2e 跑完还要按"最大 ID 水位 + 白名单行逐列比对"确认数据回到基线。这条保证"测试不是靠脏数据碰巧通过的"。
2. **压力测试**：对订单大厅与站内信推送做了并发压测（`docs/reports/pressure-test-m4-accept.md`、`pressure-test-m5-m6.md`），确认热点接口在课程验收量级下无堆积。
3. **覆盖矩阵**：四个角色 × 六条主链（下单、履约、用药、评价、消息、后台审核）在 e2e 里都有对应 spec，访问矩阵单独一个 spec 专门测"越权必被拒"（业务码 3004 而不是 HTTP 500）。

关于"是否完整"，团队的口径是保守的：**已实现的能力都有判据，没实现的能力都在文档里显式标注为"未交付"**（例如 Docker 部署与在线支付，前者因本机无 Docker 未验证而不交付，后者是产品红线）。这比"什么都写已完成"更经得起验收。

### 6.4 真实用户反馈

课程周期内没有条件做真实老年用户的长期可用性测试，团队做了两件替代的事：一是请 3 位非团队同学按"老人模式"完成一次下单与用药确认，记录卡点（主要卡在"下一步"按钮位置与日期选择器），据此调整了老人端布局；二是做了 102 张页面的 UI 走查（Playwright 批量访问 + 自动采集指标 + 人工看截图），把问题归为三类并定案（N1/N2/N3）。团队不把这两件事当成"用户研究"，报告里也不虚构用户证言——**没有真实反馈，就如实写没有**。

### 6.5 缺陷管理：每个缺陷都要留下"为什么没测出来"

团队维护了一份缺陷清单（`docs/agents/BUG_LIST.md`），每条记录四栏：现象、根因、修法、**回归判据**。第三栏之外，团队额外要求写第四栏——"为什么原有的测试没发现它"。这一栏逼出了几条测试设计上的改进：接单超卖是并发问题，原来的测试串行执行，所以永远绿；定时任务重复发送是"Mock 掉了锁"，所以永远看不出重复；前端按钮点了没反应是断言太弱，只断言"没报错"。

迭代 2 联调阶段出现过三个跨端缺陷，都属"任一单测都发现不了"的类型：一是前端把"已取消"订单也归到了"进行中"分组，因为状态映射表前端自己维护了一份；二是家属端未读数在切换角色后不刷新，因为未读数缓存按用户维度而非角色维度；三是管理员裁定评价后公开列表没有实时减一，因为列表接口多了一次不必要的缓存。三个问题的共同修法都是"把状态/口径收归后端统一计算，前端只做展示"——这条也顺手写进了前端的交互陷阱清单。

从迭代 1 到迭代 2，产品没有换赛道，也没有推倒重来：它把一条能演示的主链，做成了能验收、能审计、能展示的完整产品。四个变化最值得记录：一是**过程被记录**（订单从文字状态变成 8 个可核对的时间点）；二是**责任被留痕**（裁定、结算、审核都写审计日志，且不可撤销）；三是**边界被写死**（三条红线从口头约定变成文案、门禁与架构决策）；四是**验证被自动化**（验收标准从"演示一遍"变成"跑一遍"）。

这份稿子交在第 13 周，第 17 周还有一次演示与复盘。团队给迭代 3 定的原则是**不再扩功能**，只做三件事：把验收判据整理成一份能在现场按顺序跑完的清单、把 21 条 ADR 里真正起作用的几条讲成一个连贯的设计故事、以及把这一轮留下的已知短板写成"如果还有时间会怎么做"，而不是临时补功能去遮掩。

如果继续迭代，团队认为优先级最高的是"把区域维度与调度做实"（当前区域码已在新数据写入时解析，但仍缺区域级的运力视图）与"把助手的知识来源从平台规则扩展到社区医院的公开就诊须知"——前提仍然是那条宪法：不做诊断，不开药方。
