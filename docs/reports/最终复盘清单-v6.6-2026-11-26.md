## §2 判据与误报剔除台账

### 2.1 P 轨判据

**P0 必须同时满足四条**：
① 有真实可达入口（前端有按钮，或接口文档对目标角色有承诺）；
② 后果属于五类硬后果之一：算错钱 / 状态机错乱 / 越权读或写 / 触碰「不做诊断·隐私最小化」红线 / 不可恢复的数据丢失；
③ **上游约束链逐条排除后仍无兜底** —— 必须逐个排除：唯一键与 CHECK、`@Version` 乐观锁、状态机前置校验、事务隔离级、方法级鉴权（如 `requireInvolved`）；
④ 修复成本 ≤ 1 人日（超过则降 P1 并标注"架构级"）。

**五条排除项（命中即不得标 P0）**：
- 需要 DBA 手工 SQL 才可达；
- 已有上游锁或唯一键挡住（→ 最多算"约束缺失"P2）；
- 纯文档数字错误（→ 走 D 轨）；
- 有 ADR / AGENTS 明文记录的既定决策（→ 走 §8）；
- 只是"理论上 TOCTOU"但实际没有并发写入口。

**P1 / P2 / P3**：P1 = 功能断或主流程不可用，或风险仅在特定前置条件（并发、多角色、软删后重建）下成立；P2 = 有替代路径的体验或一致性问题、缺约束但无可达触发、可维护性债；P3 = 命名、注释、配置耦合、IDE 级告警。

### 2.2 D 轨判据（为什么不并入 P 序列）

D 类条数是 P 类的近一半，而修复成本是"改数字"。若共用 P0 序列，§1 摘要会被 5 条漂移淹没，
读者无法判断"这项目到底能不能用"。因此两轨分开计数、不换算、不混排。

- **D0**：会让验收/答辩结论直接出错的数字（表数、接口份数、FAQ 条数、变更记录断档、生成物写"0 行"）。
- **D1**：会让下一个开发者做出错误决策的口径残缺（豁免范围只登记一半、CI 里硬编码测试数、模块编号三处互斥）。
- **D2**：局部过期注释、历史快照未标基线。

### 2.3 五类定义

| 类别 | 判据 |
|---|---|
| 功能缺失 | 需求文档承诺过、后端已实现或产品上应有，但用户走不到 |
| 逻辑缺陷 | 代码与既定规则/注释自述不一致；同一口径存在两处实现 |
| 边界异常 | 极端输入、并发、时序、软删后重建等非主路径下的行为不正确 |
| 交互问题 | 用户可感知的文案、状态、反馈缺失或自相矛盾 |
| 安全漏洞 | 越权、脱敏、凭据、信息暴露 |

这一节是本清单可信度的关键。以下 4 条在探索阶段都曾作为"疑似缺陷"被提出，经读代码推翻，**不得再写进任何后续清单**：

### 2.5 门禁盲区说明

6 个静态门禁本次全部 PASS（密钥体检、指标字典人读面↔机器面、FAQ 锚点、坏字符、错误码双向一致、md 结构与路径）。
但"门禁绿"只证明**被断言的那句话成立**，不证明风险不存在。已定位的三类盲区：

1. **只测覆盖不测时序**：JaCoCo 79.1% 的行覆盖对并发类缺陷零证明力。
2. **只扫反引号里的路径**：Markdown 链接语法 `[文字](路径)` 不被校验，悬空链接可以躺在仓库里。
3. **不校验数字真实性**：`ci.yml` 注释里写 113 个测试类 / 1520 个用例，与实测 126 类 / 1281 个 `@Test` 不符，门禁不报（见 D-07）。

## §3 后端服务

### 【BE-01】「一位老人只允许一位主要家属绑定」是读时校验，没有库级约束
`#后端 #边界异常` · P2

- **问题**：绑定流程是"先查是否已被他人绑定，再写绑定关系"。校验与写入之间没有锁，也没有能表达"elder_id 全局唯一"的唯一键 —— 现有的 `uk_family_elder(family_id, elder_id)` 只约束同一对家属与老人。
- **证据**：`backend/src/main/java/org/company/nianglin/service/impl/ElderServiceImpl.java:303-323`（读时校验 → 直写）；`backend/sql/V1__init_schema.sql` 的 `uk_family_elder` 列组合。
- **影响**：两位家属同账号体系下都成为 BOUND 相关方，该老人的档案与订单相关方判定出现"双主"；后续解绑时 `countBoundRelations` 归零判定也会失真。
- **触发**：两个家属账号在同一老人的可绑定状态下，毫秒级并发请求绑定接口。
- **改法**：给 `family_elder_relation` 增加不可表达重复的约束（如按 `elder_id` 的部分唯一索引 + 只对 BOUND 生效），或对 elder 行 `SELECT ... FOR UPDATE` 串行化绑定段。前者与现有软删设计同构，改动更小 —— 但注意 §2.4 第 4 条：**不要动成"加 `deleted`"那种简单拼列**，那会连带破坏现有的 update 复原路径。
- **验收判据**：两线程并发绑定同一老人的集成测试，断言恰好 1 个成功、1 个返回业务码，重复 100 轮稳定；Flyway 迁移在空库与存量数据上均可执行。
- **反证**：若绑定入口对同一老人天然互斥（例如邀请码一次性消费且立即失效），则竞态不可达 → 降 P3。**倾向保留 P2**：当前代码里没有看到邀请码核销逻辑。
- **门禁为何漏过**：单测串行调用，无并发用例。

### 【BE-02】费用汇总重算用 `updateById` 传了 null 版本号，`@Version` 实际不参与 WHERE
`#后端 #逻辑缺陷` · P2

- **问题**：`actual_fee` 是派生字段，重算时构造一个只带 `id` 与 `actualFee` 的 patch 直接 `updateById`。由于 `CompanionOrder` 用了 `@Version`，而 patch 的 version 为 null，MyBatis-Plus 会跳过版本条件 —— 等价于"按 id 无条件覆盖"。这与项目自定的铁律「禁止先 SELECT 再按 id 无条件 UPDATE」相悖。
- **证据**：`backend/src/main/java/org/company/nianglin/service/impl/OrderFeeItemServiceImpl.java:132-135`、:174-177。
- **影响**：并发录入时可能出现较旧的合计覆盖较新的合计，导致收入页与详情页短暂对不上账。
- **触发**：同一订单两笔明细录入在时间上重叠（需同一陪诊员双端同时提交）。
- **改法**：重算改为"以明细聚合值做条件更新"（`UPDATE ... SET actual_fee = ? WHERE id = ? AND actual_fee <> ?`），或干脆在读路径实时聚合、取消这个缓存字段。
- **验收判据**：并发两笔录入后，`actual_fee` 必须等于明细求和；重复 50 轮无差异。
- **反证**：**任意一次后续录入都会重算，字段有自愈性**，错误窗口以毫秒计且不影响任何资金动作（一期线下结算）→ 因此定为 P2 而非 P1。若改为在线支付，此条须立即升 P0。

### 【BE-03】方法级注解的落点不统一：26 个 controller 里有 5 个整类无 `@PreAuthorize`
`#后端 #逻辑缺陷` · P2

- **问题**：同一类安全语义，有的靠 `@PreAuthorize`，有的靠 Service 层 `requireInvolved`，有的靠 `receiver_id` 强制注入。已确认守卫充分的（`MessageController` 类注释 :35 有论证、`OrderController` 的 5 个只读方法由 `OrderServiceImpl.requireInvolved` 兜住），但**分布本身没有规律**，新人加接口时只加一半的风险很高。
- **证据**：`backend/src/main/java/org/company/nianglin/controller/message/MessageController.java:35`（全类无注解+论证）；`backend/src/main/java/org/company/nianglin/service/impl/OrderServiceImpl.java:694`、:780-806（归属校验唯一实现）；`backend/src/main/java/org/company/nianglin/config/SecurityConfig.java:196-203`（路径级兜底）。
- **影响**：不会立刻出问题，但会让"这个接口为什么不需要注解"每次都要重新取证。
- **方向**：在 `docs/agents/backend-conventions.md` 里列一张"三类守卫各自的适用条件 + 当前落点"的表，并在 `SecurityConfig` 的路径级兜底旁注明它盖住了哪些方法级缺口。
- **反证**：若已有该表（本轮未在 backend-conventions 中检索到），则降 P3。

### 【BE-04】`controller` 层行覆盖 36%，WebSocket 握手从未压测
`#后端 #边界异常` · P2

- **问题**：AUDIT 报告 §7.4 自己标注的两处洼地，至今无更新数字。
- **证据**：`docs/agents/AUDIT_BACKEND_2026-09-16.md` §7.4（数字截至 2026-09-16，之后 Service 覆盖从 63% 提到 79%，但这两项没有跟进记录）。
- **影响**：Controller 层主要承载参数绑定与响应装配，恰恰是"缺 payload / 类型不匹配"这类错误的高发区（项目历史上 4 个越权用例假红就出在这一层）。
- **方向**：补 `@WebMvcTest` 级别的绑定与异常分支用例；WS 握手单独做一个连接建立/拒绝的并发脚本。
- **反证**：若已有 `GlobalExceptionHandlerClientErrorTest`（11 个用例）覆盖主要分支，则本条只剩"绑定层"部分 → 可降 P3。

### 【BE-05】短信重试任务的首次延迟与执行间隔共用同一个配置键
`#后端 #边界异常` · P3

- **问题**：`initialDelayString` 与 `fixedDelayString` 都读 `nianglin.sms.retry.scan-interval-ms`。改这一个值会同时改掉"多久跑一次"和"启动后多久开始跑"。若运维把间隔调到 30 分钟，首次扫描也跟着推迟 30 分钟（静默时段的待发短信会多积压半小时）。
- **证据**：`backend/src/main/java/org/company/nianglin/task/SmsRetryScheduler.java:40-42`。
- **方向**：拆成两个键，或首次延迟固定为小值（如 30 秒）。

### 【BE-06】匿名健康检查接口返回运行环境信息
`#后端 #安全漏洞` · P3

- **问题**：`/api/health` 无需登录，响应里带 `spring.profiles.active` 与 `java.version`。
- **证据**：`backend/src/main/java/org/company/nianglin/controller/common/HealthController.java:37-47`；白名单在 `backend/src/main/java/org/company/nianglin/config/SecurityConfig.java:89`。
- **影响**：给指纹识别提供便利（能判断是否 dev 环境、JDK 大版本）。属低危信息暴露，不是漏洞利用链。
- **方向**：prod profile 下只返回 `status` 与 `serverTime`，环境细节走需要登录的运维端点。

### 【BE-07】`/api/health/demo-success` 不在匿名白名单，但注释没提这一点
`#后端 #交互问题` · P3

- **问题**：白名单里 `"/api/health"` 是精确匹配，`/api/health/demo-success` 需要登录。该端点的 `@Operation` 只写"用于验证统一响应封装"，未说明需鉴权 —— 拿它当探活地址的脚本会拿到 401。
- **证据**：`backend/src/main/java/org/company/nianglin/controller/common/HealthController.java:49-56`；`backend/src/main/java/org/company/nianglin/config/SecurityConfig.java:88-119`。
- **方向**：要么在 `@Operation` 里写明"需登录"，要么明确它是开发期自检端点并在 prod 关闭。

## §4 前端应用

### 【FE-01】后端 14 个端点前端未接，其中 5 条是用户可感知的功能断点
`#前端 #功能缺失` · P1

- **问题**：后端 143 个 `/api` 端点中，有 14 个在前端 `src` 全目录下静态检索无调用点。其中 5 条不是"预留"，而是**承诺过却走不到**：
  1. `PUT /api/user/elder/{id}` —— 老人档案只能新建和删除，**不能修改**。填错一个地址就得删了重建。
  2. `PUT /api/user/profile` —— "我的"页不能改个人资料。
  3. `POST /api/order/{id}/reject` —— 陪诊员只能"不接"，**不能显式拒单**，拒单原因沉淀不下来。
  4. `GET /api/order/{id}/fulfillment` —— 家属看不到催单事件流与等待时长，只能看列表里的风险等级。
  5. `GET /api/exam-prep` —— V5「检查准备须知」整块功能**前端零入口**。
  其余 9 个（`/api/health`、`/api/health/demo-success`、订单状态分布、指标字典、执行轨迹、反馈详情、药品详情、陪诊员评分、投诉详情、`GET /api/medication/dict/{id}`）属可选下钻，可低优先。

## §6 数据与迁移

### 【DB-01】全库 0 个 CHECK 约束
`#数据 #边界异常` · P2

- **问题**：29 张表没有任何 CHECK，`status`、`score`、`amount`、`bind_status` 全靠应用层枚举与 DTO 校验保证。
- **证据**：`backend/sql/V1__init_schema.sql` 起的全部迁移脚本，CHECK 计数为 0。
- **影响**：任何一次手工修数、脚本导入、或未来新增的写入路径（如定时任务、数据迁移）都可能写入枚举外的值，之后所有按枚举分支的代码会静默走错分支（例如状态既不是 BOUND 也不是 UNBOUND，`countBoundRelations` 就数不到它）。
- **触发**：手工 SQL 修正数据、批量导入、新写入路径漏校验。
- **方向**：先在 `status` 这类枚举列上补 CHECK（成本低、风险小），金额列补 `>= 0`。不建议一次性全表加。
- **反证**：若团队明确采用"枚举只在应用层"的约定（如已有 ADR），则本条改为文档记录 → D1。

### 【DB-02】5 组唯一键不含 `deleted`，软删后无法重建同键
`#数据 #边界异常` · P2

- **问题**：`medication_task.uk_plan_time`、`order_review.uk_order_id`、`family_elder_relation.uk_family_elder`、`order_checkin.uk_order_node`、`sys_user.uk_username/uk_phone` 都是"业务键唯一"，一旦对应行被逻辑删除，同键无法再插入。
- **证据**：`backend/sql/V1__init_schema.sql` 的 11 个 UNIQUE KEY + 后续迁移新增的 4 个。
- **影响（逐条判定，不夸大）**：
  - `family_elder_relation`：**当前不可达** —— 解绑只改 status 不软删，重绑走 UPDATE（见 §2.4 第 4 条）。
  - `order_review`：一单一评，作废用 `is_valid=0` 而非软删，无重评入口 → 当前不可达。
  - `medication_task`：目前没有删除任务的接口 → 不可达；但**若将来加"纠错删除"就会立刻咬人**。
  - `order_checkin`：同理，加打卡纠错功能时会咬人。
  - `sys_user`：注销走去标识化而非软删，手机号会被改写 → 可复用。
- **方向**：不是"全都加 `deleted`"。先把"不允许软删的表"在文档里写清楚（历史表只追加），对确实需要软删的表再单独迁移。
- **反证**：若这四张表的业务规则明文禁止软删，则本条降为文档记录 D1。

### 【DB-03】种子与夹具的两个"看起来对其实不对"的值
`#数据 #边界异常` · P3

- **问题**：① 种子任务 20002 在库里实际是 `MISSED`（漏服扫描器跑过），但文档按计划写 PENDING，拿它做"今日待服"断言会假红；② `medication_task` 的备注列名是 `confirm_remark` 而非 `remark`，写 SQL 时容易写错。
- **证据**：本轮未复验（需连库 `SHOW COLUMNS` 与 `SELECT`），来源是项目长期备忘中的既有结论。
- **影响**：夹具脚本与临时排查 SQL 的第一道坎，每次都要重新踩。
- **方向**：把列名与"哪些种子行会被定时任务改写"写进夹具脚本头部注释；夹具实现时对这两点做断言。
