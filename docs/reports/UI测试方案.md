> **执行者**：UI 测试者（1 人）　**测试窗口**：4 个自然日（见 §8 日程）
> **文档形态**：方案与用例合一 —— 拿到这一份即可开工。
> **配套文档**：[`功能测试方案.md`](./功能测试方案.md) —— 另一位测试者的执行依据，**两份文档的分工切面见 §0，先读**。
> **缺陷归档**：`docs/reports/`（本方案、执行报告）；缺陷走 GitHub issue（流程见 §7）。
> **与 [`验收报告.md`](./验收报告.md) 的关系**：并存、互不修改。测完的结论写进新执行报告，**不回写验收报告**。

## 0 · 一句话分工切面（先读，避免与功能测试者重复）

**同一批页面两个人都会进，但看的东西不同：**

| | 你看（UI 测试） | 你不看（归 [`功能测试方案.md`](./功能测试方案.md)） |
|---|---|---|
| 关注点 | 长什么样、点起来什么感觉 | 逻辑对不对、数据准不准、权限守没守 |
| 举例 | 按钮点了没反馈、空态文案在接口挂了时骗人、老人模式字号没放大、列表在 1366 宽下溢出 | 订单状态流转是否合法、越权是否被拒、导出行数是否超上限、错误码是否与文档一致 |

> ⚠️ 发现"功能错了"的页面，**你仍然要记录**（截图 + 复现步骤），只是在 issue 里标注
> `transfer:功能测试者`，由功能测试者深挖根因；**不要因为'这不归我'就不记**。

## 1 · 目标与范围

### 1.1 目标

1. 验证四个角色端（家属 / 陪诊员 / 老人 / 管理员）全部页面在**真实浏览器**中的视觉与交互质量。
2. 验证**老人模式**、**桌面与移动适配**、**多浏览器**下的可用性。
3. 逐条核对 [`docs/agents/interaction-checklist.md`](../agents/interaction-checklist.md) 的交互陷阱（那是 56 页面审查沉淀的判据，**不是问题清单，是判据**）。
4. 产出可归档的截图与执行报告，作为验收证据。

### 1.2 范围内（按页面盘点，共 56 个视图）

| 分组 | 页面（`frontend/src/views/`） |
|---|---|

| 家属端（15） | `family/home`、`order-step1/2/3`、`order-list`、`order-detail`、`order-review`、`order-complaint`、`elder-list`、`elder-bind`、`elder-health`、`health`、`medication`、`message`、`assistant` |

| 老人端（4） | `elder/home`、`health`、`medication`、`message` |
| 管理端（13） | `admin/dashboard`、`order`、`companion-audit`、`complaint`、`order-dispute`、`fulfillment`、`settlement`、`user`、`export`、`operations`、`operation-param`、`oper-log`、`chat-viewer` |
| 聊天（2） | `chat/session-list`、`chat/room` |
| 公共 | `profile/index`、`legal/index`、`error/403`、`error/404` |

### 1.3 不测（明确排除，避免重复劳动）

- 订单状态机流转是否合法、越权是否被服务端拒绝、错误码是否与 `docs/api/` 一致、数据条数是否与种子一致 —— **全部归功能测试者**。
- 后端接口的性能 / 并发 —— 仓库已有压测报告（`docs/reports/pressure-test-*`），不重测。
- 自动化已覆盖的断言不重复手点：`frontend/e2e/specs/` 的 22 个 spec 是前置门禁（见 §3），你只**复核其覆盖不到的观感与体验**。

## 2 · 测试环境与前提

### 2.1 服务启动 / 停止

```powershell
# MySQL / Redis 是本机常驻服务，脚本不负责起
powershell -File tools/e2e/start-services.ps1    # 起后端 8080（前端由 Playwright webServer 自动拉起 5141）
powershell -File tools/e2e/stop-services.ps1     # 停 8080 的 Java 进程
```

- 前端开发服务器：`pnpm -C frontend run dev`（端口见 `frontend/.env.development`；Playwright 跑法会自起 5141 并复用）。
- AI 助手服务（8081）：独立进程，只监听 `127.0.0.1`，启动方式见 `ai-service/` 文档；**未启动时前端助手页应给出可理解的失败态**（这本身是一条用例，见 UI-07-06）。
- 跑任何 E2E / 探针前先过身份闸门：`python tools/e2e/l0_identity_gate.py`（确认 8080/8081/5141 上跑的确实是本项目进程，别把别人的服务当成自己的）。

### 2.2 数据基线重置（**两人共用一套环境，这条最重要**）

- **每轮测试开始前**执行：

```powershell
python tools/e2e/restore_clean_baseline.py            # dry-run，先看计划
python tools/e2e/restore_clean_baseline.py --execute  # 真删（二次确认）
```

- ⚠️ **错峰执行**：与功能测试者约定时段（建议上午你、下午他 / 或按模块轮流）。**他正在跑写路径用例时不要重置**，否则他的用例会莫名失败。
- ⚠️ `restore_clean_baseline.py` 是**破坏性**脚本：默认 dry-run，必须显式 `--execute`；出现「待删超 30% 或 500 行」守卫时**停下来核对**，不要随手 `--force`（历史上旧版脚本曾误删 629 行种子数据）。
- 你以**只读 / 低风险操作**为主（浏览、翻页、切模式、开确认框不提交）；必须产生的写操作（提交表单、点确认）在用例里标注 `写`，跑完立即重置。

### 2.3 测试账号（口令**不要**写进任何文档 / issue / 截图）

| 角色 | 账号 | user_id | 备注 |
|---|---|---|---|
| ADMIN | `admin` / `superadmin` | 1 / 2 | 管理端入口 |
| FAMILY | `fam001` … | 101 起 | 名下仅绑定老人 401、订单仅 2 条 —— **列表条数"少"不是缺陷** |
| ELDER | `elder001` … `elder030` | 201 起 | `elder030`(230) 是**封禁账号**，用于登录反向用例 |
| COMPANION | `comp001` … | 301 起 | `comp001` 已过审、可接单 |

- 统一口令由环境变量 `NIANGLIN_SEED_PASSWORD` 提供，默认值见 `backend/sql/tools/fixture_credentials.py`；前端登录页演示预填读 `frontend/.env.development` 的 `VITE_DEMO_PASSWORD`。**只在本地读，不抄进文档。**
- 账号与口令出处的权威表述见 [`docs/agents/FRONTEND_CONTRACT.md` §10.7](../agents/FRONTEND_CONTRACT.md)。

### 2.4 登录验证码

登录**必须**带图形验证码：`GET /api/auth/captcha` 拿 `captchaKey` + 图片。手工测试就看图输入；自动化 / 探针从 Redis 键 `captcha:<key>` 直取（TTL 300 秒、一次性消费），**不要写 OCR**。

### 2.5 浏览器与视口（UI 测试的主战场）

| 类型 | 要求 |
|---|---|
| 浏览器 | **Chrome 主测**、**Edge 必测**；Firefox / Safari 标注为**可选**，测了就在报告里注明 |
| 桌面视口 | 1920×1080（主）、1366×768（常见笔记本，最容易暴露溢出） |
| 移动视口 | 390×844（iPhone 尺寸）与 360×740（Android 常见尺寸），用 DevTools 设备模拟 |
| 缩放 | 浏览器 100% / 125% / 150% 各过一遍关键页（老年用户常开大缩放） |

### 2.6 AI 助手服务

`LLM_BASE_URL` / `LLM_MODEL` **留空即降级模式**，助手照常可用（回答给 FAQ 原文，`degraded=true`）。
你只测**助手页的观感**：流式输出的呈现、加载态、失败态、免责声明是否可见。对话内容正确性归功能测试者。

## 3 · 前置门禁（Day1，全绿才允许开测）

口径与 CI（`.github/workflows/ci.yml`）对齐 —— **G1–G6、G8、G9 与 CI 是同一套命令**；G7（Playwright）是本机门禁，CI 没有这一步：

| # | 命令 | 工作目录 | 通过判据 |
|---|---|---|---|
| G1 | `python tools/check_secrets.py` | 仓库根 | exit 0（密钥体检五条） |
| G2 | `python tools/check_metric_dict_parity.py` | 仓库根 | exit 0（指标字典一致） |
| G3 | `mvn -B verify` | `backend/` | BUILD SUCCESS，测试全绿（surefire 实跑口径，数字以本次运行输出为准，**不要抄旧文档**） |
| G4 | `pnpm run lint:check` | `frontend/` | 0 警告（`--max-warnings 0`） |
| G5 | `pnpm run test` | `frontend/` | vitest 全绿 |
| G6 | `pnpm run build` | `frontend/` | 构建成功 |
| G7 | `pnpm exec playwright test` | `frontend/` | 22 个 spec 全绿；HTML 报告落在仓库根 `reports/playwright/html`（已 gitignore） |
| G8 | `python -m pytest ai-service/tests -q` | 仓库根 | 全绿（**不依赖 LLM 与网络**，没配 key 也要绿） |
| G9 | `python tools/check_faq_anchors.py` | 仓库根 | exit 0（FAQ 锚点与合规词） |

> ⚠️ G7 跑之前必须先过 `l0_identity_gate.py`（§2.1）；Playwright 的 `video` 是**刻意关闭**的，
> 报「Video rendering requires ffmpeg」是环境问题，与用例无关，不要误判成产品缺陷。
> ⚠️ 门禁红了**先报给维护者修，不要绕过** —— 门禁红着开始手工测试，测出来的"绿"没有意义。

## 4 · 用例表约定

| 列 | 含义 |
|---|---|
| 编号 | `UI-<模块>-<序号>`，issue 与截图文件名都用它 |
| 优先级 | **P0** 主流程不可用 / 合规问题；**P1** 明显错误但有绕行；**P2** 次要瑕疵 |
| 前置 | 起点状态（哪个账号、哪个页面、是否需要重置基线） |
| 步骤 | 可复现的最小操作序列 |
| 预期 | **只写可观察的判定**，不写"应该没问题"这种模糊话 |
| 结果 | `通过 / 失败 / 阻塞 / 跳过`（执行时填） |
| 缺陷 | 失败时填 GitHub issue 链接；通过留空 |
| 截图 | `docs/reports/screenshots/<编号>-<说明>.png`；通过的用例也至少留 1 张关键态 |

1. **不做诊断、不开药方**：任何页面出现"建议服用""推荐剂量""诊断为""可能是 XX 病"类表述 → **P0**。药品字典只能是通用信息 + 免责声明文案。
2. **隐私最小化**：手机号、身份证号、姓名在界面上应按场景脱敏；**localStorage 里禁止出现密码、身份证号、完整手机号**（DevTools → Application → Local Storage 检查）→ 违反 **P0**。
   > 已记录的唯一豁免：`GET /api/order/{id}` 详情返回**全名**是刻意设计（列表脱敏、详情全显）。发现它先看 `AGENTS.md §0.1` 第 2 条的豁免说明，别误报。
3. **一期不做**：在线支付、地图导航入口 → 发现即 P0（IM 已按 M13 订单聊天放开，**仅限按订单**的家属↔陪诊员，出现"自由加好友式 IM"才是缺陷）。

### 6.2 UI 测试专属注意事项

1. **先跑前置门禁（§3）再开测**；门禁红了报维护者，不要绕过、不要"先测着"。
2. **共用环境错峰**（§2.2）：重置库前先和功能测试者打招呼；他跑写路径用例时你重置，他的失败会被算到你头上。
3. **不要为了让用例变绿放宽预期** —— 本仓库真实教训：4 个越权用例曾因"请求没走到鉴权层"而假红，如果当时放宽断言就会变成永远测不到鉴权的**假绿**（见 `docs/agents/BUG_LIST.md` §1）。同理：看到"暂无数据"先断网复现一次，别默认它是对的。
4. **种子条数不是你的判据**：`fam001` 名下只有 2 条订单、老人 401 有 12 条服药任务，这是**种子设计**。觉得"数据少"先查 [`FRONTEND_CONTRACT.md` §10.8](../agents/FRONTEND_CONTRACT.md)（数据真源 `backend/sql/V2__seed_data.sql`），**不要照抄旧文档的数字**（那节曾经错过，2026-10-21 实测修正过）。
5. **截图里不要出现完整手机号 / 身份证 / 口令**：截图前把表单里的敏感字段清掉或用打码工具处理；issue 里同理。
6. **验证码一次性**：登录失败提示"验证码错误或已过期"时，先确认是不是自己连点了两次（见 UI-01-02），别直接报缺陷。
7. **写用例才需要重置**：纯浏览的用例不必每条都重置库，按模块段落批量重置即可，省时间。
8. **发现页面不在 §1.2 清单里**（新增页/漏登页）：补进清单并在报告注明，清单本身也要跟着仓库长大。
9. **新踩的交互陷阱补回清单**：`interaction-checklist.md` §6 明确要求"撞见的新坑补进对应小节（症状 → 根因 → 判据）"，你是最先撞见的人。

## 7 · 缺陷记录流程

1. **每个失败用例开一个 GitHub issue**，标题格式：`[UI][P1] UI-07-01 老人端用药页失败态显示成空态`。
2. **标签**：按 [`docs/agents/triage-labels.md`](../agents/triage-labels.md) 五标签流转 —— 新建默认 `needs-triage`；确认是本项目缺陷后改 `ready-for-agent`（给 AI 修）或 `ready-for-human`（要人拍板）；不修的 `wontfix`；信息不足 `needs-info`。
3. **严重度定义**（写进 issue 正文）：

| 级别 | 定义 | 本项目示例 |
|---|---|---|
| **P0** | 主流程不可用 / **违反合规红线** | 老人端失败态骗成空态、localStorage 存了完整手机号 |
| **P1** | 主流程可用但明显错误，或有绕行 | 回车双发导致登录必失败、同路由换参显示旧数据 |
| **P2** | 次要瑕疵，不影响完成任务 | 空态文案没下一步、间距不齐 |
| **P3** | 体验优化建议 | 图标风格不统一 |

4. **issue 正文模板**：

```markdown
用例编号：UI-xx-xx
严重度：P0/P1/P2/P3
环境：Chrome 1xx / 视口 1366×768 / 后端 8080 / 基线是否重置过
复现步骤：
1. …
2. …
预期：…
实际：…
截图：docs/reports/screenshots/…（附件或路径）
是否复现：3/3
备注：是否需要转功能测试者深挖
```

5. **禁止**：issue 里贴真实手机号 / 身份证 / 口令 / 完整 JWT；贴日志前先脱敏。
6. 修复后的**复测**在 Day4 完成，复测通过把 issue 关闭并在执行报告里记一行。
