## 〇、这一版是「收敛」，不是「新建」

roadmap §7.1-3 写得很清楚：

> V3.6 开工时：**以「指标字典」为第一张票，而不是先做图表。**

而指标字典**已经在 V3.2 建好了**（`docs/spec/metric-dictionary.md`），
V3.3 / V3.5 只能「登记」不能「新定义」（决策 D6）。

所以 V3.6 的实际工作是**三件**：

1. **校验与补全**指标字典 —— 把前几版散落的口径全部收进字典，并让机器验得住；
2. **供给时段缺口分析** —— 回答「哪个时段没人接单」；
3. **干预效果对比** —— 回答「这次干预让下一次服务变好了吗」。

## 二、接口契约（建议形态）

| 端点 | 内容 |
|---|---|
| `GET /api/admin/operations/gap?range=` | 供给缺口表：`[{ weekday, hour, pendingUnaccepted, availableCompanions, gap }]` |
| `GET /api/admin/operations/effect?metric=&from=&to=` | 同一指标在两个时间段的对比 |
| `GET /api/admin/metrics` | 指标字典的只读导出（供运营查阅与对账） |

### 2.1 供给时段缺口的算法

```
按「周内第几天 × 小时」分桶：
  pendingUnaccepted = 该时段内下单但至今无人接的订单数
  availableCompanions = 该时段工作状态为 AVAILABLE 且资质通过的陪诊员数
  gap = pendingUnaccepted − availableCompanions     （> 0 即为缺口）
```

这正是迭代计划 §47 那个典型闭环的数据基础：
「订单无人接 → 统计发现 14:00–16:00 陪诊员数量不足 → 管理员调整排班 → 下一周期重新统计 → 履约率提升」。

### 2.2 干预效果对比

同一指标在两个时间段的对比，**必须用指标字典里的同一条口径** ——
否则对比的是两个不同的数，结论没有意义（决策 6.2）。

## 三、指标体系（收敛清单）

| 域 | 指标 |
|---|---|
| 订单 | 订单总量 / 完成量 / 取消量 / 待接单量 |
| 履约 | 平均接单时间 / 履约率 / 超时率 / 人工介入率 / 改派率 |
| 服务 | 平均评分 / 投诉率 / 完成率 / 服务时长 |
| 陪诊员 | 活跃人数 / 接单人数 / 人均订单 / 人均收入 |
| 健康协同 | 用药任务数量 / 完成率 / 漏服率 / 就医次数 / 陪诊次数 |

**每一个指标都必须有**：指标名称 / 统计范围 / 统计时间 / 数据来源 / 计算公式（决策 6.1）。
**同一个指标在不同角色端只能有一个口径**（决策 6.2）。

## 四、测试矩阵

| 层 | 锁住什么 |
|---|---|
| 字典校验 | 每个端点返回的指标都在字典里；字典里每条都有五要素与口径版本 |
| 缺口分析 | 分桶边界；同一人在多时段的计数不重复；空时段为 0 而不是缺行 |
| 效果对比 | 两侧用同一条口径；区间不合法 → 9002 |
| E2E | 缺口表渲染；对比图渲染；空数据走空态 |

**反向验证**：让驾驶舱的履约率与 V3.6 的履约率用**不同公式** → parity 测试变红。
