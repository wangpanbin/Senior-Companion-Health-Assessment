## 〇、开工复核结论（2026-10-20）

预写 spec 的「开工时必须复核」三条 + roadmap §7.1-2，逐一核实：

| # | 复核项 | 核实结果 | 处置 |
|---|---|---|---|
| ① | V3.1 的工作状态与履约事件是否仍是当前形态 | ✅ `WorkStatus = AVAILABLE / REST / OFFLINE`；`order_fulfillment_event` 表在位；`companion_order.fulfillment_risk` 在位 | 过滤链直接复用，不改 |
| ② | 陪诊员档案的服务区域 / 可服务时段是否仍是自由文本 | ❌ **仍是自由文本**：`service_area VARCHAR(100) NOT NULL`、`available_time VARCHAR(100) NOT NULL`；订单侧**无区域字段** | **必须做结构化改造**（V7 迁移） |
| ③ | V3.2 的指标字典里是否已有匹配效果指标 | ❌ 字典现有 32 条（V3.2 的 14 + V3.3 的 18），**无匹配相关指标** | 本版**新登记**（指标字典本就是新指标的唯一入口） |
| ④ | 距离维度有没有数据基础 | ❌ `companion_profile` **无坐标**；`companion_order` 有 `longitude` / `latitude`（打卡校验用） | 陪诊员坐标随 V7 一起加；**无坐标时该维度记 0 且标注，绝不推断** |

**结论**：预写 spec §〇 的判断成立 —— 「距离 20%」今天没有任何数据基础，
本版**先做结构化改造（expand–contract），再建规则引擎**。

### 偏差 D-3.4-1：区域码采用「市_区」两级，跨市记 0

预写 spec §3.2 写「区域码相等 = 1.0；同一区不同码 = 0.5；跨区 = 0」，
但没说「区」怎么界定。种子里的服务区域有 8 个区县、分属 4 个市
（海口 4 个、三亚 2 个、儋州 1 个、琼海 1 个）。

处置：区域码格式固定为 `<CITY>_<DISTRICT>`（全大写拼音），例如
`HAIKOU_MEILAN`。**城市前缀（`_` 之前）就是「区」这一层**：

```
区域码相等              → 1.0
同市不同区（HAIKOU_X vs HAIKOU_Y）→ 0.5
跨市（HAIKOU_x vs SANYA_y）        → 0
```

### 偏差 D-3.4-2：hall 的 `RECOMMEND` 改为「Java 侧打分 + 内存分页」

预写 spec 说「扩展 V3.1 的单一推荐序为真正的五维推荐序；响应结构零变更」。
V3.1 的实现是 **SQL `ORDER BY`**（就诊时间 → 区域匹配 → ID）。

五维加权里有三件事 SQL 做不了或做了会错：
① 距离要 Haversine（MySQL 无内置函数）；② 服务能力要按「该陪诊员在该科室的历史单数」归一化；
③ 「陪诊员无坐标 → 距离记 0 且不推断」这条规则需要一个**分支**，
而 SQL 里写 CASE 会让「无坐标」与「坐标相同（距离 0）」落进同一个值。

处置：五维打分统一由 `MatchingService` 在 **Java 侧**完成（也就是预写 spec 要求的
「无 Spring 上下文的纯函数」），hall 改为**候选集 → 打分 → 排序 → 内存分页**。

**响应契约不变**：`PageResult` 的 `total / page / size / pages / records` 结构与语义都不变，
`total` 仍是「满足大厅筛选条件的待接单订单数」（与 V3.1 一致 —— 候选集就是那批订单，
只是排序方式换了）。候选集上限由 `nianglin.matching.hall-candidate-limit` 控制（默认 500），
超限时**记一条 warn 日志**（不静默截断）。

### 偏差 D-3.4-3：`DISTANCE` 排序在「无坐标」时退化为并列

预写 spec §四 说 V3.4 开放 `sortBy=DISTANCE`。但今天**没有陪诊员填坐标**，
距离维度按规则「记 0 且不推断」→ 所有订单的距离分并列 0。

处置：`DISTANCE` 排序按距离分降序，**距离分并列时回落到就诊时间升序**。
这不是「假装能排」，而是如实反映「现在没有距离数据」；
等陪诊员开始填坐标，排序自动开始生效，不需要改代码。

### 偏差 D-3.4-4：`MatchingRule` 接口形态

预写 spec §五 与本 tickets 的 T4 写的是
`boolean supports(candidate, order)` + `double score(candidate, order)`；
实际实现（`service/support/matching/MatchingRule`）是
`String dimension()` + `String displayName()` + `DimensionResult evaluate(candidate, target)`。

理由：**「0 分」有两种完全不同的含义** —— 「不匹配」（超出服务半径）与
「降级」（没填坐标，距离算不出来）。ADR-0016 决策 3 要求这两者**必须分开表达**。
若拆成 `supports`（是否保留）+ `score`（多少分）两个方法，
「不匹配」与「降级」这两个 0 分就无处安放 —— 只能塞进某一个方法的返回值里，
而那正是决策 3 要避免的「混在一起」。

处置：`evaluate` 一次返回**得分 + 命中理由 + 降级说明**三件事（`DimensionResult`），
把区分摆在返回值里而不是方法签名里。规则仍是**纯函数**
（不碰数据库 / 时钟 / 配置），预写 spec 的核心诉求（可测）未受影响。

## 二、T1 · V7 结构化改造迁移

**新增**：`backend/sql/V7__matching_structured.sql`（Flyway 版本号接 V6）

### 2.1 expand（全部可空，老数据不受影响）

```sql
ALTER TABLE companion_profile
  ADD COLUMN longitude DECIMAL(10,7) NULL COMMENT '陪诊员档案经度（一期自填或管理员代录）',
  ADD COLUMN latitude  DECIMAL(10,7) NULL COMMENT '陪诊员档案纬度',
  ADD COLUMN service_region_code VARCHAR(32) NULL COMMENT '服务区域码（<CITY>_<DISTRICT>）；自由文本 service_area 保留';

CREATE TABLE companion_available_slot (
  id            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '时段 ID',
  companion_id  BIGINT       NOT NULL                COMMENT '陪诊员用户 ID',
  weekday       TINYINT      NOT NULL                COMMENT '周内第几天：1=周一 … 7=周日',
  start_time    TIME         NOT NULL                COMMENT '可服务起始时刻',
  end_time      TIME         NOT NULL                COMMENT '可服务结束时刻',
  create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted       TINYINT      NOT NULL DEFAULT 0      COMMENT '逻辑删除',
  PRIMARY KEY (id),
  KEY idx_companion_weekday (companion_id, weekday, deleted),
  KEY idx_companion_id (companion_id)
);

ALTER TABLE companion_order
  ADD COLUMN service_region_code VARCHAR(32) NULL COMMENT '订单服务区域码';
```

> ⚠️ **用表不用 JSON 列**：可服务时段要参与筛选（订单时间落在哪个时段里），
> 必须可索引、可 JOIN —— JSON 列做不到「按星期 + 时刻范围」的高效筛选。

### 2.2 backfill（确定性，可复现）

- 陪诊员：`service_area` 自由文本 → `service_region_code`
- 订单：`address` 里的区县文本 → `service_region_code`
- **映射不上的留空**（留空 = 该维度按「无数据」处理，**不猜**）

映射表（8 个区县 / 4 个市）由 `backend/sql/tools/gen_region_codes.py` 从
`backend/sql/tools/region_code_mapping.json` 生成，迁移文件里写死同样的 CASE，
两边由 `tools` 里的校验脚本核对。

### 2.3 contract（读路径）

**读路径优先用结构化列；结构化列缺失时回退到自由文本包含式匹配**（与 V3.1 大厅同口径）。
**一期不删旧列** —— 删列是不可逆动作，且自由文本里还有历史语义。

## 四、T3 · 匹配权重配置

**新增**：`backend/src/main/java/org/company/nianglin/config/MatchingProperties.java`
（绑定 `nianglin.matching.*`，范式照抄 `FulfillmentProperties`）

| 键 | 默认 | 说明 |
|---|---|---|
| `nianglin.matching.region.weight` | `0.30` | 区域匹配权重 |
| `nianglin.matching.time.weight` | `0.25` | 时间匹配权重 |
| `nianglin.matching.distance.weight` | `0.20` | 距离权重 |
| `nianglin.matching.skill.weight` | `0.15` | 服务能力权重 |
| `nianglin.matching.rating.weight` | `0.10` | 评分权重 |
| `nianglin.matching.distance.max-meters` | `30000` | 距离归一化的满量程（米） |
| `nianglin.matching.skill.max-orders` | `20` | 服务能力归一化的满量程（单） |
| `nianglin.matching.hall-candidate-limit` | `500` | 大厅候选集上限 |
| `nianglin.matching.recommend-limit` | `10` | 候选推荐端点返回条数上限 |

**启动期校验**（`@PostConstruct`）：
- 五个权重**之和必须等于 1**（容差 `1e-6`）；不等于 → **启动失败**
- 每个权重 `>= 0`；`distance.max-meters > 0`；`skill.max-orders > 0`
- 理由同 `FulfillmentProperties`：错误的权重不会报错，只会**静默给出错误的排序**，
> 这种故障在生产上极难定位，不如在启动的十秒内就失败。

## 五、T4 · 匹配三件套（纯函数）

**新增**（建议放 `service/support/matching/`，与 `FulfillmentRiskEvaluator` 同层）：

| 类 | 职责 |
|---|---|
| `MatchingRule`（接口） | `boolean supports(MatchingCandidate, MatchTarget)` + `double score(MatchingCandidate, MatchTarget)` |
| `MatchingScore`（值对象） | 各维度得分 + 总加权分 + **可解释**（每条推荐都能说出「为什么是他」） |
| `MatchingCandidate` | 候选人快照：陪诊员 ID / 区域码 / 坐标 / 可服务时段 / 历史科室单数 / 评分 / 工作状态 / 资质状态 |
| `MatchTarget` | 被匹配对象（订单）快照：区域码 / 就诊时间 / 坐标 / 科室 |

### 5.1 五条规则

| 规则 | 维度 | 得分 |
|---|---|---|
| `RegionMatchRule` | 区域 | 码相等 `1.0`；同市不同区 `0.5`；跨市 `0`；**双方都无区域码 → 该维度记 0**（不推断） |
| `TimeMatchRule` | 时间 | 订单时间落在某个可服务时段内 `1.0`；部分重合 `0.5`；不重合 `0`；**无可服务时段 → 记 0** |
| `DistanceMatchRule` | 距离 | Haversine 距离 / 满量程，`1 - d/max`；**陪诊员无坐标 → 记 0 并标注「无坐标」**（绝不按 (0,0) 算） |
| `SkillMatchRule` | 服务能力 | 该陪诊员在该科室的已完成单数 / 满量程，上限 1 |
| `RatingMatchRule` | 评分 | `score / 5` |

**距离必须复用 `util/GeoUtil.distanceMeters`**（已有 Haversine 实现），
**不要**再写一份 —— 两份 Haversine 迟早会漂。

### 5.2 加权（纯函数）

```java
public static double weightedTotal(Map<String, Double> dimensionScores, MatchingWeights weights)
```

- 权重之和为 1 时，加权总分落在 `[0, 1]`
- **无权重配置时不得静默按默认算** —— 由 `MatchingProperties` 的启动期校验兜底

## 六、T5 · 匹配编排 Service

**新增**：`service/MatchingService.java` + `service/impl/MatchingServiceImpl.java`
**新增**：`mapper/MatchingMapper.java`（聚合只读查询）

### 6.1 过滤链（顺序固定，短路）

1. 工作状态 `AVAILABLE`（`WorkStatus.isAccepting()`）
2. 资质 `audit_status = 'APPROVED'`
3. 区域码匹配（订单区域码 ∩ 陪诊员区域码；陪诊员无区域码 → 回退自由文本包含式）
4. 时段可服务（订单 `visit_time` 落在 `companion_available_slot` 的某个时段内）
5. 档期冲突（该时段已有在手订单：`ACCEPTED` / `IN_SERVICE`）

**每一步的失败原因都要能被解释** —— 候选被淘汰时记下原因（用于「为什么没推荐我」）。

### 6.2 编排

```
候选过滤 → 各规则算维度分 → 纯函数加权 → 排序（总分降序，同分按 id 升序兜底）→ Top N
```

**可解释性**：`MatchingScore` 里带每个维度的得分与一句话说明，
家属端能看到「推荐理由：同区 · 时间匹配 · 服务过该科室 12 单」。

## 八、T7 · 候选推荐端点

**新增**：`GET /api/order/{id}/recommend-companions`（家属端）

- 权限：`hasRole('FAMILY')` + **订单归属校验**（必须是自己下的单，否则 `3004`）
- 入参：`limit`（可选，默认 10，上限 20）
- ⚠️ **不返回**手机号、身份证号、完整姓名（脱敏走 `MaskUtil`）
- ⚠️ 决策 4.4：**排序只做推荐，接单权仍在陪诊员** —— 端点不产生任何订单状态变更

### 8.1 响应结构（字段名逐字锁定，前端按此对接）

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "orderId": 1001,
    "total": 12,
    "candidates": [
      {
        "companionId": 301,
        "companionName": "李*军",
        "totalScore": 86,
        "regionScore": 100,
        "timeScore": 100,
        "distanceScore": 0,
        "skillScore": 60,
        "ratingScore": 96,
        "reasons": ["同服务区域", "就诊时间在可服务时段内", "服务过该科室 12 单"],
        "notes": ["未填写坐标，距离维度记 0"]
      }
    ]
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `orderId` | Long | 被匹配的订单 ID |
| `total` | Integer | 通过过滤链的候选总数（Top N 之外的也有） |
| `candidates` | List | Top N 候选（按 `totalScore` 降序，同分按 `companionId` 升序） |
| `companionId` | Long | 陪诊员用户 ID |
| `companionName` | String | **脱敏姓名**（`MaskUtil.name`） |
| `totalScore` | Integer | 加权总分（0–100，四舍五入） |
| `regionScore` / `timeScore` / `distanceScore` / `skillScore` / `ratingScore` | Integer | 各维度得分（0–100） |
| `reasons` | List\<String\> | 命中的推荐理由（可解释性） |
| `notes` | List\<String\> | **降级说明**（如「未填写坐标，距离维度记 0」）；没有则为空数组 |

**得分口径**：维度原始分是 `0.0 ~ 1.0` 的双精度，VO 里乘 100 后四舍五入成整数。
加权总分 = Σ(维度分 × 权重) × 100。

**可解释性是硬要求**：每条推荐都必须能说出「为什么是他」。
`reasons` 至少一条；若某个维度因数据缺失被降级，`notes` 必须写明。
**不允许出现一个没有理由的分数。**
