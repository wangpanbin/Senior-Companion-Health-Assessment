### 偏差 D-3.6-1：缺口分析的「可服务陪诊员数」按**可服务时段**分桶，不按「工作状态」

预写 spec §2.1 写「`availableCompanions` = 该时段工作状态为 AVAILABLE 且资质通过的陪诊员数」。
按字面理解，每个桶的供给数都是同一个值（当前 AVAILABLE 的总人数），那这个指标毫无意义。

处置：供给数按**该陪诊员的可服务时段**分桶 ——
一个陪诊员只在「他确实能服务」的时段里算供给。
另设一个 `companionsWithoutSlots` 计数，说明有多少陪诊员**没有可解析的可服务时段**、
因而不参与供给统计 —— 这是对数据质量的如实披露，不是把 0 混进分母。

## 三、T2 · 端点↔指标双向校验

**新增**：`backend/src/test/java/org/company/nianglin/util/MetricEndpointContractTest.java`

三条校验（缺一不可）：

1. **yml 里声明的端点必须真实存在**
   —— 反射扫描所有 `@RestController`，收集 `@GetMapping` / `@PostMapping` / `@PutMapping` /
   `@DeleteMapping` 的路径，拼上类级 `@RequestMapping` 前缀，规范化成
   `"GET /api/xxx"` 的形式；yml 里出现一个不存在的端点 → **变红**
   （防「文档里写了一个接口，代码里没有」）。
2. **yml 里声明的指标必须在指标字典里** → 变红。
3. **指标字典里每条指标声明的端点，必须在 yml 里出现** → 变红
   （防「指标登记了但没人知道它属于哪个端点」）。

> 这一组校验是 V3.6 的**核心产出**：它把「口径登记」从「靠人记得写」变成「机器逼你写」。

## 四、T3 · 指标计算器注册表

**新增**：`backend/src/main/java/org/company/nianglin/service/support/metrics/`

```java
public interface MetricCalculator {
    /** 指标 key，必须在指标字典里登记过 */
    String metricKey();
    /** 按区间算该指标的值 */
    String calculate(DateRange range);
}
```

**新增**：`MetricCalculatorRegistry`（Spring Bean，持有全部 `MetricCalculator`）

**必须实现的指标**（key 与指标字典逐字对应）：

| key | 算的值 |
|---|---|
| `operations.fulfillment_rate` | 履约率 |
| `operations.completion_rate` | 完成率（按时） |
| `operations.complaint_rate` | 投诉率 |
| `operations.average_score` | 平均评分 |
| `operations.avg_accept_minutes` | 平均接单时间 |
| `operations.active_companion_count` | 活跃陪诊员数 |
| `operations.completed_order_count` | 完成订单数 |
| `companion.workbench.completion_rate` | 陪诊员区间完成率（**跨端口径复用同一实现**，决策 6.2） |

> ⚠️ **同一个指标在不同角色端只能有一个口径**（决策 6.2）。
> 所以 `companion.workbench.completion_rate` 与 `operations.completion_rate`
> 若公式相同，就必须**共用同一个计算器**，而不是各写一份 ——
> 否则两处迟早漂移，那正是 V3.2 在用药三桶上踩过的坑（ADR-0014）。

**不注册**的指标 key 在效果对比端点上返回 `400`（不许「猜一个算法算出来」）。

## 五、T4 · 供给时段缺口分析

**新增**：`GET /api/admin/operations/gap?range=LAST_30D`

响应：

```json
{
  "code": 200, "message": "操作成功",
  "data": {
    "periodStart": "2026-09-21", "periodEnd": "2026-10-20",
    "total": 96,
    "companionsWithoutSlots": 7,
    "items": [
      { "weekday": 6, "hour": 14, "pendingUnaccepted": 3, "availableCompanions": 1, "gap": 2 }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `total` | 返回的桶数（7 天 × 24 小时 = 168，空桶也返回） |
| `companionsWithoutSlots` | **没有可解析可服务时段**的陪诊员数（不参与供给统计，如实披露） |
| `items[].weekday` | 1=周一 … 7=周日 |
| `items[].hour` | 0–23 |
| `items[].pendingUnaccepted` | 该时段内下单但至今无人接的订单数（PENDING，按 `visit_time` 落桶） |
| `items[].availableCompanions` | 该时段**可服务**的陪诊员数（按其可服务时段分桶） |
| `items[].gap` | `pendingUnaccepted − availableCompanions`（**> 0 即为缺口**） |

**桶的粒度**：`range` 决定回溯天数（`LAST_7D` / `LAST_30D` / `CUSTOM`），
但**桶始终是「周内第几天 × 小时」**（与区间长度无关）——
这正是迭代计划 §47 那个闭环的数据基础：
「订单无人接 → 统计发现 14:00–16:00 陪诊员数量不足 → 调整排班 → 下一周期重新统计」。

⚠️ **同一陪诊员在多时段的计数不重复**：他覆盖多少个时段就在多少个桶里各计 1 次，
但**每个桶里只计 1 次**（不是按单数计）。

## 六、T5 · 干预效果对比

**新增**：`GET /api/admin/operations/effect?metric=<key>&from=&to=&compareFrom=&compareTo=`

- `metric`：指标 key，**必须在计算器注册表里**（否则 `400`）
- `from` / `to`：**后**一期的区间（闭区间，走 `DateRangeQuery`，上限 366 天 → `9002`）
- `compareFrom` / `compareTo`：**前**一期的区间；不传时自动取「与后一期等长、紧邻其前」的区间

响应：

```json
{
  "code": 200, "message": "操作成功",
  "data": {
    "metric": "operations.fulfillment_rate",
    "metricName": "履约率",
    "current":  { "from": "2026-10-01", "to": "2026-10-15", "value": "96.40%" },
    "previous": { "from": "2026-09-16", "to": "2026-09-30", "value": "92.10%" },
    "delta": "+4.30%"
  }
}
```

| 字段 | 说明 |
|---|---|
| `metricName` | 指标的中文名（从指标字典取，**不许另写一份名表**） |
| `delta` | 差值（百分点或绝对值，带正负号）；两个值格式不同（如 `%` vs 计数）时返回 `"—"` 并在报告里说明 |

> ⚠️ **两侧必须用同一条口径**（决策 6.2）—— 这由「同一个 `MetricCalculator` 算两遍」保证，
> 而不是靠两边各写一遍公式。

## 七、T6 · 指标字典补登

**改** `backend/src/main/resources/metrics/metric-dictionary.yml`（机器面）

补登迭代计划 §48 清单里尚缺、且**已有可算口径**的指标：

| key | 名称 | 公式 |
|---|---|---|
| `operations.timeout_rate` | 超时率 | 已完成订单中「未在承诺时长内完成」的单数 / 已完成单数 |
| `operations.manual_intervention_rate` | 人工介入率 | `fulfillment_risk = 'MANUAL_REQUIRED'` 的订单数 / 区间订单数 |
| `operations.reassign_rate` | 改派率 | 被管理员改派的订单数 / 区间订单数（`admin_oper_log` 的改派记录） |
| `operations.service_duration_minutes` | 平均服务时长（分钟） | `AVG(TIMESTAMPDIFF(MINUTE, start_time, finish_time))`，仅已完成 |
| `companion.profile.total_service_duration`（已存在） | — | — |
| `operations.medication_task_count` | 用药任务数 | `COUNT(*)`（三桶口径同源） |
| `operations.medication_missed_rate` | 漏服率 | 漏服桶 / 任务总数 |
| `operations.companion_count` | 陪诊员数 | `COUNT(DISTINCT companion_id)` |

**不要**为「还没有业务事实」的指标硬造条目（例如「陪诊员满意度」—— 没有数据源）。
