# Spec · 银龄伴诊 V3.x 迭代路线总纲（V3.1 – V3.6）

> **版本**：v1.0 · 2026-10-16
> **上游依据**：仓库 `plans/迭代计划.md`（V3.0 产品迭代规划，基线 2026-10-16 正式代码）
> **本 spec 范围**：把《迭代计划》的六版路线翻译成**产品与工程层面的目标、依赖与验收口径**；每版的核心成果、边界、门禁。
> **不在本 spec 范围**：V3.1 的接口 / 数据 / 并发契约（见 `V3.1-fulfillment-spec.md`）；逐票工单（见 `V3.1-tickets.md`）；V3.2 – V3.6 的接口细节（按 §七 的约定，在该版开工时用同一模板重写并细化）。
> **目标读者**：全体开发 · 测试 · 产品评审
> **状态**：待评审 → 进入开发（V3.1）

---

## 一、Problem Statement

《银龄伴诊》V3.0 已完成 20 张表、约 76 个业务端点、36 个前端路由的完整业务闭环，覆盖「陪诊链 / 用药链 / 治理链」三条主链，Playwright E2E 166/166 全绿。

但从使用者视角，V3.0 仍存在三类**未被解决的问题**：

1. **订单会失控。** 家属下单后进入 `PENDING`，系统既不过期、也不预警、更不兜底。如果没人接单，家属侧只有「等待中」三个字，管理员侧看不到任何异常。这是当前最容易被评审追问的单点。

2. **信息是散的。** 订单、用药、消息、陪诊四类功能各自成立，但家属要回答「我爸妈这个月到底怎么样」需要跨四个页面人工拼；陪诊员要回答「我这个月做得怎么样」需要全量拉订单在前端自行计算。数据存在，口径不对外。

3. **匹配与治理靠人肉。** 陪诊员看到的是一个没有排序的大厅；管理员看到的是一堆平铺的列表。平台缺一个「自动找到更合适的人」和一个「自动发现异常」的能力。

从工程视角，V3.0 已抵达「功能完整」，继续沿同一路径增加页面只会带来三个后果：页面越来越散、导航越来越长、数据口径越来越不一致。

**用户真正要的**不是更多功能，而是：

> 让老人每一次就医都**有人陪、有人知、有人管**，并让平台能够**持续提高**陪诊服务的可靠性。

---

## 二、Solution

V3.x 不以「新增页面数量」为验收标准，而以**业务闭环**为标准。六版按以下顺序串行推进，每一版只回答一个真实业务问题：

| 版本 | 回答的业务问题 | 核心成果（一句话） |
|---|---|---|
| **V3.1** 履约保障中心 | 下单后长时间没人接单怎么办？ | **订单不会因为没人接而失控** |
| **V3.2** 老人健康协同中心 | 家属怎么一眼看清老人的就医与用药状况？ | **家属能够看到老人完整的就医 / 用药协同状态** |
| **V3.3** 陪诊员工作台 | 陪诊员怎么掌握自己的工作、收入与服务质量？ | **陪诊员能够清楚掌握自己的工作、收入和服务质量** |
| **V3.4** 智能调度 | 平台怎么自动找到更合适的陪诊员？ | **平台能够自动找到更合适的陪诊员** |
| **V3.5** 平台运营驾驶舱 | 管理员怎么快速发现平台异常？ | **管理员能够快速发现平台异常** |
| **V3.6** 数据闭环 | 平台怎么通过数据持续提高服务质量？ | **平台能够通过数据持续优化服务** |

### 2.1 产品定位的升级

V3.0 之后，产品定位从「一个可以预约陪诊员的平台」升级为「**围绕老人就医过程进行多角色协同的服务平台**」：

```
有人陪   →  陪诊服务
有人知   →  家属协同 + 实时消息
有人管   →  订单履约 + 平台治理
持续优化 →  数据分析 + 智能调度
```

### 2.2 价值门禁（每个版本开工前与收口时各问一次）

一个迭代是否值得开发，用以下五问裁决，**不再**用「这个功能看起来是不是高级」：

1. **是否解决真实用户问题？** 不能 → 不做。
2. **是否形成完整业务闭环？** 只是页面 + CRUD → 价值有限。
3. **是否能够被真实数据支撑？** 虚假的 AI 指数 / 健康评分 / 推荐分 → 不做。
4. **是否提高平台可靠性？** 优先履约、安全、协同、稳定、可追溯。
5. **是否符合产品边界？** 尤其不做医疗诊断、不做药物推荐、不做治疗决策。

## 三、User Stories

### 3.1 V3.1 · 履约保障中心

1. As a 家属, I want 下单后立刻知道系统正在为我匹配陪诊员, so that 我不会以为订单被忽略了。
2. As a 家属, I want 在等待变长时收到明确的预警提示, so that 我知道需要主动做点什么。
3. As a 家属, I want 在风险足够高时能够催一次单, so that 我的催促真的能到达陪诊员。
4. As a 家属, I want 知道平台已经在人工协调, so that 我不需要反复刷新页面。
5. As a 家属, I want 在订单被接单或取消后风险提示自动消失, so that 页面不会一直显示过期的告警。
6. As a 家属, I want 催单有频率限制而不是无限点, so that 我不会把陪诊员骚扰到关闭接单。
7. As a 陪诊员, I want 自主控制自己是否接单, so that 我在休息或线下服务时不会被订单打扰。
8. As a 陪诊员, I want 暂停接单不影响我已接的订单, so that 我能安心休息而不必担心丢单。
9. As a 陪诊员, I want 在大厅按对我最合适的方式看到订单, so that 我不必自己逐条比较。
10. As a 陪诊员, I want 只看到我确实能接的订单, so that 我不会接了单却赶不上。
11. As a 陪诊员, I want 收到平台的定向催单提醒, so that 我知道有订单在等我。
12. As a 管理员, I want 一眼看到有多少订单正在失控, so that 我能把有限的时间花在最危险的地方。
13. As a 管理员, I want 按风险等级筛选风险订单, so that 我可以优先处理最紧急的。
14. As a 管理员, I want 从风险列表直接跳到订单详情, so that 我不需要再来回查找。
15. As a 管理员, I want 在订单还没被接时改派给另一位陪诊员, so that 服务能够继续下去。
16. As a 管理员, I want 我的每次人工介入都有记录和理由, so that 事后可以追溯。
17. As a 管理员, I want 风险等级自动恢复, so that 我处理完之后列表会自动收敛。
18. As a 老人, I want 家属帮我盯着订单有没有人接, so that 我不需要自己操心这件事。

### 3.2 V3.2 · 老人健康协同中心

19. As a 家属, I want 有一个属于某位老人的健康主页, so that 我不必在四个页面之间来回跳。
20. As a 家属, I want 看到今天该吃的药吃了几次, so that 我知道今天要不要再提醒一次。
21. As a 家属, I want 看到近期就医与陪诊次数, so that 我掌握老人的就医频率。
22. As a 家属, I want 看到本周用药完成率和漏服次数, so that 我能判断是否需要介入。
23. As a 家属, I want 把用药、就医、陪诊、消息按时间排成一条线, so that 我能还原某一天到底发生了什么。
24. As a 家属, I want 从时间线直接跳到对应的订单或用药详情, so that 我看到异常时可以立刻深究。
25. As a 家属, I want 只看到事实而看不到结论式判断, so that 我不会误把平台当成医疗意见。
26. As a 家属, I want 看到明确需要我处理的事项, so that 我不会漏掉要紧的事。
27. As a 老人, I want 用药信息以我能看懂的方式呈现, so that 我不需要家属代读。
28. As a 老人, I want 看到自己今天已经完成的事, so that 我知道今天做得不错。
29. As a 家属, I want 时间线在没有数据时显示空状态而不是报错, so that 我不会以为系统坏了。

### 3.3 V3.3 · 陪诊员工作台

30. As a 陪诊员, I want 打开首页就看到这个月的完成单数与收入, so that 我不用自己去数。
31. As a 陪诊员, I want 看到我的完成率与平均评分, so that 我知道平台和家属怎么评价我。
32. As a 陪诊员, I want 看到订单与收入的趋势, so that 我能判断淡旺季。
33. As a 陪诊员, I want 看到我服务过多少位不同的老人, so that 我知道自己的服务广度。
34. As a 陪诊员, I want 看到我的准时率, so that 我能发现自己的习惯问题。
35. As a 陪诊员, I want 看到我的擅长服务类型, so that 我知道什么单子该由我来接。
36. As a 陪诊员, I want 分开看到订单金额、平台服务费和我的实际收入, so that 我能核对金额。
37. As a 陪诊员, I want 看到待结算与已结算的拆分, so that 我知道哪笔钱还没拿到。
38. As a 陪诊员, I want 统计口径由后端统一, so that 我在手机上和电脑上看到的数字一样。
39. As a 陪诊员, I want 统计不依赖我一次性加载全部订单, so that 我的工作台不会卡。

### 3.4 V3.4 · 智能调度

40. As a 陪诊员, I want 大厅优先展示我确实能接的订单, so that 我少看到接不了的单。
41. As a 陪诊员, I want 同等条件下更近的单排前面, so that 我少跑冤枉路。
42. As a 陪诊员, I want 服务过我擅长的类型的陪诊员优先被推荐, so that 老人得到更合适的服务。
43. As a 家属, I want 系统更快为我找到合适的陪诊员, so that 我等待的时间变短。
44. As a 家属, I want 匹配结果仍然由我确认, so that 最终接单的人是我能接受的。
45. As a 管理员, I want 能调整匹配权重, so that 我能针对供给不足的时段调整策略。
46. As a 管理员, I want 看到匹配效果指标, so that 我能判断规则改动有没有用。
47. As a 平台, I want 匹配规则不依赖黑盒模型, so that 每一次推荐都能解释。

### 3.5 V3.5 · 平台运营驾驶舱

48. As a 管理员, I want 打开后台首页就看到今日全局指标, so that 我三十秒内知道平台是否正常。
49. As a 管理员, I want 看到需要人工介入的订单数, so that 我不会漏掉失控订单。
50. As a 管理员, I want 看到投诉率异常的陪诊员, so that 我能提前干预服务质量。
51. As a 管理员, I want 从异常卡片直接跳到处理页面, so that 发现到处理之间没有断点。
52. As a 管理员, I want 按今日 / 近 7 天 / 近 30 天 / 自定义看趋势, so that 我能区分偶发与持续。
53. As a 管理员, I want 看到履约率、平均接单时间、投诉率、平均评分, so that 我能判断平台的健康构成。
54. As a 管理员, I want 平台健康度由客观指标构成而不是一个神秘分数, so that 我能向别人解释这个数。
55. As a 管理员, I want 空数据时显示 0 或空图而不是报错, so that 我知道是真的没有数据。

### 3.6 V3.6 · 数据闭环

56. As a 平台, I want 每个核心指标都有统一的名称 / 范围 / 时间 / 来源 / 公式, so that 不同角色看到的是同一个数。
57. As a 平台, I want 能从订单无人接发现供给时段不足, so that 我能提前调度而不是事后补救。
58. As a 平台, I want 能对比干预前后的履约率, so that 我能证明运营动作有效。
59. As a 管理员, I want 指标口径变更有记录, so that 历史数据仍然可解释。
60. As a 开发者, I want 统计全部由后端聚合, so that 前端不需要拉全量数据自行计算。

## 四、Implementation Decisions

### 4.0 全局决策（对六版共同生效）

| # | 决策 | 依据 |
|---|---|---|
| G1 | **串行推进，不并行启动多个大型 Epic** | 《迭代计划》§64 |
| G2 | **最小化数据库迁移**：新增字段前先确认「是否产生新的业务事实 / 是否可由已有数据计算 / 是否应由 Service 聚合 / 是否必须持久化 / 是否会成为未来核心查询条件」 | 《迭代计划》§50 |
| G3 | **不引入 `/api/v3` 版本前缀**，保持现有 REST 风格与 `/api` 前缀 | 《迭代计划》§53 |
| G4 | **新增能力一律遵循 Controller → Service → Repository → Database**，Controller 不承载业务规则 | 《迭代计划》§54；《项目宪法》§2.3 |
| G5 | **实时通道不新增**：聊天走 WebSocket，未读 / 系统提醒 / 订单状态提醒 / 履约风险提醒走既有 SSE | 《迭代计划》§56；`docs/prd/功能拓展规划.md` §二 A3 |
| G6 | **适老化要求不降低**：≥18px 字号、≥48px 触控区、≥4.5:1 对比度、核心流程 ≤3 次点击；老人端不得为增加功能牺牲可用性 | 《迭代计划》§58；`docs/adr/0007` |
| G7 | **合规三条红线长期不变**：不做诊断 / 不开药方；隐私最小化 + 脱敏；不做在线支付 / 地图导航 | 《项目宪法》§0.1；《迭代计划》§61 |
| G8 | **前端统计零自行计算**：禁止在前端用大量订单数据 `reduce()` / `filter()` / `groupBy()` 自算核心经营指标 | 《迭代计划》§32 |
| G9 | **每个版本收口必须同步六处文档**：PRD / ADR / API Contract / 数据库 Migration / 测试报告 / CHANGELOG | 《迭代计划》§66 |

### 4.1 V3.1 · 履约保障中心

| # | 决策 |
|---|---|
| 1.1 | **订单状态机零改动。** 风险是**独立字段**，不是新状态；`status` 与 `fulfillmentRisk` 永不互相推导 |
| 1.2 | **风险升级绝不修改 `status`。** `order_status_log` 只记状态流转，履约事件走**独立表**，避免污染状态机唯一入口（ADR-0010）的日志 |
| 1.3 | **风险只在 `status = PENDING` 时有意义**；一旦离开 `PENDING`，风险回落 `NORMAL` 并停扫 |
| 1.4 | 风险等级 `NORMAL / WARNING / URGENT / MANUAL_REQUIRED`，只允许前进；回落**只**由「离开 PENDING」触发 |
| 1.5 | 一轮扫描**允许连续升级到应有等级**，但**只写一条履约事件**（记录最终等级），避免同一轮产生多条噪音通知 |
| 1.6 | **全部阈值配置化**于 `nianglin.fulfillment.*`，零硬编码分钟数 |
| 1.7 | 工作状态**扩展现有枚举**为 `AVAILABLE / REST / OFFLINE`，不新造 `WORKING / PAUSED`（`REST` 语义已是「暂停接单」） |
| 1.8 | 工作状态**只影响新订单匹配**，已接订单继续按订单状态机执行 |
| 1.9 | 管理员**改派仅限 `PENDING`**；`ACCEPTED` 及以后换人走既有纠纷仲裁通道，不造第二条状态变更路径 |
| 1.10 | 风险扫描定时任务沿用既有的「Redis 锁 + 条件更新即认领」幂等范式与「异常自接住」写法 |
| 1.11 | 催单仅开放给风险达 `URGENT` 的订单；有冷却期与次数上限，用条件更新防并发穿透 |
| 1.12 | **大厅排序在 V3.1 只做单一推荐序**（就诊时间临近 + 同服务区域优先）；加权规则引擎留给 V3.4。理由：服务区域与可服务时段是自由文本，V3.1 硬编码权重必然在 V3.4 被推翻 |
| 1.13 | 新增错误码接续 3xxx 段：`3008` 催单不允许、`3009` 催单过于频繁、`3010` 订单不可改派 |
| 1.14 | 家属端只展示**事实型风险文案**（正在匹配 / 匹配时间较长 / 订单需要协调），不展示任何医疗判断 |

**依赖**：无。是六版的起点。

### 4.2 V3.2 · 老人健康协同中心

| # | 决策 |
|---|---|
| 2.1 | 健康时间线由 Order + OrderExecution + MedicationTask + Message **在 Service 层聚合**，**不建巨型 `health_record` 表**；只有出现无法由已有数据表达的新健康业务事实时才考虑持久化 |
| 2.2 | 健康概览只展示**客观数据**（本月就医次数 / 本月陪诊次数 / 用药完成率 / 漏服次数 / 最近一次陪诊 / 最近一次用药） |
| 2.3 | **事实记录优先，不进行医疗诊断。** 允许「今日有一次服药任务未确认」，不允许「老人今天健康状况较差」 |
| 2.4 | 所有数据来自**真实任务状态**，不得使用虚构健康指标 |
| 2.5 | **不改变现有用药业务规则**；用药汇总只读聚合 |
| 2.6 | 家属端与老人端共用同一份聚合结果，避免两套口径 |
| 2.7 | **跨版本共享统计区间**：默认 30 天 / 上限 366 天 / 闭区间，落在 `common/DateRange` + `dto/DateRangeQuery`；M10 一并改用（2026-10-20 开工时拍板） |
| 2.8 | **指标字典提前到 V3.2 第一张票**（`docs/spec/metric-dictionary.md` + yml 机器面），V3.3 / V3.5 只能「登记」不能「新定义」；V3.6 退化为校验与补全（2026-10-20 开工时拍板，推翻原 §7.1-3 的「V3.6 开工时才建字典」） |
| 2.9 | **用药三桶以 `MedicationCalendarVO` 的划分为唯一真源**，顺手修 M10 的 `selectDailyMedicationCounts` 与两处错误注释（2026-10-20 开工时拍板） |

### 4.8 前端信息架构决策

V3.x 不允许「功能越来越多 / 页面越来越散 / 导航越来越长」。四端收敛为：

老人端   └── 健康中心

新增页面必须落在既有分组内；新增导航项需说明它替代或合并了哪个旧入口。

## 五、Testing Decisions

### 5.1 什么算好测试

**只测外部可观察的行为，不测实现细节。** 具体到本项目：

- ✅ 断言接口返回的 `code` / `data` 字段、履约事件的写入结果、审计日志的存在、状态机的合法流转表。
- ❌ 断言私有方法被调用了几次、内部 Map 的 key 叫什么、Service 里某行的判断顺序。
- 断言优先级：**客观事实 > 被测函数的返回值**。不把「函数返回了自己刚写进去的值」当作验证——那是把实现锁死。

### 5.2 沿用既有测试范式，不新增框架

| 层 | 既有先例 | 六版统一要求 |
|---|---|---|
| 纯函数 / 状态机 | 表驱动的状态流转单测 | V3.1 风险判定、V3.4 权重计算必须做成无 Spring 上下文的纯函数 |
| Service 单测 | Mockito + Service 层单测 | 每条业务规则至少一条正向 + 一条反向 |
| 越权矩阵 | 现有 access matrix 范式 | 每个新增端点必须有「非授权角色 + 合法 payload」的越权用例，**不允许死在校验链拿到假绿** |
| 定时任务 | 幂等 + 锁未抢到跳过 | V3.1 扫描任务连跑两轮不得产生重复事件 |
| E2E | `frontend/e2e/` + `tools/e2e/` | 每版新增场景；**原有 166 条必须全绿** |

### 5.3 每版质量门禁

**功能**：核心流程完成 · 正常路径通过 · 异常路径通过 · 权限边界通过
**后端**：Service 层业务规则完整 · Controller 无核心业务逻辑 · API 返回结构稳定 · Migration 可重复验证 · 定时任务幂等
**前端**：桌面端正常 · 移动端 / 响应式正常 · 适老化不降级 · Loading / Empty / Error 三态完整
**测试**：单元 + API + E2E + 回归
**文档**：PRD / ADR / API / CHANGELOG 四处同步

**合规扫描**：全站文案 grep 违禁词（诊断 / 建议服用 / 推荐剂量 / 疾病预测）为空；文档与示例数据中无真实手机号 / 身份证号 / 密码。

### 5.4 反向验证（防「假实现」）

对**有唯一真相表**的机制，删除一条边必须让测试变红：

| 机制 | 反向验证动作 | 期望 |
|---|---|---|
| 订单状态机 `TRANSITIONS` | 删掉任一条边 | 状态流转单测变红 |
| 风险判定阈值 | 把某阈值改成极大值 | 风险判定单测变红 |

判据：测试变红 = 机制被真正锁住；仍然全绿 = 该测试是假绿，必须重写。

## 六、Out of Scope

以下内容**明确排除**在 V3.1 – V3.6 之外（《迭代计划》§61），实施时如遇需求应主动拒绝或改写：

| 排除项 | 原因 |
|---|---|
| **在线支付**（支付 / 退款 / 支付回调 / 对账 / 资损 / 渠道管理） | 当前产品核心价值不依赖在线支付，技术与业务复杂度过高。沿用线上记账 + 线下结算 |
| **地图导航**（高德 / 百度 / 实时导航 / 路线规划） | 文字地址 + 签到坐标 + 距离校验已足以支撑陪诊业务 |
| **AI 医疗诊断**（症状诊断 / 疾病预测 / 处方推荐 / 药物推荐 / 治疗方案） | 项目合规红线，无医疗资质与依据 |
| **小程序 / 原生 App 跨端开发** | Web 端已能完整承载核心业务。除非出现明确的用户规模 / 频率 / 设备 / 推送需求 |
| **无意义 CRUD**（无业务价值的管理页、重复数据列表、重复统计页、无闭环字段） | 违反价值门禁第 2 条 |
| **V3.4 第一阶段的 AI 模型** | 先建规则引擎；AI 只在运营分析方向且需另行论证 |
| **并行启动多个大型 Epic** | 《迭代计划》§64 |
| **`/api/v3` 版本化前缀** | 保持现有 REST 风格 |
