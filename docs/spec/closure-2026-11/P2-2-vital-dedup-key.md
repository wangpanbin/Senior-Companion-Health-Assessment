# P2-2 · 体征去重键含录入人

> 批次：**B（用药与文档域）** · 级别：P2 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P2-2
> 错误码：**不新增**（复用 `2008 VITAL_SIGN_DUPLICATED`）

## Problem Statement

体征记录有防重复机制：同一老人、同一类型、同一测量时间只能有一条。撞键时返回 `2008`。

但去重键**不含录入人**。于是出现这种场景：

- 陪诊员在服务中测了血压，15:30 录入；
- 家属同时在家里用血压计也测了一次，15:30 录入（同一分钟）；
- 家属被拒绝："该体征记录已存在"。

家属看到的是一个无法理解的错误：他明明刚测完，系统说他重复了。而他根本不知道陪诊员也测过。

## Solution

去重键加上录入人：同一人同一分钟录同类体征判重，不同人各自独立。

这样「同一时刻两个人的测量」都被保留，符合现实——两台血压计本来就会给出两个值。

## User Stories

1. 作为家属，我想在陪诊员也测过血压时仍能录入我的测量结果，这样我不会被莫名拒绝。
2. 作为家属，我想看到每条体征是谁录的，这样我能判断可信度。
3. 作为陪诊员，我想我的测量不被家属的同分钟录入挡住，这样我的服务记录完整。
4. 作为陪诊员，我想误提交两次仍被拦住，这样我不会造出重复数据。
5. 作为老人，我想健康趋势图能容纳同一天多个来源的测量，这样曲线反映真实情况。
6. 作为管理员，我想在纠纷时区分「陪诊员测的」和「家属测的」，这样我能判断责任。
7. 作为运营，我想知道体征录入的渠道分布，这样我能评估哪端更活跃。
8. 作为测试者，我想看到「不同录入人同分钟同类体征 → 都成功」的用例。
9. 作为测试者，我想看到「同一录入人同分钟同类体征 → 第二条被拒」的用例（保护防重复）。
10. 作为测试者，我想看到「不同录入人不同分钟 → 都成功」的用例。
11. 作为测试者，我想看到「唯一键冲突仍返回2008」的用例（错误码不变）。
12. 作为开发者，我想去重语义有明确注释，这样后人不会误以为「同分钟只能一条」。
13. 作为开发者，我想历史数据不受影响（迁移时 `record_by` 已有值）。
14. 作为开发者，我想这次改动只动唯一键，不动服务逻辑。
15. 作为开发者，我想前端不需要改（错误码与成功路径都不变）。

## Implementation Decisions

### 数据变更（迁移脚本）

- 检查 `vital_sign_record` 现有唯一键（`V9__vital_sign_record.sql`），把去重键从 `(elder_id, type, measure_time)` 改为 `(elder_id, type, measure_time, record_by)`。
- **历史数据风险**：若库里已有「同老人同类型同分钟不同录入人」的记录，说明旧键其实没拦住（不可能——旧键会拦）。所以改键**不会因历史数据失败**（旧键更严格 ⇒ 新键必然满足）。
- 迁移脚本版本号与 A 批协商，先合先占号。

### 规则

- 服务层不改：仍靠捕获 `DuplicateKeyException` → `2008`。唯一键变严还是变松，服务层不用感知。
- **`record_by` 必须是 `NOT NULL`**：若为 null，MySQL 唯一键会把多条 null 视为不重复，去重失效。先确认该列是否已有 `NOT NULL` 约束；若没有，迁移里一并加（并确认历史数据无 null）。

### 接口变更

- 无。`2008` 的 message 可微调为「您已在该时间录入过同类体征」以体现「同一人」语义（可选）。

## Testing Decisions

### 好测试

这是**数据库约束**行为，单测无法真实验证。可行的单测层级：

- 断言「服务层的去重依赖唯一键而不是先查后插」（即：插入时不先 `selectCount`）。
  - 若现有实现是「先查后插 + 唯一键兜底」，则单测断言「`selectCount` 未被调用」是有效的实现约束，但这属于实现细节，**不推荐**。
- **推荐**：只写一条「冲突时返回 2008」的回归测试（用 mock 让 `insert` 抛 `DuplicateKeyException`），把「键包含 `record_by`」这件事交给迁移脚本 review + 人工 SQL 验证。

### 测试模块

扩展 `VitalSignSecurityTest` 或新建 `VitalSignDedupTest`

### 垂直切片

1. **红**：`唯一键冲突时应返回2008`（回归保护，若已有则跳过）。
2. **人工验证**（写进 commit body）：
   ```sql
   -- 两个不同 record_by，同分钟同类型：应都成功
   INSERT INTO vital_sign_record (elder_id, type, measure_time, record_by, ...) VALUES (301,'BP','2026-11-28 15:30:00',300,...);
   INSERT INTO vital_sign_record (elder_id, type, measure_time, record_by, ...) VALUES (301,'BP','2026-11-28 15:30:00',302,...);
   -- 同一 record_by 再插一条：应失败
   ```

### 先例

`VitalSignSecurityTest`（体征权限与去重错误码）。

## Out of Scope

- 不改体征类型枚举。
- 不改趋势聚合（同一天多条会自然出现在曲线上，是期望行为）。
- 不改前端录入表单。
- 不做「按录入人筛选」的新参数（另议）。

## Further Notes

- **本单是 25 条里唯一「单测证明力最弱」的一条**：唯一键属于 schema 行为，Mockito 单测只能断言「冲突被翻译成 2008」。因此本单的验收必须包含**人工 SQL 验证**，并写进 commit body。
- 若团队希望有自动化覆盖，可加一条 `@SpringBootTest` + 真库的 RealDb 测试（仓库里已有 `OperationsGapRealDbTest` 这样的先例）。**但这与“不连真库”的测试 seam 决策冲突**——建议仅在本地手动跑一次、不入 CI。
