# P1-4 · 用药计划创建/修改与已生成任务同源

> 批次：**B（用药与文档域）** · 级别：P1 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P1-4
> 错误码：**不新增**

## Problem Statement

两个相关的断链，都在「计划」与「任务」之间：

1. **晚间建计划即判漏服**：家属 21:00 建一个「每日 2 次 08:00 / 20:00」的计划，系统立刻生成当天两个任务（08:00 已过去 13 小时）。30 分钟扫描一看都超时 → 两条全判漏服。家属刚建完计划，漏服率就变差了。

2. **改计划不同步已生成任务**：家属把药名从「氨氯地平」改成「硝苯地平」，当天已生成的任务仍是旧药名。老人照着任务吃药，看到的是错的药。

## Solution

- 生成任务时**跳过已过去的时点**（不生成、也不补判——本来就不该在这些时点吃药）。
- 修改计划时**重算当天的未确认任务**：删掉未来 `PENDING` 的重建，已过时点的保留（那是历史事实）。

## User Stories

1. 作为家属，我想晚上建计划不会凭空产生两条漏服，这样漏服率反映真实情况。
2. 作为家属，我想建计划时系统提示「今天的 08:00 已过，从明天开始」，这样我知道生效时间。
3. 作为家属，我想改药名后当天还没吃的任务跟着变，这样老人不会吃错药。
4. 作为家属，我想改时间点后当天任务跟着调整，这样提醒时间是新的。
5. 作为家属，我想已经吃过的那条任务不被改动，这样历史记录是可靠的。
6. 作为陪诊员，我想代确认时看到的是当前药名，这样我不会确认一条已经作废的任务。
7. 作为老人，我想首页只显示还没到的服药时点，这样我不会在晚上看到「早上漏服」的自责提示。
8. 作为运营，我想新建计划当天不产生虚假漏服，这样「漏服率」这个指标可信。
9. 作为运营，我想修改计划的次数可统计，这样我能判断是不是录入太随意。
10. 作为测试者，我想看到「21:00 建计划 → 当天不生成已过时点的任务」的用例。
11. 作为测试者，我想看到「改药名 → 当天未确认任务药名更新」的用例。
12. 作为测试者，我想看到「改时间点 → 未来任务重建、历史任务不动」的用例。
13. 作为开发者，我想生成逻辑只有一个入口，这样创建与修改不会走两套。
14. 作为开发者，我想重算使用「删未来 + 重建」而不是「原地改」，这样时间点变更也能覆盖。
15. 作为开发者，我想重算时同步作废对应的未发送短信回执，这样不会给已不存在的任务发提醒。

## Implementation Decisions

### A. 生成时跳过已过时点

- `generateTasksForPlan(plan, date)`：对 `plan_time < now`（当天）的时点**跳过不生成**。
  - 边界：允许 `now + 1 分钟` 的宽容窗口（创建计划的操作本身要花时间，恰好卡在整点会漏）。
  - 配置项：`nianglin.medication.generate-grace-minutes`（默认 1）。
- **只对「今天」生效**：补跑历史日期（`date < today`）时仍生成全部时点——那是补数据，不是新建。
- 创建计划的响应/VO 应能表达「今天从哪个时点开始」，让前端提示「今天的 08:00 已过，从 20:00 开始」。**建议在 `MedicationPlanIdVO` 或新增的创建响应里带 `effectiveFrom`（今天的首个生效时点，可能为 null）。**

### B. 修改计划时重算当天任务

- `updatePlan` 在写完计划表之后（同事务）：
  1. 找出该计划**当天**、`status = 'PENDING'`、`plan_time > now` 的任务，记录 id 列表；
  2. 软删这些任务；
  3. 调用 `generateTasksForPlan(plan, today)` 重建；
  4. 调 `smsReminderService.voidUnsentForTasks(被删的 id 列表, "plan-updated")` 作废对应未发送回执（`disablePlan` 已有此调用的范式）。
- **不碰已过时点的任务**（`plan_time <= now`），无论其状态——那是历史。
- **不碰 `TAKEN` / `MISSED` 任务**，即使 `plan_time` 在未来（理论上不会有，但防御）。

### C. 与 P1-5 的边界

本单**不碰**「停用 / 重新启用」。但本单的「重算当天任务」逻辑会被 P1-5 的「启用」复用——**建议把重算抽成一个私有方法 `rebuildTodayPendingTasks(plan)`，P1-5 直接调用**。这一条要在两单之间对齐，避免各写一份。

### 接口变更

- `POST /api/medication/plan`：响应可能新增 `effectiveFrom`。
- `PUT /api/medication/plan/{id}`：行为变更——当天未来任务会被重建。
- `docs/api/05-medication.md` §4、§5 补充说明（含「修改只影响当天未到时点与未来日期」的口径）。

## Testing Decisions

### 好测试

断言「在给定的 `now` 与 `timePoints` 下，哪些任务被生成 / 被删除 / 被重建」。**时间必须可注入**——不要用 `LocalDateTime.now()` 真值断言。

### 测试模块

扩展 `MedicationServiceTest`（或新建 `MedicationPlanTaskSyncTest`，视现有测试类规模而定）

### 垂直切片

1. **红**：`晚上建计划_当天已过时点不应生成任务`。
2. 实现 A。
3. **红**：`早上建计划_当天全部时点应生成`（保护现状）。
4. **红**：`补跑历史日期仍应生成全部时点`（保护补数据场景）。
5. **红**：`改药名后_当天未来任务药名应更新`。
6. 实现 B。
7. **红**：`改时间点后_未来任务应重建为新的时点`。
8. **红**：`已过时点的任务不应被删除或重建`。
9. **红**：`重算时应作废被删任务的未发送短信回执`。

### 先例

`MedicationServiceTest`（计划 CRUD 与任务生成的既有断言）；`MedicationDraftFromOrderTest`（`voidUnsentForTasks` 的调用断言）。

## Out of Scope

- 不改漏服扫描阈值（属 P2-1）。
- 不做「修改计划的历史版本追溯」（只留日志）。
- 不改停用/启用（属 P1-5）。
- 不改前端计划表单（需另开工单：显示 `effectiveFrom` 提示）。

## Further Notes

- **时间注入是这条工单的技术难点**：`MedicationServiceImpl` 里大量 `LocalDateTime.now()`。若不方便注入 `Clock`，至少把「判断是否已过」抽成一个可覆盖的私有方法（`protected boolean isPast(LocalDateTime t)`），测试用 `spy` 覆盖。**不建议为此引入 `Clock` 全局改造**（影响面太大，不在本单范围）。
- **与 P1-5 的方法复用要在开工前对齐**：两单都改 `MedicationServiceImpl`，同一批次同一个 agent 做，顺序应是 **P1-4 先做**（建立 `rebuildTodayPendingTasks`），P1-5 后做（复用 + 改唯一键）。
