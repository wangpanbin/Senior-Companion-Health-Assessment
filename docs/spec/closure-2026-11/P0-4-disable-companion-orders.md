# P0-4 · 封禁陪诊员须处理在手订单

> 批次：**A（订单与结算域）** · 级别：P0 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P0-4
> 依赖：**P0-1 先做**（本单复用 P0-1 建立的「清 `companion_id` 回 PENDING」语义）
> 错误码：新增 `2012 COMPANION_HAS_ACTIVE_ORDER`

## Problem Statement

管理员封禁一个正在服务中的陪诊员之后，这个陪诊员的账号立刻 403，**他名下「已接单」「服务中」的订单没有任何人处理**：

- 他打不了卡、完成不了订单；
- 家属无法取消（取消只允许「待接单」）；
- 履约风险中心看不到（只扫「待接单」）；
- 唯一的出路是管理员找到这张单，手动仲裁强制终态。

家属侧看到的是「订单永远在服务中」，没有任何自助出路；后台也没有任何告警，必须靠人发现。

## Solution

封禁陪诊员时，系统强制要求管理员先处理他名下的在手订单：要么把单放回大厅（订单继续，由别人接手），要么强制取消并通知家属。不允许「一键封禁 + 留下无主订单」。

两种处置都必须留下审计记录并通知家属。

## User Stories

1. 作为管理员，我想在封禁一个有在手订单的陪诊员时被明确告知「他有 N 张在途单」，这样我不会在不知情的情况下造出无主订单。
2. 作为管理员，我想选择「把单放回大厅」来处理在途单，这样家属的服务还能继续。
3. 作为管理员，我想选择「强制取消」来处理在途单，这样家属能尽快得到明确的结论而不是无限等待。
4. 作为管理员，我想在处置时填写理由，这样审计能看到为什么。
5. 作为管理员，我想处置结果写进操作日志，这样事后能追责。
6. 作为家属，我想在陪诊员被封禁后收到站内信，这样我知道发生了什么、接下来怎么办。
7. 作为家属，我想在「放回大厅」后看到订单重新变成待接单，这样我不用重新下单。
8. 作为家属，我想在「强制取消」后看到订单进入终态，这样我能去申诉或重新下单。
9. 作为家属，我想在订单被强制取消时看到取消原因是「陪诊员账号异常」，而不是空白。
10. 作为陪诊员，我想在被封禁时手上的单不会静默消失，这样解封后我能看到这些单的去向。
11. 作为运维，我想在风险中心看到「因封禁导致改派的订单」，这样能评估这类事件的影响面。
12. 作为运维，我想封禁与订单处置在同一个事务里，这样不会出现「账号封了但订单没动」。
13. 作为测试者，我想看到一条「封禁有在途单的陪诊员 → 订单状态变成待接单」的用例，这样回归时不会退回到静默卡死。
14. 作为开发者，我想这个处置逻辑只有一个入口，这样将来加「停用资质」等其他场景时能复用。
15. 作为审计者，我想在 `admin_oper_log` 里区分「仅封禁」与「封禁并处置 N 张单」，这样事后统计更准。

## Implementation Decisions

### 规则

- `disableUser` 在**改账号状态之前**先查该用户名下的 `ACCEPTED` / `IN_SERVICE` 订单。
- 若有在途单且请求**未指定处置方式** → 抛 `2012 COMPANION_HAS_ACTIVE_ORDER`，`data` 返回 `{ activeOrderCount: n }`，前端据此弹处置选择框。
- 若有在途单且**已指定处置方式**：
  - `RELEASE`（放回大厅）：每张单执行 `status: ACCEPTED|IN_SERVICE → PENDING`、`companion_id = NULL`、`accept_time = NULL`、`start_time = NULL`、`version = version + 1`；写 `order_status_log`（`operator_role = SYSTEM`，remark 说明「陪诊员账号被封禁，订单退回待接单」）；写履约事件；通知家属。
  - `CANCEL`（强制取消）：每张单走 `forceTerminal → CANCELLED`（复用已有的唯一入口，不新写状态写入）；`cancel_reason` 写「接单陪诊员账号异常，平台强制取消」；通知家属。
- **两种处置都写 `admin_oper_log`**：`target_type = USER`，remark 里带处置方式与单号列表摘要。
- 处置与封禁**同事务**。任一单处置失败整体回滚（不留半封禁状态）。

### 接口变更

- `POST /api/admin/user/{id}/disable`：请求体新增可选字段 `activeOrderAction`（枚举 `RELEASE` / `CANCEL`，可空）；新增失败码 `2012`。
- `docs/api/08-admin.md` 封禁一节补处置说明与错误码。

### 数据变更

无新表、无新列。

## Testing Decisions

### 好测试

断言「在不同前置数据 + 不同请求参数下，`disableUser` 抛哪个码 / 调用了哪些 Mapper 的哪种更新」。不拉真库。

### 测试模块

`AdminDisableUserTest`（新建；现有 `AdminServiceTest` 覆盖了基础封禁，本单不塞进去以免测试类膨胀）

### 垂直切片

1. **红**：`封禁无在手订单的陪诊员应成功`（保护现状不被破坏）。
2. **红**：`封禁有ACCEPTED单的陪诊员且未指定处置应返回2012`，且 `data.activeOrderCount` 正确。
3. **红**：`封禁有IN_SERVICE单的陪诊员且未指定处置应返回2012`。
4. **红**：`选择RELEASE时应把单改回PENDING并清空接单人`。
5. **红**：`选择CANCEL时应走forceTerminal而不是自己写状态`（断言调用了 `orderService.forceTerminal`）。
6. **红**：`两种处置都应通知家属`。
7. **红**：`处置失败时封禁应整体回滚`（让第二张单处置抛异常，断言 `sysUserMapper` 未被更新）。
8. **红**：`封禁管理员账号仍应返回8002`（保护既有规则优先于新规则）。

### 先例

`AdminArbitrateTest`（事务内多写 + 通知 + 审计的断言组合）；`AdminReassignTest`（`admin_oper_log` 的 before/after 断言）。

## Out of Scope

- 不做「批量封禁」。
- 不做「陪诊员自行申请停用资质」时的同一套处置（后续工单）。
- 不处理家属的封禁对订单的影响（家属被封禁时订单仍在，只是他无法操作——属不同问题）。
- 不改前端用户管理页（需另开工单：弹处置选择框）。

## Further Notes

- **RELEASE 语义必须与 P0-1 完全一致**：都是「`PENDING` + `companion_id IS NULL`」。若两单写法不一致，大厅过滤会漏掉这批单。
- 强烈建议在 `docs/api/08-admin.md` 里明写「封禁陪诊员是不可逆操作，已在途订单必须先处置」，避免管理员误操作。
