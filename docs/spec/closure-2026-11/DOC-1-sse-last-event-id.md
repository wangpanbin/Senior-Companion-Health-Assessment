# DOC-1 · SSE 补齐口径与 PRD 对齐

> 批次：**B（用药与文档域）** · 级别：DOC · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §DOC-1
> 错误码：**不新增**

## Problem Statement

`docs/prd/功能拓展规划.md` 有两处把 M8 站内信标为「`Last-Event-ID` 离线补齐 ✅」：

- §1.2 已交付能力表：`| M8 站内信 | 4 类模板、SSE 未读数推送、\`Last-Event-ID\` 离线补齐 | ✅ |`
- §2.1 工程资产表 A3：`「M8 已有 \`Last-Event-ID\` 离线补齐」`

但实现里**没有这回事**：

- 全仓 Java 侧 grep `lastEventId` / `Last-Event-ID` **0 命中**；
- `MessageSseHub#push` 无事件缓冲；`sendTo` 用 `event().name().data()`，**从未设置 `.id(...)`**，服务端根本不发事件号；
- 无连接时 `push` 直接 `return`，消息只在库里，不补投。

而另外两份文档说的是相反的：

- `docs/api/07-message.md:276`：「重连后先调 `/api/message/unread-count` 对齐数字」；
- `docs/user-guide.md:217`：「断线用 `Last-Event-ID` 补齐」。

**同一件事，四份文档三种说法。** 而 `docs/prd/功能拓展规划.md` §1.2 是评审会读的表——顺着 M8 这一行追问，会发现整张 ✅ 表的证据链都不可靠。

## Solution

把文档对齐到实现：**SSE 负责「3 秒内看到红点变化」，断线后由客户端主动调 `unread-count` 对齐**。删掉所有「`Last-Event-ID` 离线补齐」的表述。

不改实现——「重连即丢、靠调用方补拉」是可接受的工程取舍，且已有轮询兜底通道。**改写文档，不补功能。**

## User Stories

1. 作为评审人，我想 PRD 里写的每一项都已实现，这样我不会怀疑其他 ✅ 也不可信。
2. 作为评审人，我想「离线补齐」这件事要么有要么没有，不要两套说法。
3. 作为前端开发者，我想文档明确告诉我「重连后要做什么」，这样我按文档写就不会漏消息。
4. 作为前端开发者，我想知道 SSE 不保证不丢消息，这样我会正确设计兜底。
5. 作为运维，我想知道这条通道的保证强度，这样我不会把它当成可靠队列。
6. 作为运维，我想文档里说清楚「有轮询兜底」，这样我知道单靠 SSE 不够时怎么办。
7. 作为测试者，我想验收清单里不含无法验证的「离线补齐」项。
8. 作为测试者，我想看到「重连后调 unread-count」被写进验收步骤。
9. 作为产品，我想 PRD 的 ✅ 每一条都能在代码里找到对应实现。
10. 作为产品，我想如果将来真要补 `Last-Event-ID`，文档里已经写清现状，这样改动有基线。
11. 作为新成员，我想四份文档说的是同一件事，这样我不会被三种说法搞晕。
12. 作为审计者，我想知道这条通道的已知限制，这样我不会过度承诺。
13. 作为开发者，我想文档改动不改代码，这样零回归风险。
14. 作为开发者，我想这条改动同时清掉 user-guide 里的错误说法。
15. 作为文档维护者，我想这次改动后跑一遍 `gate_check.py` 全绿。

## Implementation Decisions

### 改文档（四处）

1. `docs/prd/功能拓展规划.md` §1.2 表格行改为：
   `| M8 站内信 | 4 类模板、SSE 未读数推送（断线后由客户端调 unread-count 对齐） | ✅ |`
2. `docs/prd/功能拓展规划.md` §2.1 A3 行改为：
   `新事件的「下行」不必新建通道，走 M8 SSE 即可（M8 未读数推送 + 60 秒轮询兜底；SSE 不保证补投，重连后需调 unread-count）`
3. `docs/api/07-message.md` §7：**保留现状表述**（它是对的），但补一句「服务端不下发事件 id，因此浏览器不会带 `Last-Event-ID`；断线补齐由客户端调 `unread-count` 完成」——把「为什么没有」说清楚。
4. `docs/user-guide.md:217`：删除「断线用 `Last-Event-ID` 补齐」，改为「断线重连后请刷新页面或重新打开消息中心，未读数以服务端为准」。

### 可选：加一条门禁

- 若希望以后不再出现这类漂移，可在 `tools/ai_flow/gate_check.py` 加一条检查：**全仓文档里出现 `Last-Event-ID` 时，必须在同一段内出现「未实现」或「不补投」的限定词**。
  - 这是**可选**项，因为规则偏窄。本单**建议做**，因为它是唯一能防止该问题复发的机械手段。

### 不改的东西

- **不改 `MessageSseHub`**（不加事件缓冲、不加 `.id()`）。这是刻意的：加缓冲会引入内存管理、多端一致性、TTL 等一系列新问题，收益（3 秒内的红点）不值得。
- 不改 `docs/agents/PLAN_BACKEND.md:59`（那是历史计划书，属于「当时的计划」，可以保留，但要确认它不是当前契约）。
  - **若它被当作当前契约引用**，则同样改掉。
