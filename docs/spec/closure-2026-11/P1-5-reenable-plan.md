# P1-5 · 停药可重新启用（先改唯一键）

> 批次：**B（用药与文档域）** · 级别：P1 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P1-5
> 依赖：**P1-4 先做**（本单复用其 `rebuildTodayPendingTasks`）
> 错误码：**不新增**

## Problem Statement

用药计划只能「停用」，**没有「重新启用」**。家属误点了停用，或者老人出院后又需要继续吃药，只能重新建一个一模一样的计划——历史服药记录因此分裂在两条计划上。

而如果直接补一个「启用」按钮，会撞上一个埋着的雷：

- 停用时系统**软删**了当天未到点的任务（`@TableLogic`，`deleted = 1`）；
- 唯一键 `uk_plan_time(plan_id, plan_time)` **不含 `deleted`**，软删的行仍然占着这个键；
- 生成任务前的「先查后插」护栏走的是 `selectList`，`@TableLogic` 会自动追加 `deleted = 0`，**软删行对护栏不可见**；
- 于是重建时必然撞唯一键，而 `catch (DuplicateKeyException)` **只 `log.warn`，不处理、不重试、不抛**。

结果：启用成功了，但当天没有生成任何任务，界面上「启用了」，实际上「今天没药」，而且**错误信息为 0、日志只有一句 warn**。

## Solution

两步，顺序不能反：

1. **先改唯一键**，让软删行不再占位（或改用硬删）。
2. **再补「重新启用」端点**，复用 P1-4 的重算逻辑重建当天任务。

同时把静默吞异常改为「计数 + 超阈值告警」，否则同类问题下次仍然查不出来。

## User Stories

1. 作为家属，我想误点停用后能把计划恢复，这样我不用重建一个一模一样的。
2. 作为家属，我想恢复后当天还没到的时点立刻有任务，这样老人不会漏吃一顿。
3. 作为家属，我想恢复后历史服药记录仍挂在同一条计划上，这样依从性统计不分裂。
4. 作为家属，我想恢复后看到「已恢复」的明确提示，这样我确认操作生效。
5. 作为老人，我想恢复计划后首页马上显示今天的服药任务，这样我不会以为今天不用吃。
6. 作为陪诊员，我想恢复后的计划能正常代确认，这样服务不中断。
7. 作为运营，我想「计划恢复」这个动作有记录，这样我能评估停用是不是被误点。
8. 作为运维，我想任务生成撞唯一键时能看到告警而不是静默，这样我能及时发现配置问题。
9. 作为运维，我想唯一键的改动有迁移脚本可回溯，这样出问题能定位。
10. 作为测试者，我想看到「停用 → 启用 → 当天任务重新生成」的用例（**这是本单的核心回归**）。
11. 作为测试者，我想看到「启用后当天已过的时点不补生成」的用例。
12. 作为测试者，我想看到「重复启用是幂等的」的用例。
13. 作为开发者，我想唯一键与软删的交互有明确注释，这样后人不会再踩。
14. 作为开发者，我想静默吞异常改为可观测，这样同类问题不会再次隐身。
15. 作为开发者，我想这次改动不碰用药桶判定（属 P0-8）。

## Implementation Decisions

### A. 唯一键（迁移脚本，**必须先做**）

- 两个可选方案，二选一：
  - **方案 1（推荐）**：唯一键改为 `(plan_id, plan_time, deleted)`。
    - 好处：不改删除语义，`@TableLogic` 继续生效，历史可追溯。
    - 注意：MySQL 唯一键含 `deleted` 后，同一 `(plan_id, plan_time)` 最多允许**两条**（`deleted=0` 与 `deleted=1`）。若同一时点被反复「停用 → 启用 → 停用」，第三次软删会产生两条 `deleted=1` 的冲突。
    - **因此方案 1 必须配合：软删前先硬删同 `(plan_id, plan_time)` 的旧 `deleted=1` 记录**，或把 `deleted` 换成时间戳/序号（复杂度上升）。
  - **方案 2（更简单）**：停用时把「未来 `PENDING` 任务」改成**硬删**（`DELETE`），不软删。
    - 理由：这些任务从未发生，没有审计价值；已发生的任务（`TAKEN` / `MISSED`）保持不动。
    - 好处：唯一键完全不用改，零迁移风险。
    - 代价：失去「这些任务曾经生成过」的痕迹（可接受）。
- **本单推荐方案 2**：成本最低、无迁移、无索引变更风险。**方案 1 的 `deleted` 维度会让「反复停启用」产生新问题，得不偿失。**

### B. 重新启用端点

- 新增 `PUT /api/medication/plan/{id}/enable`（`FAMILY`）。
- 实现：
  1. 条件更新 `status: DISABLED → ACTIVE`（`WHERE status = 'DISABLED'`），影响 0 行则幂等返回成功。
  2. 调用 P1-4 建立的 `rebuildTodayPendingTasks(plan)` 重建当天未到点的任务。
  3. 写操作日志（复用现有的计划变更日志口径）。
- 幂等：重复启用返回成功，不重复重建（条件更新影响 0 行时直接返回）。
  - **但要注意**：若首次启用时重建了任务，第二次调用不应再删一遍重建（会打断用户的确认状态）。因此「影响 0 行」时才真正执行重建。

### C. 静默吞异常改为可观测

- `generateTasksForPlan` 的 `catch (DuplicateKeyException)` 改为：
  - 计数（本地 `AtomicInteger` 或直接统计返回值）；
  - 单轮冲突数 > 阈值（如 5）时 `log.error`（不是 `warn`），message 里带「唯一键冲突，请检查任务删除策略与唯一键定义」。
- 方法返回「新增条数」保持不变，但新增一个「冲突条数」的输出（可通过返回值对象或日志聚合）。

### 接口变更

- 新增 `PUT /api/medication/plan/{id}/enable`。
- `docs/api/05-medication.md` 新增 §6.1 或紧邻 §6（停用）补充。
- `docs/api/README.md` 权限矩阵无需改（FAMILY 已有写权限）。

### 数据变更

- 方案 2 下**无迁移脚本**。
- 若选方案 1，则需迁移脚本，版本号与 A 批协商。

## Testing Decisions

### 好测试

- **核心回归**：「停用 → 启用 → 当天任务数 > 0」。这是唯一能证明「方案 2 真的解决了软删占位」的测试。
- 断言「重建调用了 P1-4 的同一份逻辑」（`verify` 私有方法不可行，改为断言行为：任务被重建）。

### 测试模块

新建 `MedicationPlanEnableTest`

### 垂直切片

1. **红**：`启用已停用的计划应成功且状态变ACTIVE`。
2. 实现端点 + 条件更新。
3. **红**：`启用后当天未到点的任务应被重建`。
4. **红**：`启用后当天已过时点的任务不应生成`（与 P1-4 口径一致）。
5. **红**：`重复启用应幂等不重复重建`。
6. **红**：`启用不存在的计划应404`。
7. **红**：`停用应硬删未来PENDING任务而不是软删`（这条锁住方案 2 的关键决策）。
8. **红**：`停用不应删除已发生的TAKEN或MISSED任务`。
9. **红**：`唯一键冲突超阈值应error日志`（可用 `@Spy` + `ListAppender` 断言）。

### 先例

`MedicationServiceTest`（计划状态变更）；`MedicationDraftFromOrderTest`（作废回执的调用断言）。

## Out of Scope

- **不做「计划克隆」**（用户想复制一个计划而不是恢复 —— 是另一个需求）。
- 不改 `disablePlan` 的「已过时点不删」策略（那是对的）。
- 不改 P0-8 的桶判定。
- 不改前端计划列表（需另开工单：加「恢复」按钮）。

## Further Notes

- **为什么最终选方案 2**：方案 1 看起来「更正规」（保留软删痕迹），但 `(plan_id, plan_time, deleted)` 这个三元唯一键在「反复停启用」下会二次碰撞，需要额外的清理逻辑；而未来 `PENDING` 任务被删掉后本来就无价值（从没发生），硬删是对的语义。
  **如果团队坚持软删**，那就必须接受「同一时点最多停用一次」这个限制，并在 `docs/api/05-medication.md` 明写。

- **本单与 P1-4 必须同一个人做、按 P1-4 → P1-5 顺序**：P1-4 建立 `rebuildTodayPendingTasks`，P1-5 复用。若分给两人，会产生两份重建逻辑。

- **验收锚点**：`停用 → 启用` 之后，老人端首页当天必须立刻出现未到点的服药任务。这是本单唯一必须人工走查的项（单测覆盖到 service 层为止）。
