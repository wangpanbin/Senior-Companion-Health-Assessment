# P1-2 · 评价裁定无效后的正向出口

> 批次：**A（订单与结算域）** · 级别：P1 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P1-2
> 依赖：**P1-6 先做**（申诉占用按 type 隔离，是本单的前置）
> 错误码：**不新增**（复用 `REVIEW_ALREADY`）

## Problem Statement

陪诊员申诉成功、管理员把一条恶意差评裁定为「无效」之后，系统里发生的事只有：`order_review.is_valid = 0`。

于是这一单的真实状态是：

- 订单停在终态「已评价」，不能回退；
- 该单**不能重新评价**（同一订单已有评价记录，唯一约束拦住）；
- 评分聚合不再计入这条；
- 但评价率统计仍把它算作「已评价」。

结果是一单恶意差评被「纠正」后的真实效果是「这单等于没人评过」，而系统两边都记录成「已评价」。E4「评价公信力闭环」缺最后一步。

## Solution

裁定无效时给出明确的正向出口：**该订单允许再提交一次评价**。旧记录保留（作为审计证据），新记录成为唯一有效评价。

**不动订单状态**（`REVIEWED` 保持终态，符合全局状态机原则）。

## User Stories

1. 作为家属，我想在恶意评价被裁定无效后能重新评价一次，这样我的真实体验能被记录。
2. 作为家属，我想看到旧的无效评价不再显示在陪诊员页面上，这样它不会继续误导别人。
3. 作为家属，我想在重新评价时系统告诉我「上一次评价已被平台判定无效」，这样我知道为什么要重评。
4. 作为陪诊员，我想被裁定无效的差评不再拉低我的评分，这样我申诉成功是真的有用。
5. 作为陪诊员，我想我的评分只统计有效评价，这样它反映真实服务水平。
6. 作为管理员，我想裁定无效时系统自动告诉家属「可以重新评价」，这样我不用另外解释。
7. 作为管理员，我想裁定无效后订单仍然显示「已评价」，这样统计口径不变。
8. 作为管理员，我想在评价详情里看到「该评价已被裁定无效，家属已重评」这样完整的轨迹。
9. 作为运营，我想「有效评价数」与「评价率」在新口径下自洽，这样我汇报时不会自相矛盾。
10. 作为运营，我想看到重评率，这样我能评估申诉机制的效果。
11. 作为测试者，我想看到「无效 → 重评 → 新评价生效」的用例。
12. 作为测试者，我想看到「一条评价只能重评一次」的用例，防止无限重评刷分。
13. 作为开发者，我想旧评价记录不被物理删除，这样审计能追溯到原始内容。
14. 作为开发者，我想唯一约束的调整通过迁移脚本做，这样不依赖应用层保证。
15. 作为审计者，我想在库里区分「主动删除」与「裁定无效」，这样两种情况的处理不同。

## Implementation Decisions

### 数据变更（新迁移脚本）

- `order_review` 加列 `review_seq TINYINT NOT NULL DEFAULT 1`（历史数据全为 1）。
- 删除旧唯一键 `uk_order_review(order_id)`（**实际索引名以迁移脚本为准，实施前先确认**），新增 `uk_order_review(order_id, review_seq)`。
- **必须在 `backend/sql/` 新开迁移脚本**（V1–V14 已应用，不得修改）。版本号与 P1-3 / P2-4 协商，**先合的先占号，后合的在 rebase 时改号**。

### 规则

- `create` 的评价前置条件从「该订单已有任一评价」改为「该订单已有**有效**评价（`is_valid = 1`）」。
  - 存在无效评价时允许新建一条，新记录 `review_seq = 旧最大 seq + 1`、`is_valid = 1`。
- **重评上限为 1 次**：`review_seq` 最大为 2。第三次提交 → `REVIEW_ALREADY`。
- `invalidate` 在置 `is_valid = 0` 之后，**同事务**：
  - 发站内信给下单家属（`MessageType.REVIEW_INVALIDATED` 已存在），文案加「您可以重新评价本单」；
  - 刷新陪诊员评分（现有 `refreshCompanionScore` 已做，只是没有通知）。
- 评分聚合**不变**（仍按 `is_valid = 1` 统计），因为同一订单同时最多一条有效。

### 接口变更

- `POST /api/review`：前置条件变更——允许在同一订单已有无效评价时再次提交；第三次返回 `REVIEW_ALREADY`。
- `POST /api/admin/review/{id}/validity`：响应新增 `canReReview` 布尔，前端据此提示家属。
- `docs/api/06-review-complaint.md` 补说明。

## Testing Decisions

### 好测试

断言「在不同前置评价组合下，`create` 抛哪个码 / 成功且 `reviewSeq` 是多少」。

### 测试模块

新建 `ReviewResequenceTest`（`ReviewAccessMatrixTest` 是权限矩阵，不扩展它）

### 垂直切片

1. **红**：`裁定无效后家属可以再次评价_且reviewSeq为2`。
2. 实现（迁移脚本 + 实体字段 + create 逻辑）。
3. **红**：`第二次有效评价也存在时_第三次评价应被拒`。
4. **红**：`裁定无效应通知家属可重评`。
5. **红**：`裁定无效应刷新陪诊员评分`（回归保护）。
6. **红**：`无效评价不应计入评分聚合`（回归保护）。
7. **红**：`旧评价记录不被删除`。

### 先例

`SettlementServiceTest`（口径与幂等的组合断言）；`FeedbackServiceTest`（状态流转 + 通知）。

## Out of Scope

- **不让订单状态从 `REVIEWED` 回退**（终态封闭是全局原则）。
- 不做「家属主动撤回评价」。
- 不做「重评后的评价再次被申诉」的无限循环（重评只有一次）。
- 不改前端评价页（需另开工单：从站内信跳转时带 `?reReview=1` 标记）。

## Further Notes

- **本单风险最高**：迁移脚本要 drop 旧唯一索引，是破坏性变更。必须在预发库先验证。执行前先跑脏数据检查：
  `SELECT order_id, COUNT(*) FROM order_review WHERE deleted = 0 GROUP BY order_id HAVING COUNT(*) > 1;`
  若结果非空，迁移会失败。
- 若团队不接受「重评」，则本单应降为「只做通知，不做重评」——但那样 P1-2 的核心问题（无正向出口）并未解决，需在 ADR 里明确接受这个残缺。
