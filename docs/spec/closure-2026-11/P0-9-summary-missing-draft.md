# P0-9 · 服务小结缺失时降级而非拒绝

> 批次：**B（用药与文档域）** · 级别：P0 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P0-9
> 错误码：**不新增**

## Problem Statement

「从订单转入用药计划」是 V4 主推的能力：陪诊结束后，家属一键把订单里提到的药转成用药计划。

但这个能力**依赖服务小结**：小结为空时接口直接 `CONFLICT("服务小结尚未填写")` 拒绝。

而小结在「完成服务」时是**可选字段**，并且**没有任何补写入口**（订单服务里 22 个方法、控制器 15 个端点，没有一个是「修改小结」）。

于是一个陪诊员一次「没填小结就点完成」，这张订单的转计划能力就**永久失效**——状态到位、数据缺失、入口不存在。演示时随便选一张没填小结的单就会卡住。

## Solution

空小结时不再拒绝，而是**给出空草稿 + 提示家属手动补录**：家属照样能进入「填药名 / 次数 / 时间点」的界面，只是系统没有可预填的线索。

V4 的转化链本来就不依赖小结内容——它依赖的是「订单已完成、家属想建计划」这个意愿。

## User Stories

1. 作为家属，我想在服务小结为空时仍能进入用药计划创建流程，这样我不会被一个必填项卡死。
2. 作为家属，我想系统告诉我「本次订单没有服务小结，请手动填写药名」，这样我知道为什么没有预填。
3. 作为家属，我想手动填写的药名仍会做药品字典匹配，这样我仍能得到通用资料。
4. 作为家属，我想从订单转计划时老人档案自动带对，这样我不用再选一次。
5. 作为陪诊员，我想忘填小结不会让家属的后续流程断掉，这样我的疏漏后果不严重。
6. 作为陪诊员，我想完成服务时系统提示「填写小结可帮助家属转用药计划」，这样我会主动填写。
7. 作为管理员，我想看到有多少订单没填小结，这样我能评估陪诊员的填写质量。
8. 作为运营，我想「转计划成功率」不再被小结缺失拉低，这样这个指标反映真实转化。
9. 作为测试者，我想看到「空小结 → 转计划成功且草稿为空」的用例。
10. 作为测试者，我想看到「有小结 → 草稿非空」的用例（保护现状）。
11. 作为测试者，我想看到「小结命中合规词 → 仍拒绝」的用例（保护合规红线）。
12. 作为开发者，我想这条降级只改一个分支，这样影响面最小。
13. 作为开发者，我想草稿 VO 能表达「无预填」这个状态，这样前端知道怎么提示。
14. 作为开发者，我想这次改动不动小结的合规校验（命中违规词仍必须拒绝）。
15. 作为开发者，我想不给「修改小结」新开端点，这样避免引入新的权限与审计面。

## Implementation Decisions

### 规则

- `buildDraftFromOrder` 的检查顺序调整为：
  1. 参与方判定（不变，`requireInvolved`）
  2. 订单状态必须是 `COMPLETED` / `REVIEWED`（不变）
  3. **若小结非空 → 过合规词表；命中仍拒绝 `ORDER_SUMMARY_ILLEGAL`**（不变，这是红线）
  4. **若小结为空 → 不拒绝，继续**（本单唯一的行为变更）
  5. 老人档案一致性（不变）
  6. 药名匹配（不变）
- 草稿 VO 新增字段 `summaryMissing: boolean`（或复用现有 `notes` 数组追加一条提示）。**建议新增布尔字段**，让前端有稳定的判断依据，而不是靠解析提示文本。

### 为什么不补「修改小结」端点

- 补端点要动：Controller + Service + 权限 + 合规校验 + 流转日志 + 接口文档 + 前端入口，共 7 处。
- 且「完成后再改小结」会引出新问题：改完之后时间线上要不要记一笔？改之前的订单转计划草稿要不要失效？
- 降级方案成本 1 个 `if`，且**不产生新的数据一致性问题**。

### 配套（可选但建议）

- `complete` 的接口文档与前端表单增加**非强制**提示：「填写服务小结可帮助家属一键转用药计划」。不改校验，只改提示。

### 接口变更

- `POST /api/medication/plan/from-order/{orderId}`：空小结从 `CONFLICT` 改为成功返回空草稿 + `summaryMissing = true`。
- `docs/api/05-medication.md` §10 更新错误场景（删除「小结未填写」这条）与响应字段。

## Testing Decisions

### 好测试

断言「小结为空 / 非空 / 含违规词三种情况下，`buildDraftFromOrder` 分别返回什么」。

### 测试模块

扩展 `MedicationDraftFromOrderTest`（已有完整骨架）

### 垂直切片

1. **红**：`小结为空时应返回空草稿而不是409`。
2. 实现。
3. **红**：`空草稿的summaryMissing应为true`。
4. **红**：`小结非空时草稿应正常解析`（保护现状）。
5. **红**：`小结命中合规词时仍应拒绝`（保护红线）。
6. **红**：`未完成的订单仍应拒绝`（保护现状）。

### 先例

`MedicationDraftFromOrderTest`（\`SET NX\` 判重、合规校验、药名匹配的完整断言）。

## Out of Scope

- **不新增「修改服务小结」端点**（见上）。
- 不改 `complete` 时小结为必填（会让陪诊员在紧急场景无法结束订单）。
- 不改前端创建计划表单（需另开工单：用 `summaryMissing` 显示提示）。
- 不做「历史无小结订单的批量补录工具」。

## Further Notes

- **合规红线不能被降级波及**：本单只放宽「小结为空」，**不放宽「小结含违规词」**。这两条必须分开测，否则很容易在实现时把整个小结校验一起删掉。
- 若团队坚持「小结是履约凭证」，则应改为补端点——但那需要先想清楚「改小结是否要重开评价窗口」这个连带问题。**本单的立场是：与其补一个不完整的端点，不如承认小结是可选信息。**
