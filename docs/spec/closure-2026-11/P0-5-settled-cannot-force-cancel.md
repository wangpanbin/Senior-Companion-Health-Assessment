# P0-5 · 已结算订单不可强制取消

> 批次：**A（订单与结算域）** · 级别：P0 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P0-5
> 错误码：新增 `3011 ORDER_SETTLED_CANNOT_CANCEL`

## Problem Statement

一张订单已经完成、并且管理员已经核定结算（线下已付款给陪诊员）。之后因为纠纷，管理员把它强制取消——**订单状态变成「已取消」，但结算状态仍是「已结算」**。

结算台账只收「已完成/已评价」的订单，于是这张单从台账和导出里**凭空消失**了。可钱已经付出去了。对账时这笔差额无法解释。

更奇怪的是：再点一次「核定结算」，接口仍然返回成功、页面仍显示已结算——因为它对「已结算」做了幂等返回，而这个返回发生在状态校验之前。

## Solution

已结算的订单不允许被强制取消。管理员必须先在结算侧做冲正（本期不做冲正，只做「拒绝」），才能改订单状态。系统给出明确提示，而不是让台账悄悄少一条。

同时修正「已结算」的幂等返回顺序：先判状态是否可结算，再判幂等。

## User Stories

1. 作为管理员，我想在强制取消一张已结算订单时被明确拒绝，这样我不会让已付出的钱从台账里消失。
2. 作为管理员，我想被拒绝时看到「该单已结算，请先做结算冲正」这样的可执行提示，这样我知道下一步做什么。
3. 作为管理员，我想在仲裁界面看到订单的结算状态，这样我在点取消之前就能意识到风险。
4. 作为财务，我想台账里的每一笔都已真实发生，这样对账不会出现无法解释的差额。
5. 作为财务，我想导出结算单时不会漏掉已付款的单，这样我的账和平台一致。
6. 作为陪诊员，我想我已完成并已收钱的单不会被事后取消，这样我的劳动报酬有保障。
7. 作为家属，我想在订单被取消时知道「钱已结算」这件事，这样我不会以为能全额退款。
8. 作为管理员，我想在未结算的订单上仍能强制取消（这是纠纷处理的正常手段），这样我的处置能力没被削弱。
9. 作为管理员，我想对「已结算」的订单重复点核定时，若订单状态已不可结算则报错而不是假成功，这样我不会被误导。
10. 作为运维，我想在库里能查到「已结算且已取消」这类异常组合的存在数量，这样我能评估历史影响。
11. 作为测试者，我想看到「已结算 → 强制取消 → 被拒」的回归用例，这样这条约束不会再次丢失。
12. 作为开发者，我想这条检查只写在一个地方，这样将来加「已退款」等其他付款状态时容易扩展。

## Implementation Decisions

### 规则

- `forceTerminal` 目标为 `CANCELLED` 时，若 `payment_status = SETTLED` → 抛 `3011 ORDER_SETTLED_CANNOT_CANCEL`。
- 检查位置：**在 `OrderTransitionServiceImpl#forceTerminal` 内部**（不是 `AdminServiceImpl`），因为这是「强制终态」这条路径的固有约束，任何调用方都应受约束。
- 目标为 `COMPLETED` 时**不检查**结算状态（已完成本身不会让台账消失）。
- **修正 `SettlementServiceImpl#confirm` 的判定顺序**：先判「订单状态是否在可结算集合内」，再判「是否已结算」。已结算 + 状态不可结算 → 抛 `8004`（现状是假成功）。

### 接口变更

- `POST /api/admin/order/{id}/arbitrate`：新增失败分支 `3011`。
- `POST /api/admin/settlement/{orderId}/confirm`：行为变更——已结算但状态非可结算时从「假成功 200」改为 `8004`。
- `docs/api/03-order.md`、`docs/api/08-admin.md`、`docs/api/README.md`（错误码表）同步。

### 数据变更

无。

## Testing Decisions

### 好测试

断言 `forceTerminal` 与 `confirm` 在不同 `status × payment_status` 组合下抛哪个码。**用参数化测试覆盖矩阵**是这里最合适的形态（组合只有 5 × 2 = 10 种）。

### 测试模块

`OrderForceTerminalSettledTest`（新建）+ 扩展 `SettlementServiceTest`

### 垂直切片

1. **红**：`已结算订单强制取消应返回3011`。
2. 实现：加检查。
3. **红**：`未结算订单强制取消应成功`（保护现状）。
4. **红**：`已结算订单强制完成应成功`（不该被误拦）。
5. **红**：`已结算且已取消的订单再核定应返回8004而不是假成功`。
6. **红**：`参数化覆盖10种status×payment_status组合`（收口，防止漏分支）。

### 先例

`SettlementServiceTest`（幂等与状态组合）；`OrderStatusTest`（枚举矩阵参数化写法）。

## Out of Scope

- **不做结算冲正**（把 `SETTLED` 改回 `UNPAID`）——需要独立设计与审批流，本期只做「拒绝」。
- 不清理库里已存在的「已结算且已取消」脏数据（Further Notes 给出核查 SQL，由人工决定是否修）。
- 不改台账取数口径（仍按订单状态；改成「按 `payment_status` 取数」是更大的决策，需 ADR）。
