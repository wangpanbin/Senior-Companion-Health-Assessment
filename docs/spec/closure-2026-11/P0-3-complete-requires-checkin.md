# P0-3 · 完成服务须有打卡留痕

> 批次：**A（订单与结算域）** · 级别：P0 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P0-3
> 错误码：新增 `3012 ORDER_CHECKIN_REQUIRED`

## Problem Statement

陪诊员接单之后，可以直接调用「完成服务」把订单结束，**一个打卡都不做**。订单变成「已完成」，家属能去评价，但打卡表、轨迹表、服务照片全是空的——「服务过程留痕」这条主线在接口层面完全可选。

而一旦订单完成，陪诊员**再也补不了打卡**（打卡要求订单处于「已接单」或「服务中」）。事后要证明「确实到院了、确实取药了」，系统里没有任何证据。

## Solution

完成服务前必须有至少一次「到院」或「完成」打卡。若确实没有，完成接口直接拒绝并告诉陪诊员先去打卡——而不是让他在无痕状态下把单结束。

留痕检查做成**可配置开关**（默认开），便于历史数据回填与极端场景快速降级。

## User Stories

1. 作为家属，我想在订单完成时一定能看到「到院」这条打卡记录，这样我确认陪诊员真的去了医院。
2. 作为家属，我想在订单详情的时间线里看到打卡事件，这样我能还原陪诊员做了什么。
3. 作为陪诊员，我想在忘打卡就点完成时被明确拦下，并被告知「请先完成到院打卡」，这样我不会造出一张无凭证的订单。
4. 作为陪诊员，我想在被拦下后能立刻跳去打卡，这样我不用自己找入口。
5. 作为陪诊员，我想在只打了「出发」打卡时仍被要求补「到院」，这样凭证链不会断在关键节点。
6. 作为管理员，我想在仲裁纠纷时一定能看到打卡记录，这样我不会面对一张空白订单。
7. 作为管理员，我想在历史订单确实无法补录时能临时关掉这个检查，这样不会被存量数据卡死。
8. 作为运维，我想这个开关是可配置的而不是写死的，这样不同环境可以用不同严格度。
9. 作为开发者，我想这条规则只存在于一个地方，这样将来加「必须完成 6 个节点」时不用改多处。
10. 作为家属，我想在完成失败时看到人能读懂的提示，而不是「当前订单状态不允许该操作」。
11. 作为陪诊员，我想在打卡被系统自动补录时也能在时间线上看到它，这样记录是完整的而不是缺失的。
12. 作为审计者，我想区分「陪诊员自己的打卡」和「系统补录的打卡」，这样追溯责任时不会误判。

## Implementation Decisions

### 规则

- 在 `complete` 的**状态预检之后、写入之前**插入留痕检查：订单必须存在至少一条 `order_checkin` 记录，且节点属于 `{ARRIVE, FINISH}`（不含 `DEPART`——出发打卡不能证明到院）。
- 校验失败抛 `3012 ORDER_CHECKIN_REQUIRED`，message 指明「请先完成「到院」打卡」。
- **开关**：`nianglin.execution.require-checkin-on-complete`，默认 `true`；关闭时跳过检查（仅用于历史数据与应急）。
- **不选「自动补 FINISH 打卡」方案**：自动补录会让「系统替陪诊员声称他完成了服务」，与「留痕 = 陪诊员真实动作」的语义冲突。宁可拒绝，也不伪造证据。

### 接口变更

- `POST /api/order/{id}/complete`：新增失败分支 `3012`。
- `docs/api/03-order.md` §9 补充错误场景与实现要点。
- `docs/api/README.md` 3xxx 错误码表新增 `3012`。

### 依赖注入注意

`OrderServiceImpl` 现有依赖中是否已有 `OrderCheckinMapper` 需先确认；若没有则新增注入。**本单会使 `OrderServiceImpl` 多一个 Mapper 依赖，所有实例化 `OrderServiceImpl` 的单测都要补 `@Mock`——这一条容易漏，必须全仓 grep `new OrderServiceImpl(` 与所有 `@InjectMocks OrderServiceImpl`。**

## Testing Decisions

### 好测试的标准

断言「在什么前置数据下，`complete` 抛哪个 `ResultCode`」。用 `@Mock OrderCheckinMapper` 控制「有没有打卡」，**不要**用真库或 `@SpringBootTest`。

### 测试模块

`OrderCompleteCheckinTest`（新建）

### 垂直切片

1. **红**：`没有任何打卡时完成应返回3012`。
2. 实现：插入检查。
3. **红**：`只有DEPART打卡时完成应返回3012`（关键：证明不是「有打卡就过」）。
4. **红**：`有ARRIVE打卡时完成应成功`。
5. **红**：`有FINISH打卡时完成应成功`。
6. **红**：`开关关闭时无打卡也能完成`（用 `ReflectionTestUtils.setField` 设配置值）。
7. **红**：`检查失败时不应写入任何状态变更`（断言 `orderMapper.updateById` 零调用）。

### 先例

`OrderTransitionServiceImplTest` 系列（错误码优先级的断言顺序）；`ExecutionServiceTest`（打卡状态校验的写法）。

## Out of Scope

- 不要求「6 个节点全打」（当前只要 1 个关键节点）。
- 不做「打卡后置超时」（属 P1-1）。
- 不改前端打卡页。
- 不自动补打卡。

## Further Notes

- **顺序很关键**：留痕检查必须在「状态校验」之后（否则一张 `PENDING` 单会先报 `3012` 而不是 `3002`，把用户引向错误方向）。参照 `OrderServiceImpl` 现有的「先状态后身份」注释。
- 与 P0-4 / P0-5 / P0-6 同属「状态旁路」，但**不动状态机本身**。
