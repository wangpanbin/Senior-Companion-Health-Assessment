# P2-5 · 取消不清理下游（明确为设计并留证）

> 批次：**A（订单与结算域）** · 级别：P2 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P2-5
> 错误码：**不新增**

## Problem Statement

订单被取消之后，它的打卡记录、轨迹点、聊天消息、上传文件、站内信全部保留。

这在**证据角度是对的**（取消不等于销毁证据，尤其涉及纠纷时），但系统里**没有任何一处写明这是刻意的**：

- 迁移脚本里一条外键都没有，看起来像「没设计」；
- 代码里没有注释解释；
- 也没有任何地方向用户说明「取消后聊天仍可查看」。

结果：每个新人（或评审人）都会问一次「取消后这些数据为什么不删」，然后得到一个口头回答。

## Solution

把这件事从「隐性行为」变成「显性决策」：

1. 写进 ADR（本单唯一的新增文档）；
2. 在关键代码处补注释指向 ADR；
3. 在 API 文档里说明「取消后仍可查看聊天历史（交涉场景）」。

**不做任何数据删除。** 本单是澄清，不是清理。

## User Stories

1. 作为家属，我想在订单取消后仍能看到打卡与聊天记录，这样我能证明服务实际到了哪一步。
2. 作为家属，我想在取消后还能和陪诊员沟通，这样遗留问题能善后。
3. 作为陪诊员，我想我的打卡记录不因订单取消而消失，这样我的劳动有凭证。
4. 作为陪诊员，我想取消后的聊天仍可查看，这样结算争议有据可依。
5. 作为管理员，我想仲裁时一定能看到完整的过程数据，这样我能还原事实。
6. 作为管理员，我想取消原因与操作人在订单表里可查，这样审计能追责。
7. 作为审计者，我想系统里有一份文档解释「为什么不删」，这样我不必每次都去问人。
8. 作为审计者，我想「保留」这件事是有 ADR 背书的，而不是实现疏漏。
9. 作为开发者，我想看到代码里指向 ADR 的注释，这样我不会误以为该加级联删除。
10. 作为开发者，我想未来若要「真删」时知道该改哪里（有清单），这样预留了路径。
11. 作为运维，我想知道数据保留策略，这样容量规划有依据。
12. 作为测试者，我想看到「取消后打卡记录仍可查」的用例，这样这条行为被锁住。
13. 作为测试者，我想看到「取消后聊天仍可发送」的用例（已有行为，加回归保护）。
14. 作为产品，我想用户在取消页看到「取消后仍可查看历史与沟通」的说明，这样不会以为数据会消失。
15. 作为开发者，我想本单不改任何业务逻辑，这样风险为零。

## Implementation Decisions

### 文档

- 新增 `docs/adr/0023-cancel-keeps-downstream-data.md`：
  - 决策：订单进入 `CANCELLED` 后，`order_checkin` / `companion_track` / `chat_message` / `sys_file` / `internal_message` **一律保留**。
  - 理由：纠纷取证、劳动凭证、交涉场景；平台不做支付，不存在「退款后销毁交易记录」的合规需求。
  - 后果：数据只增不减；若未来需要清理，走独立的数据生命周期策略（归档而非删除）。
  - 明确列出「哪些表受此决策覆盖」「哪些不受（如 Redis 中的临时键）」。
- `docs/api/03-order.md` §5（取消订单）：补一句「取消不删除任何下游数据：打卡、轨迹、聊天、附件、站内信均保留，家属与陪诊员仍可查看」。
- `docs/api/11-order-chat.md`：已有「`CANCELLED` 后仍可互发」的说明，补一句引用 ADR-0023。

### 代码注释

在以下位置补一行 `// 取消不清理下游：见 ADR-0023`：
- `OrderServiceImpl#cancel` 的状态写入之后；
- `OrderTransitionServiceImpl#forceTerminal` 的 `CANCELLED` 分支之后。

### 测试

- 加两条回归测试锁住现状（防止后人「顺手」加级联删除）。

## Testing Decisions

### 好测试

断言「取消订单后，调用 `checkins(orderId)` 仍能返回数据」「取消后 `ChatService.send` 不报 `CHAT_NOT_AVAILABLE`」。

### 测试模块

扩展 `ChatServiceTest` + 新建 `CancelRetainsDownstreamTest`

### 垂直切片

1. **保护性测试**：`取消后打卡记录仍可查询`（先写断言现状）。
2. **保护性测试**：`取消后仍可发送聊天消息`。
3. **保护性测试**：`取消不删除任何打卡记录`（`verify(checkinMapper, never()).delete(any())`）。

### 先例

`ChatServiceTest`（已有取消后可聊的用例）；`ExecutionServiceTest`（打卡查询）。

## Out of Scope

- **不做任何数据删除或归档**。
- 不做「用户主动申请删除自己的数据」（已有账号注销与数据导出，属另一条链）。
- 不改前端取消确认弹窗的文案（需前端工单）。

## Further Notes

- **本单的价值全在「留证」**。若团队认为不必写 ADR，至少要在代码里留注释——否则下一次代码评审会重现同一个问题。
- 与 P1-1 的超时机制交互：被超时取消的订单同样保留下游数据，ADR 里要写明。
