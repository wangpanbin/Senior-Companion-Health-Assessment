# DOC-3 · `03-order.md` §五 整节重写（含 DOC-4）

> 批次：**B（用药与文档域）** · 级别：DOC · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §DOC-3、§DOC-4

## Problem Statement

`docs/api/03-order.md` §五「已知限制（一期）」这一节，**整体已经过期**，而且过期的方向是**反向误导**——它说「还没做」的事，实际上已经做了：

| 文档现在写的 | 实际情况 |
|---|---|
| 「**管理员强制改终态未实现**（M9）。因此「已接单之后家属想取消」目前无解…纠纷处理入口在 M9 才交付」 | 已实现：`AdminServiceImpl#arbitrate` + `OrderTransitionServiceImpl#forceTerminal`，M9 早已交付 |
| 「**站内信 / WebSocket 推送未实现**（M8 / M5）：下单、接单、完成都不会触发任何通知」 | 已实现：`MessageSseHub` SSE、`MessageService` 模板消息、STOMP 进度通道 |
| 「`version` 只在接单时递增。开始服务 / 完成服务用条件更新，不改 `version`」 | 部分已变：`transition()` 走 `updateById` 会递增 version |

仍然成立的只有三条：`area` 是文本模糊匹配、拒单无风控、取消/纠纷原因不做内容合规校验。

**这是答辩风险最高的一处反向误导**：老师读这一节会以为 M8 / M9 没做，而实际做了。

（DOC-4 一并处理：两处注释/文档与代码不符——`ElderServiceImpl` 说没有 `(family_id, elder_id)` 唯一索引而实际有；`02-elder-family.md` 说重绑会 UPDATE 原行而实际是 INSERT 新行。）

## Solution

把 §五 整节重写成「**当前仍然成立的限制 + 已由后续版本解决的限制（附指向）**」两段式。已解决的不删，而是明确标注「已于 Mx 解决，见 §y」——这样读者能看出系统在演进，而不是看到一片空白。

同时修正 DOC-4 的两处错误陈述。

## User Stories

1. 作为评审人，我想看到「已知限制」都是当前事实，这样我不会误判项目完成度。
2. 作为评审人，我想看到「这条限制已于 M9 解决」这样的标注，这样我能看出演进轨迹。
3. 作为评审人，我想不会因为读到过期的「未实现」而低估这个项目。
4. 作为前端开发者，我想知道哪些限制还在、哪些已经不用规避，这样我不会白做兼容。
5. 作为前端开发者，我想知道「已解决」的条目对应哪个版本、哪个接口。
6. 作为后端开发者，我想在补新限制时有固定格式，这样不用每次重新设计这一节。
7. 作为后端开发者，我想「已解决」的条目保留，这样历史评审记录完整。
8. 作为测试者，我想验收清单不再引用「未实现」的项。
9. 作为测试者，我想每条限制都有可验证的判据。
10. 作为维护者，我想维护这一节时知道要同步哪些代码位置。
11. 作为维护者，我想「已解决」条目不必逐版清理（只在重大变化时更新）。
12. 作为新成员，我想读这一节就能知道系统边界，这样不会问重复的问题。
13. 作为审计者，我想看到「注释说没有唯一索引但实际有」这类错误被修正。
14. 作为审计者，我想文档对「重绑行为」的描述与代码一致。
15. 作为文档维护者，我想这次改动后 `gate_check.py` 全绿。

### 5.1 仍成立的限制

| # | 限制 | 影响 | 后续计划 |
|---|---|---|---|
| 1 | 大厅的 `area` 是地址文本模糊匹配，不是地理筛选 | 「美兰区」能否筛到取决于家属写全了地址 | 一期用文字地址替代地图导航的直接后果，不计划改为地理筛选（ADR-0022 只放开渲染，未放开检索） |

| 原限制 | 状态 | 解决位置 |

## Further Notes

- **这一节为什么不整段删掉「已解决」条目**：保留并标注能让读者看到系统确实在演进；直接删掉会让评审人以为「一开始就没有这些问题」，反而不诚实。**取舍：保留 + 标注，成本更低、信息量更大。**
