# P2-1 · 漏服升级加时间下界

> 批次：**B（用药与文档域）** · 级别：P2 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P2-1
> 错误码：**不新增**

## Problem Statement

漏服提醒是三级升级的：漏服 30 分钟后通知家属，2 小时后通知陪诊员，24 小时后通知管理员。

但扫描条件是「`status = 'MISSED'` 且 `notify_level < 3`」——**没有时间下界**。这意味着：

- 三个月前的一条漏服记录，只要 `notify_level` 还没到 3，每轮扫描都会把它捞出来重新判定；
- `dueLevel` 按 `plan_time` 正向计算，历史任务的「已漏服时长」早就超过 24 小时 → 直接跳到 L3 → 给管理员发一条「某老人三个月前漏服」的提醒；
- 管理员收到一堆历史噪音，真正需要处理的当天漏服被淹没。

## Solution

给升级扫描加时间下界：只处理「最近 N 天内」的漏服任务。历史任务不再被回溯升级。

## User Stories

1. 作为管理员，我想只收到近期漏服的升级提醒，这样我不会被三个月前的记录打扰。
2. 作为管理员，我想噪音减少后当天的问题更显眼，这样我能及时介入。
3. 作为家属，我想历史漏服记录仍然可查，这样我能回顾依从性趋势。
4. 作为家属，我想历史记录不会被重新推送，这样我不会反复收到旧提醒。
5. 作为陪诊员，我想 L2 升级只覆盖近期任务，这样我不会被无关的旧单打扰。
6. 作为运营，我想升级数量与真实紧迫度相关，这样这个指标有意义。
7. 作为运维，我想扫描成本随时间收敛而不是随历史累积增长，这样性能可预测。
8. 作为测试者，我想看到「30 天前的 MISSED 不再被升级」的用例。
9. 作为测试者，我想看到「昨天的 MISSED 仍会被升级」的用例（保护近期任务）。
10. 作为测试者，我想看到「下界可配置」的用例。
11. 作为开发者，我想下界只加在升级扫描上，不改「判漏服」的扫描（那是另一件事）。
12. 作为开发者，我想这个阈值与提醒模板里的文案不冲突（模板说「今天」）。
13. 作为开发者，我想配置项有默认值，这样不改配置也能工作。
14. 作为开发者，我想 SQL 条件能走现有索引（`idx_status_plan_time`）。
15. 作为审计者，我想历史任务仍保留 `notify_level` 的原值，不被改成 3，这样审计能看到「本来该升没升」。

## Implementation Decisions

### 规则

- `scanMissedTasks` 的**升级扫描**（②段）增加条件：`plan_time >= now - floorDays`。
- 默认 `floorDays = 30`，配置项 `nianglin.medication.escalation-floor-days`。
- **不改「判漏服」扫描**（①段，`PENDING → MISSED`）——那段本来就只处理近期超时任务，且加下界会让长期未确认的任务永远停在 PENDING。
  - **但要注意**：若某任务在 `deleted = 0` 且 `PENDING` 状态挂了 90 天，①段仍会把它判为 MISSED（正确的，因为它确实没吃），只是②段不会再给它升级（也正确，因为它太旧了）。这个组合是对的。
- **不改历史任务的 `notify_level`**：不升级就不动，保持原值，审计可见。
- 索引友好：现有 `idx_status_plan_time(status, plan_time)` 正好覆盖新条件。

### 配置

- `nianglin.medication.escalation-floor-days`（默认 30）。允许通过 `sys_dict` 的 `OPS_PARAM` 覆盖（与现有漏服阈值一致——`OperationParam.MEDICATION_MISSED_THRESHOLD_MINUTES` 已有此机制）。
  - 若走 OPS_PARAM，需在 `OperationParam` 枚举与 `sys_dict` 种子数据里新增一行，并同步 `docs/api/08-admin.md` §28.4。

### 接口变更

- 无新端点。行为变更为「更少的升级通知」。
- `docs/api/05-medication.md` §2.1 补充下界说明。

## Testing Decisions

### 好测试

断言「给定 `plan_time` 距今天数，升级扫描是否包含该任务」。用 mock 的 Mapper 返回任务列表 + 捕获 wrapper 条件。

### 测试模块

扩展 `MedicationServiceTest` 或新建 `MedicationEscalationFloorTest`

### 垂直切片

1. **红**：`30天前的MISSED任务不应被升级`。
2. 实现下界条件。
3. **红**：`昨天的MISSED任务仍应被升级`（保护近期）。
4. **红**：`恰好在边界上的任务应被包含`（闭区间语义）。
5. **红**：`下界可配置`（改配置后行为变化）。
6. **红**：`判漏服扫描不受下界影响`（保护①段）。

### 先例

`MedicationServiceTest`（漏服扫描的既有断言）；`OperationsGapRealDbTest`（真实 SQL 条件的写法，仅供参考，本单不写 RealDb）。

## Out of Scope

- 不改三级升级的阈值（30 分钟 / 2 小时 / 24 小时）。
- 不做「历史任务的清理」（只停止升级，不删数据）。
- 不改提醒文案。
- 不改 P0-8 的桶判定。

## Further Notes

- **为什么是 30 天而不是 7 天**：家属回看上月依从性时，若某条历史漏服突然收到提醒会很困惑；30 天给了足够缓冲，同时把「三个月前的噪音」切掉。
- 若团队觉得 30 天太长，改配置即可，**不需要改代码**——这是把它做成配置项的主要理由。
