# P0-1 · 改派语义与抢单语义冲突

> 批次：**A（订单与结算域）** · 级别：P0 · 来源：`reports/business-closure-final-assessment-2026-11-28.md` §P0-1
> 依赖：**B 批 P0-2 先合**（本单不碰 `hall` / `accept` 两个方法）
> 错误码：复用 `3010 ORDER_NOT_REASSIGNABLE`、`3003 ORDER_ALREADY_TAKEN`，**不新增**

## Problem Statement

管理员把一张待接单订单改派给陪诊员 A 之后，这张单**仍然出现在公共大厅里**，任何其他陪诊员都能把它抢走。A 从头到尾没有收到任何「你的单被抢了」的信号，管理员在后台也看不出改派已失效。

更糟的是：如果 A 拒单，这张单**再也无法改派给第三人**——因为改派的前置条件是「接单人为空」，而拒单并不清空接单人。管理员此时只有一个选择：打电话协调，系统帮不上忙。

对家属来说，这意味着「平台已经安排好了人」这句话随时可能被推翻，而他看不出为什么。

## Solution

明确「改派」与「抢单」的语义边界：

- **指派单不进公共大厅**。一旦管理员把单指派给某人，这张单就从大厅消失，只有被指派人能看到并接单。
- **改派可以多次**。原来指派的 A 拒单或被换掉之后，管理员能再次指派给 C，系统留下 `A → C` 的完整轨迹。
- **改派与抢单只有一个能成功**。两者更新同一行，输的一方拿到明确的业务错误，而不是静默覆盖。

## User Stories

1. 作为管理员，我想在改派成功后看到这张单从大厅消失，这样我确认指派真的生效了。
2. 作为管理员，我想在被指派人拒单之后能再次改派给其他人，这样我不必线下打电话协调。
3. 作为管理员，我想在改派轨迹里看到「从谁改到谁」，这样出纠纷时我能还原调度过程。
4. 作为管理员，我想在改派与抢单同时发生时只让一个成功，这样不会出现「两个人以为自己是接单人」。
5. 作为陪诊员，我想在大厅里只看到「没有任何人指派」的订单，这样我不会白抢一张已经被安排的订单。
6. 作为陪诊员，我想在自己被指派时收到明确的通知，这样我知道有一张单在等我。
7. 作为陪诊员，我想在拒掉一张指派给我的单之后，这张单不再挂在我名下，这样我不会被一张我不接的单无限期占用。
8. 作为陪诊员，我想在拒单之后不再收到这张单的推送，这样不会被同一张单反复打扰。
9. 作为陪诊员，我想在抢一张单失败时得到「已被管理员指派给他人」这类可区分的提示，而不是笼统的「手慢了」。
10. 作为家属，我想在管理员完成改派后收到一条站内信，这样我知道换人了。
11. 作为家属，我想在改派发生后看到订单时间线里多一条记录，这样我能核对「谁在什么时候被换成谁」。
12. 作为家属，我想在没有任何陪诊员被指派时订单照常进入大厅，这样不会被多余的指派流程拖慢。
13. 作为运维，我想在履约事件表里查到所有 `ORDER_REASSIGNED` 事件，这样我能统计改派频次。
14. 作为运维，我想在并发场景下改派与抢单不会同时成功，这样改派台账不会与事实不符。
15. 作为开发者，我想「改派」这条路径有明确的、单一的写入点，这样将来加新规则时不需要改三处。

## Implementation Decisions

### 语义决策

- **改派不改变订单状态**，仍是 `PENDING`（维持现状，ADR-0010：改派不走状态机）。
- **被指派单不进公共大厅**：大厅查询加 `companion_id IS NULL` 条件。
- **接单必须校验「无既有指派」**：`accept` 增加「若 `companion_id` 非空且不等于当前用户 → 拒绝」的判定。**注意这一条与 B 批 P0-2 修改的是同一个方法，本单只加这一条判定，不动 P0-2 引入的接单状态判定。**
- **拒单清空 `companion_id`**：拒单后该单回到「无指派」状态，重新进入大厅并允许再次改派。
  - 用一个**条件更新**完成：`UPDATE ... SET companion_id = NULL, version = version + 1 WHERE id = ? AND companion_id = ? AND status = 'PENDING'`。条件不满（例如已被别人接走）时不影响订单，仍写拒单日志。
- **改派允许多次**：前置条件从「`companion_id IS NULL`」放宽为「`status = 'PENDING'`」。用一句话表达清楚：只要订单仍是 `PENDING`，管理员就可以改派，无论当前有没有被指派人。
  - 条件更新同时递增 `version`，兑现 ADR-0012「改派与抢单只有一个成功」的承诺。
- **履约事件记 `from → to`**：`ORDER_REASSIGNED` 事件的备注里带原接单人 ID 与新接单人 ID；原接单人为空时记「未指派」。
- **通知三方**：下单家属、新被指派人、**原被指派人**（若与原不同）各发一条 `ORDER_REASSIGNED` 站内信。

### 接口变更

- `POST /api/admin/order/{id}/reassign`：**语义放宽**——从前置条件「无人指派」改为「订单仍待接单」。响应新增 `fromCompanionId`（可能为 null）。
- `GET /api/order/hall`：**行为变更**——不再返回已有指派人的订单。**属 B 批 P0-2 修改的同一方法，本单只加这条 filter。**
- `POST /api/order/{id}/reject`：**行为变更**——拒单后清空 `companion_id`。

### 数据变更

无新表、无新列。`companion_order.version` 在改派时递增（这是 `@Version` 字段的正常语义）。

## Testing Decisions

### 什么是好测试

只断言**通过公开方法可观察的行为**：抛了哪个 `ResultCode`、返回 VO 的哪些字段、Mapper 收到的条件更新包里有哪些 `eq` 条件。不断言私有方法、不断言 SQL 字符串。

### 测试模块

`AdminReassignTest`（扩展）+ `OrderAcceptRejectTest`（新建）

### 测试清单（垂直切片，一次一片）

1. **红**：`改派已有人接单的PENDING单_应成功` → 先写「改派一张已有 `companion_id` 的 `PENDING` 单，断言不抛 3010」，此时会红。
2. 实现：放宽 `reassign` 的前置条件。
3. **红**：`改派时版本号必须递增` → 断言条件更新包里含递增。
4. **红**：`大厅不返回已指派订单` → 断言 `hall` 的 wrapper 含 `companion_id IS NULL`。
5. **红**：`接单时若已被指派给他人应返回已接单`。
6. **红**：`拒单后接单人应被清空` + `拒单后该单可再次改派`。
7. **红**：`改派事件应记录原接单人与新接单人`。
8. **红**：`改派应通知原接单人`（原与被指派人为不同人时才发）。

## Out of Scope

- **不做「我的指派」独立入口**（本单让指派单不进大厅即可）。这会留下一个已知空窗：被指派人暂时只能靠站内信通知点进订单详情接单，大厅里看不到。已在 Further Notes 登记。
- 不引入 `assigned_companion_id` 独立字段（当期用 `companion_id` 承载指派语义，与接单人合一）。
- 不改前端大厅页面（B 批 P0-2 会动 `hall.vue`）。
- 不处理「改派后原被指派人已在途中」这类现实纠纷（走 M9 仲裁）。

## Further Notes

- **必须与 P0-4 保持同一套语义**：P0-4 封禁陪诊员时「自动回 PENDING + 清 `companion_id`」正是本单建立的语义。若两单口径不一致，系统里会出现两种「PENDING 但有 `companion_id`」的单，比现状更糟。
- **已知空窗（需在合并时同步在 `docs/api/03-order.md` §3 写明）**：指派单不进大厅之后，被指派人只能通过站内信链接进入订单详情接单，大厅里看不到。若团队认为不可接受，应在本单内一并做「我的指派」筛选参数（`GET /api/order/hall?assignedToMe=true`），而不是留空窗。
- ADR-0012 关于「改派与抢单只有一个成功」的表述需随本单同步更新（从「条件更新 `isNull`」改为「乐观锁 + `PENDING` 条件」）。
