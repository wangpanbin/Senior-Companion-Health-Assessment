## 〇、开工复核结论（2026-10-20）

| # | 复核项 | 核实结果 | 处置 |
|---|---|---|---|
| ① | V3.1 履约风险中心的实际接口形态 | ✅ `GET /api/admin/fulfillment/summary` → `FulfillmentSummaryVO{manualRequired, urgent, warning, normal}`；`GET /api/admin/fulfillment/risk-list` → `PageResult<AdminFulfillmentRiskItemVO>` | 异常中心**直接复用**这两处的判定结果，不另建一套 |
| ② | V3.2 / V3.3 登记进指标字典的指标 | ✅ 字典已有 32 条（V3.2 的 14 + V3.3 的 18），V3.4 将再登记匹配相关指标 | 本版继续**只登记不新定义** |
| ③ | M10 统计模块的口径是否仍与总纲一致 | ✅ M10 的 `StatisticsMapper` 三条铁律（`deleted=0` / 已完成含 REVIEWED / 闭区间）仍成立；V3.2 已修掉用药三桶漂移（ADR-0014） | 驾驶舱复用同一套写法，不另立口径 |

### 偏差 D-3.5-1：「履约率」与「完成率」是两个不同的指标，不是同一个数

迭代计划 §42 的概览与 §45 的健康度都同时列了「履约率」与「完成率」。
如果两者都按「完成 ÷（完成 + 取消）」算，那就是**同一个数字挂了两个名字** ——
决策 6.2 明令禁止「同一指标在不同端出现不同口径」，反过来也禁止「两个名字一个数」。

处置：两者**口径明确分开**，各自登记：

| 指标 | 公式 | 含义 |
|---|---|---|
| `operations.fulfillment_rate` | `(COMPLETED + REVIEWED) / (COMPLETED + REVIEWED + CANCELLED)` | 区间内订单**最终履约**的比例 |
| `operations.completion_rate` | 按时完成单数 / 已完成单数，其中「按时」= `finish_time ≤ visit_time + 履约时长窗口`（默认 240 分钟，配置化） | 已完成订单里**没超时**的比例 |

界面上分别标注「履约率」与「完成率（按时）」，避免误读。

### 偏差 D-3.5-2：异常卡片的 `linkUrl` 必须是**真实存在的路由**

决策 5.4：「异常卡片到处理页面必须可达，不允许『看到了但处理不了』」。
前端后台已有路由：`/admin/dashboard`、`/admin/order`、`/admin/complaint`、
`/admin/fulfillment`、`/admin/order-dispute`、`/admin/user`、`/admin/companion-audit`、
`/admin/export`、`/admin/oper-log`、`/admin/chat`。

处置：四类异常的处理入口只用**上表里已存在**的路由，并逐个写进工单。
E2E 逐个点开验证 —— 「链接指向 404」是本版最典型的假绿。

## 三、T2 · 运营聚合 Mapper

**新增**：`backend/src/main/java/org/company/nianglin/mapper/OperationsMapper.java`

原生 `@Select` 只读聚合。**每条 SQL 必须写 `deleted = 0`**；
「已完成」= `COMPLETED` + `REVIEWED`；区间一律 `[start, end]` 闭区间。

| 方法 | 用途 | 关键口径 |
|---|---|---|
| `selectOrderStats(start, end)` | 概览 | `todayCount`（今日新增）/ `completedCount` / `cancelledCount` / `inServiceCount` / `pendingCount` / `onTimeCompletedCount`（`finish_time ≤ visit_time + 窗口`）/ `avgAcceptMinutes`（`TIMESTAMPDIFF(MINUTE, create_time, accept_time)`）/ `avgFinishDelayMinutes` |
| `selectCompanionStats(start, end)` | 概览 / 健康度 | 活跃陪诊员数（区间内有接单的）/ 接单陪诊员数 / 人均订单 / 人均收入 |
| `selectComplaintStats(start, end)` | 概览 / 异常 | 投诉单数 / 涉诉陪诊员数 |
| `selectReviewStats(start, end)` | 概览 | 平均评分（`order_review` 有效评价的 `AVG(score)`）/ 评价条数 |
| `selectDailyOrderTrend(start, end)` | 趋势（订单 / 陪诊员活跃 / 履约率） | 按天分组的订单数与状态数 |
| `selectDailyComplaintTrend(start, end)` | 趋势（投诉） | 按天分组的投诉数 |
| `selectDailyReviewTrend(start, end)` | 趋势（评价） | 按天分组的评价数与均分 |
| `selectDailyMedicationTrend(start, end)` | 趋势（用药任务） | 按天分组的任务数与漏服数（**三桶口径用 `MedicationBucketSql.CASE_BUCKET`**） |
| `selectCompanionComplaintRates(lookbackStart, lookbackEnd)` | 异常（投诉率异常陪诊员） | 陪诊员维度的投诉数 / 接单数 |
| `selectMissedMedicationCount(start, end)` | 异常（用药漏服） | 漏服桶计数（与服药日历同源） |
| `selectRecentMissedOrders(start, end, limit)` | 异常（用药漏服的处理入口） | 最近漏服任务所属的订单（给 `linkUrl` 与 `referenceId`） |

> ⚠️ 用药漏服的三桶**必须**用 `constant/MedicationBucketSql.CASE_BUCKET` ——
> V3.2 已经在 ADR-0014 里把这条锁死，驾驶舱不得另写一套（那正是 V3.2 踩过的坑）。

### 4.3 趋势 `OperationsTrendVO`

- 入参 `dimension`：`ORDER` / `COMPANION_ACTIVE` / `FULFILLMENT_RATE` / `COMPLAINT` / `REVIEW` / `MEDICATION`
- 入参 `range`：`TODAY` / `LAST_7D` / `LAST_30D` / `CUSTOM`
- `CUSTOM` 时用 `startDate` / `endDate`（走共享 `DateRangeQuery`，上限 366 天 → `9002`）
- 响应：`{ dimension, range, granularity, periodStart, periodEnd, categories[], series[] }`
- **无数据的桶补 0**，`categories` 与 `series.data` 长度严格一致

### 4.4 健康度 `OperationsHealthVO`

**六个并列指标，不给合成分**（决策 5.2）：

```java
String fulfillmentRate;       // 履约率
String avgAcceptMinutes;      // 接单速度（分钟，字符串）
String completionRate;        // 完成率（按时）
String complaintRate;         // 投诉率
String averageScore;          // 平均评分
Integer activeCompanionCount; // 活跃陪诊员数
```

**禁止**出现「AI 平台健康指数 96」这类无法解释的数。

| 字段 | 类型 | 说明 |
