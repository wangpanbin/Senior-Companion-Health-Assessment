## 〇、这一版最贵的一件事：结构化改造

迭代计划 §37 的匹配模型要求五个维度：区域匹配 / 时间匹配 / 距离 / 服务能力 / 评分。
**当前的数据基础撑不起其中两个。**

| 维度 | 现状 | 能不能算 |
|---|---|---|
| 服务能力 | `companion_order.department` 有真实数据 | ✅ 能算 |
| 评分 | `companion_profile.score` | ✅ 能算 |
| 区域匹配 | 陪诊员 `service_area VARCHAR(100)` 是**自由文本**；订单侧**没有**区域字段 | ⚠️ 只能做包含式匹配 |
| 时间匹配 | 陪诊员 `available_time VARCHAR(100)` 是**自由文本** | ⚠️ 只能做包含式匹配 |
| 距离 | 订单有 `longitude` / `latitude`，**陪诊员档案没有坐标** | ❌ **完全算不了** |

ADR-0013 原文即写着「一期无坐标、无真实结算」。
所以「距离 20%」这个权重在今天**没有任何数据基础**。

**因此本版必须先做一次结构化改造（expand–contract）**，否则匹配引擎只能建在流沙上。

## 二、数据模型（V7 迁移）

### 2.1 expand

| 变更 | 说明 |
|---|---|
| `companion_profile` 增 `longitude DECIMAL(10,7) NULL` / `latitude DECIMAL(10,7) NULL` | 陪诊员坐标；一期由陪诊员自填或管理员代录 |
| `companion_profile` 增 `service_region_code VARCHAR(32) NULL` | 区域码（单值 → 用列不用表） |
| 新表 `companion_available_slot (id, companion_id, weekday, start_time, end_time, deleted, create_time, update_time)` | 可服务时段；**用表不用 JSON 列** —— 时段要参与筛选，必须可索引可 JOIN |
| `companion_order` 增 `service_region_code VARCHAR(32) NULL` | 订单侧区域码 |

**全部可空**，老数据不受影响。

### 2.2 backfill

按现有 `service_area` 自由文本映射到 `service_region_code`。
映射表放在 `backend/sql/tools/` 的生成器里（可复现）；**映射不上的留空**。

### 2.3 contract（读路径）

读路径**优先**用结构化列；结构化列缺失时**回退**到自由文本包含式匹配（与 V3.1 大厅同口径）。
**一期不删旧列**。

## 三、匹配引擎三件套

| 类 | 职责 |
|---|---|
| `MatchingService` | 编排：候选人过滤 → 规则计算 → 评分 → 排序 → 推荐 |
| `MatchingRule`（接口） | `boolean supports(candidate, order)` + `double score(candidate, order)`；规则可插拔 |
| `MatchingScore`（值对象） | 承载各维度得分与总加权分，**可解释**（每条推荐都能说出「为什么是他」） |

### 3.1 过滤链（顺序固定，短路）

1. 工作状态 = `AVAILABLE`（V3.1 的 `WorkStatus`）
2. 资质 `audit_status = 'APPROVED'`
3. 区域码匹配（订单区域码 ∩ 陪诊员区域码；陪诊员无区域码则回退文本包含式）
4. 时段可服务（订单 `visit_time` 落在 `companion_available_slot` 的某个时段内）
5. 档期冲突（该时段已有在手订单）

### 3.2 评分权重（配置化，启动期校验总和 = 1）

| 维度 | 权重 | 计算 |
|---|---|---|
| 区域匹配 | 30% | 区域码相等 = 1.0；同一区不同码 = 0.5；跨区 = 0 |
| 时间匹配 | 25% | 订单时间与可服务时段的重合度 |
| 距离 | 20% | Haversine（订单坐标 vs 陪诊员档案坐标）；**陪诊员无坐标 → 该维度记 0 并标注「无坐标」，绝不推断** |
| 服务能力 | 15% | 历史完成该 `department` 订单数归一化 |
| 评分 | 10% | `companion_profile.score` 归一化 |

权重键：`nianglin.matching.region.weight` / `.time.weight` / `.distance.weight` /
`.skill.weight` / `.rating.weight`。

**权重计算必须做成无 Spring 上下文的纯函数**（与 V3.1 的 `FulfillmentRiskEvaluator` 同范式），
这样「每个阈值的边界」都能毫秒级覆盖。

## 四、接口契约

| 端点 | 变化 |
|---|---|
| `GET /api/order/hall?sortBy=RECOMMEND` | **扩展** V3.1 的单一推荐序为真正的五维推荐序；响应结构零变更 |
| `GET /api/order/hall?sortBy=DISTANCE` / `TIME_MATCH` | V3.1 明确返回 400「该维度将在后续版本开放」→ **本版开放** |
| `GET /api/order/hall?sortBy=INCOME` | **仍不做** —— 没有真实结算金额口径（见 D8） |
| `GET /api/order/{id}/recommend-companions` | 供家属端「系统正在为你匹配」展示 Top N 候选 |

**边界（决策 4.4）**：排序**只做推荐**，接单权仍在陪诊员；
不引入 AI 模型（决策 4.1）；匹配权重变更写审计（复用 `admin_oper_log`）。

## 五、测试矩阵

| 层 | 锁住什么 |
|---|---|
| `MatchingRuleTest`（纯函数） | 每条规则的支持判定与得分边界；无坐标时距离维度记 0 且不推断 |
| `MatchingWeightConfigTest` | 权重之和 = 1 的启动期校验；改坏权重 → 变红 |
| `MatchingServiceTest` | 过滤链顺序与短路；可解释性字段（每条推荐带得分构成） |
| `DistanceTest` | Haversine 边界（同点、极远、跨半球） |
| 回归 | V3.1 的 `HallSortTest` 需按新排序语义更新并同步 spec |
| E2E | 大厅按新序展示；`DISTANCE` / `TIME_MATCH` 不再 400；`INCOME` 仍 400 |

**反向验证**：把距离维度的「无坐标 → 记 0」改成「按 0 坐标算距离」→ `MatchingRuleTest` 变红。
