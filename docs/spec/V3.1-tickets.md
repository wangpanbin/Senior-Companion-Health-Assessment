> **版本**：v1.0 · 2026-10-16

> **上游路线**：[`V3.x-roadmap-spec.md`](./V3.x-roadmap-spec.md) §4.1
> **流程约定**：每张票走 TDD（红 → 绿 → 重构）。本表已按依赖排序，**默认串行执行**；标注「可并行」的票在无共享写的前提下可同时开工。
> **状态**：全部 `ready-for-agent`
> **工单形态说明**：本仓库按单文件维护工单（先例：E4 工单表），与逐票一文件的通用约定不同；每票仍保持独立可执行、自带阻断边与验收判据。

## 执行纪律

| 项 | 要求 |
|---|---|
| 流程 | 每票内部走 **RED（写不出绿的测试）→ GREEN（最小实现让测试变绿）→ REFACTOR（不留测试债地重构）**。禁止先写实现再补测试 |
| 收敛 | 每票结束后跑该票的验收命令，绿了才能开下一票。红了先分清是**实现 bug** 还是**断言 bug**——把断言改钉到客观事实（阈值数值、错误码、SQL 条件），不要改断言去迁就症状 |
| 范围 | 一票只做它承诺的那条端到端行为。**发现额外问题记到 issue tracker，不要顺手扩范围** |
| 提交 | 提交前展示变更摘要，**不自动提交或推送** |
| 合规 | 新增文案过合规词表；出参走脱敏工具；日志先脱敏再拼接 |
| 反向验证 | 对「唯一真相表」类机制（风险阈值、状态机转移表），删除一条边必须让测试变红。仍然全绿 = 测试假绿，必须重写 |

## T0 · 陪诊员接单状态自助控制

**要构建的端到端行为**：陪诊员能在自己的界面上把接单状态切到「休息中」或「离线」，刷新页面、重启服务后状态保持；且**切换不影响他手上任何一笔已接订单**。

**阻断边**：无（可立即开工）

**状态**：ready-for-agent

### RED
- 状态切换测试：切到 `AVAILABLE` / `REST` / `OFFLINE` 三种值各自成功，响应带回新的状态与中文标签；
- 非法字面量 → `400`；
- 资质未通过的陪诊员切换 → `2003`；
- **在手订单不受影响**：构造一笔该陪诊员 `ACCEPTED` 的订单，切换到 `REST` 后断言该订单 `status` 不变、且陪诊员仍可正常推进它到下一节点；
- 越权矩阵：FAMILY / ELDER / ADMIN 三个角色调用该端点各一条，全部 `403`；
- 枚举测试：`OFFLINE` 的中文标签有值，且状态判定顺序仍是「先资质、再状态」。

### GREEN
- 扩展既有接单状态枚举为三值（**新增第三个值，不新造第二套枚举**）；
- 新增端点 `PUT /api/user/companion/work-status`，请求体只含状态字面量；
- 陪诊员档案读接口的回填字段增加对应标签；
- Service 单表单更新，事务边界内只改档案本身；
- **不动订单**：本票**禁止**触碰订单相关的任何 Service 方法。

### REFACTOR
- 把「状态字面量 → 枚举」的解析收敛到既有枚举工具方法，不在 Controller 里写 `switch`；
- 中文标签只从枚举取值，**不在 VO 装配处写 `if/else` 拼文案**。

### 验收判据
- [ ] 三种状态均可切换并持久化
- [ ] 非法字面量返回 `400`
- [ ] 资质未通过返回 `2003`
- [ ] **切换后在手订单状态完全不受影响**
- [ ] 三个非陪诊员角色调用均 `403`
- [ ] 订单状态机零改动（`git diff` 中不出现订单状态相关文件）

**验收命令**：后端全量测试通过；前端静态检查 0 警告。

## T1 · 履约风险字段、事件表迁移与风险判定纯函数

**要构建的端到端行为**：空库与既有库各跑一次迁移后成功；「订单等了多久」能被判定为 `NORMAL` / `WARNING` / `URGENT` / `MANUAL_REQUIRED` 四个等级之一，且判定逻辑无需启动 Spring、无需数据库、无需构造当前时间。

**阻断边**：T0

**状态**：ready-for-agent

> **为什么排在 T0 之后**：常量 / 枚举 / 配置层先落地并保持编译绿，再动数据库迁移，避免出现「迁移已执行但枚举没补齐」的中间态。这是刻意的顺序，不是技术依赖。

### RED
- 迁移测试：空库可完整执行；已有数据的库可完整执行且既有行取到默认值；迁移可重复执行不报错；
- 风险判定表驱动测试，全部用例如下：

| 等待分钟 | 期望等级 |
|---|---|
| `-1` | `NORMAL`，且不抛异常 |
| `0` | `NORMAL` |
| `warning - 1` | `NORMAL` |
| `warning`（恰好等于） | `WARNING` |
| `urgent - 1` | `WARNING` |
| `urgent`（恰好等于） | `URGENT` |
| `manual - 1` | `URGENT` |
| `manual`（恰好等于） | `MANUAL_REQUIRED` |
| `manual + 1000` | `MANUAL_REQUIRED` |

- 单调性测试：等待分钟从 `0` 遍历到 `manual + 10`，返回等级序列**不出现下降**；
- 配置校验测试：紧急阈值小于预警阈值时**启动失败并给出明确错误**（反向验证，不能静默生效）。

### GREEN
- 新建迁移脚本 **`V6__order_fulfillment.sql`**（`V1` / `V2` / `V3` 已冻结，`V4` / `V5` 已占用）：
  - 订单表增三列：`fulfillment_risk`（非空，默认 `NORMAL`）、`urge_count`（默认 `0`）、`last_urge_at`（可空）；
  - 建 `(fulfillment_risk, status, create_time)` 复合索引；
  - 新建履约事件表：订单 ID / 事件类型 / 变更前风险 / 变更后风险 / 触发来源 / 操作人 ID / 操作人角色 / 备注 / 发生时间 + 既有审计四字段；
  - 建两个索引：`(order_id, operate_time)` 与 `(event_type, operate_time)`；
  - 字符集与既有表一致。
- 新增风险等级枚举（四值）与履约事件类型枚举（八值）；
- 新增**纯函数风险判定器**，签名形如 `evaluate(waitMinutes, warningMinutes, urgentMinutes, manualRequiredMinutes)`：
  - **无状态、无 Spring、无 Mapper、无时钟依赖**（时间由参数传入）；
  - 阈值用 `>=` 比较，**恰好等于阈值即升档**；
  - 负值返回最低等级且不抛异常。
- 配置键全部落在 `nianglin.fulfillment` 命名空间下，缺省值走配置兜底：
  - `warning-minutes` = `10`、`urgent-minutes` = `30`、`manual-required-minutes` = `120`、`urge-cooldown-minutes` = `10`、`urge-max-times` = `3`、`scheduler-interval-ms` = `300000`、`scheduler-initial-delay-ms` = `60000`、`scheduler-enabled` = `true`、`hall-default-sort` = `RECOMMEND`。

### REFACTOR
- 等级大小比较不要散落 `if (a > b)`，收敛到枚举自身提供的能力（顺序 / 比较）；
- 中文标签只从枚举取值。

### 验收判据
- [ ] 空库迁移成功
- [ ] 既有库迁移成功，既有行取到默认值
- [ ] 迁移可重复执行
- [ ] 风险判定**全部边界用例**通过
- [ ] 单调性测试通过
- [ ] 阈值配置反向（紧急 < 预警）时启动失败
- [ ] 风险判定单测**不加载 Spring 上下文**（运行时间应在百毫秒级）
- [ ] **反向验证**：把任一阈值改成极大值 → 阈值测试必须变红
- [ ] 订单状态机零改动

**验收命令**：风险判定单测独立可跑且全绿；后端全量测试通过。

## T2 · 履约风险扫描定时任务

**要构建的端到端行为**：一条等待时长足够的 `PENDING` 订单，在扫描跑一次后升级到应有风险等级，家属收到**一条**通知；连跑两次不会产生第二条事件。

**阻断边**：T1

**状态**：ready-for-agent

### RED
- 单轮升级：构造等待时长足够、风险为 `NORMAL` 的订单 → 扫描一次 → 等级变为应有等级，**事件表恰好新增一条**，且该事件的变更前等级是 `NORMAL`、变更后是最终等级；
- **连升只写一条**：构造一条已等待远超人工介入阈值的订单 → 扫描一次 → 等级直接落到最高级，但**事件表只新增一条**；
- **幂等**：紧接着再扫描一次 → 事件表**不再新增**；
- **认领失败静默跳过**：构造两条同批订单，模拟认领条件更新返回 0 行 → 断言该条**不写事件、不发通知**，另一条正常处理；
- 只升级不降级：构造一条等级高于应有值的脏数据 → 扫描后**等级不被下调**；
- 已离开 `PENDING` 的订单不参与扫描；
- 候选集超过批次上限 → 只处理上限内的部分；
- 锁未抢到 → 直接返回，**不执行任何扫描**；
- 扫描中途抛异常 → 异常被接住并记日志，**调度线程不中断**。

### GREEN
- 扫描服务：查出候选订单 → 逐条按**旧值认领**的条件更新 → 更新成功才写事件与站内信；
  - 认领条件必须包含「按读到的旧风险等级」这一项，这是幂等与互斥的全部来源；
  - `rows = 0` 即被他人抢先，静默跳过；
- 新建定时任务类，**逐条沿用既有定时任务的四项写法**：
  1. 分布式锁写在任务方法内，TTL 小于扫描间隔（建议锁 4 分钟 / 间隔 5 分钟）；
  2. 锁策略为「宁可不执行，也不并发执行」（漏跑可接受、重复执行不可接受）；
  3. 方法内 `try/catch` 自接住异常并记错误日志；
  4. 条件装配开关，测试可整体关闭。
- 站内信复用既有通道，**不新建实时通信机制**；风险升级 → 写站内信在**同一事务**内，SSE 推送在事务**外**。

### REFACTOR
- 把「认领条件更新」抽成一个语义明确的方法，让幂等性有单一出处；
- 批次上限写成配置项，不硬编码。

### 验收判据
- [ ] 单轮升级正确，事件恰好一条
- [ ] 连升只写一条事件、只发一条通知
- [ ] 连扫两次无重复事件
- [ ] 认领失败静默跳过
- [ ] 等级只升不降
- [ ] 非 `PENDING` 订单不参与
- [ ] 批次上限生效
- [ ] 锁未抢到时跳过
- [ ] 异常不中断调度线程
- [ ] 通知未在事务内推送
- [ ] 订单状态机零改动

**验收命令**：扫描任务相关单测全绿；后端全量测试通过。

## T3 · 家属催单

**要构建的端到端行为**：风险达到「高风险」的订单，家属点「催促接单」后成功一次并收到确认；立刻再点第二次被拦下并看到明确提示。

**阻断边**：T2

**状态**：ready-for-agent

### RED
- 正常催单：风险达高风险 → 成功，响应带催单次数、最近催单时间、下次可催时间；
- 订单不存在 → `3001`；
- **非下单人（另一家属）→ `3004`**；
- 非 `PENDING`（已接单 / 已取消）→ `3008`；
- 风险**未达**高风险（仍为预警或正常）→ `3008`；
- 冷却期内再催 → `3009`；
- 次数达上限 → `3009`；
- **并发穿透**：条件更新返回 0 行 → `3009`（三种失败原因对外统一，不泄漏他人操作时序）；
- 履约事件写入「家属催单」，触发来源为 `USER`；
- 站内信只发给**可接单**（工作状态为可接单且资质已通过）的陪诊员，**不发管理员**；
- 备注字段过合规词表，命中违禁词被拦；
- 越权矩阵：陪诊员 / 老人 / 管理员调用该端点各一条，全部 `403`。

### GREEN
- 新增端点 `POST /api/order/{id}/urge`，请求体可含可选备注（≤200 字）；
- 前置校验**顺序固定**：订单存在 → 下单人 → 状态为待接单 → 风险达高风险 → 冷却与次数；
- 扣减资格与自增**合并为一条条件更新**，`WHERE` 同时带上：订单 ID、未删除、状态为待接单、风险在高等级集合内、次数未超上限、最近催单时间已过冷却线；
  - **禁止「先查后写」**——那会让并发请求双双通过校验并把次数写成同一个值；
  - `rows = 0` 一律翻译为 `3009`；
- 三件事同事务：条件更新 → 写履约事件 → 写站内信；SSE 推送在事务外。

### REFACTOR
- 把「冷却时间边界」的计算抽成一个方法，避免冷却期在两处各算一遍。

### 验收判据
- [ ] 正常催单成功且响应含三项
- [ ] 五类失败路径分别返回 `3001` / `3004` / `3008` / `3009`
- [ ] **并发穿透被挡**
- [ ] 履约事件与站内信在同一事务内写入
- [ ] 站内信只发给可接单陪诊员
- [ ] 备注过合规词表
- [ ] 越权矩阵四条全绿
- [ ] 订单状态机零改动

**验收命令**：催单相关单测 + 越权矩阵全绿；后端全量测试通过。

## T4 · 履约读口径

**要构建的端到端行为**：家属和陪诊员在订单详情看到**同一套**风险文案；等待时长随时间自动增加；订单被接走后风险提示自动消失。

**阻断边**：T1

**状态**：ready-for-agent
**可并行**：与 T2 / T3 无共享写，可同时开工。

### RED
- 订单详情返回五个增量字段：风险等级、风险中文文案、等待分钟数、催单次数、是否可催单；
- **不在 `PENDING` 时**：风险恒为 `NORMAL`、等待分钟数为 `0`；
- 等待分钟数随「现在」推进而增加（注入可控时间源，不写死当前时间）；
- 履约详情端点：事件流按时间**升序**返回，从「订单创建」到当前；
- 事件流为空时返回**空数组**，不是 `null`，不报错；
- 参与方判定：下单家属 / 接单陪诊员 / 就诊老人 / 管理员可读；**无关家属与无关陪诊员各一条用例返回 `3004`**；
- 管理员风险列表中的姓名**脱敏**（订单详情的全名豁免**不适用**于列表）。

### GREEN
- 订单出参新增五个只读字段；**既有字段零删除、零改名、零改语义**；
- 等待分钟数由「当前时间 − 下单时间」算出，**不落库**；
- 履约详情端点按既有参与方判定放行，不新写一套权限逻辑；
- 管理员风险计数端点返回四个字段，**为 0 时返回 0 而非省略**；
- 风险列表默认排序：风险等级降序 → 等待时长降序 → ID 降序。

### REFACTOR
- 等待分钟数、风险文案的中文标签都从枚举取，不在装配处拼字符串。

### 验收判据
- [ ] 五个增量字段全部返回
- [ ] 非 `PENDING` 时风险归零
- [ ] 等待分钟数随时间自增
- [ ] 事件流升序
- [ ] 空事件流返回空数组
- [ ] 两类无关方各返回 `3004`
- [ ] 管理端列表姓名脱敏
- [ ] **既有出参字段零破坏**（既有 E2E 无需修改即可通过）

**验收命令**：出参与读口径单测全绿；后端全量测试通过。

## T7 · 管理员人工协调与改派

**要构建的端到端行为**：管理员能把一笔还没人接的订单改派给另一位合格陪诊员；改完家属、目标陪诊员、原陪诊员都收到通知；操作留下可追溯的审计记录。

**阻断边**：T6

**状态**：ready-for-agent
**可并行**：与 T5 无共享写，可同时开工。

### RED
- 正常改派：成功，响应带回改派前后陪诊员与当前风险等级；
- 六类拒绝路径：订单不存在 `3001`；非待接单 `3010`；已有接单人 `3010`；目标陪诊员不存在 `2007`；目标资质未通过 `2003`；目标处于休息或离线 `3010`；目标曾拒过该单 `3010`；
- **本操作不改变订单状态**：断言改派后订单 `status` 仍为待接单；
- 审计记录：含操作类型、目标、前后陪诊员、理由；
- 三类接收方通知齐全（下单家属 / 目标陪诊员 / 原陪诊员；原陪诊员为空时只发两方）；
- 理由字段长度不足或含违禁词被拦；
- **与抢单竞争**：条件更新失败 → `3010`，不产生脏数据；
- 越权矩阵：家属 / 陪诊员 / 老人调用改派端点各一条，全部 `403`，且**必须携带能通过参数校验的合法请求体**（合规的目标陪诊员 + 10–200 字理由），否则会死在参数校验拿到假绿。

### GREEN
- 新增端点 `POST /api/admin/order/{id}/reassign`，请求体含目标陪诊员与理由；
- 前置校验**顺序固定**（六条，见上）；
- **条件更新**：以「状态为待接单 **且** 接单人为空」为条件写入目标陪诊员——这是与抢单竞争不失手的唯一来源；
- 四件事同事务：条件更新 → 写履约事件「订单改派」 → 写操作审计（含前后值与理由）→ 写站内信；SSE 推送在事务外；
- **边界（必须写进接口文档）**：本端点**只处理未接单订单**。已接单 / 服务中的订单需要换人属纠纷处理，走既有管理员仲裁通道，**不在本端点处理**。

### REFACTOR
- 「目标陪诊员是否合格」的判定抽成一个方法，避免五处 `if` 各判一半。

### 验收判据
- [ ] 正常改派成功且响应含前后值
- [ ] 七类拒绝路径分别返回 `3001` / `2007` / `2003` / `3010`
- [ ] **改派不改变订单状态**
- [ ] 审计记录含前后值与理由
- [ ] 三类接收方通知齐全
- [ ] 与抢单竞争时败者得到 `3010` 且无脏数据
- [ ] 越权矩阵三条全绿且携带合法请求体
- [ ] 接口文档已写明「仅限未接单订单」的边界
- [ ] 订单状态流转唯一入口**未被改出第二条改状态路径**（风险回落搭同一条乐观锁 `UPDATE`，不额外发 `UPDATE`；取舍与理由见 spec §5.3「取舍记录」）

**验收命令**：改派相关单测 + 越权矩阵全绿；后端全量测试通过。

## T8 · 订单大厅推荐排序

**要构建的端到端行为**：陪诊员打开大厅，订单按「就诊时间临近优先、同服务区域优先」排列；传入尚未开放的排序维度时得到明确拒绝而不是被静默忽略。

**阻断边**：T1

**状态**：ready-for-agent
**可并行**：与 T2 / T3 / T5 无共享写，可同时开工。

### RED
- 缺省排序键取配置项，缺省值为推荐序；
- **非法排序值 → `400`，且错误消息说明该维度后续版本开放**；
- 尚未开放的三种维度（距离 / 时间匹配 / 收益优先）传值同样 `400`，**不静默降级为默认序**；
- 排序语义：就诊时间升序 → 服务区域匹配者优先 → ID 升序兜底（保证分页稳定）；
- 区域匹配口径：订单医院名 / 地址与陪诊员服务区域、可服务时段做**包含式**匹配；两者都不匹配时按未匹配处理排后，**不做任何推断**；
- 资质未通过的陪诊员调用 → `2003`；
- 既有大厅响应结构零变更。

### GREEN
- 大厅查询增加**可选**排序参数，走**白名单**校验（不在白名单内的字面量一律 `400`）；
- 本版**只实现一种排序**；
- 区域匹配口径与「不做推断」原则写进接口文档；
- 大厅页在只有一个排序项时**不显示排序选择器**，改为一行说明「更多排序方式后续开放」。

### REFACTOR
- 排序键 → 排序列的映射收敛到白名单映射表，不写多个 `if` 分支。

### 验收判据
- [ ] 缺省排序键来自配置
- [ ] 非法排序值返回 `400` 且消息说明后续开放
- [ ] 三种未开放维度均 `400`，不静默降级
- [ ] 排序键三级稳定，分页不重不漏
- [ ] 区域匹配为包含式且不做推断
- [ ] 资质未通过返回 `2003`
- [ ] **既有大厅响应结构零变更**
- [ ] 静态检查 0 警告

**验收命令**：大厅排序单测全绿；前端静态检查 0 警告。
