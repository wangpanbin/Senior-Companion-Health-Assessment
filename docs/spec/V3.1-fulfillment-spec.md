## 二、接口契约

> 全部走 `/api` 前缀与现有 REST 风格，**不引入 `/api/v3`**。业务失败一律 HTTP 200（除 Spring Security 直接抛的 401 / 403 与容器返回的 404 / 405）。

### 2.1 `PUT /api/user/companion/work-status` · 陪诊员切换接单状态

| 项 | 规格 |
|---|---|
| 角色门槛 | `@PreAuthorize("hasRole('COMPANION')")` |
| 请求体 | `{ "workStatus": String }`，取值 `AVAILABLE` / `REST` / `OFFLINE`；非法值 → `400` |
| 成功响应 | `Result<CompanionProfileVO>`（复用既有 VO，新增 `workStatus` / `workStatusLabel`，前端可就地回填） |
| 错误码 | `2003` 资质尚未通过 · `400` 非法状态字面量 · `401` 未登录 · `403` 非陪诊员 |
| 事务边界 | `@Transactional(rollbackFor = Exception.class)`；单表单更新，无跨表写 |
| **关键规则** | **不校验、不影响该陪诊员的任何在手订单。** 切换状态后已 `ACCEPTED` / `IN_SERVICE` 的订单继续按订单状态机执行，不因 `REST` / `OFFLINE` 而中断 |
| 判定顺序 | 保持既有语义：**先看资质，再看状态**。`auditStatus != APPROVED` 的陪诊员即便切到 `AVAILABLE` 也接不了单 |

**响应示例（脱敏）**

```json
{ "code": 200, "message": "接单状态已更新", "data": { "workStatus": "REST", "workStatusLabel": "休息中", "...": "..." } }
```

### 2.2 `POST /api/order/{id}/urge` · 家属催单

| 项 | 规格 |
|---|---|
| 角色门槛 | `@PreAuthorize("hasRole('FAMILY')")` |
| 路径变量 | `id` Long（订单 ID） |
| 请求体 | 无（可接受可选 `remark`，≤200 字；**remark 必须过合规词表**） |
| 成功响应 | `Result<OrderUrgeResultVO>`：`{ orderId, urgeCount, lastUrgeAt, nextUrgeAvailableAt }` |
| 错误码 | `3001` 订单不存在 · `3004` 非下单人 · `3008` 非 `PENDING` 或风险未达 `URGENT` · `3009` 冷却期内或次数超限 |
| 前置校验（顺序固定） | ① 订单存在 → `3001`；② `familyId == 当前用户` → `3004`；③ `status == PENDING` → `3008`；④ `fulfillmentRisk >= URGENT` → `3008`；⑤ 冷却期与次数上限 → `3009` |
| 事务边界 | 三件事**同事务**：条件更新订单 → 写履约事件 `USER_URGED` → 写站内信 |
| 并发 | **单条条件更新**完成自增与资格判定，靠 `WHERE` 条件挡穿透，不做「先查后写」 |
| 通知 | 站内信推给**全部 `workStatus = AVAILABLE` 且资质已通过**的陪诊员（不是管理员），文案不含任何医疗内容 |

**条件更新的判定契约**（这是本端点的并发核心，必须精确实现）：

```
UPDATE companion_order
   SET urge_count    = urge_count + 1,
       last_urge_at  = <now>
 WHERE id            = :id
   AND deleted       = 0
   AND status        = 'PENDING'
   AND fulfillment_risk IN ('URGENT', 'MANUAL_REQUIRED')
   AND urge_count    < :maxTimes
   AND (last_urge_at IS NULL OR last_urge_at <= :cooldownBoundary)
```

`rows = 0` → 统一翻译为 `3009`（要么被别人抢先、要么冷却期内、要么超限，三者对外不区分，避免泄漏他人操作时序）。

> **为什么用「条件更新」而不是「先查后写」**：两个并发请求都通过第 ⑤ 步校验时，先查后写会双双成功并把 `urge_count` 写成同一个值；条件更新让第二个请求 `rows = 0`，天然互斥。这与本项目既有的乐观条件更新写法一致。

### 2.3 `GET /api/order/{id}/fulfillment` · 订单履约详情

| 项 | 规格 |
|---|---|
| 角色门槛 | 无类级注解，按参与方校验 |
| 访问控制 | 复用既有「订单参与方」判定：下单家属 / 接单陪诊员 / 就诊老人 / 管理员；其余 → `3004` |
| 成功响应 | `Result<OrderFulfillmentVO>`：`{ orderId, orderNo, status, statusLabel, fulfillmentRisk, fulfillmentRiskLabel, waitMinutes, urgeCount, canUrge, nextUrgeAvailableAt, events[] }` |
| `events[]` 元素 | `{ eventType, eventLabel, fromRisk, fromRiskLabel, toRisk, toRiskLabel, triggerSource, operatorRole, remark, operateTime }` |
| 排序 | `events` 按 `operateTime` **升序**（从「订单创建」到「当前」） |
| 空数据 | 事件流为空时返回空数组，**不返回 null，不报错** |
| 错误码 | `3001` 订单不存在 · `3004` 非参与方 |
| 事务边界 | 只读，无事务 |
| 脱敏 | 事件中的 `operatorId` 若指向陪诊员，其姓名字段走脱敏；`remark` 原样返回但已在写入侧过合规词表 |

### 2.4 `GET /api/order/hall?sortBy=…` · 大厅排序（路径不变，加参数）

| 项 | 规格 |
|---|---|
| 角色门槛 | `@PreAuthorize("hasRole('COMPANION')")` |
| 查询参数 | `sortBy` String，可选。**白名单**：`RECOMMEND`（唯一实现值）。缺省取配置项 `nianglin.fulfillment.hall-default-sort`（缺省 `RECOMMEND`） |
| 非法值 | 传 `sortBy=DISTANCE` / `TIME_MATCH` / `INCOME` 或任意其他字面量 → `400`，**并在错误消息中说明该维度将在后续版本开放**（V3.1 不静默降级） |
| 成功响应 | `Result<PageResult<OrderVO>>`，**结构与既有大厅完全一致**，零字段变更 |
| 排序语义 | 二级排序键：① `visitTime` 升序（就诊时间临近优先）② 服务区域匹配者优先（非匹配者排后）。同键时按 `id` 升序兜底，保证分页稳定 |
| 区域匹配口径 | 订单**没有**独立的「服务区域」字段，匹配以**订单医院名 + 地址**与陪诊员 `serviceArea` / `availableTime` 做**包含式**匹配；两者都不匹配时按未匹配处理（排在匹配者之后），**不做任何推断或猜测** |
| 错误码 | `2003` 资质未通过 · `400` 非法 `sortBy` |

> **范围声明（必须写进接口文档）**：本版**只实现一种排序**。距离 / 时间匹配 / 收益优先三个维度在 V3.4 的加权规则引擎中随权重配置一并开放。原因是服务区域与可服务时段当前是**自由文本**，此时给出四种排序必然在 V3.4 被推翻。

### 2.5 `GET /api/admin/fulfillment/summary` · 风险中心顶部计数

| 项 | 规格 |
|---|---|
| 角色门槛 | 管理端类级 `@PreAuthorize("hasRole('ADMIN')")` |
| 成功响应 | `Result<FulfillmentSummaryVO>`：`{ manualRequired, urgent, warning, normal }`，**四个字段全部返回**，为 0 时返回 0 而非省略 |
| 统计口径 | 只统计 `status = 'PENDING'` 的订单；按 `fulfillment_risk` 分组计数 |
| 事务边界 | 只读 |
| 错误码 | 无（越权由注解返回 403） |

### 2.6 `GET /api/admin/fulfillment/risk-list` · 风险订单列表

| 项 | 规格 |
|---|---|
| 角色门槛 | 管理端类级 |
| 查询参数 | 分页参数（沿用既有分页入参，`size` 上限 100）· `risk` 可选，取四个枚举值之一，缺省返回**全部**（含 `NORMAL`） |
| 默认排序 | 风险等级**降序**（`MANUAL_REQUIRED` → `URGENT` → `WARNING` → `NORMAL`），同级按等待时长**降序**，再按 `id` 降序兜底 |
| 成功响应 | `Result<PageResult<AdminFulfillmentRiskItemVO>>`，元素含：`orderId` / `orderNo`（**脱敏**）· 老人姓名（**脱敏**）· 医院 / 科室 / 就诊时间 · 风险等级与文案 · 等待时长 · 催单次数 · 是否已有人工介入记录 |
| 姓名脱敏 | 列表口径**一律脱敏**（`MaskUtil.name()`），不适用订单详情的全名豁免 |
| 事务边界 | 只读 |

### 2.7 `POST /api/admin/order/{id}/reassign` · 管理员改派

| 项 | 规格 |
|---|---|
| 角色门槛 | 管理端类级 |
| 路径变量 | `id` Long（订单 ID） |
| 请求体 | `{ "companionId": Long, "reason": String, 10..200 chars }`，reason 必填且过合规词表 |
| 成功响应 | `Result<ReassignResultVO>`：`{ orderId, fromCompanionId, toCompanionId, fulfillmentRisk }` |
| 错误码 | `3001` 订单不存在 · `3010` 不可改派 · `2007` 目标陪诊员不存在 · `2003` 目标陪诊员资质未通过 |
| 前置校验（顺序固定） | ① 订单存在 → `3001`；② `status == 'PENDING'` 且 `companionId IS NULL` → `3010`；③ 目标陪诊员存在 → `2007`；④ 目标陪诊员 `auditStatus == APPROVED` → `2003`；⑤ 目标陪诊员 `workStatus == AVAILABLE` → `3010`；⑥ 目标陪诊员未拒过该单 → `3010` |
| 事务边界 | **同事务四件事**：条件更新订单 → 写履约事件 `ORDER_REASSIGNED` → 写操作审计（操作类型 / 目标类型 / 前后值 / reason）→ 写站内信 |
| 通知 | ① 通知**下单家属**：订单已由平台协调安排陪诊员；② 通知**目标陪诊员**：有一笔订单已指派给您，请尽快确认；③ 通知**原陪诊员**（`fromCompanionId` 非空时，即此前有陪诊员看过但未接）：该订单已改派给其他陪诊员 |
| 状态机 | **本操作不改变 `status`**（订单仍是 `PENDING`），因此**不经过订单状态流转唯一入口**；`status` 仍由陪诊员接单时经该入口变更 |
| 并发 | 与陪诊员抢单竞争同一行：改派走条件更新（见 §六），抢单走既有乐观锁；败者分别得到 `3010` / `3003` |

> **边界（必须写进接口文档）**：改派**仅对 `PENDING` 且尚无接单人的订单开放**。已 `ACCEPTED` / `IN_SERVICE` 的订单需要换人，属纠纷处理，走既有管理员纠纷仲裁通道（可强制终态并通知双方），**不在本端点处理**。这避免了同一件事存在两条状态变更路径。

## 三、数据契约

### 3.1 迁移脚本：`V6__order_fulfillment.sql`

> `V1` / `V2` / `V3` 已执行并冻结，`V4__order_fee_item.sql` 与 `V5__chat_message.sql` 已占用。本版的结构变更**全部集中在 `V6`**，**不得回改已冻结脚本**。

**`companion_order` 增量三列**

| 列名 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `fulfillment_risk` | `VARCHAR(20)` | `'NORMAL'` | 履约风险等级；`NOT NULL` 以便直接 GROUP BY 与建索引 |
| `urge_count` | `INT` | `0` | 累计催单次数 |
| `last_urge_at` | `DATETIME` | `NULL` | 最近一次催单时间；`NULL` 表示从未催单 |

**新增索引**：`(fulfillment_risk, status, create_time)` 复合索引。服务两个查询：风险扫描的候选集筛选、风险中心列表的分组与排序。

> **为什么加 `NOT NULL DEFAULT`**：风险中心的四个计数来自 `GROUP BY fulfillment_risk`，可空列会产生一个语义不明的 `NULL` 分组；`NOT NULL` 让「没有风险等级」这一状态不可能存在。

### 3.2 新表 `order_fulfillment_event`

语义：**只增不改**的履约事件流水表。与 `order_status_log` **同风格不同语义**——后者记的是 `from_status → to_status` 的**状态流转**，本表记的是**履约过程**；两者**不可互相替代**。

| 列名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | PK, AUTO_INCREMENT | — |
| `order_id` | `BIGINT` | NOT NULL | 订单 ID |
| `event_type` | `VARCHAR(30)` | NOT NULL | 事件类型（见 §3.4） |
| `from_risk` | `VARCHAR(20)` | NULL | 变更前风险等级；首次事件为 `NULL` |
| `to_risk` | `VARCHAR(20)` | NULL | 变更后风险等级；非风险类事件可与 `from_risk` 相同 |
| `trigger_source` | `VARCHAR(20)` | NOT NULL | 触发来源：`USER` / `ADMIN` / `SYSTEM` |
| `operator_id` | `BIGINT` | NULL | 操作人用户 ID；系统自动触发为 `NULL` |
| `operator_role` | `VARCHAR(20)` | NULL | ELDER / FAMILY / COMPANION / ADMIN / SYSTEM |
| `remark` | `VARCHAR(500)` | NULL | 备注 |
| `operate_time` | `DATETIME` | NOT NULL | 发生时间 |
| `create_time` / `update_time` / `deleted` | — | — | 继承既有审计字段约定 |

**索引**：`(order_id, operate_time)` 服务按订单拉事件流；`(event_type, operate_time)` 服务按事件类型做运营统计。

**字符集**：与其他表一致，`utf8mb4` / `utf8mb4_general_ci`。

### 3.3 `OrderVO` 增量字段

| 字段 | 类型 | 何时填 | 说明 |
|---|---|---|---|
| `fulfillmentRisk` | String | 始终 | 枚举名；不在 `PENDING` 时恒为 `NORMAL` |
| `fulfillmentRiskLabel` | String | 始终 | 中文文案，供前端直接展示 |
| `waitMinutes` | Integer | 始终 | 从下单到当前的等待分钟数；不在 `PENDING` 时为 `0` |
| `urgeCount` | Integer | 始终 | 累计催单次数 |
| `canUrge` | Boolean | 始终 | 前端据此决定催单按钮是否可用；服务端**仍会二次校验**，前端禁用不是安全边界 |

> **既有字段零改动**：不删除、不重命名、不改语义。既有前端与 E2E 不需要任何修改即可继续工作。

### 3.4 `FulfillmentRisk` 枚举

```
NORMAL          正常等待
WARNING         等待时间较长
URGENT          履约风险较高
MANUAL_REQUIRED 需要管理员人工介入
```

### 3.5 `FulfillmentEventType` 枚举

```
ORDER_CREATED          订单创建
MATCHING_STARTED       开始在大厅匹配
FULFILLMENT_WARNING    风险升为预警
USER_URGED             家属催单
FULFILLMENT_URGENT     风险升为高风险
MANUAL_REQUIRED        风险升为需人工介入
ADMIN_COORDINATED      管理员已人工协调
ORDER_REASSIGNED       管理员改派陪诊员
```

> ⚠️ **待解项 U1**：`ORDER_CREATED` 与 `MATCHING_STARTED` 语义可能重叠。前者定义为「订单落库瞬间」，后者定义为「大厅首次可见（就诊时间未过且未被拒）」——二者在多数场景下同日。**合并判据**：若实施中发现「大厅首次可见」无法被稳定、可重复地判定（例如无法在不引入额外查询的前提下确定），则**合并为一个事件**，并回写本 spec 的枚举。不得为了保留两个事件而引入一次额外的逐单查询。

### 3.6 「最小化迁移」自查（对齐总纲 G2）

| 问 | 本版的答案 |
|---|---|
| 是否产生了新的业务事实？ | **是**。「这单等了多久」「催了几次」「风险升到哪一级」都是新的业务事实 |
| 是否可以由已有数据计算？ | 等待时长可由 `create_time` 算出；但**催单次数与风险等级是历史动作的沉淀**，不是可重算的纯函数 |
| 是否应该由 Service 聚合？ | 等待时长是；催单次数与风险等级**不是**，它们需要被查询、被筛选、被建索引 |
| 是否必须持久化？ | **是**。风险中心要按等级筛选与分页，等级必须是可索引的列 |
| 是否会成为未来核心查询条件？ | **是**。V3.5 的异常中心直接消费风险等级 |

结论：三列**必须持久化**；事件表用于可追溯，满足总纲 §五 的审计要求。

## 五、Service 实现要点

> 本节只写**决策密度高、用散文说不准**的部分（并发判定、事务边界、幂等语义）。常规样板代码省略。

### 5.1 `FulfillmentRiskEvaluator` · 唯一新增测试接缝

```
static FulfillmentRisk evaluate(int waitMinutes,
                                int warningMinutes,
                                int urgentMinutes,
                                int manualRequiredMinutes)
```

| 决策点 | 规格 |
|---|---|
| 纯度 | **无状态、无 Spring 上下文、无 Mapper、无时钟依赖**。时间由参数传入（等待分钟数），因此单测不需要构造「当前时间」 |
| 分档 | `waitMinutes >= manualRequired` → `MANUAL_REQUIRED`；`>= urgent` → `URGENT`；`>= warning` → `WARNING`；否则 `NORMAL` |
| 边界 | 恰好等于阈值时**升档**（`>=` 而非 `>`）。测试必须钉住这一点 |
| 负值 | `waitMinutes < 0` 一律返回 `NORMAL`，不抛异常（防御脏数据） |
| 单调性 | `waitMinutes` 单调递增时返回等级**不得下降**（本实现天然满足，测试需钉住） |

> **为什么这是唯一的新接缝**：风险判定是本版唯一有「分支组合爆炸」风险的新逻辑（三个阈值 × 边界值 × 负值）。把它做成纯函数，就能用十几条毫秒级单测覆盖全部组合，而不需要 Spring 上下文、数据库或时间旅行。其余模块（催单、改派、扫描）都是「一次查询 + 一次条件更新 + 一次写」的直白编排，用既有 Service 单测范式即可覆盖。

### 5.2 风险扫描的幂等语义

**扫描一轮要做的事**：查出所有 `status = 'PENDING'` 且 `fulfillment_risk <> 当前应有等级` 的订单 → 对每一条尝试升级。

**「认领」的条件更新契约**：

```
UPDATE companion_order
   SET fulfillment_risk = :expected
 WHERE id                = :id
   AND deleted           = 0
   AND status            = 'PENDING'
   AND fulfillment_risk  = :actual      -- 关键：按读到的旧值认领
```

`rows = 0` → 已被另一实例抢先处理，**跳过该条，不写事件、不发通知**。

| 决策点 | 规格 |
|---|---|
| 单轮连升 | **允许一次扫描内连续升级到应有等级**，例如某单已等 130 分钟，本轮从 `NORMAL` 直接落到 `MANUAL_REQUIRED` |
| 事件条数 | 连升**只写一条事件**，`from_risk` 记扫描前的实际值、`to_risk` 记最终等级。这样家属不会在一次扫描里收到三条递进告警 |
| 通知条数 | 同上，只发**一条**通知，文案按**最终等级**选（不按中间等级） |
| 幂等 | 连扫两轮，第二轮所有订单的「当前等级」已等于「应有等级」，不进入认领分支，**不产生任何新事件** |
| 自愈 | 服务重启导致等级停在旧值，下一轮按等待时长重算并补升 |
| 等级只能前进 | 扫描**只做升级**，永不降级；降级只由「离开 `PENDING`」触发 |

### 5.3 「离开 `PENDING`」时的风险收敛

| 触发 | 行为 |
|---|---|
| 陪诊员接单（`PENDING → ACCEPTED`） | `fulfillment_risk` 回落 `NORMAL` |
| 家属取消（`PENDING → CANCELLED`） | 同上 |
| 管理员仲裁导致离开 `PENDING` | 同上 |

**实现位置**：订单状态流转唯一入口的**既有流程内**，不新增第二条改状态路径，也不新增第二个改风险等级的入口。风险收敛与状态变更在**同一事务**内。

> **本版零改动的部分**：`OrderStatus` 枚举、`TRANSITIONS` 转移表、`canTransitTo` 的判定逻辑、状态流转入口本身——**一行都不改**。风险只是搭一次车。

### 5.4 定时任务

沿用既有定时任务的四项既定写法，不发明新模式：

1. 分布式锁用既有锁工具，**锁写在任务方法内**，TTL 小于扫描间隔（锁 4 分钟 / 间隔 5 分钟），保证下一轮能正常抢到；
2. 锁 TTL 按「丢失代价 vs 重复代价」定：风险升级**漏跑一次可接受**（下轮补上）、**重复执行不可接受**（重复告警），所以策略是「宁可不执行，也不并发执行」；
3. 方法内 `try/catch` 自接住异常并记错误日志，**不让异常打断调度轮次**；
4. 条件装配开关，测试环境可整体关闭。

**批次上限**：单轮扫描的候选集必须有上限（建议 200 条，按等待时长倒序取），避免订单量增长后单轮执行时间过长而超出锁 TTL。

### 5.5 事务与推送的边界

| 动作 | 同事务内 | 事务外 |
|---|---|---|
| 风险升级 | 条件更新订单 + 写履约事件 + 写站内信 | SSE 推送 |
| 家属催单 | 条件更新订单 + 写履约事件 + 写站内信 | SSE 推送 |
| 管理员改派 | 条件更新订单 + 写履约事件 + 写审计 + 写站内信 | SSE 推送 |

> **为什么推送在事务外**：推送是尽力而为，不能让它拖垮事实落库。站内信已落库时，SSE 推送失败可由断线重连与下次进入页面补齐；站内信落库失败则整个事务回滚，保证「有告警就有记录」。

## 六、并发与竞争

| 场景 | 手法 | 败者看到 |
|---|---|---|
| 两实例同时扫同一批 `PENDING` | 分布式锁 + 按旧值认领的条件更新 | `rows = 0` → 静默跳过，不产生重复事件 |
| 家属并发催单 | 单条条件更新同时完成「自增 + 资格判定 + 冷却判定」 | `rows = 0` → `3009` |
| 陪诊员抢单 vs 管理员改派 | 抢单走既有乐观锁；改派走「`companionId IS NULL` 且 `status = 'PENDING'`」的条件更新 | 抢单败 `3003`；改派败 `3010` |
| 家属取消 vs 风险升级 | 取消走状态流转入口；升级的条件更新带 `status = 'PENDING'` 条件 | 升级 `rows = 0` → 跳过 |
| 同一管理员重复改派 | 第二次条件更新因 `companionId IS NULL` 不成立而失败 | `3010` |
| 催单把站内信广播打爆 | 只推 `workStatus = AVAILABLE` 且资质已通过的陪诊员；冷却期以 `last_urge_at` 为准 | — |

**不变式（必须由测试钉住）**：

1. `status` 与 `fulfillment_risk` **永不互相推导**；
2. `order_status_log` **只**记状态流转，`order_fulfillment_event` **只**记履约过程；
3. 订单状态**只有一条**变更路径（状态流转唯一入口），V3.1 不新增第二条；
4. 任何新增接口**不返回**未经脱敏的手机号、身份证号、完整姓名（订单详情的全名豁免**不适用**于本版新增的管理端列表）。

## 七、测试矩阵

### 7.1 纯函数单测（最高优先级，毫秒级）

**`FulfillmentRiskEvaluator`** —— 阈值表驱动：

| 用例 | 等待分钟 | 期望 |
|---|---|---|
| 负值防御 | `-1` | `NORMAL`，不抛异常 |
| 刚下单 | `0` | `NORMAL` |
| 差一格预警 | `warning - 1` | `NORMAL` |
| 恰好到预警 | `warning` | `WARNING` |
| 差一格紧急 | `urgent - 1` | `WARNING` |
| 恰好到紧急 | `urgent` | `URGENT` |
| 差一格人工 | `manualRequired - 1` | `URGENT` |
| 恰好到人工 | `manualRequired` | `MANUAL_REQUIRED` |
| 远超人工 | `manualRequired + 1000` | `MANUAL_REQUIRED` |
| 单调性 | 遍历 `0..manualRequired+10` | 等级序列不下降 |

> 反向验证：把某个阈值改成极大值 → 该测试必须变红。仍然全绿说明测试是假绿，必须重写。

### 7.2 Service 单测

**催单**：正常催单 → 非下单人 `3004` → 非 `PENDING` `3008` → 风险未达 `URGENT` `3008` → 冷却期内 `3009` → 超次数 `3009` → 条件更新 `rows = 0` 翻译为 `3009` → 履约事件写入 `USER_URGED` 且 `trigger_source = USER` → 站内信只发给可接单陪诊员。

**改派**：正常改派 → 订单不存在 `3001` → 非 `PENDING` `3010` → 已有接单人 `3010` → 目标陪诊员不存在 `2007` → 目标资质未过 `2003` → 目标处于休息/离线 `3010` → 目标曾拒过该单 `3010` → 审计记录含前后陪诊员与理由 → 三类接收方通知齐全 → **`status` 未被本操作改变**。

**工作状态**：切到 `AVAILABLE` / `REST` / `OFFLINE` 均成功 → 非法字面量 `400` → 资质未过 `2003` → **切换后在手订单状态不受影响**（断言在手订单的 `status` 与原值一致）。

**扫描幂等**：构造一条等待时长足够的订单 → 扫描一次，风险升到应有等级且**事件表只多一条** → 再扫描一次，**事件表不再增加**。

## 九、验收标准

### 9.1 功能

- 陪诊员可以切换 / 暂停接单，切换后在手订单不受影响；
- `PENDING` 订单进入履约风险检测，等级随等待时长自动变化；
- 家属在风险达 `URGENT` 后可以催单，且催单有频率与次数限制；
- 家属端按四个等级展示不同文案；
- 管理员可以查看风险计数与风险订单列表，可从列表跳到订单详情；
- 管理员可以对 `PENDING` 订单改派，非 `PENDING` 被明确拒绝；
- 管理员的人工协调与改派都写入审计与履约事件；
- 大厅按单一推荐序展示，非法排序参数被明确拒绝而非静默忽略。

### 9.2 稳定性（**硬性**）

- **订单状态机语义零改动**，订单状态仍只有一条变更路径；
- 既有订单相关 API 的路径与响应结构零破坏（只增字段，不改不改名）；
- **订单状态流转唯一入口的既有实现零改动**；
- 既有用药系统、消息系统、权限体系零破坏；
- **既有 E2E 166 条全绿**；
- 新增履约场景 E2E 全绿。

### 9.3 门禁

| 项 | 判据 |
|---|---|
| 后端 | `mvn -B verify` 全绿 |
| 前端 | `lint:check` 0 警告 + 单元测试全绿 + 构建成功 |
| 合规 | 新增文案与示例数据中无违禁词、无真实手机号 / 身份证号 / 密码 |
| 文档 | PRD / ADR / API 契约 / 迁移说明 / 测试报告 / CHANGELOG 六处同步 |
| 反向验证 | 删除风险判定阈值 → 阈值单测变红；删除状态机任一转移边 → 状态流转单测变红 |

### 9.4 Definition of Done

1. 陪诊员能够自主控制接单状态；
2. 系统能够识别长时间未接单订单；
3. 系统能够自动升级履约风险；
4. 家属能够获得明确的履约反馈；
5. 家属能够合理催单；
6. 管理员能够发现高风险订单；
7. 管理员能够人工介入；
8. 管理员能够完成订单改派；
9. 所有关键履约事件可追溯；
10. 不破坏现有订单状态机；
11. 不破坏现有 IM 能力；
12. 不破坏用药系统；
13. 不破坏现有权限体系；
14. 既有 E2E 全部通过；
15. 新增 E2E 全部通过；
16. PRD / ADR / API / 迁移 / CHANGELOG 同步更新。

## 十一、Further Notes

### 11.1 实施时最容易做错的三件事

1. **把风险升级写成状态流转。** 风险是独立字段。若实施时发现自己在给 `OrderStatus` 加枚举值，说明已经跑偏——回到 §5.3，风险搭状态流转的「车」即可。
2. **在扫描里发多条通知。** 一轮连升只发一条（§5.2），否则家属会在同一分钟收到「预警」「紧急」「需人工」三条消息。
3. **让前端算风险等级。** 后端已给出判定，前端只展示。前端自行判断会导致管理员端与家属端出现不同等级（总纲 §6 明确禁止）。
