预写 spec 的「事实基线」逐条核实，**全部成立**：

| # | 复核项 | 核实结果 | 处置 |

| ② | 该端点是否只允许下单家属 | ✅ 服务层再校验 `order.familyId == 当前用户`，否则 `3004` | 门面复用同一归属校验语义 |

**结论**：spec 的十六项决策全部有事实支撑，无需改设计。

### 偏差 D-3.7-1：FAQ 用 JSON 而非 YAML

spec §四 脚注已预留「若改 YAML 需追加 `PyYAML` 并报批」。**本版直接用 JSON**
（Python 标准库直接读，零依赖），不为一个格式问题新增依赖。

### 偏差 D-3.7-2：合规词表的 Python 侧路径做成可配置

spec 写「默认 `../backend/src/main/resources/compliance/medical-advice-words.txt`」。
实现时改为**环境变量 `NIANGLIN_COMPLIANCE_WORDS_PATH` 优先**，默认值同 spec。
理由：生产部署时两个服务的代码目录布局未必与仓库一致，可配置比硬编码相对路径可靠。

### 偏差 D-3.7-3：词表是 **17 词**，不是 18

开工复核 ⑤ 查出：预写 plan 把词表词数**心算成了 18**，实际是 **17**
（诊断结论 4 + 开药动作 6 + 用药调整 7）。这个数字被复制进了 ADR-0020、spec、
Java 单测与 Python 单测。

处置：写 `tools/fix_compliance_word_count.py`，**由脚本从词表文件程序化数出词数**
再统一各文件表述 —— 词数不再靠人算。改完复核为 17，两侧单测的快照同步更新。

### 偏差 D-3.7-4：派单措辞做**词语级纠正**而非整段替换

spec §4.10 原写「命中「已指派 / 已分配 / 自动派单」→ **整段替换**为推荐免责话术」。
实现时改为：**词语级纠正**（已指派→推荐 / 已分配→推荐 / 自动派单→自动推荐）
并追加免责句。

理由：派单措辞是**产品边界**问题而不是合规红线 —— 纠正后语义依然正确
（推荐 ≠ 派单，但推荐本身是允许说的）；而医疗内容是合规红线，
纠正后仍可能残留医学判断，所以必须**整段拒答**。整段丢掉会让家属白问一次。

## 四、留给后续版本的三件事

1. **流式输出** —— 现状是一次性返回 + 按请求覆写 60s 超时。流式要新增 SSE 通道 +
   改前端渲染 + 改 Java 转发，收益（少等几秒）不抵复杂度。
2. **真实家属问题清单** —— 当前 FAQ 30 条是按仓库 docs 推导的，覆盖真实提问分布的情况
   未经用户验证。有真实清单时直接替换条目即可（条目结构与校验脚本都不用改）。
3. **助手专属的端到端用例** —— 正式 E2E 套件有防「假绿」硬规则，本版 E2E 列为可选，
   核心门禁是 pytest + JUnit + vitest。
