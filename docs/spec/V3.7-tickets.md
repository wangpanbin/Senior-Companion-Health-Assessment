**结论**：spec 的十六项决策全部有事实支撑，无需改设计。

### 偏差 D-3.7-1：FAQ 用 JSON 而非 YAML

spec §四 脚注已预留「若改 YAML 需追加 `PyYAML` 并报批」。**本版直接用 JSON**
（Python 标准库直接读，零依赖），不为一个格式问题新增依赖。

### 偏差 D-3.7-2：合规词表的 Python 侧路径做成可配置

spec 写「默认 `../backend/src/main/resources/compliance/medical-advice-words.txt`」。
实现时改为**环境变量 `NIANGLIN_COMPLIANCE_WORDS_PATH` 优先**，默认值同 spec。
理由：生产部署时两个服务的代码目录布局未必与仓库一致，可配置比硬编码相对路径可靠。

### 偏差 D-3.7-3：词表是 **17 词**，不是 18

开工复核 ⑤ 查出：预写 plan 把词表词数**心算成了 18**，实际是 **17**
（诊断结论 4 + 开药动作 6 + 用药调整 7）。这个数字被复制进了 ADR-0020、spec、
Java 单测与 Python 单测。

处置：写 `tools/fix_compliance_word_count.py`，**由脚本从词表文件程序化数出词数**
再统一各文件表述 —— 词数不再靠人算。改完复核为 17，两侧单测的快照同步更新。

### 偏差 D-3.7-4：派单措辞做**词语级纠正**而非整段替换

spec §4.10 原写「命中「已指派 / 已分配 / 自动派单」→ **整段替换**为推荐免责话术」。
实现时改为：**词语级纠正**（已指派→推荐 / 已分配→推荐 / 自动派单→自动推荐）
并追加免责句。

理由：派单措辞是**产品边界**问题而不是合规红线 —— 纠正后语义依然正确
（推荐 ≠ 派单，但推荐本身是允许说的）；而医疗内容是合规红线，
纠正后仍可能残留医学判断，所以必须**整段拒答**。整段丢掉会让家属白问一次。

### 偏差 D-3.7-5：历史的单位是「消息条数」不是「轮」

spec 原文写 `@Size(max = 6)`，而前端每轮发 2 条（user + assistant）——
问到第 5 轮就会发 8 条 → 被 `@Size` 拦成 400。
**用得越久越坏**，而只测 1–2 轮时完全看不出来。

处置：上限改为**消息条数** 12（= 6 轮），配置键同步改名为 `max-history-messages`。
「轮」与「条」的换算写进字段注释与 spec，不再靠猜。

### 偏差 D-3.7-6：推荐词表不用裸词「陪诊员」

spec 原文列了裸词「陪诊员」。但推荐分支在 FAQ 检索**之前**，
裸词会把「陪诊员资质怎么审核」（FAQ 里有现成条目）也路由到推荐分支 ——
答非所问比「没听懂」更糟，因为它看起来像个答案。

处置：改用**具体搭配**（「几位陪诊员」「陪诊员为什么」「为什么合适」…），
既覆盖「这几位陪诊员为什么合适」这类问法，又不误伤资质 / 打卡 / 评价类问题。

### 偏差 D-3.7-7：兜底检索比主检索简单（有意为之）

Java 兜底只做「关键词命中计数」，Python 主检索是「关键词 + 2-gram 重叠」。
**两套并存是有意的**：兜底是降级路径，宁可用简单算法，
也不要引入第二套需要同步维护的检索逻辑。
「口径一致」只在**答案来源**与**依据引用格式**两层成立（同一份 faq.json、同一套 `§` 引用格式）。

### 偏差 D-3.7-8：三份共享合规资产，而不只是医疗词表

收口评审发现：医疗词表虽已共享，但**辱骂 / 违规引流词**在 Python 侧是手工抄的第二份 ——
正好违反 ADR-0020 自己写下的「不要另起一份词表」。
而**固定拒答模板**若两侧各写一份，早晚有一侧会写进禁用词、
把自己拦下（拒答模板被拒答）。

处置：三份资产全部收进 `backend/src/main/resources/compliance/` ——
`medical-advice-words.txt` / `sensitive-words.txt` / `refusal-template.txt`，
Java 与 Python 读同一份，各自 fail-fast。

### 偏差 D-3.7-9：Java 侧也校验词表关键词

原先只有 Python 侧校验「必须含『建议服用』『剂量』」，Java 侧只查词数。
两边口径不同 → 读错文件时 Java 照常放行、Python 拒启动，行为分叉。

处置：Java 侧补上同样的关键词校验，两侧口径对齐。

## 五、留给后续版本的三件事

1. **流式输出** —— 现状是一次性返回 + 按请求覆写 60s 超时。流式要新增 SSE 通道 +
   改前端渲染 + 改 Java 转发，收益（少等几秒）不抵复杂度。
2. **真实家属问题清单** —— 当前 FAQ 30 条是按仓库 docs 推导的，覆盖真实提问分布的情况
   未经用户验证。有真实清单时直接替换条目即可（条目结构与校验脚本都不用改）。
3. **助手专属的端到端用例** —— 正式 E2E 套件有防「假绿」硬规则，本版 E2E 列为可选，
   核心门禁是 pytest + JUnit + vitest。
