## 二、接口契约

> 全部走 `/api` 前缀与现有 REST 风格，**不引入 `/api/v3`**（决策 G3）。
> 业务失败一律 HTTP 200（除 Spring Security 直接抛的 401 / 403）。
> 字段级契约见 [`docs/api/12-elder-health.md`](../api/12-elder-health.md)。

| # | 端点 | 角色 | 归属校验 | 主要错误码 |
|---|---|---|---|---|
| F-1 | `GET /api/family/health/summary` | FAMILY | 天然按当前家属取数 | 401 / 403 |
| F-2 | `GET /api/family/elder/{elderId}/health/overview` | FAMILY | `requireAccessible` | 2001 / 2006 / 9002 / 400 |
| F-3 | `GET /api/family/elder/{elderId}/health/timeline` | FAMILY | `requireAccessible` | 2001 / 2006 / 9002 / 400 |
| F-4 | `GET /api/elder/health/overview` | ELDER | 档案 ID 从登录态取 | 2001 / 401 / 403 |
| F-5 | `GET /api/elder/health/timeline` | ELDER | 同上 | 2001 / 400 / 9002 / 401 / 403 |

### 2.1 两条不可协商的接口约束

**① 老人端不接受 `elderId` 入参。**
把 `elderId` 放进路径或查询参数，等于开了一个「改一下参数就能看别人」的洞 ——
即使服务端会校验，那也是多一次可以出错的地方。
F-4 / F-5 **一个 `elderId` 都不收**，服务端从登录态直接取。

**② 家属端的归属校验不能省。**
`@PreAuthorize("hasRole('FAMILY')")` 只回答「你是家属吗」。
「这位老人是不是你家的」由 `ElderService.requireAccessible(elderId)` 判定，否则返回 `2006`。
少了它，任何家属都能读别人家老人的健康数据。

### 2.2 零新增错误码

本版**目标零新增错误码**，全部复用：

| 场景 | 复用码 | 出处 |
|---|---|---|
| 区间越界 / 起止颠倒 | `9002 STAT_RANGE_INVALID` | M10 已有 |
| 无权访问该老人 | `2006 NO_PERMISSION_FOR_ELDER` | M3 已有 |
| 老人档案不存在 / 未建档 | `2001 ELDER_NOT_FOUND` | M3 已有 |
| 参数不合法（分类 / 游标 / 日期格式） | `400 PARAM_ERROR` | 通用 |
| 未登录 / 角色不符 | `401` / `403` | Spring Security |

## 三、数据契约

### 3.1 聚合入口：`elder_id` 唯一

`order_checkin` 与 `internal_message` **都没有老人 ID**，
所以聚合统一以「先取该老人的订单 ID 集合，再让子表用 `IN (...)` 过滤」的方式取数。
**禁止**为每类事件各写一条 JOIN（那会让 `companion_order` 被重复扫 N 次）。

| 子查询 | 走法 | 命中索引 |
|---|---|---|
| 家属名下老人 | `family_elder_relation` JOIN `elder_profile` | `family_elder_relation(family_id)` |
| 用药三桶 | `medication_task` WHERE `elder_id IN (...)` AND `plan_date BETWEEN` | `idx_elder_date_status` |
| 就医统计 | `companion_order` WHERE `elder_id IN (...)` AND `visit_time BETWEEN` | `idx_elder_id` |
| 待处理计数 | `companion_order` WHERE `elder_id IN (...)` GROUP BY | `idx_elder_id` |
| 打卡事件 | `order_checkin` WHERE `order_id IN (...)` AND `checkin_time BETWEEN` | `idx_order_time` |
| 站内信事件 | `internal_message` WHERE `biz_type` + `biz_id` | `idx_biz` |

### 3.2 口径定义

| 指标 | 公式 | 登记于 |
|---|---|---|
| 就医次数 | `COUNT(status IN ('COMPLETED','REVIEWED'))` | `elder.visit.order_count` |
| 陪诊人数 | `COUNT(DISTINCT companion_id WHERE status IN ('COMPLETED','REVIEWED'))` | `elder.visit.companion_count` |
| 用药三桶 | `MedicationBucket.of(status, was_missed)` | `elder.medication.*`（区间）· `elder.today.*`（当天） |
| 用药完成率 | `taken / total`；`total = 0` → `"0.00%"` | `elder.medication.completion_rate` |
| 今日用药 | **当天**口径（`plan_date = 今天`），**不随统计区间浮动** | `elder.today.*` |
| 待处理类别数 | 满足任一待处理判定的类别数 | `elder.summary.pending_item_count` |

> **「已完成」= `COMPLETED` + `REVIEWED`** 是 M10 起的铁律：
> 把已评价的单排除会让完成率随着用户评价而下降。

### 3.3 待处理事项的四个判定

| type | 判定 | 家属端链接 | 老人端 |
|---|---|---|---|
| `MEDICATION_PENDING` | 今日 `status='PENDING'` 的任务数 > 0 | `/family/medication` | ✅ 保留 |
| `ORDER_WAITING` | `status='PENDING'` 的订单数 > 0 | `/family/order` | ❌ 不返回 |
| `ORDER_TO_REVIEW` | `status='COMPLETED'` 的订单数 > 0 | `/family/order` | ❌ 不返回 |
| `FULFILLMENT_RISK` | `status='PENDING'` 且风险 ∈ {URGENT, MANUAL_REQUIRED} | `/family/order` | ❌ 不返回 |

> 老人端只保留与自身相关的事项（决策 U-3：老人端只讲自己的事）。

## 五、并发、失败与恢复语义

| 项 | 语义 |
|---|---|
| 写操作 | **本版零写操作**。无 `@Transactional`、无乐观锁、无条件更新 |
| 并发 | 聚合读天然容忍并发；跨表读取非快照隔离，允许同一请求内看到略有偏差的计数 —— **可接受**（事实型指标，不做财务对账） |
| 单个子查询失败 | **整个请求失败**（抛 `BusinessException`），**不返回半截数据**。半个健康概览比一个报错更容易误导人 |
| 空数据 | 计数为 0、集合为空数组；**绝不返回 null** |
| 脏数据防御 | 状态字段出现枚举外的值 → 归入兜底桶（TAKEN）或默认分类，**不抛异常**（与 V3.1 `FulfillmentRisk.of` 兜底范式一致） |
| 越权 | 一律 `requireAccessible` / 登录态取档案 ID；**服务端拦截**，不依赖前端隐藏 |
| 幂等 | 只读天然幂等 |
| 游标 | 翻页与排序共用同一套比较器（`occurredAt DESC` → `eventId ASC`），不会漏条或重复 |
| **截断** | 每类事件封顶 200 **条事件**；任一类触顶 → 响应 `truncated = true`，**前端必须如实提示**，不能让用户以为看到的就是全部 |
| 缓存 | **不加**（ADR-0003 已否决统计缓存；推翻需新 ADR） |

## 六、前端契约

| 页面 | 路由 | 内容 | 三态 |
|---|---|---|---|
| 家庭健康协同首页 | `/family/health` | 老人列表卡（今日用药 x/y · 近期就医 n 次 · 待处理 n 项） | Loading 骨架 / Empty（没绑老人）/ Error（重试） |
| 某老人健康中心 | `/family/elder/:id/health` | 基础信息 + 六项概览 + 待处理 + 健康时间线 | 同上 + 时间线无数据空态 |
| 老人端健康中心 | `/elder/health` | 今日用药（大字）+ 近期就医 + 待办 + 做过的事 | 同上 |

### 6.1 入口

| 入口 | 位置 |
|---|---|
| 家属工作台 → 家庭健康 | `views/family/home.vue` 的 `quickEntries`（移动与桌面两个形态共用） |
| 家庭健康 → 某老人健康中心 | 首页的老人卡片 |
| 老人首页 → 我的健康 | `views/elder/home.vue` 的「我的健康」卡 |

**导航项不新增**（迭代计划 §57）：三个页面都落在既有分组内，
底部 TabBar 不加项（它按角色硬编码，V3.2 不动）。

### 6.2 适老化（AGENTS.md §3.5 + 决策 G6）

- 正文 ≥ 18px、点击区 ≥ 48px、对比度 ≥ 4.5:1、核心流程 ≤ 3 次点击
- 老人端信息密度低优先于完整性：概览只留 4 项；时间线只显示「图标 + 一句话 + 时间」，**不显示多行 detail**
- 老人端大字：`today__v` 56px，指标 32px

### 6.3 UI 纪律

界面只留**结论与状态**；口径说明、免责文案、字段释义全部进 `docs/`。
强调色收敛为一个主色，状态色只用于状态标签本身。

### 6.4 前端零计算（G8）

完成率、漏服数、待处理数一律**后端算好，前端原样展示**。
`utils/elderHealth.js` 里的 `completionRateText` 只做兜底（后端没给值 → `0.00%`），不做任何除法。
`elderHealth.test.js` 钉住这一点。

### 6.5 页面编号

`docs/design/design.md` 的页面编号表只到 M-28 / W-10。V3.2 续编：

| 路由 | code |
|---|---|
| `/family/health` | M-29 |
| `/family/elder/:id/health` | M-30 |
| `/elder/health` | M-31 |

（与 V3.1 的 `admin/fulfillment` 挂 W-10、M13 聊天挂 M-27 / M-28 同理。）
