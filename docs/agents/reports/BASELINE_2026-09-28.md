### 3.1 🔴 build 首跑失败（阻断）

```powershell
cmd /c 'cd /d "...\frontend" && pnpm.cmd build'
# [vite:css] [sass] Undefined variable.
#   at src\views\companion\reviews.vue
# BUILD_EXIT=1
```

**根因**：`companion/reviews.vue` 与 `family/order-detail.vue` 引用了 3 个
**在 `variables.scss` 中根本不存在**的变量：

| 代码里写的 | `variables.scss` 实际令牌 | 按语义映射为 |
|---|---|---|
| `$nl-radius-md` | `$nl-radius-card: 14px` | `$nl-radius-card` |
| `$nl-shadow-1` | `$nl-shadow-card: 0 2px 8px …` | `$nl-shadow-card` |
| `$nl-radius-sm` | `$nl-radius-chip: 6px` | `$nl-radius-chip` |

共 5 处引用（reviews.vue 4 + order-detail.vue 1），全部来自 E4 提交（`b6e1b71`~`a20b98d`）。

**这个缺陷此前完全不可见**，因为：
- `pnpm lint` 只跑 ESLint，**不编译 SCSS** → 0 警告
- 该页面在 E2E 里靠接口断言，不截图 → 不会因样式报错失败
- 「代码完成度 95%」的盘点看的是"有没有漏 import / 有没有 mock 壳"，不跑 build

修复后：

```powershell
cmd /c 'cd /d "...\frontend" && pnpm.cmd build'
# BUILD_EXIT=0 · ✓ built in 7.30s
```

### 3.2 🟡 端口文档漂移 5173 → 5141

dev server 实测监听 **5141**（非 5173）。追查发现**代码是对的、文档是错的**：

| 位置 | 值 |
|---|---|
| `vite.config.js:34` | `port: Number(env.VITE_PORT) \|\| 5141` |
| `playwright.config.js:22` | `BASE_URL = … \|\| 'http://127.0.0.1:5141'` |
| `playwright.config.js:70` | `webServer.command` 硬编码 `--port 5141` |

而 5 处文档仍写 5173：`README.md:142`、`README.md:162`、`AGENTS.md:268`（§2.10 CORS）、
`docs/agents/FRONTEND_CONTRACT.md:26`、`:633`、以及 `application-dev.yml:82` 注释。

**还发现一处真实代码缺陷**：`WebMvcConfig:30` 的
`@Value("${nianglin.cors.allowed-origins:http://localhost:5173,…}")` 兜底默认值也是 5173。
开发期因 `application-dev.yml` 用 `[*]` 通配而没暴露，但该 profile 缺失时就会放行错端口。已一并修正为 5141。

> `FRONTEND_CONTRACT.md:633` 那条注释解释了**为什么**项目用 5141 而非 5173：
> Windows Hyper-V/WSL 会动态保留大批 TCP 端口（本机曾整段占掉 5152–5251）。
> 已保留该警示，只把端口号订正。


**这正是文档 §七 预言的"最大变量"：E2E 从未在本轮跑过，红了要翻倍。**

### 4.2 根因：不是代码错，是夹具数据漂移

逐层排查（**没有停在"测试写错了"就改测试**）：

1. **测试契约**：`e2e/helpers/accounts.js:14` 明确声明 `{ account: 'comp025', audit: 'PENDING' }`，
   且 spec 注释写「未过审陪诊员」
2. **后端实现**：`OrderServiceImpl:256` 的 `hall()` **确实**调用了 `requireApprovedCompanion(me.userId())`，
   6 处调用点齐全 → 代码正确
3. **种子数据**：`V2__seed_data.sql:392` 中 325 的 `audit_status` = `'PENDING'` → 种子正确
4. **实际数据库**：

```
mysql> SELECT cp.user_id,u.username,cp.audit_status
     FROM companion_profile cp JOIN sys_user u ON u.id=cp.user_id
     WHERE u.username IN ('comp025','comp001');
user_id  username  audit_status
301      comp001   APPROVED
325      comp025   APPROVED     ← 应该是 PENDING
```

5. **漂移时间点**：`update_time = 2026-09-19 13:46:17`，
   且 `companion_audit_record` 里 325 记录 `audit_status=APPROVED, audit_admin_id=1`

→ **9 天前（2026-09-19）某次后台/管理端 E2E 运行把 comp025 审批通过了，脏数据留在库里。**
Flyway 三个版本（1/2/3，均 `success=1`）早已执行完毕，不会重播种子；测试依赖的是"种子刚导入"的干净状态。

这与 `docs/agents/FIXTURE_ROLLBACK_PLAN.md` 记录的"**L1 不可重跑**"完全同源：
现有工具**只读不写**，无 fixture 重建，E2E 跑一次数据就变一次。

### 4.3 修复：恢复夹具，不改已执行的种子脚本

⚠️ **没有修改 `V2__seed_data.sql`** —— 它已被 Flyway 执行且 `validate-on-migrate: true` 会校验
checksum，改动会导致下次启动迁移失败（AGENTS.md §5 明令）。改为定向 UPDATE 恢复：

```sql
UPDATE companion_profile      SET audit_status='PENDING', update_time='2026-09-28 16:40:00'
 WHERE user_id=325 AND audit_status='APPROVED';
UPDATE companion_audit_record SET audit_status='PENDING', audit_admin_id=NULL, audit_time=NULL
 WHERE applicant_user_id=325 AND audit_status='APPROVED';
```

## 8. 需要人工处理的一件事

**远端 `master` 分支删不掉。** 本地已 `master → main` 改名并推送，`develop` 已建并推送，
`origin/HEAD` 已指向 `main`，但 GitHub 拒绝删除默认分支：

```
! [remote rejected] master (refusing to delete the current branch: refs/heads/master)
```

**需在 GitHub 网页操作一次**：Settings → Branches → 默认分支 `master` → 改为 `main`。
之后 `git push origin --delete master` 即可生效。

（与 memory 里那条"机器级 `setx` 属系统配置变更、AI 不代劳"同理 —— GitHub 默认分支
是仓库级设置，只能人工在 UI 改。）
