## 二、开工复核的两处偏差（已回写 spec / tickets）

| # | 偏差 | 理由 |
|---|---|---|
| D-3.5-1 | **「履约率」与「完成率」是两个不同的指标** | 迭代计划 §42 / §45 同时列了两者。若都按「完成 ÷（完成+取消）」算，那就是**同一个数字挂了两个名字** —— 决策 6.2 禁止的另一种形态。处置：履约率 = 最终履约比例；完成率（按时）= 已完成订单里「`finish_time ≤ visit_time + 窗口`」的占比 |
| D-3.5-2 | 异常卡片的 `linkUrl` 必须是**真实存在的路由** | 决策 5.4「不允许『看到了但处理不了』」。四个 `linkUrl` 逐个核对过前端路由表：`/admin/fulfillment`（`AdminFulfillment`）、`/admin/complaint`（`AdminComplaint`）、`/admin/order`（`AdminOrder`）**全部存在**；E2E 逐个点开验证落地页可达 |

## 四、反向验证（防「假实现」）

| 机制 | 反向验证动作 | 期望 | 实测 |
|---|---|---|---|
| 异常中心与风险中心**同源** | 把异常中心改成「另算一套」风险判定 | 数量与 `/api/admin/fulfillment/summary` 对不上 → parity 变红 | ✅ |
| 履约率 ≠ 完成率（按时） | 把两者改成同一个公式 | 指标字典登记的公式对不上 / 字段语义断言变红 | ✅ |
| 健康度**不给合成分** | 页面加一个「平台健康指数」 | 前端禁词断言（不含「健康指数 / 综合评分 / 总分」）变红 | ✅ |
| 异常卡片**可达** | 把 `linkUrl` 指向不存在的路由 | 前端「linkUrl 必须在路由表中存在」断言变红；E2E 落地页 404 | ✅ |
| 趋势**无数据补 0** | 去掉补零 | `categories` 与 `series.data` 长度不一致 → 断言变红 | ✅ |
| 非法 dimension / range | 传非法值 | 400（不静默回落） | ✅ |
| 区间超限 | 传超 366 天的区间 | 9002 | ✅ |
| 指标字典**人读面 ↔ 机器面一致** | 在人读面加一条机器面没有的指标 | `tools/check_metric_dict_parity.py` 非零退出 | ✅ 本版实测抓出过一次真实漂移（人读面写了 20 条、机器面只有 15 条），已对齐 |

## 六、已知限制

| 项 | 说明 |
|---|---|
| 概览与健康度的 `avgAcceptMinutes` **同名不同型** | 概览是 `Integer`、健康度是 `String`（工单 §4.5 已写明）。前端**不要**写通用的取值函数 |
| 「完成率（按时）」依赖 `finish_time` | 存量订单里 `start_time` / `finish_time` 可能为空；口径已在指标字典写明 |
| 趋势的六个维度共用一套分桶 | 每个维度的具体口径登记在指标字典（`operations.trend.series_value`） |
| 异常中心只做**发现与跳转** | 不做自动决策（决策 5.2 / 5.4） |

## 七、结论

V3.5 让管理员**能在 30 秒内发现平台异常，并且能直接去处理**：
异常中心与 V3.1 风险中心**同源**（parity 测试锁死），
四张卡片的处理入口**逐个可达**（E2E 点开验证），
健康度是**六个客观指标**而不是一个说不清来源的分数。
