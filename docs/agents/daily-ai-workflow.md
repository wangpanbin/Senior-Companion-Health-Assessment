# AI 日常工作流（银龄伴诊）

> **这份文件是什么**：一份「把重复劳动交给 AI」的落地规程 —— 四个环节、每个环节的触发指令与完成判据、环节之间的衔接方式，以及什么该交给我、什么必须你拍板。
>
> 配套工具在 `tools/ai_flow/`，用法见 [tools/ai_flow/README.md](../../tools/ai_flow/README.md)。
>
> 本文件是**工作流真源**；业务规则的真源仍然是 [docs/agents/doc-sync.md](doc-sync.md)、[docs/agents/git-workflow.md](git-workflow.md) 等既有文件，本文件不改它们，只引用。

---

## 1 · 为什么是这四个环节

从三个高频痛点倒推，而不是先设计流程再找活干：

| 痛点 | 根因 | 对应环节 |
|---|---|---|
| 文档同步费时 | 联动矩阵在 [docs/agents/doc-sync.md](doc-sync.md)，但哪几行被触发了要靠人记 | **L1 文档同步环** |
| 跑门禁费时 | CI 与本地的门禁集合不一致，红点还得自己读输出 | **L2 门禁定位环** |
| 提交准备费时 | 每次都要重新组织「改了什么 / 为什么 / 影响面」 | **L3 提交准备环** |
| 多项目并行切换费神 | 每次切回来都要重建上下文 | **L4 项目切换环** |

L4 不解决新活，只解决**上下文重建成本** —— 它的产出是另外三环的输入。

## 2 · 什么该交给我，什么你留着

判定标准，**三条同时成立**才整段交给我：

1. **规则有真源** —— 判定依据在仓库里是文件，不是记忆（如 doc-sync.md、ResultCode.java）
2. **结果可机器验证** —— 能给出 PASS/FAIL 判据，不靠「看一眼觉得对」
3. **动作可逆** —— 错了能撤，不产生对外可见的后果

不满足就反过来分工：

| 情况 | 归谁 |
|---|---|
| 规则明确 + 可验证 + 可逆 | **整段交给我**，你只看结论 |
| 规则明确，但结果只能人判断（文案品味、交互手感） | 我出候选 + 判据，**你选** |
| 不可逆或对外可见（git commit/push、CI/CD 配置、发布、删数据） | **你点头我才动**，我准备到「一键可执行」为止 |
| 一次性、不会再发生的活 | 不值得为它建流程 |

落到这个仓库：

| 环节 | 交给我 | 你保留 |
|---|---|---|
| L1 文档同步 | 算影响面、补文档、跑一致性校验、出对账表 | 判定语义是否等价 |
| L2 门禁 | 跑门禁、定位红点、给修复建议 | 是否接受某个失败为「已知」 |
| L3 提交准备 | 生成 commit message、变更摘要、评审清单 | **提交动作本身**（AGENTS.md §7.3） |
| L4 项目切换 | 重建上下文快照、给出下一步 | 选哪个项目、方向 |

## 3 · 四个环节

### L1 文档同步环

- **何时**：代码 / 接口改动定稿后
- **指令**：`同步文档`
- **我做什么**：
  1. 读改动面 → 跑 `python tools/ai_flow/impact_map.py`
  2. 对每个命中的联动项，去目标文档里**核对接口路径是否已覆盖**
  3. 缺什么补什么（接口文档、错误码总表、状态机章节、对应单测）
  4. 跑 `python tools/ai_flow/gate_check.py`
  5. 出一张对账表：已覆盖 / 真欠账 / 抽查 / 需你确认
- **产出**：文档改动 + 对账表
- **完成判据**：gate_check 全绿，且对账表「真欠账」为 0

> ⚠️ **本仓库执行接口先行**（[docs/agents/api-first.md](api-first.md)），接口文档常常在**更早的提交**里就写好了。
> 所以判定必须是「接口路径是否出现在文档里」，不能是「这次 diff 有没有碰过它」——
> 后者会把已写好的文档误报成欠账。`impact_map.py` 走的是前者。

### L2 门禁定位环

- **何时**：改完代码、准备收工前
- **指令**：`跑门禁`
- **我做什么**：
  1. `python tools/ai_flow/gate_check.py` —— 静态门禁，秒级，不依赖 MySQL / Redis / 浏览器
  2. 需要全量时：`powershell -ExecutionPolicy Bypass -File tools/verify_all.ps1`（依赖本机 MySQL / Redis 常驻 + 前端 dev server）
  3. 红点定位：读日志找到**第一个真实失败**，区分「代码缺陷 / 夹具漂移 / 环境问题」
  4. 给修复建议，**不擅自改断言去迁就症状**
- **产出**：门禁表 + 失败归因 + 修复建议
- **完成判据**：能指出红点的第一现场

### L3 提交准备环

- **何时**：要提交时
- **指令**：`准备提交`
- **我做什么**：
  1. 检查分支合规（不得在 main / develop 上直接写代码，AGENTS.md §0.2）
  2. 生成 commit message（Conventional Commits，简洁英文）
  3. 生成变更摘要：改了什么 / 为什么 / 影响面 / 验证方式 —— 这是给评审看的
  4. 列出「还没做的」（L1 的抽查项、未闭环欠账）
  5. **停下来**，等你确认后再执行提交
- **产出**：commit message + 变更摘要 + 待确认清单
- **完成判据**：你只回一句「提交」即可执行
- **红线**：AGENTS.md §7.3 —— 没有明确授权，不执行 commit / push

### L4 项目切换环

- **何时**：切到另一个项目，或隔天回来
- **指令**：`我在哪`
- **我做什么**：
  1. 各项目当前分支 + 未提交改动 + 最近提交
  2. 未闭环的欠账（从 L1 对账表、L2 门禁结果里读）
  3. 下一步建议，按「哪个欠账最卡脖子」排序
- **产出**：跨项目状态快照

## 4 · 环节怎么衔接：交接卡

**不靠对话记忆**。每一环结束写一张卡，下一环读它 —— 这样换会话、换项目、隔天回来都不会丢上下文。

```bash
python tools/ai_flow/handoff.py new --loop L1 \
  --summary "补了 ExamPrep 接口文档" \
  --verdict "gate_check 全绿，欠账 0" \
  --next "跑 L2 门禁" \
  --risks "R13 交互清单未抽查"

python tools/ai_flow/handoff.py latest
```

卡片落在 `.workbuddy/handoff/`（已被 .gitignore 忽略，不入库）。固定五个字段：
**时间 / 分支 / commit**、**本环完成**、**判定结果**、**下一步**、**遗留风险**。

## 5 · 指令速查

| 你说 | 我做 |
|---|---|
| `同步文档` | L1 全流程，末尾给对账表 |
| `跑门禁` | L2 全流程，末尾给红点归因 |
| `准备提交` | L3 全流程，**停在等你确认** |
| `我在哪` | L4 跨项目状态快照 |
| `这条链路做完了吗` | 读最新交接卡 + 复跑对应门禁 |

## 7 · 落地状态（2026-11-16）

**已跑通：L1。** 搭这套东西时顺手查出来的真实缺口：

1. **本地总闸门缺三道 CI 才有的静态门禁** ——
   [tools/verify_all.ps1](../../../tools/verify_all.ps1) 只跑 lint / build / mvn test / playwright / 覆盖率，
   **没有**密钥体检、指标字典 parity、FAQ 锚点。「本地全绿、CI 红了」的风险就在这三行。
   已由 `gate_check.py` 补齐，两个入口都调同一份脚本，规则不复制。

2. **错误码总表漂移** ——
   `ResultCode.java` 里的 `REVIEW_NOT_FOUND(6005)` 与 `REVIEW_ALREADY_REPLIED(6006)`
   在 [docs/api/README.md](../../api/README.md) §4.7 里**缺失**；
   而 [docs/spec/E4-review-credibility.md](../../spec/E4-review-credibility.md) §427 / §430 早就写明要补。
   这是「清单里写了但没落地」的同步项，已补齐。

3. **接口文档覆盖度此前无人核对** ——
   新增 `impact_map.py` 做契约级核对：解析 Controller / 前端封装的接口路径，去目标文档里查出现过没有。

**CI 已接入**（2026-11-16 追加）：

- `.github/workflows/ci.yml` 新增第 6 个 job `static-gates`，跑两项此前无人覆盖的门禁：
  **错误码双向一致**（全量，与 diff 无关）+ **文档三项校验**（增量，只查本次改动碰过的 .md）。
- 与既有 job 分工不重叠：密钥体检 / FAQ 锚点 / 指标字典 parity 已分别在
  `secrets` / `ai-service` / `metric-dict` job 里跑，新 job 不重复跑。
- 规则本体仍在 `tools/ai_flow/gate_check.py`，CI 与本地调同一份脚本。
- 文档校验为什么走增量而不是全量 —— 仓库里的 spec 与归档计划天然引用
  「还没实现 / 已删除」的路径（那是它们的性质，不是错误），全量扫要开一堆豁免；
  豁免越多门禁越不可信。门禁的价值是挡住**新引入**的问题，不是清算历史。

**仍待决定**：

- L2 / L3 / L4 的完整落地 —— 目前只有 L1 真跑过，L2/L3/L4 是设计态。

## 8 · 红线（每次都适用）

- **不自动 commit / push**（AGENTS.md §7.3）
- **不改** CI/CD 配置、.env、密钥（红线）
- **不删**数据、**不改** git 历史
- **写代码前先开分支**（AGENTS.md §0.2）
- 改后端跑 `mvn -B verify`，改前端跑 `pnpm run lint:check` 与 `pnpm run test`（与 CI 同命令）
