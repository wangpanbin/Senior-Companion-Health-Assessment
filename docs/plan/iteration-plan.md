# 1. 产品定位

## 1.1 产品简介

《银龄伴诊》是一套面向老年人就医场景的陪诊与家庭健康协同平台。

平台围绕老年人一次完整的就医过程，将：

- 老人
- 家属
- 陪诊员
- 平台管理员

四类角色连接起来，为老人提供陪诊服务，为家属提供远程协同能力，为陪诊员提供服务与履约工具，为平台提供运营管理和治理能力。

## 1.2 核心价值

V3.0 之后，产品定位不再只是：

> “一个可以预约陪诊员的平台”。

而应该逐渐升级为：

> **“围绕老人就医过程进行多角色协同的服务平台。”**

核心价值可以概括为：

```
有人陪
    ↓
陪诊服务

有人知
    ↓
家属协同 + 实时消息

有人管
    ↓
订单履约 + 平台治理

持续优化
    ↓
数据分析 + 智能调度
```

# 12. V3.1 —— 履约保障中心

## 12.1 版本目标

解决：

> **订单创建之后，如果长时间没有陪诊员接单怎么办？**

当前系统已经具备订单状态机，但“无人接单”属于状态机之外的履约风险问题。

因此 V3.1 的核心目标是：

> **让订单不会因为无人接单而失控。**

# 13. V3.1 核心能力

## 13.1 陪诊员工作状态

陪诊员增加：

```
WORKING
PAUSED
OFFLINE
```

或者采用项目现有 `WorkStatus` 枚举进行扩展。

状态含义：

| 状态     | 是否接受新订单 |
| -------- | -------------- |
| 接单中   | 是             |
| 暂停接单 | 否             |
| 离线     | 否             |

规则：

```
工作状态
    ↓
只影响新订单匹配

已经接受的订单
    ↓
继续按照订单状态机执行
```

不得因为陪诊员暂停接单而影响已有订单。

# 14. V3.1 履约风险模型

不要修改现有订单状态机。

现有：

```
PENDING
ACCEPTED
IN_SERVICE
COMPLETED
...
```

继续保留。

新增独立的：

```
FulfillmentRisk
```

建议：

```
NORMAL
WARNING
URGENT
MANUAL_REQUIRED
```

含义：

| 风险等级        | 含义               |
| --------------- | ------------------ |
| NORMAL          | 正常等待           |
| WARNING         | 等待时间较长       |
| URGENT          | 履约风险较高       |
| MANUAL_REQUIRED | 需要管理员人工介入 |

原则：

> `Order.status` 表示订单业务状态，`FulfillmentRisk` 表示履约风险。

二者不得混淆。

# 15. V3.1 自动履约流程

建议流程：

```
创建订单
    ↓

    ↓
自动匹配
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
```

# 71. V3.x 最终判断标准

未来判断一个迭代是否值得开发，不再使用：

> “这个功能看起来是不是高级？”

而使用以下五个问题：

### ① 是否解决真实用户问题？

如果不能：

```
不做
```

### ② 是否形成完整业务闭环？

如果只是：

```
页面 + CRUD
```

价值有限。

### ③ 是否能够被真实数据支撑？

如果只是：

```
虚假的 AI 指数
虚假的健康评分
虚假的推荐分
```

不做。

### ④ 是否提高平台可靠性？

优先考虑：

```
履约
安全
协同
稳定
可追溯
```

### ⑤ 是否符合产品边界？

尤其严格遵循：

```
不做医疗诊断
不做药物推荐
不做治疗决策
```

## 74.1 版本目标

平台的服务规则（费用、取消、投诉、评价、打卡、推荐逻辑）散落在 `docs/api/*.md` 与 `docs/plan/plan.md` 里，
**没有任何问答入口** —— 家属只能自己翻文档。

V3.7 给家属端加一个**智能助手**：用自然语言问到平台规则，并看懂「为什么推荐这位陪诊员」。

## 74.2 核心能力

| 能力 | 说明 |
|---|---|
| 平台规则问答 | 下单、费用、取消、催单、评价、投诉、打卡、聊天、通知、账号、平台能力边界 |
| 推荐解释 | 候选陪诊员的三段式理由（命中理由 / 未命中说明 / 降级说明）**原样转述** |
| 下单草稿 | 抽到就诊信息时把草稿填好，**提交由家属在确认页完成**（助手永不自动下单） |
| 合规护栏 | 医疗意图**固定拒答**并引导线下就医；推荐 ≠ 派单；距离算不出来就说算不出来 |

## 74.3 能力边界（受 §60 三档约束）

- 落在 §60 的**「谨慎使用」档**：推荐陪诊员、订单智能推荐、异常检测。
  → LLM **只负责把规则引擎算好的结果讲成人话**，**不重排、不改分、不编造分数**。
- **绝不碰「禁止档」**：疾病诊断、疾病预测、治疗建议、药物推荐、药物剂量调整、医疗风险诊断。
  → 三层护栏：输入侧固定拒答（**不经 LLM**）、prompt 层约束、输出侧扫描（**代码层兜底**）。
- **护栏写在代码里，不写在 prompt 里** —— prompt 是「请求模型遵守」的约定，
  代码才是「模型不遵守也拦得住」的保证。

## 74.4 第二个技术栈（唯一已记录的例外）

V3.7 起项目含**第二个技术栈**：`ai-service/`（Python 3.12 + FastAPI + LangChain，
独立进程，端口 8081，只监听 `127.0.0.1`）。

- 依赖清单由**人工逐项批准并冻结**在 `ai-service/requirements.txt`；
  **越出该清单需重新报批**（连同理由一并说明），不得擅自添加。
- 这条豁免**只对已批准的清单生效**，不适用于其它任何新增依赖。
- 已同步进项目宪法（`AGENTS.md` §0 技术栈表 / §0.1 已记录的例外 / §2.11 Python 侧规范）——
  否则后来的 agent 会把这项当成违规实现。

## 74.5 验收标准

| # | 项 |
|---|---|
| 1 | 平台规则类问题能问出答案，且**每条回答都带依据引用**（`sources` 非空） |
| 2 | 医疗类提问**不可能**得到含剂量 / 诊断 / 疗效判断的回答 |
| 3 | 推荐叙述含可解释理由，三段式不合并，**不得**出现「距离近 / 离得近 / 就在附近」 |
| 4 | 助手**永不自动下单** —— 只填草稿，提交由用户确认 |
| 5 | 关键词覆盖门禁：179 条模拟问法召回 ≥ 95%、抢占 0（`ai-service/tests/test_faq_coverage.py`） |
| 6 | 降级路径（未接大模型 / 模型故障 / Python 服务不可用）**三种成因都可用**且日志与行为一致 |
| 7 | 角色边界：仅 `FAMILY`；ELDER / COMPANION / ADMIN 一律 403 |

## 74.6 已知限制

1. **FAQ 覆盖未经真实用户验证** —— 关键词覆盖用的是**大模型生成的模拟问法**，
   不是真实用户提问。PRD 风险表第 5 条**保持未关闭**，只能靠上线后的未命中问题回流关闭。
2. **限流阈值（每用户每分钟 10 次）是拍板值** —— 无真实流量数据支撑。
3. **推荐是订单锚定的** —— 没下单就想看陪诊员本版不支持，助手引导先成单。
4. **降级模式下回答是 FAQ 原文** —— 读起来像文档而不是聊天。

# 75. 结语

《银龄伴诊》V3.0 已经不再是一个单纯的课程级 CRUD 项目。

当前阶段最重要的事情不是继续增加功能数量，而是：

```
从“功能集合”
        ↓
升级为
“完整业务系统”
        ↓
再升级为
“具备运营能力的平台”
```

因此 V3.x 的核心方向确定为：

```
V3.1  履约保障
V3.2  健康协同
V3.3  陪诊员工作台
V3.4  智能调度
V3.5  运营驾驶舱
V3.6  数据闭环
```

其中：

> **V3.1 是当前第一优先级。**

整个 V3.x 最终形成：

```
             银龄伴诊 V3.x
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
     老人        家属       陪诊员
       │          │          │
       └──────────┼──────────┘
                  ↓
              陪诊服务
                  ↓
              履约保障
                  ↓
              实时协同
                  ↓
              健康沉淀
                  ↓
              平台治理
                  ↓
              数据分析
                  ↓
              智能调度
                  ↓
              服务优化
                  │
                  └──────────→ 下一次服务
```

**产品最终目标：**

> ### 让老人每一次就医都有人陪、有人知、有人管，并让平台能够持续提高陪诊服务的可靠性。
