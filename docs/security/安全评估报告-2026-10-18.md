## 2. 总体评价与风险概览

**一句话结论**：本项目的**代码层安全水位显著高于同规模课程项目**——SQL 全走参数绑定、前端零 XSS 逃逸口、ELDER 只读默认拒绝、订单归属校验覆盖到位、上传走 magic bytes + UUID 重命名、JWT 有黑名单 + 密码版本 + 封禁三重校验、密码 BCrypt、CI 内置密钥体检。**风险几乎全部集中在"配置层"而非"代码层"**：四个高危项都源于同一种模式——**生产环境未注入环境变量时，静默回落到仓库中公开可见的开发默认值**，叠加"默认 profile 是 dev"。这是典型的"代码写对了、部署写错了"型风险：修复成本低、收益极高。

## 3. 详细发现

> 每条格式：编号 · 类别（snake_case） · 等级 · 置信度 · 定位（`文件:行号`，行号为右值） · **来源→汇点**证据链 · 利用场景 · 影响范围 · 修复建议（文字，不含 patch）。

### F-01 · `hardcoded_secret`（JWT 签名密钥默认值） · 🔴 高危 · 置信度 0.95

**定位**
- [application.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application.yml#L91-L92) `secret: ${JWT_SECRET:nianglin-dev-secret-key-please-change-in-production-0123456789}`
- [application-prod.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-prod.yml) —— **全文无 `nianglin.jwt` 段**，故生产若未注入 `JWT_SECRET` 即使用上一行的默认值。

**来源→汇点证据链**
1. 来源：部署期环境变量 `JWT_SECRET` 缺席（运维遗漏）→ Spring 占位符 `:默认值` 语法生效，取仓库公开串。
2. 汇点：[JwtTokenProvider](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/security/JwtTokenProvider.java) 的 `@PostConstruct init()` 只校验"密钥 ≥ 32 字节"；该默认串长 55 字符，**通过校验、签发与验签全部生效**。
3. 该密钥签出的 JWT 载荷为 `sub / role / ver / jti`；[JwtAuthenticationFilter](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/security/JwtAuthenticationFilter.java) 信任这些声明并写入 `SecurityContext`；后续 `@PreAuthorize("hasRole('ADMIN')")` 直接按 `role` 放行。

**利用场景**：攻击者从公开仓库读到默认密钥 → 用 HS256 自签 `role=ADMIN` 的令牌 → 直连 `/api/admin/**`。因 `jti` 未被拉黑、`ver` 无从核对（攻击者自选），三重校验全部失效。**完全绕过认证并取得管理员权限**。

**影响范围**：全平台账户接管、全量 PII（身份证、手机号、档案）读取、任意订单/用户状态篡改、管理员操作日志伪造。

**修复建议**：见 §8 P0-1 —— 在 **prod profile** 下把该项改为**无默认值** `${JWT_SECRET}`，缺失即启动失败（与 `SecurityProperties#validate()` 既有的"启动即失败"策略一致）。

> 对应计划：**H-01**

### F-02 · `hardcoded_secret`（身份证 AES 密钥默认值 + 校验放行） · 🔴 高危 · 置信度 0.95

**定位**
- [application.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application.yml#L170-L172) `id-card-key: ${ID_CARD_AES_KEY:nianglin-dev-id-card-key-please-change-in-production}`
- [SecurityProperties.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/security/SecurityProperties.java#L28) `MIN_ID_CARD_KEY_LENGTH = 16`
- [SecurityProperties.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/security/SecurityProperties.java#L79-L93) `validate()` 只判"非空 + 长度 ≥ 16"

**来源→汇点证据链**
1. 来源：`ID_CARD_AES_KEY` 缺席 → 取默认串 `nianglin-dev-id-card-key-please-change-in-production`（**51 字符**）。
2. 校验形同虚设：`validate()` 的阈值是 16，51 > 16，**启动期放行**，且日志 `log.info("... idCardKey 长度={}", )` 只打长度、不打内容，运维看不出"这是默认值"。
3. 汇点：[AesUtil](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/util/AesUtil.java) 用该密钥做 `SHA-256 派生 → AES-256-GCM` 加解密身份证号；密文落库，解密点在 [AdminServiceImpl#maskedIdCard](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/service/impl/AdminServiceImpl.java#L1206-L1212)。

**利用场景**：攻击者取得数据库读取/备份（脱库、误配只读账号、备份泄露）→ **离线**用公开默认密钥解密全部身份证号密文。不需要任何在线接口权限。

**影响范围**：全量身份证号（不可变更的敏感标识）泄露，合规红线（隐私最小化）直接击穿。

**修复建议**：见 §8 P0-1；另建议 `validate()` 显式拒绝已知的 dev 默认串，避免"长度够就放行"。

> 对应计划：**H-02**

### F-03 · `insecure_default_config`（默认 profile = dev） · 🔴 高危 · 置信度 0.90

**定位**：[application.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application.yml#L18-L22) `spring.profiles.active: dev`

**来源→汇点证据链**
1. 来源：生产启动未显式指定 `SPRING_PROFILES_ACTIVE` → 该行硬编码 `dev` 生效。
2. 汇点（多重）：
   - [application-dev.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-dev.yml) 的 `mybatis-plus.configuration.log-impl: StdOutImpl` → **业务 SQL（含身份证明文参数）打印到标准输出**；
   - `springdoc.api-docs.enabled=true` + `knife4j.enable=true`，且 `/doc.html`、`/swagger-ui/**`、`/v3/api-docs/**` 在 [SecurityConfig PUBLIC_ENDPOINTS](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/config/SecurityConfig.java#L104-L108) 中 permitAll → **接口文档公开暴露**；
   - `nianglin.cors.allowed-origins` 为 `http://localhost:[*]`（开发放行）；
   - F-01 / F-02 的 dev 默认密钥**直接生效**。

**利用场景**：部署脚本忘带 profile → 攻击者访问 `/doc.html` 拿到完整接口清单与字段结构 → 结合 F-01 自签令牌 → 精准打击。同时 SQL 日志把身份证明文写入容器 stdout，被日志采集系统长期留存。

**影响范围**：信息面（接口文档）+ 敏感数据面（SQL 日志）+ 认证面（dev 密钥），三面同时失守。

**修复建议**：见 §8 P0-2。

> 对应计划：**H-03**

### F-04 · `sensitive_data_exposure`（重置密码明文回传 + 硬编码默认口令） · 🔴 高危 · 置信度 0.90

**定位**
- [SecurityProperties.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/security/SecurityProperties.java#L45-L57) `private String defaultPassword = "Nl@123456";`
- [AdminServiceImpl.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/service/impl/AdminServiceImpl.java#L403-L424) `resetPassword()`：L408 用该默认值 `encode()` 落库，L423 `ResetPasswordResultVO.of(id, securityProperties.getDefaultPassword())` **把明文回传**。
- [ResetPasswordResultVO.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/vo/ResetPasswordResultVO.java#L27-L30) `defaultPassword` 字段。
- [application-prod.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-prod.yml) —— **无 `nianglin.security` 段**，故 `default-password` 在生产同样回落源码默认值。

**来源→汇点证据链**
1. 来源：源码常量 `Nl@123456` 是仓库公开信息（`grep` 命中 16 处，见 §3.12）。
2. 汇点：`resetPassword` 把该口令设为用户新密码（`need_change_password=1`），并作为响应体返回。
3. 副作用：`tokenStore.bumpPasswordVersion(id)` 只使旧令牌失效，**不影响"所有被重置账号口令都相同且公开"这一事实**。

**利用场景**：任何被管理员重置过的账号（含全部种子账号）在首次改密前，其口令 = 仓库公开常量 → 攻击者直接登录。响应对管理员的明文回传属业务设计（电话念读），真正的高危点是**口令值的固定性与公开性**。

**影响范围**：任意被重置账号登录接管（含 ADMIN 种子号，其默认口令同样来自该常量）。

**修复建议**：见 §8 P0-3（不再硬编码回传明文；改由环境变量注入且投产后只回传"已重置 + 需首次改密"标志）。注意：`ResetPasswordResultVO` 的 javadoc 与 `docs/api/08-admin.md` §7 需同步。

> 对应计划：**H-04**

### F-05 · `broken_access_control`（未认证可读上传文件） · 🟠 中危 · 置信度 0.85

**定位**
- [SecurityConfig.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/config/SecurityConfig.java#L101-L102) `PUBLIC_ENDPOINTS` 含 `/uploads/**`（permitAll）
- [WebMvcConfig.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/config/WebMvcConfig.java#L55-L59) 把 `/uploads/**` 静态映射到磁盘目录

**来源→汇点证据链**
1. 来源：**未认证**的 `GET /uploads/{yyyyMM}/{uuid}.{ext}`（无 Authorization 头）。
2. 汇点：直接命中静态资源 handler，返回磁盘文件字节流。
3. 缺失的控制：**无鉴权、无授权（不校验该文件属于谁）、无过期、无一次性令牌**。
4. 落盘命名与目录见 [FileStorageServiceImpl#store](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/service/impl/FileStorageServiceImpl.java#L94-L96)：`/uploads/{yyyyMM}/{uuid}.{ext}`，**路径不含 `bizType` 分段 → 证件与照片混放同一月份目录**（G1 核查结论）。
5. 文件 cover 面（[SysFile](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/entity/SysFile.java) 的 `biz_type`）：`COMPANION_CERT`（资质证件）/ `CHECKIN`（打卡照片）/ `COMPLAINT`（投诉证据）/ `AVATAR` / `REVIEW` → **证件类也走这条公开路径**。

**利用场景**：文件 URL 会被写入数据库并下发给多方（家属、陪诊员、管理员）；一旦通过 Referer、聊天分享、日志、前端源码或误配 CDN 泄露 → **任何未登录者**可长期、无限制地拉取证件/投诉证据。UUID 不可枚举降低了"盲扫"概率，但"泄露后永久有效"把风险从"不可枚举"提升为"一旦泄露即无法收回"（这正是 [docs/api/README.md] 之外的常见痛点）。

**影响范围**：身份证/资质证件影像、投诉证据等 PII 的未授权读取。

**修复建议**：见 §8 P1-1 —— 用户已决策**只收紧证件类**（`bizType=COMPANION_CERT`），照片/头像/打卡照保持公开（保证前端 `<img>` 直连渲染不回归）。因 G1 已判定"路径不可区分证件与照片"，落地采用**带过期签名的短期 URL** 或**新增 `/api/file/cert/**` 鉴权下载端点**（二选一，见 §8 落地要点）。

> 对应计划：**M-01**

### F-06 · `insecure_default_config`（生产 Redis 口令默认空） · 🟠 中危 · 置信度 0.85

**定位**：[application-prod.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-prod.yml#L18-L24) `password: ${REDIS_PASSWORD:}`

**来源→汇点证据链**
1. 来源：`REDIS_PASSWORD` 缺席 → 空串。
2. 汇点：Lettuce 以**无口令**连接 Redis。
3. 敏感数据面：Redis 存有 JWT 黑名单（`jti`）、密码版本（`ver`）、登录失败计数、验证码、封禁标记——这些都是**安全状态**。

**利用场景**：Redis 若与不可信网络/共租户共享且无口令 → 攻击者可**写入/删除关键键**：删除 `jti` 黑名单使已登出令牌复活；清零失败计数绕过登录锁定；改 `ver` 使密码版本校验错位。属"安全状态被外部篡改"。

**影响范围**：令牌生命周期与登录防护失效。

**修复建议**：见 §8 P1-2（prod 下 `${REDIS_PASSWORD}` 无默认值，缺失即启动失败）。

> 对应计划：**M-02**

### F-07 · `cors_misconfiguration`（生产缺 CORS 段 + 两处兜底漂移） · 🟠 中危 · 置信度 0.80

**定位**
- [SecurityConfig.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/config/SecurityConfig.java#L82) `@Value("${nianglin.cors.allowed-origins:http://localhost:5141,http://127.0.0.1:5141}")`

- [application-prod.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-prod.yml) —— **无 `nianglin.cors` 段**

**来源→汇点证据链**
1. 来源：生产未配 `nianglin.cors.allowed-origins` → 回落 `@Value` 兜底串（localhost）。

**利用场景**：当前默认值（localhost）**不会**直接造成跨站读取；该条的真实风险是**配置正确性脆弱 + 未来放宽时的放大器**（`allowCredentials(true)`）。因此定性为中危（边界），按"防御纵深 / 配置漂移"治理。

**影响范围**：跨域策略的可预测性；一旦放宽即演化为凭据跨域泄露。

**修复建议**：见 §8 P1-3（prod 显式补真实域名；两处 `@Value` 兜底统一到同一常量/配置项）。

### F-08 · `sensitive_data_exposure`（SSE / WS 令牌走 URL query） · 🟠 中危 · 置信度 0.90

**定位**
- [JwtHandshakeInterceptor.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/websocket/JwtHandshakeInterceptor.java#L66-L84) `?token=<accessToken>&orderId=<orderId>`
- [MessageSseController.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/controller/message/MessageSseController.java#L66-L69) `@RequestParam(required = false) String token`
- [SecurityConfig.java](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/java/org/company/nianglin/config/SecurityConfig.java#L92-L100) `/ws/**`、`/sse/**` permitAll

**来源→汇点证据链**
1. 来源：浏览器原生 `WebSocket` / `EventSource` **不能自定义请求头**，故前端被迫把 access token 放进 URL query。
2. 汇点（三处泄露面）：
   - Web 容器/反向代理的**访问日志**会记录完整 query（令牌原文入日志）；
   - 浏览器**历史记录**保留带令牌的 URL；
   - 页面若引第三方资源，**Referer** 会把 URL（含令牌）带给外部域。
3. 缓解现状：两处代码的 `log.warn/info` **刻意不打印 token 本身**（代码注释已注明）；但**容器层访问日志不受应用控制**。

**利用场景**：能读到反代/容器访问日志的人（运维、共租户、日志平台越权）可直接提取令牌 → 在 120 分钟有效期内冒充该用户。

**影响范围**：会话劫持（受限于 access token 120 分钟有效期，但足够完成高危操作）。

**修复建议**：见 §8 P1-5。**修复实际采用"结论 + 运维配置"而非 ticket 改造**——理由见 §10.4：① 应用侧日志经逐文件核验**一律用 `request.getRequestURI()`（不含 query）**，token 原文不入应用日志；② 浏览器原生 `WebSocket`/`EventSource` **不能自定义请求头**，令牌走 query 是唯一可行路径，"握手首帧"方案会引入"未认证连接的中间态"（`JwtHandshakeInterceptor` 的 javadoc 已论证并否决）；③ 一次性 ticket 改造会改动实时通道（E2E 覆盖的核心功能），与"不影响现有业务正常运行"的硬要求冲突。**真实泄露面在反向代理访问日志**，应用无法控制，故以 `log_format` 屏蔽片段交付（§10.4）。

> 对应计划：**M-04**

### F-09 · `insecure_transport`（数据库连接无 TLS + 公钥检索） · 🟠 中危 · 置信度 0.85

**定位**
- [application-prod.yml](file:///f:/test/Senior%20Companion%20Health%20Assessment/backend/src/main/resources/application-prod.yml#L6-L10) `...&useSSL=false&allowPublicKeyRetrieval=true`

**来源→汇点证据链**

**影响范围**：数据库凭据窃取 + 传输中的 PII 截获。

**修复建议**：见 §8 P2-2（评估 `useSSL=true` + `requireSSL`，视部署是否有 TLS 终止；**先出结论、再决定是否改代码**）。

### 10.4 P1-5 决策：以"结论 + 运维配置"收口（未改代码）

**未按计划原文引入"握手首帧 / 一次性 ticket"**，理由：

1. **应用侧无泄露**：逐文件核验 `JwtHandshakeInterceptor` / `MessageSseController` / `GlobalExceptionHandler` 的日志**一律用 `request.getRequestURI()`（不含 query string）**，令牌原文不入应用日志；项目亦未启用 Tomcat access log。F-08 的真实泄露面在**反向代理访问日志**，属应用不可控范围。
2. **query 令牌是浏览器的唯一路径**：原生 `WebSocket` / `EventSource` 不能自定义请求头；"握手首帧"方案需先接受"未认证连接"的中间态，`JwtHandshakeInterceptor` 的 javadoc 已论证并否决。
3. **不改动实时通道规避回归**：ticket 改造会触及 SSE/WS（E2E 覆盖的核心功能）并引入"每次重连都要换票"的异步控制流，与用户硬要求"不影响现有业务正常运行"冲突，收益却仅作用于代理日志。

**交付（运维片段）**：在 Nginx 以 `map` 屏蔽 query 中的 `token=`，使代理访问日志不落令牌原文：

```nginx
# 屏蔽 SSE / WebSocket 握手 query 中的令牌
map $args $masked_args {
    default                                 $args;
    "~^(?<pre>.*(?:^|&)token=)[^&]*(?<post>.*)$"   "${pre}***${post}";
}
log_format masked '[$time_local] "$request_method $uri?$masked_args $server_protocol" '
                  '$status $body_bytes_sent "$http_referer" "$http_user_agent"';
access_log /var/log/nginx/access.log masked;
```

> 残余风险：令牌仍在 120 分钟有效期内可被"能读到代理日志者"利用。**更彻底的方案（一次性 ticket）已评估但本次不实施**，如需可在后续迭代单列任务，届时同步改 `JwtHandshakeInterceptor` + `MessageSseController` + 前端 `realtime.js`/`message.js`。

### 10.5 P2 结论（评估项，均未改代码）

- **P2-1（F-10，token 存 localStorage）｜结论：维持现状，不迁 httpOnly Cookie。** 依据：本项目 `SessionCreationPolicy.STATELESS`、无 Cookie 会话，令牌走 `Authorization` 头；迁 Cookie 需重建会话态、重新引入 CSRF 防护、改动跨源/`allowCredentials` 语义、老人机/移动 WebView 的 Cookie 行为亦需回归——成本高、收益中。且**当前无可达读取路径**：全仓 `v-html`/`innerHTML`/`dangerouslySetInnerHTML` **0 命中**（§6），Vue 默认转义。**建议将"前端零 raw-HTML 逃逸口"作为常驻不变量**，一旦引入显式 HTML sink 再重估。
- **P2-2（F-09，DB 连接无 TLS）｜结论：视部署拓扑定，代码不改。** 若 MySQL 与应用同主机或同可信私网段（本项目 docker-compose 默认为此），`useSSL=false` 属可接受；一旦跨不可信网络（云内东西向/shared VLAN），应改 `sslMode=REQUIRED`（有 CA 则 `VERIFY_CA`）并**去掉 `allowPublicKeyRetrieval=true`**（该参数在明文连接下才有 MITM 面）。要求：**生产数据库不得暴露在不可信网络**，或按上述开启 TLS——建议写入部署检查表。
- **P2-3（F-12，示例口令散落）｜结论：耦合已被 P0-3 化解，不做集中化改造。** P0-3 去掉了 `SecurityProperties` 的硬编码默认值、prod 要求 `DEFAULT_RESET_PASSWORD` 环境变量注入，**"示例口令 = 生产默认口令"这条现实危害链已断**。其余 `Nl@123456` 引用经核验均为**开发/测试资产**（`.env.development` 的 DEV 门控演示口令、`application-{dev,local}.yml` 的本地兜底、`fixture_credentials.py` 单一来源、测试常量、`GenSeedSecrets`），且 CI `secrets` job 的排除规则（`${` / `os.environ` / `example` / `/test/` 等）已覆盖之。**强制集中化会触碰种子生成工具与测试常量，回归风险大于收益**，故记录结论而不动代码；单一来源约定为 `backend/sql/tools/fixture_credentials.py` 与 `NIANGLIN_SEED_PASSWORD`。**执行确认**：2026-10-18 用户以"好的，执行吧"确认采纳本结论（不做集中化改造）。
