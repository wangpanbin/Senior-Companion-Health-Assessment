# 银龄伴诊 · 功能拓展规划 v1.0

> **文档性质**：产品功能拓展规划（Extension Plan），非工程实施计划
> **受众**：课程评审 + 4 人开发团队
> **上游依据**：`docs/prd/PRD.md` v1.0（产品宪法）、`plan.md`（模块验收）、`AGENTS.md`（编码红线）、`docs/api/`（接口契约）
> **现状基线**：以 2026-09-16 后端全量验证（`mvn verify` 517 测试全绿）与前端联调收口为基准
> **分层关系**：本文档只回答「下一步做什么、为什么、按什么顺序」；**怎么做**归 `plan.md` 与各模块设计评审

## 一、现有产品概述

### 1.1 定位（承接 PRD §1，不改）

**一句话定位**：让不会用手机的老人，也能有人陪着把病看好。

**产品边界（三条红线，长期不变）**：

| 编号 | 红线 | 现有替代实现 |
|---|---|---|
| 红线-1 | 不做诊断、不开药方 | 药品字典仅「通用信息 + 免责声明」；服务小结走 `ComplianceCheckUtil` 词表拦截（错误码 `3007`） |
| 红线-2 | 隐私最小化 | `MaskUtil` 全链路脱敏；`ElderReadOnlyInterceptor` 拦截老人写操作（非 GET 一律 403） |
| 红线-3 | 不做在线支付 / 地图导航 / IM | 线上记账 + 线下结算；文字地址 + 签到坐标；站内信 + 双通道推送 |

> 本次规划**不触碰任何一条红线**，所有方向均在上述边界内做「闭环补强」而非「能力扩张」。

### 1.4 三条已闭环的核心业务链

```
① 陪诊链：家属下单 → 陪诊员接单 → 6 节点打卡 → 家属实时看进度 → 评价
          PENDING → ACCEPTED → IN_SERVICE → COMPLETED → REVIEWED
② 用药链：家属建计划 → 07:00 生成任务 → 服药确认 → 超时判漏服 → 通知家属
③ 治理链：评价 / 投诉 → 管理员仲裁 → 强制终态 + 双方通知 + 操作留痕
```

**关键判断**：本次规划的价值不在"再加一个模块"，而在**把这三条链上已断掉或单向的环节补成双向闭环**。

## 二、可复用的工程资产（拓展的原料清单）

拓展方向必须"骑在"已有资产上，否则成本会失控。以下 6 类资产是本次所有方向的技术前提：

| # | 资产 | 位置 | 可被复用的方式 |
|---|---|---|---|
| A1 | **状态机 + 条件更新范式** | `OrderServiceImpl`（`UPDATE ... WHERE status = 期望值`）、`MedicationServiceImpl#scanMissedTasks`（条件更新即"认领"） | 任何"多实例并发处理同一批数据"的新任务直接照抄该范式 |
| A2 | **定时任务 + Redis 分布式锁** | `MedicationScheduler`（`RedisLockUtil.tryLock`，锁写在任务方法内、按业务定粒度） | 新增扫描类任务的**唯一正确模板**；锁粒度须按任务的"丢失代价 vs 重复代价"单独定 |
| A3 | **双通道实时推送** | M5 STOMP `/ws/order-progress`、M8 SSE `/sse/message` | 新事件的"下行"不必新建通道，走 M8 SSE 即可（M8 已有 `Last-Event-ID` 离线补齐） |
| A4 | **消息模板统一入口** | `MessageService.send(userId, template, params)` + `internal_message.link_url` / `biz_type` / `biz_id` | 新增业务事件只需加模板，不必碰推送链路；`link_url` 已支持点对点跳转 |
| A5 | **文件服务与白名单** | `FileController` + `FileBizType`（仅放行 `COMPANION_CERT` / `COMPLAINT` / `AVATAR`） | 新增业务附件须**显式扩充 `FileBizType` 白名单**，不可绕过（`CHECKIN` 刻意被拒，打卡照片有专用端点） |
| A6 | **审计与合规守卫** | `admin_oper_log`、`sys_login_log`、`ComplianceCheckUtil`、`MaskUtil`、`ElderReadOnlyInterceptor` | 新写操作默认继承老人只读拦截；新文案默认过合规词表；新出参默认过脱敏 |

### 2.1 一条必须尊重的硬约束：数据库迁移已冻结

`V1__init_schema.sql` / `V2__seed_data.sql` / `V3__seed_boundary.sql` **已执行，不得修改**；所有结构变更只能**新开 `V4__*.sql`**。

**这一条直接决定了排序**：凡是"零数据库迁移"的方向，落地成本显著更低、回归面更小。因此本文在优先级评分中专设该观察项（见 §5.1）。

## 三、缺口清单（每个方向都从证据出发）

以下缺口均为**代码事实**，非主观推断：

| 编号 | 缺口 | 证据（文件 / 行） | 业务影响 |
|---|---|---|---|
| **G1** | **老人本人收不到用药提醒**——漏服只通知家属 | `MedicationServiceImpl.java:493` 仅调用 `notifyFamily(task)`；`MedicationScheduler` 只生成任务与判漏服 | 用药链最后一公里断在"老人不会主动打开 App"；且全平台**无短信服务**（`forget.vue:5-16` 已如实降级为引导页） |
| **G2** | **陪诊员收入无服务端聚合**——前端循环分页拉全量再自算 | `income.vue:39-66`：`for (page...) listMyOrders({page,size:100})` 拉完所有订单，前端 `reduce` 汇总 | 订单量增长后页面线性变慢；无月度结算单，金额口径散在前端 |
| **G3** | **陪诊员无法回复/申诉评价** | `order_review.companion_reply` 字段与 `ReviewVO.companionReply` 均已就绪，但 `ReviewController` 仅 4 个端点（create / order / companion / score），**无写入口** | PRD §3.3 明确痛点"评价公正、纠纷可申诉"，当前**单向**：只能被评，不能回应 |
| **G4** | **陪诊员"接单开关"未实现** | `companion_profile.work_status` 存在且 `CompanionProfileVO` 已含 `workStatusLabel`，但全仓仅实体与 VO 引用，**无设置端点** | 陪诊员无法"临时停止接单"，冷启动期派单体验差 |
| **G5** | **订单无人接单无兜底** | `task/` 下仅 `MedicationScheduler`；`PENDING` 状态无超时机制、无催单入口 | 家属下单后订单可能长期挂着，无人知晓——**履约链最大单点风险** |
| **G6** | **无角色级数据看板** | `/api/statistics/**` 权限矩阵为 ADMIN 专属；陪诊员 / 家属无任何统计能力 | 陪诊员无法自证经营状况；家属无法一眼看到老人的用药依从性 |
| **G7** | **自助找回密码缺失** | 无"手机号 + 验证码重置"接口（`01-auth-user.md` 仅 `PUT /api/auth/password` 需登录 + 管理员重置） | 与 G1 同源：受"无短信服务"制约 |
| **G8** | **`sys_dict` 数据字典表已建未用** | 仅有 `SysDict.java` 与 `SysDictMapper.java`，无 Service / Controller 引用 | 阈值（漏服阈值、扫描批量、导出上限）散落在 `application.yml`，运营不可调 |

> **归因小结**：G1、G7 同源（缺短信通道）；G2、G3、G5 同源（**服务端聚合/兜底能力缺失，功能被推到前端或干脆缺失**）；G4、G8 同源（**字段/表已预留但未接通**——这类是"最高性价比"的补全）。

## 四、拓展方向（6 个）

> 每个方向固定四段：**用户价值 → 应用场景 → 与现有实现的衔接 → 边界与风险**。
> 「衔接」段严格回答三个问题：改哪里 / 复用什么 / **不新增什么**。

### 方向 E1 · 提醒触达分层：把用药提醒送到"人"而不只是"账号"

**用户价值**：用药依从性从「家属知道有没有漏服」升级为「老人能被提醒到」。这是 PRD §9.1 演示指标"漏服率对比"能否成立的关键——目前漏服提醒对老人**零触达**。

**应用场景**：独居老人 08:00 需服降压药；家属在外地工作无法打电话；老人不会主动打开 Web 页面。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | `MedicationScheduler` 的扫描任务与 `notify_sent` / `notify_time` 去重字段（**已存在**）；`MessageService` 模板机制；`medication_task.plan_time` 已含具体服药时刻 |
| 改造 | 把"通知"从硬编码的 `notifyFamily(task)` 抽成 `ReminderDispatcher`（渠道策略接口），现有站内信作为**默认实现**；渠道按 `medication_plan` 配置逐条选择 |
| 新增 | `PUT /api/medication/plan/{id}/reminder`（家属设置提醒渠道与提前量）；新开 `V4__medication_reminder_channel.sql` 加 1–2 个字段 |
| **不新增** | 不新建推送通道（走 A3 的 SSE）、不新建消息表、不改 30 分钟扫描节奏与 Redis 锁粒度（会让漏服判定的既有压测结论失效） |

**分两步落地（关键判断）**：

- **E1a（无外部依赖，可立即做）**：强化现有站内信 + 新增"陪诊员代提醒"——当老人当天有陪诊订单时，漏服提醒同时投递给该订单的陪诊员（复用 `companion_order` 关系，无需新表）。
- **E1b（依赖外部短信/语音服务商）**：接入短信或语音外呼通道，作为 `ReminderDispatcher` 的第二个实现。

**边界与风险（合规判断，必须写进接口文档）**：

1. **外呼/短信文案禁止包含剂量**——红线-1 要求系统不提供用药建议；家属录入的剂量属于"用户数据"，但通过平台外呼播报会被理解为"平台在指导用药"。**提醒文案只播报药名与服药时间**，剂量一律让用户回 App 看。
2. 需在用药计划页补充"提醒渠道授权说明"，避免过度打扰（老人反感外呼会直接拒接，反而降低依从性）。
3. 单个计划的外呼重试次数必须设上限（建议 ≤2 次/次服药），失败即回落站内信。

---

### 方向 E2 · 履约兜底：未接单超时预警 + 匹配排序 + 催单

**用户价值**：消除"下单后石沉大海"。这是当前产品**最容易被评审追问的单点**——`PENDING` 没有任何过期或兜底机制。

**应用场景**：家属深夜为次日早晨就诊下单，附近陪诊员均未在线；偏远医院订单长期无人接单。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | A2 定时任务 + Redis 锁范式（照抄 `MedicationScheduler`）；A4 消息模板；`companion_profile.service_area` / `available_time`（**已存在的接单偏好字段**，此前未参与派单） |
| 新增 | `OrderTimeoutScheduler`（扫描超时未接单 → 站内信通知家属 + 标记）；`POST /api/order/{id}/urge`（家属催单，限频）；`GET /api/order/hall?sort=match`（按服务区域/时段偏好计算匹配度排序）；`POST /api/admin/order/{id}/reassign`（管理员协调改派，复用既有强制终态路径的留痕逻辑） |
| 迁移 | 新开 `V4__order_urge_fields.sql`（`urge_count` / `last_urge_time`，2 个字段） |
| **不新增** | **不新增订单状态**——状态机已有 5 状态 + 1 终态且被 226 项越权矩阵与状态机测试锁死，新增状态会牵动 M4/M5/M7/M9/M10 全部既有断言。超时只做「标记 + 通知 + 排序加权」，订单仍留在 `PENDING` |

**为什么坚持不新增状态**：产品上"超时"不是订单的一种**状态**，而是一种**风险信号**。把信号塞进状态机，会让"陪诊员接单时该不该放行"等判定多出一个分支，收益远小于回归成本。若未来确需"自动流单"，应作为**独立决策点**重新评审，而非顺手加状态。

**边界与风险**：催单必须限频（建议同一订单 ≤3 次/天），否则会变成骚扰通道；改派不得绕过"资质先审"（`2003`）与"老人只读"两道闸门。

### 方向 E3 · 陪诊员结算与收入服务端化

**用户价值**：把陪诊员的核心诉求「接单有依据、做完有凭证」落到**金额可核对**。当前"我的收入"页是前端全量拉取后自算，既慢又无法对外解释口径。

**应用场景**：陪诊员周末核对本周/本月收入；家属回看某单费用明细；管理员按周期出结算清单。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | `companion_order.fee` / `actual_fee` / `payment_status`（**已存在**）；`companion_profile.order_count` / `accept_count` / `score`（**已存在的聚合字段**）；M10 的 `ExportService` + EasyExcel 导出规范 |
| 新增 | `GET /api/settlement/summary`（周期汇总：接单数 / 完成数 / 待结算金额 / 已结算金额）；`GET /api/settlement/items`（明细分页，白名单排序字段）；`GET /api/settlement/export`（结算单导出）；前端 `income.vue` 改为**直接消费服务端聚合**，删除循环分页逻辑 |
| **不新增** | **零数据库迁移**（纯聚合查询）；不新增资金表；不接入任何支付/提现能力 |

**准资金场景的严谨性要求（主动适用，不滥用清单）**：

本方向不涉及资金**流转**，故不适用"幂等 + 对账 + 资损监控"三件套；但涉及**金额口径**，以下三条必须遵守：

1. **金额唯一真源在服务端**：页面与导出不得自算，`actual_fee` 缺失时按项目既有约定回退 `fee`（`income.vue:24-27` 已确立该口径，需固化到接口文档）。
2. **口径可核对**：结算周期采用闭区间，与 `docs/api/README.md` §七 的 `startDate`/`endDate` 约定一致；未结算与已结算必须分列，禁止只给一个"总收入"。
3. **导出不含敏感字段**：导出列不得含身份证号、完整手机号、密码（红线-2）。

**边界与风险**：文案严禁出现"提现""原路退回""在线支付"等字样（红线-3）；`payment_status` 由管理员核定，陪诊员侧只读。

### 方向 E4 · 评价公信力闭环：回复 + 申诉 + 有效性裁定

**用户价值**：把评价从「单向判决」变成「可回应、可申诉、可裁定」。这是 PRD §3.3 陪诊员痛点里**唯一未被满足**的一条。

**应用场景**：陪诊员收到失实差评（如老人失约却计入其服务态度），希望通过平台申诉，而非线下扯皮。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | `order_review.companion_reply` / `reply_time`（**字段已存在，缺写入口**）；`order_review.is_valid`（**字段已存在**，说明设计时已预留"无效评价"概念）；`complaint` 表 + `ComplaintController` 三状态机 + M9 管理端处理路径 |
| 新增 | `POST /api/review/{id}/reply`（陪诊员回复，一评一回复）；`POST /api/admin/review/{id}/validity`（管理员裁定有效性，写 `admin_oper_log` + 双方通知）；申诉**不新增表和状态**，走既有投诉入口，`complaint.type` 新增枚举值 `REVIEW_APPEAL` |
| 口径 | 评分聚合只计入 `is_valid = 1` 的评价（`companion_profile.score` 重算沿用 M7 既有聚合 SQL） |
| **不新增** | **零数据库迁移**；不新增申诉工单表；不改评价唯一性约束 |

**为什么这条路"优雅"而不是"取巧"**：投诉表本身已具备 `type` / `target_user_id` / `target_role` / `evidence` / 三状态流转 / 管理员处理结果 / `penalty_to_target`，**申诉与投诉在数据模型上是同构的**。复用它意味着新功能的测试面可以大量复用既有投诉矩阵，而新建一张"申诉表"则会额外引入一套状态机与越权矩阵。

**边界与风险（最重要的产品判断）**：

1. **申诉不是"删差评"通道**。管理员只能裁定"有效 / 无效"，**禁止**物理删除评价或改写评分内容；`is_valid = 0` 的评价仍对家属可见并标注"平台已裁定为无效评价"。
2. 陪诊员回复**不经过**敏感词裸奔——复用 M7 既有敏感词过滤（`6003`）。
3. 申诉限时（建议订单评价后 15 日内），避免长期悬而未决。
4. 复评风险：不得出现"因申诉被差评"的二次评价入口（一单一评约束已保证）。

---

### 方向 E5 · 角色级轻量看板：让非管理员也看得见数据

**用户价值**：把 M10 已有的聚合能力**按角色切片**，让陪诊员能自我经营、家属能远程掌握老人状况。

**应用场景**：陪诊员看近 30 天接单趋势与评分变化；家属打开首页即见"老人本月用药依从率 + 最近一次就诊"。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | `StatisticsController` 的聚合 SQL 与 ADR-0003 的缓存策略；`medication_task.was_missed` / `status`（依从率数据源已存在）；`companion_order` 状态时间戳 |
| 新增 | `GET /api/statistics/companion/me`（陪诊员：接单趋势 / 评分趋势 / 完成率）；`GET /api/statistics/family/elder/{elderId}`（家属：用药依从率 / 就诊次数 / 下次就诊） |
| **不新增** | **零数据库迁移**；不新建缓存层（沿用既有策略与 TTL 口径）；不新增图表类型（复用 M10 已验收的图表模板） |

**安全边界（本项目反复强调的三段式，必须落在 Service 层）**：

- 认证（过滤器）→ 角色（`@PreAuthorize`）→ **归属（Service）**。
- `@PreAuthorize("hasRole('FAMILY')")` **分不开家属 A 与家属 B**，`/family/elder/{elderId}` 必须在 Service 校验 `family_elder_relation` 归属（否则是一次彻底的越权数据泄露，错误码沿用 `2006`）。
- 陪诊员的 `/companion/me` 必须**从令牌解析用户身份**，禁止接受 `companionId` 作为入参（否则等于开放任意陪诊员数据查询）。

**边界与风险**：看板**禁止**输出任何健康风险预测、诊断倾向或用药建议（红线-1），只呈现"记录事实 + 计数"，例如"本月 12 次服药中 2 次漏服"，而非"漏服率偏高，建议……"。

### 方向 E6 · 数据权利与账号治理（合规向）

**用户价值**：满足个人信息保护要求下的"用户权利"（查阅 / 更正 / 删除），并让账号生命周期完整（注册 → 使用 → 注销）。

**应用场景**：家属更换手机号后希望导出/更正个人信息；不再使用平台时申请注销账号。

**与现有实现的衔接**：

| 层面 | 做法 |
|---|---|
| 复用 | `sys_user.deleted` 逻辑删除（**已存在**）；`ElderController` 已有 `DELETE /api/user/elder/{id}` 与解绑 `DELETE /{id}/bind`；`MaskUtil` 脱敏出口 |
| 新增 | `POST /api/user/deactivate`（注销申请，二次确认 + 密码复验）；`GET /api/user/data-export`（个人数据导出，复用 EasyExcel 导出规范，全字段脱敏） |
| **不新增** | 不做物理删除（保持逻辑删除 + 去标识化）；不新增注销状态机——复用 `sys_user.status`（`正常 / 封禁`）+ `deleted` 组合表达 |
| 迁移 | 若需记录注销申请时间，优先复用 `sys_user.remark` / `last_login_time` 等既有列，**尽可能避免 V4 迁移** |

**边界与风险（必须显式说明，避免承诺做不到的事）**：

1. **交易记录不可删**：订单、评价、投诉、操作日志属留存义务范围，注销后**保留但去标识化**（姓名、手机号、身份证置为脱敏占位），页面须如实说明，不得承诺"彻底删除全部数据"。
2. 注销前置校验：无进行中订单（`PENDING` / `ACCEPTED` / `IN_SERVICE`）才允许注销，否则提示先处理，避免服务中断纠纷。
3. 注销后 token 必须立即失效——复用 M2 既有的 `pwd:version` 递增机制（**只有改密与封禁这两条路径会递增**，注销应并入其中，需在接口文档中明确）。
4. G7（自助找回密码）依赖短信，**不在本方向内解决**，作为已知限制记录。

## 五、优先级排序

### 5.1 评分模型

按用户要求的三个维度评分（1–5 分），并**显式披露项目特有因子**：

| 维度 | 含义 | 分值方向 |
|---|---|---|
| **业务收益 B** | 对"闭环完整性 / 真实痛点 / 竞讲可演示性"的综合贡献 | 越高越好 |
| **开发成本 C** | 后端端点 + 前端页面 + 测试矩阵的总体工作量 | **越低越好**（记分时已折算） |
| **落地难度 D** | 外部依赖、合规风险、回归面大小 | **越低越好** |
| 结构迁移 M | 是否需新开 Flyway `V4` 迁移（结构冻结约束） | 零迁移加分 |

综合分 = B + (6 − C) + (6 − D)，区间 3–15。

### 5.2 评分矩阵

| 方向 | 业务收益 B | 开发成本 C | 落地难度 D | 迁移 M | 综合分 | 档位 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| **E4 评价公信力闭环** | 4 | 1 | 1 | 零迁移 | **13** | **P0** |
| **E2 履约兜底** | 5 | 2 | 3 | 需 2 字段 | **11** | **P0** |
| **E3 结算服务端化** | 4 | 3 | 1 | 零迁移 | **11** | **P1** |
| **E5 角色级看板** | 3 | 3 | 2 | 零迁移 | **10** | **P1** |
| **E1a 提醒触达（无外部依赖部分）** | 4 | 3 | 3 | 需 1–2 字段 | **9** | **P2** |
| **E6 数据权利治理** | 3 | 3 | 3 | 尽量零迁移 | **9** | **P2** |
| **E1b 短信/语音通道** | 5 | 3 | 5 | 同 E1a | **8** | **P3（待依赖）** |

> 评分理由摘要：
> - **E4 综合分最高**：字段已就绪、可复用投诉状态机、零迁移、越权测试可大量复用——**投入产出比最佳**。
> - **E2 业务收益满分**：消除履约单点风险，但需 2 个字段与一个新定时任务，且改动了"派单排序"这一敏感逻辑，故难度高于 E4。
> - **E3 与 E5 同档**：都是"零迁移的纯服务端聚合"，成本主要在 SQL 与测试矩阵；E3 收益更高（涉及金额口径）故排在 E5 前。
> - **E1 拆两段**：需求价值最高（B=5，直击依从性），但**无短信服务这一外部依赖把它从 P0 打到 P3**。产品决策是：**不因外部依赖而整体搁置**，先落 E1a。
> - **E6 排在 E1a 之后**：合规价值真实，但对课程演示的直接说服力弱于"漏服提醒送不到人"。

### 5.3 分档结论与排序说明

| 档位 | 方向 | 一句话理由 |
|---|---|---|
| **P0（优先做）** | E4 → E2 | 一个补"公平性"，一个补"确定性"；两者都是**已存在但只做了一半**的能力，补全成本最低 |
| **P1（其后做）** | E3 → E5 | 零迁移的服务端聚合，顺手解决前端性能与口径问题 |
| **P2（有余力做）** | E1a → E6 | 前者是无依赖的半程方案，后者是合规加分项 |
| **P3（条件触发）** | E1b（短信/语音） | **阻塞于外部依赖**，依赖就绪即升级为 P0 |

**为什么不是"按业务收益从高到低排"**：E1 收益最高（B=5），但唯一可行的完整方案依赖短信服务商，在本项目一期范围（无短信）内**无法闭环**。产品上的正确做法是**拆解需求**——把"老人被提醒到"这个价值拆成"家属/陪诊员代提醒"（现在能做）与"短信外呼"（等依赖）两段，而不是把它整体排到第一却迟迟交不出。这是本次排序与"直觉排序"最大的差异点，建议评审时重点过这一条。
