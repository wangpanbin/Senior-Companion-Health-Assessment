## 二、背景与目标

### 2.1 要解决的产品问题

**下单之后到有人接单之前，是一段平台既没有能力、也没有反馈的空白期。**

在这段空白期里：

| 角色 | 他的处境 |
|---|---|
| 家属 | 下完单页面就静止了。他不知道「平台正在匹配」还是「没人看见这一单」，唯一能做的就是反复刷新，或者打电话问客服 |
| 陪诊员 | 大厅按下单时间排，一单躺在大厅里没人接，没有任何人被提醒 |
| 平台 | 没有任何指标能回答「有多少单现在还没人接」，更谈不上兜底 |

这不是一个「等待时长」的问题，而是一个**信息不对称**的问题：
三方面对同一个事实，但只有系统知道这个事实，另外两方都拿不到。

### 2.2 目标

把这段空白期变成一段**有反馈、有节奏、有人兜底**的时间：

1. 家属能看见「现在处于哪一种等待状态」，且能做一件对自己有意义的事（催单）；
2. 陪诊员能自己决定「现在要不要接单」，而不是被强制在线；
3. 平台能看见「哪些单正在没人接」，并有一条明确的兜底动作（人工改派）。

### 2.3 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 距离 / 时间 / 收益多维排序 | 见 [ADR-0013](../adr/0013-hall-single-recommend-order.md)。一期无坐标、无真实结算，三种维度都只能排出不可信的顺序 |
| 陪诊员在线状态展示 | `OFFLINE` 只作状态标记，不做实时在线展示、不按在线状态路由消息。没有产品依据的行为变更不做 |
| 对已接单订单换人 | 已接单 / 服务中的订单换人属纠纷处理，走既有仲裁通道。本版改派**仅限未接单订单** |
| 触发用户真实短信 / 电话 | 一期通知通道只有站内信 + SSE，不做外呼 |

## 三、风险文案口径（合规与情绪负担）

四档文案由后端下发（`fulfillmentRiskLabel`），前端只做「等级 → 视觉」的映射，
**两端不各自判断等级**——否则会出现「家属端显示紧急、管理员端显示正常」的口径分裂。

| 等级 | 触发条件 | 对家属的文案 | 语气约束 |
|---|---|---|---|
| `NORMAL` | 等待 < 10 分钟 | 正常等待 | 不出现任何警示词 |
| `WARNING` | 等待 ≥ 10 分钟 | 等待时间较长 | 只陈述事实，不表达焦虑 |
| `URGENT` | 等待 ≥ 30 分钟 | 履约风险较高 | 「风险」指履约风险，不是健康风险 |
| `MANUAL_REQUIRED` | 等待 ≥ 120 分钟 | 需要人工介入 | 明确告知平台已介入，而非「出问题了」 |

三条硬约束：

1. **不使用纯红 alarming 底色**。老人模式下红色大面积底色的对比度与情绪负担都偏高，风险表达一律用「图标 + 文案 + 左侧色条」；
2. **不出现医疗判断**。任何文案不得含「病情」「危险」「耽误治疗」等表述——本项目不做诊断（合规红线-1）；
3. **不制造紧迫感以促成催单**。催单按钮由后端 `canUrge` 驱动，文案不主动教用户去催。

阈值 `10 / 30 / 120` 分钟为产品确认值，写在 `application.yml` 的 `nianglin.fulfillment.*`，
**不是硬编码**——阈值是运营可调的，代码只认配置。

## 四、功能需求

### FR-Status · 陪诊员接单状态自助控制

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我希望今天排满了就关掉接单开关，而不是被迫挂着接单又不得不拒单 |
| 交付 | `WorkStatus` 增加 `OFFLINE`；`PUT /api/user/companion/work-status` 只写 `work_status` 一列 |
| 关键约束 | **切换状态不触碰在手订单**。切到休息 / 离线后，`ACCEPTED` / `IN_SERVICE` 的订单继续按状态机推进，不中断、不取消 |
| 验收 | 三种状态切换成功；非法字面量 400；资质未过 2003；切换后在手订单 `status` 与原值一致 |

### FR-Risk / FR-Scan · 履约风险识别与升级

| 项 | 内容 |
|---|---|
| 用户故事 | 作为平台，我需要在「等太久」这件事变成投诉之前就发现它 |
| 交付 | `companion_order.fulfillment_risk` 一列 + `FulfillmentRiskEvaluator` 纯函数 + 5 分钟一次的扫描任务 |
| 关键约束 | 风险与订单状态**永不互相推导**（[ADR-0012](../adr/0012-fulfillment-risk-not-order-status.md)）；**只升不降**，回落只由「离开 `PENDING`」触发 |
| 并发 | Redis 锁（TTL 4min < 间隔 5min）+ 按旧值认领的条件更新；两实例同时扫同一批，败者静默跳过，不产生重复事件 |
| 验收 | 构造等待足够的订单 → 扫描一次等级正确且事件只多一条 → 再扫一次事件不再增加（幂等） |

### FR-Urge · 家属催单

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我希望在等太久时能做点什么，而不是干等 |
| 交付 | `POST /api/order/{id}/urge`；`OrderVO.canUrge` 驱动按钮显隐 |
| 频率约束 | 冷却期 10 分钟、累计上限 3 次（均配置化）。资格判定与计数自增**合并为同一条条件更新**，不做「先查后写」 |
| 广播范围 | 只推给「资质已过审 **且** 处于接单中」的陪诊员。推给休息中 / 离线的人，他接不了单又被打扰，只会更快地关掉接单开关 |
| 合规 | 备注过 `ComplianceCheckUtil` 词表（词表与服务小结 `3007` 同一份，命中返回 `6003`）——催单不是绕过「不做诊断」红线的旁路 |
| 验收 | 正常催单 / 非下单人 3004 / 非待接单 3008 / 风险不足 3008 / 冷却内 3009 / 超次数 3009 / 条件更新失败 3009 |

### FR-Read · 履约读口径（家属端风险条）

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我打开订单详情就该看到「现在是什么情况」，而不是自己判断 |
| 交付 | `OrderVO` 五个只读字段；`GET /api/order/{id}/fulfillment` 事件流水；家属端状态条 + 列表轻量标记 |
| 关键约束 | **非 `PENDING` 时风险恒为 `NORMAL`、等待时长恒为 0、不可催单**——已被接走的订单继续挂「等待时间较长」，是在提示一件已经结束的事 |
| 隐私 | 列表的姓名与订单号脱敏；详情的全名豁免仅对已过归属校验的详情生效 |
| 验收 | 四种等级渲染正确；非待接单状态条消失；催单按钮完全由后端字段驱动；列表不新增列 |

### FR-Admin · 管理员风险中心与改派

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我需要一眼看见「多少单没人接」，并能把某一单安排出去 |
| 交付 | `GET /api/admin/fulfillment/summary`（四档计数）· `GET /api/admin/fulfillment/risk-list`（列表）· `POST /api/admin/order/{id}/reassign`（改派） |
| 计数口径 | 只统计 `status = PENDING`；四档字段恒定全返，为 0 时返回 0 而非省略 |
| 列表口径 | 排序固定「等级降序 → 等待时长降序 → id 降序」，不开放 `sortField`；姓名与订单号脱敏 |
| 改派边界 | **仅处理「待接单且尚无接单人」的订单**。已接单订单要换人走仲裁通道。本操作**不改变订单状态**，因此不经过状态流转唯一入口 |
| 改派四件事 | 条件更新 → 写 `ORDER_REASSIGNED` 事件 → 写操作审计（含前后陪诊员与理由）→ 发三方站内信（家属 / 目标 / 原陪诊员） |
| 验收 | 七类拒绝路径各返回正确错误码；改派后 `status` 仍为 `PENDING`；与抢单竞争失败时不留脏数据 |

### FR-Hall · 大厅推荐序

见 [ADR-0013](../adr/0013-hall-single-recommend-order.md)。一句话：**只实现一种排序，非法值 400 不静默降级**。

## 五、业务规则汇总

| # | 规则 | 违反后果 |
|---|---|---|
| 1 | `status` 与 `fulfillment_risk` 永不互相推导 | 状态机铁律失效，时间线被污染 |
| 2 | 风险只升不降，回落只由「离开 `PENDING`」触发 | 已接单订单仍显示风险，家属看到假告警 |
| 3 | 催单资格判定与计数自增必须在同一条 UPDATE 里 | 并发催单绕过冷却期 |
| 4 | 改派只处理未接单订单，且不改变 `status` | 出现两条改变订单归属的路径，事后无法追责 |
| 5 | 风险中心的计数与列表共用同一份候选集定义 | 卡片显示 5 单、列表只有 4 行 |
| 6 | 管理端**不得**另写一套风险判定 | 家属端与管理端对同一笔订单给出两种结论 |
| 7 | 阈值只认配置，不硬编码 | 运营调阈值要改代码 |

## 六、验收标准

| # | 验收项 | 验证方式 |
|---|---|---|
| 1 | 陪诊员能自主控制接单状态，切换不影响在手订单 | `CompanionWorkStatusTest` 17 条 |
| 2 | 系统能识别长时间未接单订单并自动升级风险 | `FulfillmentRiskEvaluatorTest` 26 条 + `FulfillmentSchedulerTest` 6 条 |
| 3 | 家属能获得明确的履约反馈（风险条 + 列表标记） | `OrderVOFulfillmentTest` 17 条 + 前端 `fulfillment.test.js` 16 条 |
| 4 | 家属能合理催单，且有频率与次数限制 | `FulfillmentServiceUrgeTest` 16 条 |
| 5 | 管理员能发现高风险订单（计数 + 列表） | `AdminFulfillmentTest` 17 条 |
| 6 | 管理员能完成订单改派 | `AdminReassignTest` 19 条 |
| 7 | 所有关键履约事件可追溯 | `order_fulfillment_event` 只增不改；履约详情事件流升序返回 |
| 8 | 不破坏现有订单状态机 / 实时通信 / 用药 / 权限体系 | 全量 `mvn verify` + 既有 Playwright 套件零修改通过 |
| 9 | 文案无违禁表述、无真实敏感信息 | `ComplianceCheckUtil` 词表拦截 + 全仓扫描 |
