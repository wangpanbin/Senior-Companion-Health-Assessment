## 二、背景与目标

### 2.1 要解决的产品问题

**陪诊员要回答「我这段时间做得怎么样、赚了多少」，得自己在几个页面之间人工拼。**

| 角色 | 他的处境 |
|---|---|
| 陪诊员 | 完成单数要自己数订单，服务时长要自己算时间差，收入要自己加金额；而且这些数还是在**手机端和电脑端两个地方**、用**两套算法**算出来的 |
| 平台 | 陪诊员的服务质量（准时率、完成率、服务广度）没有出口 —— 想评估一个陪诊员，只能靠人工翻单 |

这不是「缺一个统计页」的问题，是**统计口径长在页面上、而不是长在后端**的问题。

而且 V3.3 开工复核时发现，V3.2 建立指标字典后仍有一处没收敛：
既有的收入页还在用 `reduce()` 拉全量订单自算「累计 / 已结算 / 未结算」——
**口径写在页面上，就必然在两个页面分叉**。

所以 V3.3 要同时做两件事：

1. **把散在订单页、收入页的经营数字聚合成「一个工作台」**；
2. **把口径从「写在页面上」搬回「写在后端与指标字典里」**。

### 2.2 目标

1. 陪诊员打开首页就看到区间完成单数、区间服务时长、区间完成率、平均评分、区间收入五项经营指标；
2. 陪诊员能按「订单 / 收入 / 评分」三个维度、日 / 周 / 月三种粒度看趋势，区分淡旺季；
3. 陪诊员能看到累计口径的服务画像（累计完成单数、累计服务老人数、准时率、累计完成率、累计服务时长、擅长服务）；
4. 陪诊员能核对金额：订单金额、实际收入、待结算、已结算、代垫与服务费构成；
5. **所有统计口径由后端计算并登记在指标字典**，前端零自行计算（决策 G8），手机上和电脑上的数字永远一致。

### 2.3 目标对应的用户故事（roadmap §3.3）

| # | 用户故事 | 落在哪 |
|---|---|---|
| 30 | 打开首页就看到完成单数与收入 | FR-Overview（口径由「本月」修正为「区间」，见 D-3.3-1） |
| 31 | 看到完成率与平均评分 | FR-Overview |
| 32 | 看到订单与收入的趋势 | FR-Trend |
| 33 | 看到我服务过多少位不同的老人 | FR-Profile（累计服务老人数） |
| 34 | 看到我的准时率 | FR-Profile |

| 36 | 分开看到订单金额、平台服务费和实际收入 | FR-Income —— **「平台服务费」这一项已被决策 3.6 移除**，改为「代垫 / 服务费」两型费用构成 |
| 37 | 看到待结算与已结算的拆分 | FR-Income |

### 2.4 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 提现 / 结算流程自动化 | 一期为线上记账 + 线下结算；本版只呈现金额，不做任何资金流转 |
| 替换既有收入页 | 决策 3.4：新工作台与既有收入页**并存且口径一致**，不替换 |
| 引入新的金额字段（含「平台服务费」） | 决策 3.6：现有费用模型只有 `fee`（合同服务费）、`actualFee`（结算金额）与费用项 `ADVANCE` / `SERVICE` 两型（[ADR-0009](../adr/0009-order-fee-item-model.md)）。迭代计划 §34 的「三分」与之冲突时，**以不新增金额字段为先** |
| 陪诊员之间的排名 / 竞争榜 | 无业务依据，且与「服务老人」的定位冲突 |
| 改费用模型 / 改订单状态机 | 本版是纯只读聚合 |
| 新增独立统计表 | 沿用 M10 的聚合查询写法，与 V3.2 零迁移决策一致 |
| 「本月」这类固定日历月口径 | 决策 3.5 + 偏差 D-3.3-1：全部走共享统计区间 |
| 陪诊员坐标与区域结构化 | 属 V3.4 结构化改造范围，本版不涉及 |

## 三、文案口径（合规与情绪负担）

### 3.1 只陈述事实

| 允许 | 不允许 |
|---|---|
| 「区间完成 28 单，完成率 93.00%」 | 「你的服务质量在下滑」 |
| 「准时率 92.00%」 | 「你经常迟到，建议改善」 |
| 「擅长服务：普通门诊 12 单」 | 「你最擅长普通门诊，可以重点接这类单」 |
| 「区间收入 3680.00 元，其中待结算 1200.00 元」 | 「你的收入偏低，需要提升接单量」 |

三条硬约束：

1. **不使用任何结论式判断词**。陪诊员端只呈现客观数字与业务动作，不评价服务质量的好坏；
2. **不制造紧迫感**。本版不做任何催单或收入焦虑提示，「待结算」只报金额与状态，不提示「尽快结算」；
3. **擅长服务标签只来自真实业务数据**（决策 3.3），且**样本 < 5 单的科室不展示** —— 接过 1 单就自称「擅长」是噪声。

### 3.2 「区间」而不是「本月」

「本月」是固定日历月，「统计区间」是可传参的区间（默认最近 30 天、上限 366 天、闭区间）。
两者不可兼得：同一个数字会因「默认区间 / 手动传参」被解释成两个口径，
正是决策 6.2 要禁掉的那类漂移。

因此**指标名与界面文案统一用「区间」，不出现「本月」**，页面必须**明示当前统计区间**。

### 3.3 收入口径：区间收入，不是累计收入

既有收入页的「累计收入」是拉全量订单在前端 `reduce()` 算出来的，既违反决策 G8，
也无法用统计区间表达（区间上限 366 天，装不下「累计」）。

处置：收入页改为消费后端端点，**KPI 文案从「累计收入」改为「区间收入」**，并明示区间；
**账单明细列表保留** —— 那是账单，不是统计指标。

本版呈现的金额共五项：**订单金额 / 实际收入 / 待结算 / 已结算 / 费用构成（代垫、服务费）**，
全部取自既有费用模型，**不出现「平台服务费」**。

### 3.4 指标口径必须先登记

> 同一份数据在两个页面给出不同的数，是「数据看起来对、合起来不对」的头号原因。
> 而靠注释约束口径是最不可靠的一种约束 —— **注释不会在改动时报警**。

本版沿用 V3.2 建立的指标字典，且**只登记不新定义**（决策 2.8）：
新增指标 → 先在字典登记（名称 / 范围 / 时间 / 来源 / 公式 五要素）→ 才允许出现在 VO 里；
字典与 VO 双向核对，**改公式即变红**。

### 3.5 页面语气

| 场景 | 口径 |
|---|---|
| 有数据 | 直接给数字与单位，不加形容词 |
| 空数据 | 「该区间暂无记录」——不是「加载失败」，也不是空白 |
| 加载失败 | 「数据加载失败，重试」——不给「暂无数据」，避免把故障读成「没单」 |
| 区间选择 | 始终明示当前统计区间（开始日 ~ 结束日） |

> **空态与故障态必须可区分**：把「请求失败」渲染成「暂无数据」，
> 陪诊员会以为自己这段时间一单没接 —— 这是口径问题，不是界面问题。

## 四、功能需求

### FR-Overview · 陪诊员工作台概览

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我希望打开首页就看到这段时间的经营核心指标，而不用自己去数订单 |
| 交付 | `GET /api/statistics/companion/me` + `/companion/workbench` 页的经营指标卡区 |
| 关键约束 | 陪诊员身份**从登录态取**，不接收 `companionId` 入参；区间默认 30 天 / 上限 366 天 / 闭区间；「已完成」= `COMPLETED` + `REVIEWED`；完成率分母**不含拒单**；空数据返回 0 而非报错 |
| 边界与例外 | 区间超限返回 `9002`；非 `COMPANION` 角色返回 `403`；请求里带 `?companionId=` 会被完全忽略，返回的始终是登录者本人的数据 |
| 验收 | 五项指标齐全；空数据返回 0 而不是报错；两个陪诊员账号交叉验证互不可见 |

### FR-Trend · 订单 / 收入 / 评分趋势

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我想按天 / 周 / 月看订单、收入、评分的走势，好区分淡旺季 |
| 交付 | `GET /api/statistics/companion/me/trend` + 工作台趋势图区 |
| 关键约束 | 维度 `ORDER` / `INCOME` / `RATING`，粒度 `DAY` / `WEEK` / `MONTH`；**无数据的桶补 0**，`categories` 与每条 `series.data` 长度严格一致；周 / 月粒度的评分**按评价条数加权** |
| 边界与例外 | 非法 `dimension` / `granularity` 返回 `400`，**不静默降级**；长度不一致会让折线图静默跳段，是最难查的一类假绿 |
| 验收 | 三个维度 × 三种粒度均可渲染；无数据的桶补 0 且长度一致；周 / 月粒度评分按条数加权 |

### FR-Profile · 陪诊员服务画像

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我想知道我累计服务了多少人、准时率多少、擅长什么，以便判断自己的服务广度 |
| 交付 | `GET /api/statistics/companion/me/profile` + 工作台服务画像区 |
| 关键约束 | **历史累计口径，不随统计区间浮动**；字段名带 `total` 前缀与区间口径区分；准时率分子 = 存在 `ARRIVE` 打卡且不晚于 `visit_time` 的订单数，分母 = 已接单订单数，**没有 `ARRIVE` 打卡视为不准时**；擅长服务按科室取 TOP 5 |
| 边界与例外 | 样本 < 5 单的科室不展示；画像与概览是**两个口径**，不互相覆盖 |
| 验收 | 六项画像指标齐全；擅长服务不出现样本 < 5 单的科室；无 `ARRIVE` 打卡的单计入不准时 |

### FR-Income · 收入中心

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我想核对订单金额、我的实际收入，以及哪笔钱还没结算 |
| 交付 | `GET /api/statistics/companion/me/income` + 工作台收入摘要区 |
| 关键约束 | 收入口径 `SUM(COALESCE(actual_fee, fee))`（结算金额为空时回退合同服务费）；待结算 / 已结算按 `payment_status` 分组；费用构成按 `item_type` 分 `ADVANCE` / `SERVICE` 两型 |
| 边界与例外 | **恒等式** `待结算 + 已结算 = 实际收入`；本接口**没有「平台服务费」字段** |
| 验收 | 恒等式成立（单测 + 真库 + E2E 三处各断言一次）；`actual_fee` 为空时回退合同服务费 |

### FR-IncomePage · 既有收入页口径对齐

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我希望工作台和原来的收入页显示同一个数，而不是两套算法 |
| 交付 | 既有 `/companion/income` 页改造：KPI 三项改为消费后端端点 |
| 关键约束 | **零 `reduce()` / `filter()` / `groupBy` 口径计算**（决策 G8）；KPI 文案「累计收入」→「区间收入」；页面明示当前统计区间；**账单明细列表保留** |
| 边界与例外 | 账单明细的金额与结算状态仍取订单字段，不改明细结构 |
| 验收 | 页面中不出现 `reduce(` / `.filter(` / `groupBy` 口径计算（含扫描器自证用例）；页面明示当前统计区间；账单明细列表仍在 |

### 工作台页面结构

| 区块 | 内容 | 口径 |
|---|---|---|
| 经营指标卡 | 区间完成单数 / 区间服务时长 / 区间完成率 / 平均评分 / 区间收入 | 区间 |
| 趋势图 | 维度切换（订单 / 收入 / 评分）+ 粒度切换（日 / 周 / 月） | 区间 |
| 服务画像 | 累计完成单数 / 累计服务老人数 / 准时率 / 累计完成率 / 累计服务时长 + 擅长服务 | 累计 |
| 收入摘要 | 订单金额 / 实际收入 / 待结算 / 已结算 | 区间 |

三态齐全：**加载中（骨架）/ 空数据（空态）/ 请求失败（可重试）**。
页面**零 `reduce()` 口径计算** —— 所有数字直接来自后端响应。

## 五、明确的口径决定

### 5.1 开工复核与实现期发现的口径偏差

| # | 偏差 | 决定 | 理由 |
|---|---|---|---|
| D-3.3-1 | 预写 spec 写「本月完成单数 / 本月收入」，与决策 3.5 的可传参统计区间冲突 | 指标名与界面文案统一用「**区间**」，全部走共享区间实现，不出现「本月」 | 「本月」是固定日历月，与可传参区间不是一回事；否则同一个数字会被解释成两个口径 |
| D-3.3-2 | 概览（区间）与画像（累计）都有「完成率」「服务时长」 | **字段名自带口径**：概览用 `completedOrderCount` / `serviceDurationMinutes` / `completionRate` / `periodIncome`；画像用 `totalCompletedOrderCount` / `totalServiceDurationMinutes` / `totalCompletionRate` / `totalServedElderCount` / `punctualityRate` | 都叫 `completionRate` 的话，接口契约本身就埋了口径分裂 |
| D-3.3-3 | 既有收入页「累计收入」是前端 `reduce()` 自算 | 改为消费后端端点，文案「累计收入」→「**区间收入**」并明示区间；账单明细列表保留 | 既违反决策 G8，也装不进 366 天的区间上限 |
| D-3.3-4 | `companion_profile.order_count` 运行期无人维护（只在建档时置 0） | 「累计完成单数」改为从 `companion_order` 现算，指标字典公式同步改写 | 预写 spec 要求读它，实际会永远返回 0；这是**存量数据缺陷**，顺带修掉 |

### 5.2 roadmap 决策（V3.3）

| # | 决定 | 依据 |
|---|---|---|
| 3.1 | 统计一律由后端完成，沿用 M10 的聚合与口径规范；前端零自行计算 | 用户拍板；roadmap §4.3 |
| 3.2 | 金额遵循现有费用模型，不引入新的金额字段 | 用户拍板；被 3.6 修正 |
| 3.3 | 擅长服务标签必须来源于真实业务数据或明确配置，不得由算法臆造 | 用户拍板；roadmap §4.3 |
| 3.4 | 新工作台**不替代**既有收入页面，两者并存且口径一致 | 用户拍板；roadmap §4.3 |
| 3.5 | 统计时间范围沿用 M10 约定：闭区间、默认最近 30 天、上限 366 天 | 用户拍板；roadmap §4.3 |
| 3.6 | **不引入「平台服务费」**；本版只做「订单金额 / 实际收入 / 待结算 / 已结算 / 费用构成」五项 | 用户拍板；**修正 3.2**（迭代计划 §34 的「三分」与「不新增金额字段」冲突时以不新增为先） |

### 5.3 其它口径约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | 「已完成」= `COMPLETED` + `REVIEWED` | 评价只是完成之后的后续动作，把已评价的单排除会让完成率随着用户评价而下降 |
| 2 | 完成率分母**不含拒单** | 被拒的单不构成平台未履约的部分 |
| 3 | 准时率：**没有 `ARRIVE` 打卡 = 不准时** | 没打卡本身就是履约问题 |
| 4 | 擅长服务：**样本 < 5 单的科室不展示**，TOP N ≤ 5 | 接过 1 单就自称「擅长」是噪声 |
| 5 | 区间口径的订单一律按 `visit_time` 过滤 | 与 V3.2 家属端 `elder.visit.order_count` 同一时间字段，两端必须同源 |
| 6 | 零新增错误码，全部复用 | AGENTS.md §2.7 段位纪律 |

### 7.3 已知限制（如实披露，不静默）

| 项 | 说明 |
|---|---|
| 画像的「累计」不随区间浮动 | 有意设计：画像回答「我到底什么水平」，概览回答「这段时间怎么样」。字段名与指标字典两处都写明了 |
