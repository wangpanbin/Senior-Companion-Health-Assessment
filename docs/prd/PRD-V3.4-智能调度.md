## 二、背景与目标

### 2.1 要解决的产品问题

**家属要回答「多久能等到一个真正合适的陪诊员」，而系统今天只会把订单扔进一个大厅。**

| 角色 | 他的处境 |
|---|---|
| 家属 | 下单后订单进入大厅，谁能看到、什么时候被看到，全凭陪诊员自己刷屏。家属对「还要等多久」没有任何预期 |
| 陪诊员 | 大厅只有一个排序（就诊时间），**接不了的单和能接的单混在一起**：不在服务区域、时间对不上、没做过的科室，全都得自己筛 |
| 平台 | 想优化匹配，只能凭感觉调参数 —— 因为「为什么这一单排在这」根本说不清 |

这不是「排序不够好」的问题，是**平台没有可用的匹配输入**的问题。

开工核实的结果比预想更严重：匹配模型要求的五个维度里，
**三个维度今天没有任何数据基础** ——
陪诊员的服务区域与可服务时段是**自由文本**，陪诊员档案**没有坐标**。
预写 spec 里的「距离 20%」在开工当天是一个**没有数据支撑的权重**。

所以 V3.4 要做的不是「调排序」，而是**先补上可算的东西，再建引擎**：

1. **先做结构化改造**（expand–contract），让区域、时段、坐标成为可索引、可 JOIN 的字段；
2. **再建五维规则引擎**，且每条规则都是**无 Spring 上下文的纯函数**；
3. **最后把引擎接到两个出口**：大厅排序（陪诊员侧）与候选推荐（家属侧）。

### 2.2 目标

1. 陪诊员在大厅里优先看到**自己确实能接**的订单，且能按「距离最近」「时间匹配」自行排序；
2. 家属在自己的订单详情里能看到系统给出的候选陪诊员与**匹配理由**；
3. 每条推荐都能解释「为什么是他」，以及哪些维度因为**数据缺失**没算出来；
4. 五维权重**配置化**，管理员可针对供给不足的时段调整策略而**不发版**；
5. 匹配规则与加权是**纯函数**，每个边界可被毫秒级反复测试。

### 2.3 目标对应的用户故事（roadmap §3.4）

| # | 用户故事 | 落在哪 |
|---|---|---|
| 40 | 大厅优先展示我确实能接的订单 | FR-Hall（过滤链） |
| 41 | 同等条件下更近的单排前面 | FR-Hall（`sortBy=DISTANCE`） |
| 42 | 服务过我擅长的类型的陪诊员优先被推荐 | FR-Rules（服务能力维度） |

| 45 | 管理员能调整匹配权重 | FR-Rules（权重配置化，启动期校验） |

### 2.4 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 第一阶段引入 AI 模型 | 决策 4.1：先建立规则引擎。AI 只在运营分析方向且需另行论证；且合规红线禁止疾病诊断 / 药物推荐 / 治疗建议 / 医疗风险预测（决策 4.5） |
| 自动派单 | 决策 4.4：**推荐 ≠ 派单**，接单权始终在陪诊员手里 |
| 跨城市调度 | 一期区域码两级跨市记 0；跨城市供给调度属平台级策略，不在本版 |
| 收益优先排序（`sortBy=INCOME`） | 需要真实结算金额口径，而现有费用模型没有这一条（[ADR-0009](../adr/0009-order-fee-item-model.md)）；继续返回 `400`，错误消息给一句人话 |
| 删除 `service_area` / `available_time` 旧列 | 删列不可逆，且旧文本里还有历史语义；本期只做加列 + 回退读取 |
| 实时在线状态展示 / 按在线状态路由 | 沿用 V3.1 决策：`OFFLINE` 只作状态标记 |
| 地图导航 / 路线规划 | 合规红线：文字地址 + 签到坐标已足以支撑业务 |
| 陪诊员之间的排序竞争 | 无业务依据 |

> ⚠️ **一处与 roadmap §6.1 的差异**：roadmap 写「不改服务区域的数据录入形态（结构化改造另议）」，
> 但开工核实确认**服务区域与可服务时段仍是自由文本、陪诊员无坐标**，
> 「距离 20%」没有任何数据基础 —— 因此结构化改造成为本版**必做前置**（[ADR-0016](../adr/0016-matching-structured-and-explainable.md)）。

## 三、文案口径（合规与情绪负担）

### 3.1 推荐 ≠ 派单

界面必须明确标注「**推荐仅供参考，最终由陪诊员本人确认接单**」。

| 禁止出现 | 原因 |
|---|---|
| 「已指派」「已分配」「自动派单」 | 那是产品边界的改变，不是文案问题 |
| 「系统已为您锁定该陪诊员」 | 与决策 4.4 直接冲突 |

匹配端点**不产生任何订单状态变更** —— 它只读订单与陪诊员档案，只返回候选。

### 3.2 命中理由与降级说明必须分开

这是本版最容易出错、也最容易被误读的一处：

| 类别 | 含义 | 举例 |
|---|---|---|
| 命中理由（`reasons`） | 这一维**匹配上了** | 「同服务区域」「就诊时间在可服务时段内」「服务过该科室 12 单」 |
| 降级说明（`notes`） | 这一维**没法算**，不是「不匹配」 | 「未填写坐标，距离维度记 0」 |

把降级写进理由里，会让人误以为「距离不匹配」，而真相是「距离没法算」——
运营会拿一个不存在的结论去调权重。**不允许出现一个没有理由的分数。**

### 3.3 无坐标时的距离口径

陪诊员没填坐标时，距离维度**记 0 并标注「无坐标」**，
**绝不按 (0, 0) 推断**——那会把「没填资料」翻译成「离几内亚湾 2000 公里」，
然后在排序里把真正合适的人挤下去。

### 3.4 隐私

候选列表只返回**脱敏姓名**（`李建军` → `李*军`），
**不返回手机号、身份证号**。

### 3.5 大厅排序白名单

| `sortBy` | 本版行为 | 说明 |
|---|---|---|
| `RECOMMEND`（缺省） | 五维加权排序 | V3.1 的三级键（就诊时间 → 区域匹配 → ID）被本版替换 |
| `DISTANCE` | 开放 | 按距离分降序；**距离分并列时回落到就诊时间升序**（见 D-3.4-3） |
| `TIME_MATCH` | 开放 | 按时间匹配分降序；并列时同样回落到就诊时间升序 |
| `INCOME` | 仍 `400` | 「收益优先需要真实结算金额口径，本版未开放」—— 不是「还没做」，是「没有可信的数据」 |
| 其它取值 | `400` | 错误消息**回显传进来的取值**，不静默降级到推荐序 |

> 配置项 `hall-default-sort` 同样受白名单约束：配成未开放维度时，大厅**一并返回 `400`**，
> 不会带着一个拿不到实现的排序键继续跑。

### 3.6 指标口径必须先登记

本版**新登记** 6 条匹配指标（`matching.*`：五个维度 + 加权总分）——
指标字典本就是新指标的唯一入口（决策 2.8）。
公式、范围、来源见 [`metric-dictionary.md`](../spec/metric-dictionary.md) §2.5。

## 四、功能需求

### FR-Structure · 服务区域与可服务时段结构化

| 项 | 内容 |
|---|---|
| 用户故事 | 作为平台，我需要「区域」和「时段」成为可筛选的字段，而不是一段不能可靠解析的自由文本 |
| 交付 | 陪诊员档案增坐标与区域码、订单增区域码、新增可服务时段表；自由文本 → 结构化字段的确定性回填 |
| 关键约束 | **expand–contract**：新列全部可空，老数据一行不改继续跑；**一期不删旧列**；回填**映射不上的留空**（留空 = 该维度按「无数据」处理，不猜）；读路径**优先结构化列，缺失时回退自由文本包含式匹配** |
| 验收 | 迁移可重复验证，老数据不受影响；回填 SQL 与可复现生成器逐字一致；映射不上的数据留空而非被猜出来 |
| 边界与例外 | 区域码格式为 `<CITY>_<DISTRICT>`，城市前缀即「区」这一层；回填 SQL 由可复现生成器产出并与迁移文件逐字核对，不一致即非零退出 |

### FR-Rules · 五维匹配规则引擎

| 项 | 内容 |
|---|---|
| 用户故事 | 作为平台，我需要匹配规则是可解释、可复算、可测试的，而不是一个说不清的黑盒分数 |
| 交付 | 匹配三件套（规则 / 得分 / 候选人快照）+ 五条规则 + 可配置的加权 |
| 关键约束 | 五维 = 区域 30% / 时间 25% / 距离 20% / 服务能力 15% / 评分 10%，**权重配置化**且**启动期校验权重之和 = 1**（不等于 1 直接启动失败）；规则是**无 Spring 上下文的纯函数** |
| 边界与例外 | 权重错误不会报错、只会让排序悄悄变得不合理 —— 所以让它在启动的十秒内失败；距离复用既有 Haversine 实现，不另写一份 |
| 验收 | 五条规则的边界逐条锁住；权重之和 ≠ 1 时启动失败；无坐标时距离维度记 0 且带标注 |

### FR-Hall · 大厅推荐序升级

| 项 | 内容 |
|---|---|
| 用户故事 | 作为陪诊员，我想在大厅里优先看到我确实能接的订单，少翻接不了的单 |
| 交付 | `GET /api/order/hall` 的 `sortBy` 扩展：`RECOMMEND`（五维加权）/ `DISTANCE` / `TIME_MATCH` |
| 关键约束 | **响应结构零变更**：分页字段与语义都不变，`total` 仍是「满足大厅筛选条件的待接单订单数」；排序只影响 `records` 的顺序；候选集整批加载后**内存分页**，候选集上限由配置控制，超限**记 warn 日志，不静默截断** |
| 边界与例外 | `INCOME` 仍 `400`（缺真实结算金额口径）；其它非法值仍 `400` 且**错误消息回显传进来的取值**；资质未通过仍先报 `2003`；仍排除该陪诊员已拒过的订单 |
| 验收 | 三个可选排序均可用、`INCOME` 仍 `400`；分页字段与语义零变更；`total` 仍是候选订单数 |

### FR-Recommend · 候选陪诊员推荐（家属端）

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我希望在订单详情里看到系统给出的候选陪诊员和匹配理由，而不是只等到有人接单 |
| 交付 | `GET /api/order/{id}/recommend-companions` + 订单详情页的候选展示区 |
| 关键约束 | 权限 `FAMILY` + **订单归属校验**（必须是自己下的单）；过滤链**顺序固定、逐级短路**：工作状态 → 资质 → 区域 → 时段 → 档期冲突；每一步的淘汰原因都要能被解释；返回各维度得分 + 命中理由 + 降级说明；姓名脱敏 |
| 边界与例外 | 非本人订单 → `3004`；**缺资料与不匹配是分开的** —— 只是没填区域码 / 没登记时段的候选人被**放行并降级**，而不是被淘汰；`total` 是**通过过滤链的候选总数**，不是返回条数；本端点**不产生任何订单状态变更** |
| 验收 | 每条候选至少一条命中理由；有维度降级时必带降级说明；非本人订单返回 `3004`；响应中无手机号 / 身份证号 |

### 大厅与候选推荐的界面结构

| 位置 | 内容 | 口径约束 |
|---|---|---|
| 大厅列表 | 排序选项（推荐序 / 距离 / 时间匹配） | 选项的可用性由**后端白名单**决定，前端不自行判断；`INCOME` 不出现在可选项里 |
| 候选展示区 | 脱敏姓名 + 总分 + 各维度得分 + 命中理由 + 降级说明 | 必须带「推荐仅供参考，最终由陪诊员本人确认接单」的说明；不出现「已指派」「自动派单」字样 |

### 五个匹配维度与初始权重

| 维度 | 初始权重 | 得分口径 | 缺数据时 |
|---|---|---|---|
| 区域 | 30% | 区域码相等 `1.0`；同市不同区 `0.5`；跨市 `0` | 双方都无区域码 → 该维度记 `0` 并标注（**不推断**） |
| 时间 | 25% | 订单时间落在可服务时段内 `1.0`；部分重合 `0.5`；不重合 `0` | 无可服务时段 → 记 `0` 并标注 |
| 距离 | 20% | 直线距离 / 满量程，`1 − d/max` | 陪诊员无坐标 → 记 `0` 并标注「无坐标」 |
| 服务能力 | 15% | 该陪诊员在该科室的已完成单数 / 满量程（上限 1） | 无历史单 → 记 `0` |
| 评分 | 10% | 评分 / 5 | 无有效评分 → 记 `0` 并标注 |

> 权重之和为 1 时，加权总分落在 `[0, 1]`，接口按 ×100 后四舍五入成 `0–100` 的整数。
> 五个权重**全部配置化**（`nianglin.matching.*.weight`），运营改策略不发版。

## 五、明确的口径决定

### 5.1 开工复核与实现期的偏差

| # | 偏差 | 决定 | 理由 |
|---|---|---|---|
| D-3.4-0 | roadmap §6.1 写「不改服务区域的数据录入形态（结构化改造另议）」，但开工核实确认服务区域 / 时段仍是自由文本、陪诊员无坐标 | 结构化改造（加列 + 回填 + 回退读）列为本版**必做前置**，再上规则引擎 | 「规则引擎是怎么算，结构化改造是有什么可算」。顺序反了，权重配得再漂亮，算出来的分也是空的 |
| D-3.4-1 | 预写 spec 写「区域码相等 / 同一区不同码 / 跨区」，但没说「区」怎么界定 | 区域码固定 `<CITY>_<DISTRICT>`，**城市前缀即「区」这一层**：码相等 `1.0` / 同市不同区 `0.5` / 跨市 `0` | 种子的服务区域有 8 个区县、分属 4 个市；只有一级的话，同市的两个区只能算「不同」，但它们其实是同一市场的供给 |
| D-3.4-2 | 预写 spec 说「扩展 V3.1 的单一推荐序为五维推荐序，响应结构零变更」，但 V3.1 的实现是 SQL `ORDER BY` | 五维打分统一在 **Java 侧**完成（纯函数），大厅改为「候选集 → 打分 → 排序 → **内存分页**」 | 三件事 SQL 做不了或做了会错：距离要 Haversine；服务能力要按历史单数归一化；「无坐标 → 记 0 且不推断」需要一条**分支**，SQL 的 CASE 分不出「没数据」与「距离为零」 |
| D-3.4-3 | 预写 spec 说开放 `sortBy=DISTANCE`，但今天没有陪诊员填坐标 | `DISTANCE` 开放，按距离分降序，**距离分并列时回落到就诊时间升序** | 这不是「假装能排」，而是如实反映「现在没有距离数据」；陪诊员开始填坐标后排序自动生效，不需要改代码 |

### 5.2 roadmap 决策（V3.4）

| # | 决定 | 依据 |
|---|---|---|
| 4.1 | 第一阶段不直接使用 AI，先建立规则引擎 | 用户拍板；roadmap §4.4 |
| 4.2 | 规则引擎由匹配服务 / 规则 / 得分三件构成 | 用户拍板；roadmap §4.4 |
| 4.3 | 初始权重（区域 30% / 时间 25% / 距离 20% / 服务能力 15% / 评分 10%）**仅作为初始配置**，权重键配置化，不硬编码 | 用户拍板；roadmap §4.4 |
| 4.4 | 排序**只做推荐**，接单权仍在陪诊员 | 用户拍板；roadmap §4.4 |
| 4.5 | 未来若引入 AI，优先用于运营分析 / 异常总结 / 服务质量分析 / 用户反馈归纳 / 管理员辅助决策；**禁止**疾病诊断 / 药物推荐 / 治疗建议 / 医疗风险预测 | 用户拍板；roadmap §4.4 |

### 5.3 其它口径约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | 过滤链五步顺序固定、逐级短路，每步淘汰原因可解释 | 决策 4.4 + ADR-0016 |
| 2 | 大厅 `total` 仍是「满足筛选条件的待接单订单数」，**不因排序方式改变语义** | ADR-0016 后果章 |
| 边界与例外 | 非法 `sortBy` 一律 `400` 且回显取值，**不静默降级到推荐序** | [ADR-0013](../adr/0013-hall-single-recommend-order.md) |
| 4 | 候选集超上限时**记 warn 日志，不静默截断** | ADR-0016 后果章 |
| 5 | 零新增错误码，全部复用 | AGENTS.md §2.7 段位纪律 |

### 5.4 过滤链的五步与降级放行

| 步 | 判定 | 缺数据时的处置 |
|---|---|---|
| 1 | 工作状态可接单 | — |
| 2 | 资质已过审 | — |
| 3 | 区域匹配（区域码 ∩） | 缺区域码 → **回退自由文本包含式**并降级标注，不淘汰 |
| 4 | 时段可服务（就诊时间落在可服务时段内） | 未登记时段 → **降级放行**，不淘汰 |
| 5 | 档期冲突（该时段已有在手订单） | — |

> 「缺资料」与「不匹配」是两件事。淘汰一个只是没填资料的人，
> 等于让「资料填得全」变成接单的前提 —— 所以缺资料是**放行 + 降级标注**，不是淘汰。

## 七、指标与后续

### 7.1 本版登记进指标字典的指标（6 条）

| key | 名称 |
|---|---|
| `matching.total_score` | 匹配总分 |
| `matching.region_score` | 区域维度得分 |
| `matching.time_score` | 时间维度得分 |
| `matching.distance_score` | 距离维度得分 |
| `matching.skill_score` | 服务能力维度得分 |
| `matching.rating_score` | 评分维度得分 |

> 维度得分是「0–1 原始分 × 100 后的整数」；加权总分 = Σ(维度分 × 权重) × 100。
> 公式、来源字段见 [`metric-dictionary.md`](../spec/metric-dictionary.md) §2.5。

### 7.2 后续版本的承接点

| 承接方 | 要接住什么 |
|---|---|
| V3.5 平台运营驾驶舱 | 「匹配效果」在管理端的观察（异常中心里的超匹配预警、趋势里的履约率）建立在本版匹配能力之上；**驾驶舱不另建一套匹配判定** |

### 7.3 已知限制（如实披露，不静默）

| 项 | 说明 |
|---|---|
| 距离维度目前恒为 0 | 陪诊员坐标是本版新增的列，存量全空。如实反映「现在没有距离数据」，坐标一填即自动生效 |
