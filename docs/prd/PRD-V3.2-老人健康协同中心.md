## 二、背景与目标

### 2.1 要解决的产品问题

**家属要回答「我这个月到底怎么样」，得跨四个页面人工拼。**

| 角色 | 他的处境 |
|---|---|
| 家属 | 想知道「爸妈这个月怎么样」：得先翻订单页看有没有陪诊，再翻用药页看漏没漏服，再翻消息页看有没有异常提醒 —— 三个页面，三次拼装 |
| 老人 | 想知道「我今天做了哪些事」，得自己在订单、用药、消息之间来回点；大字版页面只有用药和订单两个孤立模块 |
| 平台 | 数据都存着，但没有一张能把它们摆在一起的视图 —— 想做运营分析，只能直接查库 |

这不是「缺一个页面」的问题，是**信息散了**的问题。

而 V3.1 落地后暴露了一个更尖锐的问题：**同一份数据，在两个页面给出不同的数**。
M6 服药日历说「漏服 2 次」，M10 统计图说「漏服 0 次」——
因为两处各写了一套判定，而两处注释都宣称「口径一致」。

所以 V3.2 要同时做两件事：

1. **把散的信息聚合成「一位老人一个视图」**；
2. **把口径从「写在注释里」变成「写在代码与测试里」**。

### 2.2 目标

1. 家属有唯一的入口看到每位老人的健康全貌（就医 / 陪诊 / 用药 / 待办）；
2. 家属能把「订单 / 打卡 / 用药 / 提醒」按时间排成一条线，还原某一天到底发生了什么；
3. 老人能在自己看得懂的方式下看到「今天完成了什么」；
4. 同一个指标在家属端、老人端、管理端**永远是同一个数**。

### 2.3 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 健康评分 / 健康指数 | 无医疗依据，且「家长式」评估风险高。迭代计划 §28 明确「事实记录优先，不进行医疗诊断」 |
| 疾病风险预测 / 异常健康判断 | 合规红线-1 |
| 老人端健康数据录入 | 老人账号是只读的；健康事实来自家属代录与陪诊服务 |
| 独立 `health_record` 表 | 见 [ADR-0015](../adr/0015-elder-health-aggregation-no-new-table.md) |
| 新增底部导航项 | 迭代计划 §57「导航越来越长」是明确要避免的；三个页面都落在既有分组内 |
| 实时推送健康提醒 | SSE 通道已存在，但健康事件本身是「回看」场景，不需要实时 |
| 改订单状态机 / 改用药规则 | V3.2 是纯只读聚合 |

## 三、文案口径（合规与情绪负担）

### 3.1 只陈述事实

| 允许 | 不允许 |
|---|---|
| 「今日有 1 次服药任务未确认」 | 「老人今天健康状况较差」 |
| 「近 30 天就医 3 次」 | 「老人存在某疾病风险」 |
| 「有订单在等待接单」 | 「陪诊迟迟未到，情况紧急」 |
| 「漏服 2 次」 | 「服药不规律，需要干预」 |

四条硬约束：

1. **不使用任何结论式判断词**。禁用词表在 `frontend/src/utils/elderHealth.js` 的 `FORBIDDEN_JUDGMENT_WORDS`，
   由前端单测与全仓文案扫描共用。
2. **不制造紧迫感**。家属端文案陈述事实即可，不主动教用户去催单 —— 催单由 V3.1 的 `canUrge` 驱动。
3. **时间线事件标题用业务动作**（「已接单」「服务完成」「已服药」），不用形容词。
4. **异常只标「异常」二字**（打卡偏离超限），不解释后果。

### 3.2 指标口径必须先登记

> 同一份数据在两个页面给出不同的数，是「数据看起来对、合起来不对」的头号原因。
> 而靠注释约束口径是最不可靠的一种约束 —— **注释不会在改动时报警**。

所以 V3.2 建立**指标字典**（`docs/spec/metric-dictionary.md`）：

```
新指标 → 先在指标字典登记（名称/范围/时间/来源/公式 五要素）→ 才允许出现在 VO 里
       → MetricDictionaryTest 双向核对：字典里的字段必须真的存在，VO 里的字段必须真的登记过
```

V3.3 / V3.5 只能「登记」不能「新定义」；V3.6 退化为校验与补全。

## 四、功能需求

### FR-Summary · 家庭健康协同首页

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我希望有一个页面能看到我关心的每位老人的健康摘要，而不是先点进某一位老人 |
| 交付 | `GET /api/family/health/summary` + `/family/health` 页 |
| 关键约束 | 只含**当前家属**名下 `BOUND` 的绑定关系；姓名脱敏；「今日用药」是当天事实，不随统计区间浮动 |
| 验收 | 多位老人各一栏；未绑定老人返回空数组而非报错；解绑后不再出现 |

### FR-Overview · 某位老人的健康概览

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我想一眼看到这位老人这个月就医几次、吃药完成得怎么样、还有什么要我处理 |
| 交付 | `GET /api/family/elder/{elderId}/health/overview` + `/family/elder/:id/health` 页 |
| 关键约束 | 区间默认 30 天、最多 366 天；**三桶之和恒等于总数**；完成率由后端算好；完成率 0 时是 `0.00%` 不是 `NaN%` |
| 验收 | 六项客观指标齐全；待处理事项可直达处理页；`taken + missed + pending == total` |

### FR-Timeline · 老人健康时间线

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我想把订单、打卡、用药、提醒按时间排成一条线，好还原某一天到底发生了什么 |
| 交付 | `GET /api/family/elder/{elderId}/health/timeline` + 时间线区块 |
| 关键约束 | 四类事件；按时间倒序；游标翻页不重不漏；**待服不是事件**（属于待处理）；订单聊天内容不进时间线 |
| 验收 | 事件倒序、字段齐备、分类合法；按 `categories` 过滤生效；`limit` 生效且 `hasMore` 与 `nextCursor` 配套 |

### FR-Pending · 待处理事项

| 项 | 内容 |
|---|---|
| 用户故事 | 作为家属，我希望知道「现在有什么事需要我处理」，而不是自己去找 |
| 交付 | 概览页的 `pendingItems` + 首页的 `pendingItemCount` |
| 关键约束 | 四类判定（今日待服 / 待接单 / 待评价 / 高风险）；只陈述数量，**不做判断**；每项可直达处理页；首页角标与详情列表**恒等** |
| 验收 | 有待办时列出且计数一致；无待办时不出现空卡片 |

### FR-Elder · 老人端健康中心

| 项 | 内容 |
|---|---|
| 用户故事 | 作为老人，我想用看得懂的方式看到「我今天完成了哪些事」 |
| 交付 | `GET /api/elder/health/overview` + `GET /api/elder/health/timeline` + `/elder/health` 页 |
| 关键约束 | **不接收任何 `elderId` 入参**；内容是家属端聚合结果的**子集**（去掉费用 / 催单 / 履约风险 / 家属姓名）；大字；待办只留与自身相关的 |
| 验收 | 老人只看得到自己；看不到费用与履约风险；页面无违禁文案 |
