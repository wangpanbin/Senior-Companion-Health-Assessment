## 二、背景与目标

### 2.1 要解决的产品问题

**管理员要回答「平台现在有没有问题」，得在四个后台页面之间来回巡检。**

| 角色 | 他的处境 |
|---|---|
| 管理员 | 后台首页给的是「管理数据」（订单列表、用户列表、导出入口），不是**平台状态**。有没有订单卡住、哪个陪诊员投诉率异常、哪批用药漏服了，得自己知道去哪个页面查 |
| 平台 | 履约风险中心（V3.1）只覆盖「订单卡住」这一类异常。投诉率异常、用药漏服异常**有数据，但没有人把它们摆到同一处** |
| 家属 / 陪诊员 | 平台越晚发现问题，自己的单就等得越久 |

这不是「缺一个仪表盘」的问题，是**异常没有出口**的问题。

而「有出口」这件事有两个容易做假的地方，本版必须堵死：

1. **另建一套风险判定**——驾驶舱自己算一遍「有几单超时」，与 V3.1 的风险中心对不上，
   两套判定必然漂移（这正是 V3.2 在用药三桶上踩过的坑）；
2. **给出一个说不清的总数**——「AI 平台健康指数 96」看着漂亮，但没人能向别人解释这个数怎么来的。

所以 V3.5 的产品命题是：**从「管理数据」升级到「发现平台问题」**，
且发现之后要能**一步跳到能处理的地方**，而不是「看到了但处理不了」。

### 2.2 目标

1. 管理员打开后台首页就看到今日与区间内的全局运营指标，**三十秒内判断平台是否正常**；
2. 管理员在一个异常中心里看到四类异常的**数量**与**处理入口**；
3. 管理员能按今日 / 近 7 天 / 近 30 天 / 自定义看六个维度的趋势，区分偶发与持续；
4. 平台健康度由**六个客观指标**构成，每个都能单独解释；
5. 空数据时显示 0 或空图，**不报错**——让管理员知道是真的没有数据。

### 2.3 目标对应的用户故事（roadmap §3.5）

| # | 用户故事 | 落在哪 |
|---|---|---|
| 48 | 打开后台首页就看到今日全局指标 | FR-Overview |
| 49 | 看到需要人工介入的订单数 | FR-Exception（`MANUAL_REQUIRED`） |
| 50 | 看到投诉率异常的陪诊员 | FR-Exception（`COMPANION_COMPLAINT_RATE`） |
| 51 | 从异常卡片直接跳到处理页面 | FR-Exception（决策 5.4 可达性） |
| 52 | 按今日 / 近 7 天 / 近 30 天 / 自定义看趋势 | FR-Trend |
| 53 | 看到履约率、平均接单时间、投诉率、平均评分 | FR-Health |
| 54 | 平台健康度由客观指标构成而不是一个神秘分数 | FR-Health（决策 5.2，六个并列指标） |
| 55 | 空数据时显示 0 或空图而不是报错 | 全部 FR |

### 2.4 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 无法解释的综合评分 / 平台健康总分 | 决策 5.2：健康度由客观指标构成，**禁止**「AI 平台健康指数 96」这类数，除非存在明确计算公式 |
| 自动决策 | 决策 5.4 + 5.1：异常中心只做**发现与跳转**，处置动作仍由管理员执行；平台不替管理员做投诉裁定、改派、仲裁 |
| 实时秒级刷新 | 统计按区间查询与轮询刷新，不做秒级推送；运营看的是区间趋势，不是秒级监控 |
| 另建一套履约风险判定 | 决策 5.1：异常中心**聚合** V3.1 风险中心，数量必须相等，由 parity 测试锁死 |
| 另写一套用药漏服判定 | 用药三桶以唯一真源为准（[ADR-0014](../adr/0014-medication-bucket-single-source.md)） |
| 医疗 / 健康类综合评估 | 合规红线-1：不做诊断、不做风险预测 |
| 新增导航一级入口之外的页面群 | 驾驶舱落在既有管理后台分组内 |

## 三、文案口径（合规与情绪负担）

### 3.1 异常卡片只陈述事实

四类异常的文案由后端下发，前端只做「等级 → 视觉」的映射，**两端不各自判断等级**。

| 类型 | 标题 | 文案口吻 | 禁止 |
|---|---|---|---|
| `MANUAL_REQUIRED` | 需人工介入订单 | 陈述「已达人工介入阈值，需要管理员协调」 | 不写「情况紧急」「客户已投诉」 |
| `MATCH_WARNING` | 超匹配预警时间订单 | 陈述「等待时间超过预警阈值，系统正在扩大匹配范围」 | 不写「无人接单，平台失职」 |
| `COMPANION_COMPLAINT_RATE` | 投诉率异常陪诊员 | 陈述「回溯期内投诉率超过阈值，需关注服务质量」 | 不点名、不评价陪诊员品行 |
| `MEDICATION_MISSED` | 用药漏服异常 | 陈述「区间内漏服任务数超过阈值」 | 不出现任何健康判断（合规红线-1） |

三条硬约束：

1. **不出现医疗判断**。任何文案不得含「病情」「危险」「耽误治疗」等表述；
2. **不制造紧迫感**。异常卡片表达「有多少、是什么、需要人去处理」，不渲染红色大面积底色，
   统一用「图标 + 文案 + 左侧色条」；
3. **只报数量与状态，不下结论**。不写「某陪诊员服务态度差」，只写「投诉率超过阈值」。

### 3.2 「履约率」与「完成率（按时）」是两个不同的指标

界面上分别标注「履约率」与「完成率（按时）」，**不得合并展示、不得共用一个数**。

| 指标 | 回答的问题 |
|---|---|
| 履约率 | 区间内的订单，最终有多大比例真正履约了 |
| 完成率（按时） | 已完成的订单里，有多大比例没超出履约时长窗口 |

若两者都按「完成 ÷（完成 + 取消）」算，那就是**同一个数字挂了两个名字**——
决策 6.2 禁止「同一指标在不同端出现不同口径」，反过来也禁止「两个名字一个数」。

### 3.3 健康度不给合成分

健康度是**六个并列指标卡**，界面与接口都**不出现**「健康指数」「综合评分」「总分」字样。
每个指标各自成立、各自可解释；把它们合成一个数的那一步不存在，所以也无需解释。

### 3.4 趋势的六个维度

| 维度 | 看什么 | 空数据时 |
|---|---|---|
| `ORDER` | 订单量与状态分布 | 补 0 |
| `COMPANION_ACTIVE` | 区间内有接单的陪诊员数 | 补 0 |
| `FULFILLMENT_RATE` | 履约率随时间的变化 | 补 0 |
| `COMPLAINT` | 投诉数 | 补 0 |
| `REVIEW` | 评价数与均分 | 补 0 |
| `MEDICATION` | 用药任务数与漏服数（三桶同源） | 补 0 |

区间支持今日 / 近 7 天 / 近 30 天 / 自定义；自定义区间的长度上限与其它统计口径一致。

### 3.5 指标口径必须先登记

本版沿用指标字典，**只登记不新定义**（决策 2.8）：15 条管理端指标登记在字典 §2.6，
与机器面逐条对齐；**人读面与机器面的一致性由脚本机械校验**，不一致即非零退出。

## 四、功能需求

### FR-Overview · 平台运营概览

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我希望打开后台首页就看到今日全局指标，三十秒内知道平台是否正常 |
| 交付 | `GET /api/admin/operations/overview` + 驾驶舱首页概览区 |
| 关键约束 | 区间默认最近 30 天 / 上限 366 天 / 闭区间；「已完成」= `COMPLETED` + `REVIEWED`；今日订单数按**当天**统计，不随区间浮动；无已接单订单时平均接单时间为 `0`；空数据返回 0 而非报错 |
| 边界与例外 | 区间超限 `9002`；非 `ADMIN` 一律 `403`，未登录 `401` |
| 验收 | 八项概览指标齐全；空数据返回 0；今日订单数不随区间浮动 |

### FR-Exception · 异常中心

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我希望在一个地方看到所有需要我介入的异常，并一步跳到能处理它的页面 |
| 交付 | `GET /api/admin/operations/exceptions` + 四张异常卡片，每张带「去处理」入口 |
| 关键约束 | 四类异常的数量**必须等于** V3.1 履约风险中心的对应计数（`manualRequired` 与 `warning + urgent`），由 **parity 测试锁死**；异常卡片到处理页面的入口必须是**真实存在**的前端路由，由 E2E **逐个点开**验证落地页可达；`level` 只有 `DANGER` / `WARNING` / `INFO` 三档 |
| 边界与例外 | 页面**不做自动决策**——发现与跳转为止，处置由管理员在目标页执行；`referenceId` 可为空 |
| 验收 | 四张卡片渲染；每张卡片的处理入口指向**存在的路由**且落地页不 404；前两项数量与 V3.1 风险中心相等 |

#### 四类异常与处理入口

| 类型 | 中文名 | 等级 | 处理入口 | 定位 ID |
|---|---|---|---|---|
| `MANUAL_REQUIRED` | 需人工介入订单 | `DANGER` | 履约风险中心 | 无 |
| `MATCH_WARNING` | 超匹配预警时间订单 | `WARNING` | 履约风险中心 | 无 |
| `COMPANION_COMPLAINT_RATE` | 投诉率异常陪诊员 | `WARNING` | 投诉处理页 | 无 |
| `MEDICATION_MISSED` | 用药漏服异常 | `WARNING` | 订单管理页 | 最近一条异常订单 ID |

> 处理入口是**后端下发的真实路由**，前端**直接跳转、不自己拼**。
> 「看到了但处理不了」是本版最典型的假绿。

### FR-Trend · 运营趋势

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我想按今日 / 近 7 天 / 近 30 天 / 自定义看趋势，好区分偶发与持续 |
| 交付 | `GET /api/admin/operations/trend` + 驾驶舱趋势区 |
| 关键约束 | 六个维度：订单 / 陪诊员活跃 / 履约率 / 投诉 / 评价 / 用药任务；区间：今日 / 近 7 天 / 近 30 天 / 自定义；**无数据的桶补 0**，`categories` 与每条 `series.data` 长度严格一致 |
| 边界与例外 | 非法 `dimension` / `range` 返回 `400`，**不静默降级**；自定义区间超 366 天返回 `9002` |
| 验收 | 六条维度均可渲染；无数据的桶补 0 且与分类轴长度一致；自定义区间生效 |

### FR-Health · 平台健康度

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我希望看到平台的健康构成，而不是一个我解释不了的分数 |
| 交付 | `GET /api/admin/operations/health` + 驾驶舱健康度区 |
| 关键约束 | **六个并列指标**：履约率、接单速度、完成率（按时）、投诉率、平均评分、活跃陪诊员数；**不合成总分**；六个指标各自有明确公式并登记在指标字典 |
| 边界与例外 | 概览与健康度里存在**同名不同型**的字段（接单时间在概览是整数、在健康度是字符串），前端按各自契约处理，不写通用取值函数 |
| 验收 | 六个指标齐全；页面**不出现**「健康指数 / 综合评分 / 总分」字样；每项各自有公式 |

### 驾驶舱页面结构

| 区块 | 内容 | 口径约束 |
|---|---|---|
| 概览 | 八项运营指标 | 区间口径 + 今日事实分开呈现 |
| 异常中心 | 四张异常卡片 + 「去处理」 | 入口是后端下发的真实路由 |
| 趋势 | 维度切换（六个）+ 区间切换（今日 / 近 7 天 / 近 30 天 / 自定义） | 无数据补 0，长度一致 |
| 健康度 | 六个并列指标卡 | **不合成总分** |

三态齐全：**加载中 / 空数据（显示 0 或空图，而不是报错）/ 加载失败（可重试）**。

## 五、明确的口径决定

### 5.1 开工复核与实现期的偏差

| # | 偏差 | 决定 | 理由 |
|---|---|---|---|
| D-3.5-1 | 迭代计划 §42 的概览与 §45 的健康度都同时列了「履约率」与「完成率」 | 两者**口径明确分开**并各自登记：履约率 = 订单最终履约的比例；完成率（按时）= 已完成订单里「未超出履约时长窗口」的比例 | 若都按「完成 ÷（完成 + 取消）」算，就是同一个数字挂了两个名字 —— 决策 6.2 的另一种形态 |
| D-3.5-2 | 预写 spec 未约束异常卡片的处理入口 | 四类异常的处理入口只用**已存在**的前端路由，并**逐个写进工单**、E2E **逐个点开**验证 | 决策 5.4：不允许「看到了但处理不了」。「链接指向 404」是本版最典型的假绿 |

### 5.2 roadmap 决策（V3.5）

| # | 决定 | 依据 |
|---|---|---|
| 5.1 | 异常中心**聚合 V3.1 风险中心**，不另建一套风险判定 | 用户拍板；roadmap §4.5 |
| 5.2 | 平台健康度**由客观指标构成**（履约率 / 接单速度 / 完成率 / 投诉率 / 平均评分 / 活跃陪诊员数）；**禁止**无法解释的合成分 | 用户拍板；roadmap §4.5 |
| 5.3 | 趋势时间范围支持今日 / 近 7 天 / 近 30 天 / 自定义 | 用户拍板；roadmap §4.5 |
| 5.4 | 异常卡片到处理页面必须**可达**，不允许「看到了但处理不了」 | 用户拍板；roadmap §4.5 |

### 5.3 其它口径约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | 异常中心的订单风险两类数量**必须等于** V3.1 风险中心对应字段 | 决策 5.1；由 parity 测试锁死 |
| 2 | 用药漏服三桶**必须**用唯一真源判定，与服药日历同源 | [ADR-0014](../adr/0014-medication-bucket-single-source.md) |
| 3 | 履约时长窗口是**配置项**（默认 240 分钟），不是硬编码 | 与 V3.1 阈值纪律一致 |
| 4 | 投诉率判定有**最小接单量门槛**，样本太小不判定 | 样本过小的时候，比率没有意义 |
| 5 | 趋势分桶**无数据补 0**，`categories` 与 `series.data` 长度严格一致 | 长度不齐的折线图会静默跳段，是最难查的一类假绿 |
| 6 | 零新增错误码，全部复用 | AGENTS.md §2.7 段位纪律 |

### 7.2 后续版本的承接点

| 承接方 | 要接住什么 |
|---|---|
| V3.6 数据闭环 | 本版 15 条管理端指标是效果对比端点的**候选指标池**——V3.6 用「同一个计算器算两遍」保证两期同口径；本版的履约率 / 完成率与 V3.3 陪诊员端的完成率**共用同一实现** |
| V3.6 供给缺口分析 | 本版异常中心只回答「有几单卡住」，V3.6 进一步回答「**哪个时段**没人接单」，两者的候选过滤条件必须一致 |

### 7.3 已知限制（如实披露，不静默）

| 项 | 说明 |
|---|---|
| 异常中心只做**发现与跳转** | 不做自动决策（决策 5.2 / 5.4）；处置动作在目标页由管理员执行 |
| 概览与健康度存在同名不同型字段 | 接单时间在概览是整数、在健康度是字符串；前端按各自契约处理 |
| 投诉率有最小接单量门槛 | 样本过小不判定，避免用噪声比例做运营决策 |
| 驾驶舱**不做实时秒级刷新** | 统计按区间查询与轮询刷新；运营看的是区间趋势，不是秒级监控 |

### 7.4 本版沉淀的机制

| 机制 | 解决什么问题 |
|---|---|
| 异常中心与风险中心的 **parity 测试** | 「两套判定必然漂移」—— 同源关系由测试锁死，而不是靠约定 |
| 异常卡片入口的 **E2E 逐个点开** | 「看到了但处理不了」是最典型的假绿 |
| 人读面 ↔ 机器面的**一致性校验脚本** | 指标字典的漂移由机械校验拦下 |
