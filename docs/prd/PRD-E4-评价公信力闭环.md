## 二、背景与目标

### 2.1 背景

M7 交付的评价体系是**单向**的：家属评陪诊员（1–5 星 + 标签 + 文字），陪诊员只能被动接受。三条代码事实说明系统**设计时预留了闭环概念，但从未接通**：

| # | 事实 | 证据位置 |
|---|---|---|
| F1 | `order_review.companion_reply` / `reply_time` 字段已建，`ReviewVO.companionReply` 已透出，接口文档 §ReviewVO 已声明该字段——但**全库无任何写入口** | `docs/db/01-ER图.md` §3.5 · `ReviewVO.java:77` · `docs/api/06-review-complaint.md` §一 |
| F2 | `order_review.is_valid` 字段已建，且**读路径已全部消费**：公开列表过滤 `is_valid=1`（`ReviewServiceImpl:193`，注释明确写「被管理员判定无效的评价不出现在公开列表里」）、平均分与分布 SQL 均带 `is_valid=1`（`ReviewReadMapper:49,61`）、统计排行同口径（`StatisticsMapper:193,195`）——但**没有任何写路径能把 `is_valid` 置 0**，这条口径今天是「死代码」 | 同左 |
| F3 | 陪诊员对失实差评的唯一救济路径是普通投诉（`ComplaintType` 6 个枚举值均面向服务方违约），申诉与普通投诉在管理端无法区分，管理员也没有「裁定评价有效性」的处置手段 | `ComplaintType.java` · `AdminController#handleComplaint` |

**一句话归因**：评价公信力的「读侧」（不展示无效评价、聚合剔除无效评价）已经按终态设计完毕，**缺的是写侧的三个入口**——回复、申诉、裁定。

### 2.2 要解决的问题

| 编号 | 问题 | 对谁 | 现状代价 |
|---|---|---|---|
| P1 | 陪诊员收到失实差评无法自证 | 陪诊员 | 评分直接影响接单（`companion_profile.score` 参与排行），失实评价造成真实收入损失 |
| P2 | 家属只能看到单方陈述 | 家属 | 选陪诊员时信息不完整，评价公信力打折 |
| P3 | 管理员遇到「评价不实」类投诉无处下手 | 管理员 | 只能口头调解，评价本身无法处置，`is_valid` 机制闲置 |

### 2.3 成功指标与口径

| 指标 | 目标值 | 口径 | 验证手段 |
|---|---|---|---|
| 裁定后评分一致性 | 裁定生效后，`GET /api/review/companion/{id}/score` 与页面分数 **立即一致** | 裁定由 Review module 内部完成评分快照刷新与 Redis 缓存删除（TTL 10 分钟仅兜底） | e2e：裁定 → 立即查 score，断言与手工 SQL `AVG(score) WHERE is_valid=1` 一致 |
| 无效评价剔除率 | 100% | `is_valid=0` 的评价不出现在陪诊员公开评价列表、不计入平均分 / 星级分布 / 好评率 / 排行榜 | 既有 3 处 SQL 口径已实现，新增用例断言 |
| 回复内容安全 | 敏感词命中 100% 拒绝 | 复用 `SensitiveWordUtil.firstHit`，返回 `6003` | 单测 + e2e |
| 越权拦截 | 陪诊员 A 回复陪诊员 B 的评价 → `3004`；家属/老人调回复接口 → `403` | Service 层归属校验：`review.companionId == 当前用户` | 越权矩阵追加（见 §十一） |
| 申诉防滥用 | 同一评价同时**最多 1 个未结案申诉**；申诉时限 15 日 | 复用投诉「同订单未结案唯一」约束（`ComplaintServiceImpl:111-116`）+ 新增评价级约束 | 单测 |

> 指标均为**演示可量化**口径（对齐 PRD §9.1 风格），非商业 KPI。

## 三、名词与术语定义

| 术语 | 定义 |
|---|---|
| **回复（Reply）** | 陪诊员对自己收到的某条评价的一次性文字回应，落 `order_review.companion_reply` / `reply_time` |
| **申诉（Appeal）** | 陪诊员认为评价失实时，通过**既有投诉通道**发起的、类型为 `REVIEW_APPEAL` 的投诉，目标为评价人（家属） |
| **有效性裁定（Validity Ruling）** | 管理员对评价作出的「有效 / 无效」判定，落 `order_review.is_valid`（1 → 0 仅此一个方向），并写 `admin_oper_log` |
| **无效评价** | `is_valid = 0` 的评价。**不物理删除**：评价人自己仍可在订单详情看到，并带「平台已裁定为无效评价」标注；公开列表与全部聚合口径中不出现 |
| **有效评价** | `is_valid = 1` 的评价，即当前所有存量评价（`create()` 默认置 1，`ReviewServiceImpl:143`） |
| **一评一回复** | 同一评价有且仅有一条回复，提交后**不可修改、不可删除** |

### 4.1 包含（In-scope）

| # | 内容 | 类型 |

| 3 | 管理员有效性裁定（新端点 `POST /api/admin/review/{id}/validity`） | 功能 |
| 4 | 裁定后评分实时重算（由 Review module 内部同步评分） | 功能 |
| 5 | 回复与裁定的站内信通知（`MessageType` 新增 3 个模板） | 功能 |

| 7 | 前端入口：陪诊员「收到的评价」页（含回复表单）、家属订单详情展示回复与裁定标注、admin 投诉管理页的裁定操作 | 功能 |
| 8 | 越权矩阵与 e2e 用例追加 | 质量 |

### 4.2 不包含（Out-of-scope）

| # | 内容 | 不做的理由 |
|---|---|---|
| 1 | 评价的物理删除或内容改写 | 裁定只影响展示与聚合，内容永远留痕；「删差评」会摧毁评价体系公信力 |
| 2 | 家属对回复的再回复（多轮往来） | 一轮回复 + 一次申诉 + 一次裁定已构成完整闭环；多轮往来属 IM 范畴，踩红线-3 |
| 3 | 回复的编辑与删除 | 一评一回复、落库即定稿，可测且免纠纷；编辑历史会引入「改口」争议 |
| 4 | 评分修改 | 评分一旦提交不可改（既有一单一评约束），申诉的唯一救济是裁定无效 |
| 5 | 系统自动判定（关键词/模型识别失实评价） | 红线-1 边界：自动判定「失实」本质是对主观陈述的裁判，必须人（管理员）来做 |
| 6 | 被投诉家属的对称申诉权（家属申诉陪诊员回复） | 回复不是评分，不参与聚合，不影响接单；如需后续支持，记入后续版本池（§十四） |
| 7 | 评价端 IM 化的任何形态 | 红线-3 |

## 五、方案对比与选型说明

### 5.1 决策点 1：申诉走「复用投诉通道」还是「新建申诉工单」

| 维度 | 方案 A：复用投诉（`ComplaintType` + `REVIEW_APPEAL`）✅ 推荐 | 方案 B：新建 `review_appeal` 表 |
|---|---|---|
| 实现成本 | **低**：加 1 个枚举值；创建/列表/详情/管理端处置全链路零改动 | 高：新表 + 新 Controller/Service + 新状态机 |
| 开发复杂度 | 低：与投诉同构（双方由订单关系自动推导） | 高：需复制一套「待处理→处理中→已结案」流转 |
| 用户体验 | 中：申诉与投诉在同一入口同一列表，学习成本低 | 好：可做申诉专属视图（但收益边际） |
| 风险 | 中：管理端需按 type 区分处置动作（本 PRD 已覆盖） | 低：隔离干净 |
| 测试复用 | **高**：投诉既有越权矩阵、敏感词、状态机用例大量复用 | 低：全部新建 |

**推荐 A 的核心理由**：申诉与投诉在数据模型上**同构**——`complaint` 表的 `type` / `complainant_id` / `target_user_id` / `evidence` / 三状态流转 / `handle_result` / `penalty_to_target` 字段对申诉场景**全部够用且语义吻合**（投诉人=陪诊员、被投诉人=家属，由订单关系自动推导的逻辑 `ComplaintServiceImpl:90-104` 已天然覆盖「陪诊员 → 家属」方向）。新建表只会引入第二套状态机与第二份越权矩阵。

### 5.2 决策点 2：回复是否可编辑

| 维度 | 一次性回复 ✅ 推荐 | 可编辑（限 1 次） |
|---|---|---|
| 实现成本 | 零额外字段 | 需记录编辑次数 / 编辑历史 |
| 可测性 | 一条断言（已回复 → `6006`） | 状态组合翻倍 |
| 公信力 | 高：落库即定稿，双方看到同一份陈述 | 低：「改口」会让截图取证失去意义 |

**推荐一次性**。陪诊员对措辞不满意时，救济路径是申诉（由管理员裁定），而不是反复编辑。

### 5.3 决策点 3：裁定入口放评价模块还是投诉模块

推荐放 **`/api/admin/review/{id}/validity`（评价模块）** 而非挂在 `complaint/{id}/handle` 上：

1. 裁定的**操作对象是评价**（写 `order_review.is_valid`），投诉只是触发线索；把写评价的接口放进投诉处理器，会让「改了哪张表」变得难审计。
2. 现实中管理员可能在**没有申诉**的情况下主动裁定（巡查发现明显失实/恶意评价），裁定入口必须独立于申诉存在。
3. `handleComplaint` 的既有语义（推进投诉状态机 + 双方通知）不被污染，回归面最小。

**演进路径**：本期裁定与投诉处置是两次独立操作（管理员先裁定评价、再结案投诉）；若实际使用中发现两步操作繁琐，后续版本可在 `handleComplaint` 内提供「结案并同步裁定」的组合快捷项——**触发条件**：管理端实际使用 ≥ 2 周且两步操作被反馈为高频负担。

## 六、用户角色与使用场景

### 6.1 角色与能力变化

| 角色 | 现有能力 | 新增能力 | 不变（红线） |
|---|---|---|---|
| 陪诊员 COMPANION | 被评价、看自己评价列表与评分 | **回复评价**（一评一回复）、**发起申诉** | 不能自评、不能改分、不能删评价 |
| 家属 FAMILY | 评价订单、看陪诊员公开评价 | 看到**回复内容**、看到**裁定标注**、收到回复/裁定通知 | 不能回复（一轮闭环）、不能申诉自己的评价被裁定（可向管理员电话申诉，走线下） |
| 管理员 ADMIN | 处置投诉（三状态） | **裁定评价有效性**、申诉类投诉的处置 | 不能删评价、不能改评分内容 |
| 老人 ELDER | 只读 | 只读（回复/申诉均为写操作，`ElderReadOnlyInterceptor` 自动拦截 403，无需额外开发） | 一切写操作 403 |

### 6.2 核心场景（三个）

**场景 1 · 陪诊员回复差评**（主场景）

> 陪诊员小李完成一单后收到 2 星评价，标签「迟到」，文字称「迟到了半小时」。实际上订单时间线（`order_status_log` + `order_checkin`）显示其 08:20 已到院打卡。小李打开「收到的评价」页，在该评价下提交回复：「当日 08:20 已到院打卡（可查证），迟到或因老人下楼较慢，全程服务节点均按时完成。」回复对所有人可见，家属收到站内信。

**场景 2 · 失实评价申诉 + 裁定**（关键场景）

> 家属因老人转述误会产生差评。小李回复后仍认为评分不公，点击「申诉该评价」，系统自动创建一条 `REVIEW_APPEAL` 类型投诉（被投诉人=该家属），附上打卡记录截图为证据。管理员在投诉管理页看到申诉，点开关联评价与订单时间线核对，裁定「评价无效」：`is_valid` 置 0、写 `admin_oper_log`、双方收站内信、小李的评分**立即重算**。该评价从公开列表消失，但家属在订单详情仍能看到，且带「平台已裁定为无效评价」标注。

**场景 3 · 管理员巡查主动裁定**（无申诉路径）

> 管理员日常巡查陪诊员评价列表，发现一条「根本没来人」的 1 星评价，但该订单有完整 6 节打卡记录与照片。无需等待申诉，管理员直接在 admin 端评价管理中裁定无效。

### 6.3 用户故事与验收标准

**US-01 回复评价**

```
作为【陪诊员】，我想要【对我收到的评价做出一次性公开回应】，
以便【向后续下单的家属补充服务过程的事实依据】。

验收标准：
- Given 我是被评价的陪诊员，When 我对未回复过的评价提交 5-200 字回复，
  Then 回复成功，reply_time 落库，家属收到站内信，公开列表可见回复。
- Given 该评价已有回复，When 我再次提交回复，Then 返回 6006，数据库无变更。
- Given 我是陪诊员 A，When 我回复陪诊员 B 收到的评价，Then 返回 3004。
- Given 我的回复包含敏感词，When 提交，Then 返回 6003，数据库无变更。
- Given 我是 ELDER / FAMILY，When 调用回复接口，Then 返回 403。
```

**US-02 发起评价申诉**

```
作为【陪诊员】，我想要【对失实评价向平台申诉】，
以便【通过管理员裁定恢复我的公正评分】。

验收标准：
- Given 订单已评价且评价后 ≤ 15 日，When 我以 REVIEW_APPEAL 类型发起申诉，
  Then 创建一条投诉（我=投诉人，评价家属=被投诉人），管理员收到站内信。
- Given 同一评价已有未结案申诉，When 再次发起，Then 返回 409。
- Given 距评价提交已超 15 日，When 发起申诉，Then 返回 409 并提示时限。
- Given 评价内容或订单与申诉人不匹配（非本人收到的评价），
  When 发起申诉，Then 返回 3004。
```

**US-03 裁定评价有效性**

```
作为【管理员】，我想要【将失实评价裁定为无效】，
以便【保护陪诊员评分的公正性，同时不删除任何记录】。

验收标准：
- Given 一条 is_valid=1 的评价，When 我裁定为无效并填写理由（≥ 10 字），
  Then is_valid 置 0，admin_oper_log 留痕，双方收站内信，
  陪诊员平均分/分布/好评率立即按 is_valid=1 口径重算。
- Given 该评价已被裁定过，When 再次裁定，Then 返回 409，数据库无变更。
- Given 陪诊员平均分在裁定前为 4.50（含该 1 星差评），
  When 裁定无效后，Then score 接口返回的重算值与手工 SQL
  AVG(score) WHERE is_valid=1 AND companion_id=? 完全一致。
- Given 我是 FAMILY / COMPANION / ELDER，When 调用裁定接口，
  Then 返回 403（/api/admin/** 过滤链预检，早于参数解析）。
```

**US-04 家属查看回复与裁定标注**

```
作为【家属】，我想要【看到陪诊员对我评价的回复与平台的裁定结论】，
以便【完整了解双方陈述，判断是否需要修正我的评价习惯】。

验收标准：
- Given 我评价过的订单，When 打开订单详情，Then 评价卡片下方展示
  陪诊员回复（含回复时间），无回复时不展示该区块。
- Given 我的一条评价被裁定无效，When 打开订单详情，Then 该评价
  带灰色「平台已裁定为无效评价」标注；When 查看该陪诊员公开评价列表，
  Then 这条评价不出现。
```

## 七、功能需求

> 状态词统一：**必须**（shall）/ **应该**（should）/ **可以**（may）/ **禁止**（must not）。
> 全部 FR 的工程落点对齐项目「5 件套」交付规范（实现 / 单测 / 越权矩阵 / e2e / docs 同步）。

### FR-01 陪诊员回复评价

**接口**：`POST /api/review/{id}/reply`　权限：`COMPANION`（`@PreAuthorize` 收口）

**请求体**：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `content` | String | ✓ | 5–200 字符（与评价文字同一下限口径） | 回复内容 |

**业务规则**：

1. 评价必须存在，否则返回新错误码 **`6005 评价不存在`**（现状无此码：`6004` 是投诉不存在，评价侧缺口）。
2. 归属校验在 Service 层：`review.companionId == 当前用户`，不匹配返回 `3004`（与订单相关方口径一致的家族错误码）。
3. 一评一回复：`companion_reply` 已非空时返回新错误码 **`6006 该评价已回复，不能重复回复`**；提交后回复**不可修改、不可删除**。
4. 内容必须过 `SensitiveWordUtil.firstHit`，命中返回 `6003`（复用既有错误码与词表）。
5. 回复**不改变**订单状态、**不触发**评分重算（回复不参与聚合）。
6. 回复落库后必须向评价家属发送站内信（见 FR-05），消息携带订单号与评价摘要。
7. ELDER / FAMILY 调用本接口必须 403：FAMILY 由 `@PreAuthorize` 拦，ELDER 由 `ElderReadOnlyInterceptor` 拦（**必须带合法 payload 断言 403**，遵守 `docs/api/README.md` §2.5 时序约定）。

**验收标准**：见 US-01。

### FR-02 评价申诉通道（复用投诉）

**接口**：复用 `POST /api/complaint`（**不新增端点**），`ComplaintType` 枚举新增值：

| 传值 | 中文 | 触发约束 |
|---|---|---|
| `REVIEW_APPEAL` | 评价申诉 | 见下 |

**请求体变更**（`ComplaintCreateDTO` 新增 1 个可选字段）：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `reviewId` | Long | 仅 `type=REVIEW_APPEAL` 时必填 | 必须为申诉人本人收到的评价 | 关联评价 ID |

**业务规则**：

1. 申诉人与被投诉人由订单关系自动推导（既有逻辑 `ComplaintServiceImpl:90-104` 天然支持「陪诊员 → 家属」方向，**不新增推导代码**）；`reviewId` 对应评价的 `orderId` 必须与 `dto.orderId` 一致且评价的 `companionId` 必须为申诉人，否则 `3004`。
2. **时限**：评价 `create_time` 距今 ≤ **15 日**方可申诉，超时返回 `409` 并提示「评价申诉须在评价提交后 15 日内发起」。时限值落 `application.yml`（`nianglin.review.appeal-deadline-days: 15`），与项目阈值管理惯例一致。
3. **唯一性（两层）**：
   - 继承既有约束：同一订单存在未结案投诉时 `409`（`ComplaintServiceImpl:111-116`，零改动）；
   - 新增评价级约束：同一 `reviewId` 存在未结案（PENDING/PROCESSING）的 `REVIEW_APPEAL` 投诉时返回 `409`。
4. 证据材料走既有 `evidence` 字段（≤ 6 个，`FileBizType.COMPLAINT` 白名单**已存在，无需扩充**）；内容过敏感词（`6003` 复用）。
5. 申诉创建后必须通知全部管理员（复用既有 `notifyAdmins`）与被申诉家属（复用 `notifyTarget`），通知文案区分「这是一条评价申诉」。
6. 申诉**不改变**订单状态（订单早已 REVIEWED 终态），**不冻结**评价展示（裁定前评价照常展示与聚合）。

**验收标准**：见 US-02。

### FR-03 管理员有效性裁定

**接口**：`POST /api/admin/review/{id}/validity`　权限：`ADMIN`（`/api/admin/**` 过滤链预检）

**请求体**：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `isValid` | Boolean | ✓ | 仅接受 `false`（见规则 2） | 裁定结论 |
| `reason` | String | ✓ | 10–200 字符 | 裁定理由（对双方可见） |

**业务规则**：

1. 评价必须存在，否则 `6005`。
2. **单向裁定**：本接口只做「有效 → 无效」。理由：恢复有效性意味着撤销一次已通知双方的裁定，其公信力代价远大于收益；若确属误裁，处置路径是管理员线下沟通 + 记录在案（本期不做「恢复有效」入口，记入 §十四遗留）。
3. 已裁定（`is_valid=0`）的评价再次裁定返回 `409`（与投诉「状态只能正向流转」同风格）。
4. 裁定必须在一个事务内完成四件事：① `order_review.is_valid` 置 0；② Review module 内部完成评分快照刷新与 Redis 删除；③ 通过共享审计 module 写 `admin_oper_log`（操作类型 `REVIEW_RULING`，目标=评价，记录理由）；④ 向评价家属与陪诊员各发一条站内信。
5. 裁定**禁止**修改 `score` / `content` / `tags` / `companion_reply` 中任何内容——裁定只动 `is_valid` 一个字段。
6. 裁定**不要求**存在关联申诉（场景 3：巡查主动裁定）。

**验收标准**：见 US-03。

## 九、业务流程与状态流转

### 9.1 评价生命周期（新增两态语义，不新增状态字段）

```
                    ┌──────────────┐
                    │ is_valid = 1 │ 有效评价（create 默认）
                    └──────┬───────┘
              家属提交评价   │ 陪诊员一次性回复（companion_reply 填充，可发生在任意时点★）
                           ▼
        ┌────────────────────────────────────────────┐
        │            申诉窗口（≤ 15 日）              │
        │  陪诊员发起 REVIEW_APPEAL 投诉（可 0~1 条未结案）│
        └───────────────────┬────────────────────────┘
                            │ 管理员裁定（须填理由 ≥10 字）
                            ▼
                    ┌──────────────┐
                    │ is_valid = 0 │ 无效评价（终态，单向不可逆）
                    └──────────────┘
                     公开列表隐藏 / 聚合剔除 / 相关方可见+标注
```

★ 回复与申诉无先后依赖：可只回复不申诉，可只申诉不回复，也可两者都做。

**状态机口径**：`order_review` 本身**不引入新状态列**；`is_valid` 是唯一的状态性字段，且只有 `1 → 0` 单向迁移。回复（`companion_reply` 空与非空）是独立于裁定的正交维度。

### 9.2 申诉投诉状态机（完全复用，零改动）

```
PENDING → PROCESSING → RESOLVED / REJECTED     （ComplaintStatus 既有流转，禁止回退跳级）
```

申诉类投诉与普通投诉在状态机上**无差别**；差别仅在：处置时管理员可（非必须）联动调用 FR-03 裁定接口。

### 9.3 端到端时序（场景 2 完整链路）

```
陪诊员                系统                     家属                管理员
  │ 提交回复 ──────────►│ companion_reply 落库       │                    │
  │                    │ ── REVIEW_REPLIED 站内信 ──►│                    │
  │ 发起申诉(≤15日) ───►│ complaint(REVIEW_APPEAL)   │                    │
  │                    │ ── 申诉通知 ────────────────►│ ── 新投诉待处理 ──►│
  │                    │                            │                    │ 核对时间线/打卡
  │                    │                            │                    │ 裁定无效(事务:
  │                    │                            │                    │  is_valid=0
  │                    │◄─── REVIEW_INVALIDATED ────│◄── REVIEW_INVALIDATED
  │                    │    + score 立即重算         │                    │ admin_oper_log
  │                    │    + 公开列表即时隐藏        │                    │ (再单独结案投诉)
```

### 11.1 权限矩阵（新增部分）

| `POST /api/complaint`（type=REVIEW_APPEAL） | 403（拦截器） | 403（推导失败） | **✅ 须为该评价的陪诊员** | 403（推导失败） | 评价↔订单↔申诉人三方一致 |
| `POST /api/admin/review/{id}/validity` | 403（过滤链） | 403（过滤链） | 403（过滤链） | **✅** | 无需归属（ADMIN 全局权） |
| `GET /api/review/companion/{id}`（既有） | 可 | 可 | 可 | 可 | 无（公开口碑数据，不变） |

### 11.2 越权矩阵追加（对齐项目 4 角色 × 接口惯例）

| 用例组 | 覆盖 | 断言要点 |
|---|---|---|
| 回复越权 | 8 条 | 陪诊员 A→B 评价 `3004`；FAMILY/ELDER/ADMIN 调用 403；**FAMILY/ELDER 用例必须携带合法 payload**（`docs/api/README.md` §2.5 时序陷阱：缺 payload 会死在参数解析，拿不到 403 造成假红） |
| 申诉越权 | 6 条 | 非该评价陪诊员发起 `3004`；评价与订单不一致 `3004`；超时 `409`；重复申诉 `409`；ELDER 403 |

- 裁定理由对双方可见，**禁止**包含管理员主观贬损表述（产品侧以提示文案约束 + 评审抽检，不做技术强制）。
