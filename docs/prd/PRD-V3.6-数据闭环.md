## 二、背景与目标

### 2.1 要解决的产品问题

**平台要回答「这次干预让下一次服务变好了吗」，而今天连「哪个时段没人接单」都还答不出来。**

| 角色 | 他的处境 |
|---|---|
| 平台 | 订单无人接，只能事后才知道。**哪个时段供给不足**这件事没有数据 —— 现有统计全是「按天」的，看不出「周日下午三点没人」 |
| 管理员 | 调整了排班、改了运营策略，但**没有办法验证有没有用** —— 缺少一个「改前 vs 改后」的可比视图 |
| 开发者 | 「同一指标在不同角色端只能有一个口径」这条约束**靠文档维持**。文档不会在改动时报警，四个人并行开发、每版新增 10–20 条指标的情况下，漂移是迟早的事 |

这不是「再加两个报表」的问题，是**闭环缺最后一环**的问题。

迭代计划 §46 描述的链条是：

```
用户行为 → 业务数据 → 统计分析 → 异常发现 → 运营干预 → 业务结果 → 再次统计
```

V3.2 – V3.5 把「统计分析」和「异常发现」两段做实了，
但**「再次统计」这一段缺一个能回答问题的工具**，闭环就断在这里。

而工具能不能可信，取决于口径能不能自证。所以 V3.6 做两件事：

1. **把口径登记从「人读的表」升级成「机器校验的面」**——
   「哪个端点返回了哪些指标」变成机器可查、可校验的事实；
2. **给闭环两个新能力**：供给时段缺口分析（回答「哪个时段没人接单」）、
   干预效果对比（回答「这次干预有没有用」）。

### 2.2 目标

1. 每个统计端点返回的指标，都能在**机器面**上查到它登记在哪个端点；
2. 同一个指标**物理上只有一份计算实现**，跨角色端共用，不存在「两份实现漂移」的可能；
3. 管理员能看到 7×24 的**供给时段缺口**，定位「周几几点缺人」；
4. 管理员能对任一已登记指标做**前后两期对比**，看到差值；
5. 缺口分析与效果对比的每个数字都来自**同一口径**，能解释、能复算。

### 2.3 目标对应的用户故事（roadmap §3.6）

| # | 用户故事 | 落在哪 |
|---|---|---|
| 56 | 每个核心指标都有统一的名称 / 范围 / 时间 / 来源 / 公式 | FR-Contract + FR-Calculator |
| 57 | 能从订单无人接发现供给时段不足 | FR-Gap |
| 58 | 能对比干预前后的履约率 | FR-Effect |
| 59 | 指标口径变更有记录，历史数据仍可解释 | 决策 6.1 + 字典变更记录（改公式 + 升口径版本 + 留一行，**不改写历史数据**） |
| 60 | 统计全部由后端聚合，前端不拉全量数据自行计算 | 全部 FR |

### 2.4 非目标（本版明确不做）

| 不做 | 原因 |
|---|---|
| 不可解释的指标 | 决策 6.1：每个核心统计指标必须明确「名称 / 范围 / 时间 / 来源 / 公式」；说不清来源与公式的数一律不做 |
| 与前五版并行的第二套口径 | 决策 6.3：指标体系是 V3.2 – V3.5 各端口径的**收敛**，不新增平行口径 |
| 历史数据的重算 / 改写 | 口径变更 = 改公式 + 升口径版本 + 在变更记录里留一行；**不改写历史数据** |
| 自动调参 / 自动改排班 | 本版只提供**发现与对比**；运营动作仍由管理员执行 |
| 为「还没有业务事实」的指标硬造条目 | 例如「陪诊员满意度」没有数据源 —— 不造 |
| 新增页面 / 新增导航入口 | 缺口表与效果对比落在**已有的驾驶舱页内**，不新开页面（导航越来越长是 V3.x 明令禁止的） |
| 医疗 / 健康类指标 | 合规红线-1：不做诊断、不做风险预测 |
| 在线支付 / 地图导航 | 合规红线-3：一期线上记账 + 线下结算，文字地址 + 签到坐标 |

## 三、文案口径（合规与情绪负担）

### 3.1 供给缺口的数据质量必须如实披露

`companionsWithoutSlots` 是本版最需要克制的一处文案。

它的含义是：**有多少陪诊员没有可解析的可服务时段，因而不参与供给统计**。

| 必须 | 禁止 |
|---|---|
| 如实披露这个数，让管理员知道供给数偏低是「真的没人」还是「没人登记时段」 | 把这些 0 混进分母却不说明 |
| 表述为「未登记可服务时段」这类**中性事实** | 表述成「这些陪诊员不专业」「资料不全」 |

把 0 混进分母却不说明，就是**用一个不存在的结论去调运营策略**。

### 3.2 缺口可以为负

供给多于待接量时 `gap < 0`，**不截断成 0**——富余就是富余。
界面照实显示负值，不改写成「0」。

### 3.3 差值格式不可比时给「—」

两期取值格式不同（如百分比 vs 计数）时，`delta` 返回 `"—"`，
**不硬凑一个数字**。指标名从指标字典取，不另写一份名表。

### 3.4 不做医疗判断

缺口与效果对比是**履约与供给**的分析，不是健康分析。
任何文案不得出现「病情」「危险」「耽误治疗」等表述（合规红线-1）。

### 3.5 指标口径必须先登记（本版把登记变成机器校验）

```
指标字典（机器面） ── 指标名 / 范围 / 时间 / 来源 / 公式
端点机器面       ── 哪个端点返回了哪些指标
两条面之间做双向核对：少一边就变红
```

本版起「口径登记」不再依赖「写 VO 时顺手记得登记」：
**端点↔指标机器面** + **指标计算器注册表**把决策 6.2 从文档约束变成结构约束。

### 3.6 机器面的三条双向校验

| # | 校验 | 挡住什么 |
|---|---|---|
| ① | 机器面里声明的端点**必须真实存在**（按控制器映射方法反射扫描） | 「文档里写了一个接口，代码里没有」 |
| ② | 机器面里声明的指标**必须在指标字典里** | 「端点返回了口径没人登记过的数字」 |
| ③ | 指标字典里每条指标声明的端点**必须在机器面里出现** | 「指标登记了，但没人知道它属于哪个端点」 |

> 这三条是本版的**核心产出**：它把「口径登记」从「靠人记得写」变成「机器逼你写」。
> 指标字典的「人读面」与「机器面」是否逐条一致，另由脚本机械校验。

## 四、功能需求

### FR-Contract · 端点 ↔ 指标机器面

| 项 | 内容 |
|---|---|
| 用户故事 | 作为开发者，我希望「这个端点返回了哪些指标」是机器可查的事实，而不是散落在各人的脑子里 |
| 交付 | 端点↔指标机器面文件 + 三条双向校验 |
| 关键约束 | ① 声明的端点**必须真实存在**（按控制器映射方法反射扫描）；② 声明的指标**必须在指标字典里**；③ 字典里每条指标声明的端点**必须在机器面里出现** |
| 边界与例外 | 这一组校验是本版**核心产出**：它把「口径登记」从「靠人记得写」变成「机器逼你写」。任一侧缺登记即变红 |
| 验收 | 删掉机器面里的一行即变红；声明了不存在的端点即变红；声明了字典里没有的指标即变红 |

### FR-Calculator · 指标计算器注册表

| 项 | 内容 |
|---|---|
| 用户故事 | 作为开发者，我希望一个指标在系统里只有一份实现，这样它就不可能在两个端点漂移 |
| 交付 | 指标计算器接口 + 注册表；注册表里**同一个 key 只能有一个实现** |
| 关键约束 | 跨端共用的指标登记为**别名**，指向同一个计算器对象，而不是各写一份公式；重复 key **启动失败**，绝不「后注册覆盖先注册」；注册表里的 key 必须是字典里登记过的 |
| 边界与例外 | 未注册的指标 key 在效果对比端点返回 `400`（**不许「猜一个算法算出来」**） |
| 验收 | 同一个 key 注册两个实现 → **启动失败**；别名与主 key 指向同一计算器对象；未注册 key 被拒 |

### FR-Gap · 供给时段缺口分析

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我想知道「周几几点没人接单」，好去调整排班与运营策略 |
| 交付 | `GET /api/admin/operations/gap` + 驾驶舱页内的 7×24 缺口网格 |
| 关键约束 | 桶的粒度固定为「周内第几天 × 小时」（7×24 = 168 桶），**与查询区间长度无关**——只有这样「这一周和上一周的同一时段」才可比；供给数按**可服务时段**分桶，且只算**有资格接单**的陪诊员（资质已过审且处于可接单状态）；同一陪诊员在多时段各计 1 次，**每桶只计 1 次**（按人计，不按单计）；**空桶返回 0 而不是缺行** |
| 边界与例外 | 缺口**可为负**（供给多于待接量），不截断成 0；解析不出时段的陪诊员**不进任何桶**，由 `companionsWithoutSlots` 如实披露 |
| 验收 | 168 个桶齐全（周日 = 7、小时 0 与 23 都在内）；同一陪诊员在多时段**每桶只计 1 次**；空桶为 0 而不是缺行；任一桶的可服务陪诊员数不超过有资格接单的陪诊员总数 |

#### 缺口桶的读法

| 字段 | 含义 | 怎么读 |
|---|---|---|
| `weekday` | 周内第几天（1 = 周一 … 7 = 周日） | 跨周对比时，桶的粒度与区间长度无关 |
| `hour` | 0–23 的整点 | 整点落在可服务时段内即算该小时可服务 |
| `pendingUnaccepted` | 该时段内下单但至今无人接的订单数（按就诊时间落桶） | 需要供给的量 |
| `availableCompanions` | 该时段**可服务**的陪诊员数（按其可服务时段分桶） | 能接单的量 |
| `gap` | 待接量 − 可服务人数 | **> 0 即为缺口**；< 0 表示供给富余 |

### FR-Effect · 干预效果对比

| 项 | 内容 |
|---|---|
| 用户故事 | 作为管理员，我想对比干预前后两期的同一指标，看运营动作到底有没有用 |
| 交付 | `GET /api/admin/operations/effect` + 驾驶舱页内的效果对比区 |
| 关键约束 | 两侧数值由**同一个计算器**算两遍得到，不写第二份公式；不传对比区间时自动取「与后一期**等长、紧邻其前**」的区间；指标中文名**从指标字典取**；`delta` 带正负号 |
| 边界与例外 | 未注册指标 → `400`；区间不合法 → `9002`；两值格式不同 → `delta` 返回 `"—"` |
| 验收 | 两侧数值由同一实现算出；缺省对比区间**等长且紧邻**；换指标会重新请求；空数据走空态 |

### 驾驶舱页内的两块新增

| 区块 | 形态 | 约束 |
|---|---|---|
| 供给时段缺口表 | 7×24 热力网格（周一 ~ 周日 × 0–23 时），颜色深浅表示缺口大小；悬停显示「待接 N 单 / 可服务 M 人 / 缺口 K」 | **空桶显示 0 而不是空白**；不新增路由 |
| 干预效果对比 | 选一个指标 + 两个区间 → 并排显示两期值与差值 | 指标只能选**已注册**的；差值格式不可比时显示 `—` |

### 端点清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/admin/operations/gap` | `ADMIN` | 供给时段缺口分析（7×24 桶） |
| GET | `/api/admin/operations/effect` | `ADMIN` | 干预效果对比（前后两期） |

## 五、明确的口径决定

### 5.1 开工复核与实现期的偏差

| # | 偏差 | 决定 | 理由 |
|---|---|---|---|
| D-3.6-1 | 预写 spec §2.1 写「`availableCompanions` = 该时段工作状态为 `AVAILABLE` 且资质通过的陪诊员数」 | 供给数改为**按该陪诊员的可服务时段分桶**——一个陪诊员只在「他确实能服务」的时段里算供给；另设 `companionsWithoutSlots` 计数，说明有多少陪诊员没有可解析的可服务时段、因而不参与供给统计 | 按字面理解，每个桶的供给数都是同一个值（当前可接单的总人数），那这个指标毫无信息量。而 `companionsWithoutSlots` 是**对数据质量的如实披露**，不是把 0 混进分母 |
| D-3.6-2 | 开工细化时只写了「按可服务时段分桶」，把「资质 + 工作状态」这层过滤漏掉了 | 供给取数**补上**「资质已过审且处于可接单状态」的过滤，并由真库测试加一条**反向用例**锁住：任一桶的可服务陪诊员数**不得超过**「有资格接单」的陪诊员总数 | 没通过审核的陪诊员、休息 / 离线的陪诊员**根本接不了单**，把他们算作供给，平台会以为「这个时段有人」——而那正是这个指标要回答的问题。这会让缺口被**系统性低估** |

### 5.2 roadmap 决策（V3.6）

| # | 决定 | 依据 |
|---|---|---|
| 6.1 | 每个核心统计指标必须明确：**指标名称 / 统计范围 / 统计时间 / 数据来源 / 计算公式** | 用户拍板；roadmap §4.6 |
| 6.2 | **禁止同一指标在不同角色端出现不同口径**（家属端一个 / 陪诊员端一个 / 管理员端另一个） | 用户拍板；roadmap §4.6 |
| 6.3 | 指标体系是 V3.2 – V3.5 各端口径的**收敛**，不新增平行口径 | 用户拍板；roadmap §4.6 |
| 6.4 | 闭环验证必须能回答「这次干预让下一次服务变好了吗」，否则不算闭环 | 用户拍板；roadmap §4.6 |

### 5.3 其它口径约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | 同一个 key 在计算器注册表里**只能有一个实现**，重复即**启动失败** | [ADR-0017](../adr/0017-metric-endpoint-machine-contract.md) |
| 2 | 效果对比两期**必须等长**（缺省时自动取等长且紧邻其前的区间） | 两期长度不等时比的是「一段 7 天 vs 一段 30 天」，那是量纲错误 |
| 3 | 改派率的分子（操作日志时间）与分母（下单时间）**时间字段不同源**，已在字典公式里写明 | 订单表里没有被改派过的痕迹 —— 藏着不说才是问题 |
| 4 | 用药漏服桶与服药日历**同源**判定 | [ADR-0014](../adr/0014-medication-bucket-single-source.md) |
| 5 | 口径变更 = 改公式 + 升口径版本 + 在变更记录留一行；**不改写历史数据** | V3.6 范围外条款 |
| 6 | 缺口分析的供给只算**有资格接单**的陪诊员（资质已过审且处于可接单状态） | 见偏差 D-3.6-2：把接不了单的人算成供给，会让缺口被系统性低估 |
| 7 | 效果对比只接受**已注册**的指标 key | 未注册的指标没有可复算的实现，猜一个算法出来的对比没有意义 |

## 六、验收标准

### 6.1 计划书验收项（迭代计划 §47 – §49）

- [x] 典型数据闭环成立：订单无人接 → 统计发现 14:00–16:00 供给不足 → 调整排班 → 下一周期重新统计 → 履约率提升
- [x] 指标体系覆盖订单域、履约域、服务域、陪诊员域、健康协同域（补登缺失且已有可算口径的部分）
- [x] 所有核心统计指标明确「指标名称 / 统计范围 / 统计时间 / 数据来源 / 计算公式」
- [x] 不出现「家属端一个口径 / 陪诊员端一个口径 / 管理员端另一个口径」

### 6.2 本版追加（tickets §十一 收口清单）

- [x] 缺口分析：桶边界正确、同一人不重复计数、空桶为 0
- [x] 效果对比：两侧同口径、区间非法 → `9002`、未注册指标 → `400`
- [x] 指标字典补登完成，字典 ↔ VO 双向校验全绿

### 7.2 后续版本必须继承的机制

| 机制 | 落点 | 解决什么问题 |
|---|---|---|
| 指标字典（机器面 + 人读面） | 指标字典文件 + 人读面文档 | 「同一指标在不同角色端只有一个口径」 |
| 人读面 ↔ 机器面一致性校验 | 校验脚本 | 人读面与机器面漂移 |
| 端点↔指标机器面 | 机器面文件 + 契约测试 | 「某个端点返回的口径没人登记过」 |
| 指标计算器注册表 | 注册表 | 同一指标跨端各写一遍公式 |
| 共享统计区间 | 共享区间实现 | 各端口径不一致 |

> 后面每加一个统计端点，都要**同时**在机器面与指标字典里登记，
> 漏了哪一边，测试立刻变红 —— 这正是本版要留下的东西。

### 7.3 后续版本的承接点

| 承接方 | 要接住什么 |
|---|---|
| 后续任何统计端点 | 新增端点必须**同时**在指标字典与端点↔指标机器面里登记，**漏哪一边测试立刻变红** |
| 后续版本 | 本版的核心产出是**机制，不是页面** —— 缺口表与效果对比只是机制的第一个使用者 |

### 7.4 已知限制（如实披露，不静默）

| 项 | 说明 |
|---|---|
| `companionsWithoutSlots` 目前为 30 | 存量陪诊员的可服务时段是自由文本，解析不出来的那部分**不进任何桶**；响应里如实披露这个数 |
| 缺口**可为负** | 供给多于待接量时 `gap < 0`，**不截断成 0** |
| 改派率的分子分母**时间字段不同源** | 分子按操作日志时间、分母按下单时间；已写进字典公式，不是藏着 |
| 区间陪诊员数与活跃陪诊员数**同值** | 两者公式逐字相同，共用同一计算器（别名）。这是**语义重复的登记**，已在字典里写明；后续应收敛为只留一条 |
| 跨端共用的计算器**没有陪诊员维度** | 陪诊员端完成率的字典范围是「当前陪诊员」，而效果对比端点是**管理端视角**，只能给平台口径值；已在字典范围里写明 |
| 机器面目前只覆盖**统计类端点** | 业务 CRUD 端点返回的字段不是统计指标，不进这张表 —— 边界是「这个字段是不是一个**有口径的统计量**」 |
